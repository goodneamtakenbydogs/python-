## 2. 类型系统的分类维度

给一门语言贴上“静态”“动态”“强”或“弱”的标签之前，必须先问这些词在回答什么问题。

至少要分开以下维度：

| 维度 | 主要问题 | 常见描述 |
|---|---|---|
| 类型检查时机 | 类型错误主要在运行前还是运行时发现 | 静态 / 动态 |
| 隐式转换宽松程度 | 不同类型是否会被大量自动转换 | 相对强 / 相对弱 |
| 类型表达方式 | 是否必须显式写出类型 | 显式声明 / 类型推断 |
| 类型约束覆盖程度 | 是否允许逐步加入或绕过检查 | 静态 / 渐进式 / `any` 等逃生口 |
| 执行方式 | 源码、字节码或机器码怎样执行 | 编译 / 解释 / JIT |

这些维度可以组合。例如：

- Python 通常被描述为动态类型、较强类型。
- Java 通常被描述为静态类型、较强类型。
- JavaScript 是动态类型，并具有大量隐式转换。
- TypeScript 在 JavaScript 上增加渐进式静态检查，但运行时仍执行 JavaScript。

因此，下面的说法都不准确：

```text
动态类型一定是弱类型
静态类型一定要手写所有类型
编译型语言一定是静态类型
解释型语言一定是动态类型
```

## 3. 静态类型：运行前基本确定类型

静态类型语言通常在程序运行前，通过编译器或类型检查器确定变量、表达式和函数接口的类型关系。

Java 示例：

```java
int count = 10;
// count = "ten";  // 编译检查失败
```

编译器已经把 `count` 约束为 `int`。把字符串赋给它，不必等程序真正运行到这一行，检查阶段就可以拒绝。

静态类型的典型收益包括：

- 很多类型错误能在运行前发现。
- 编辑器更容易提供补全和重构。
- 函数接口可以表达更明确的类型约束。
- 编译器可能利用类型信息优化代码。

典型代价包括：

- 类型设计和泛型有时增加代码复杂度。
- 灵活数据的建模可能需要联合类型、接口或额外转换。
- 能通过类型检查不等于业务逻辑正确。

静态类型检查只能证明类型系统覆盖范围内的一些性质。数组越界、错误业务条件、网络失败等问题仍可能在运行时发生。

---

## 4. 动态类型：运行时根据当前对象决定行为

动态类型语言通常不要求名字预先永久绑定某一种类型：

```python
value = 10
value = "ten"
```

运行到操作位置时，解释器根据当前对象的类型决定操作是否合法：

```python
def combine(left, right):
    return left + right


combine(1, 2)        # 3
combine("a", "b")  # "ab"
# combine(1, "b")   # TypeError
```

动态类型的典型收益包括：

- 代码可以快速表达不同对象遵循的共同行为。
- 原型开发和数据处理通常较直接。
- 不需要为每个局部名字提前写出类型。

典型代价包括：

- 某些错误只有执行到特定路径才暴露。
- 大型项目需要测试、类型标注和工具补充约束。
- 阅读函数时，可能需要更多上下文才能确定对象能力。

动态类型不等于没有类型。对象仍然有明确类型，类型规则也仍然存在；只是许多检查发生在运行时。

---

## 5. 类型推断不等于动态类型

很多静态类型语言允许省略显式类型名称：

### 5.1 Rust

```rust
let mut value = 10;
// value = "ten";  // 类型已经推断为整数，检查失败
```

### 5.2 Go

```go
value := 10
// value = "ten" // 编译失败
```

### 5.3 C++

```cpp
auto value = 10;
// value = "ten";  // value 已被推断为整数
```

### 5.4 Java

```java
var value = 10;
// value = "ten";  // value 仍是静态整数类型
```

这些写法都没有在左侧手写具体类型，但编译器会根据初始表达式推断并固定类型关系。因此判断静态或动态不能只看源码中有没有 `int`、`str` 等名称。Rust 还允许使用新的 `let` 重新建立同名绑定，这叫遮蔽；它不是把原绑定的静态类型在运行中改掉。

```text
类型推断：由工具帮你算出静态类型
动态类型：运行时根据当前对象决定类型行为
```

## 6. 强类型与弱类型的分类标准

“静态/动态”虽然也有复杂边界，但基本问题比较明确。“强类型/弱类型”没有一套被所有教材和研究者统一采用的严格定义。

人们通常用它讨论：

- 不同类型之间是否大量隐式转换。
- 不兼容操作是否直接报错。
- 是否容易通过指针、强制转换或通用逃生口绕过约束。
- 类型错误是否容易变成其他含义继续执行。

因此更稳妥的说法是：

```text
这门语言在某类操作上转换严格或宽松
```

而不是宣称：

```text
这门语言在任何意义下都是绝对强类型或绝对弱类型
```

Python 通常被称为强类型，因为它不会把字符串和整数任意混合：

```python
# "10" + 5  # TypeError
```

JavaScript 的转换更加宽松：

```javascript
1 + "2"   // "12"
"5" - 2   // 3
```

但 Python 也允许 `int + float`，Java 也允许字符串拼接时转换其他值。这些语言仍可整体归为较强类型，因为相关转换有明确、受限的规则。强弱是整体倾向，不应由一个例子决定。

## 7. 常见语言的类型系统对比

下面是面试语境中的常见分类，不是不可争议的数学定理：

| 语言 | 静态/动态 | 强弱倾向 | 典型体现 |
|---|---|---|---|
| Python | 动态 | 较强 | 名字可重新绑定；不兼容操作通常抛出 `TypeError` |
| Ruby | 动态 | 较强 | 运行时类型；数字和字符串通常不随意混算 |
| JavaScript | 动态 | 转换宽松 | `+`、宽松相等和布尔环境包含大量强制转换 |
| PHP | 动态 | 相对宽松 | 数字字符串和宽松比较等场景存在自动转换 |
| Java | 静态 | 较强 | 编译期检查、受限的数值扩大转换 |
| C# | 静态为主 | 较强 | 默认静态检查，提供显式 `dynamic` 逃生口 |
| Go | 静态 | 较强 | 类型推断仍静态，数值转换通常要求显式写出 |
| Rust | 静态 | 很严格 | 类型、所有权和数值转换都受到严格检查 |
| Kotlin | 静态 | 较强 | 类型推断、空安全和编译期检查 |
| Swift | 静态 | 较强 | 类型推断、可选类型和显式转换 |
| Haskell | 静态 | 很严格 | 强类型推断，表达式在运行前具有确定类型 |
| C | 静态 | 相对宽松 | 隐式数值转换、指针和强制转换较多 |
| C++ | 静态 | 分类有争议 | 静态检查较强，但隐式转换、指针和多种转换可绕过约束 |
| TypeScript | 渐进式静态检查 | 编译期较强，运行时继承 JS | 类型被擦除后运行 JavaScript |

面试中若对方追问“C++ 到底算强还是弱”，不要执着于争一个唯一标签。直接说明它是静态类型，但允许较多隐式转换、底层指针操作和显式类型转换，因此强弱分类取决于采用的定义。

## 8. Python 为什么是动态且较强

同一段代码可以分别体现两个维度：

```python
value = 10
value = "hello"  # 动态：名字可以改为指向另一类型对象

# value + 5       # 较强：不兼容类型不会被任意拼接或转换
```

Python 允许明确支持的混合操作：

```python
1 + 2.5   # 3.5，数值类型之间有明确兼容规则
"ha" * 3 # "hahaha"，字符串明确定义了重复操作
```

准确表达不是“Python 完全不做隐式转换”，而是：

> Python 的类型规则相对严格，不兼容类型通常不会被随意转换；类型明确支持的组合仍可正常工作。

---

## 9. Java 的静态类型检查与运行时检查

Java 变量和表达式受到编译期类型约束：

```java
int count = 10;
// count = "ten"; // 编译失败
```

但 Java 仍然存在运行时行为，例如向下转型失败、数组越界和空引用访问。静态类型系统并不能在编译期证明所有运行错误都不存在。

Java 还允许受限的数值扩大转换：

```java
int count = 10;
double result = count + 2.5;
```

并允许字符串拼接：

```java
String message = "count=" + 10;
```

这些是语言明确规定的操作，不足以据此把 Java 简单归为弱类型。

另一个常见混淆是“动态分派”。Java 可以在运行时根据对象实际类型选择重写方法，但这不等于 Java 是动态类型语言。方法分派时机和类型检查时机是不同问题。

## 10. JavaScript 的隐式类型转换

JavaScript 是动态类型语言，变量可以重新绑定：

```javascript
let value = 10;
value = "hello";
```

它还定义了大量隐式强制转换。结果不是随机的，而是由具体运算符的规则决定。问题在于规则稳定，却未必符合人的第一直觉。

```javascript
typeof (1 + "2")  // "string"
typeof ("5" - 2)  // "number"
```

同一个输入类型组合遇到不同运算符，可能走入不同转换路径。因此 JavaScript 工程通常强调显式转换和严格相等。

---

## 11. JavaScript 的 `+`：数值加法与字符串拼接

JavaScript 的二元 `+` 同时负责：

1. 数值加法。
2. 字符串拼接。

可以先使用下面的简化流程：

```text
两个操作数先转成原始值
→ 如果其中一个是字符串，双方转成字符串并拼接
→ 否则双方进入数值运算
```

所以：

```javascript
1 + "2"        // "12"
"score=" + 10 // "score=10"
1 + 2          // 3
```

结果类型可以用 `typeof` 验证：

```javascript
typeof (1 + "2") // "string"
typeof (1 + 2)   // "number"
```

更完整的规范还涉及对象转原始值、`Number` 与 `BigInt`，但理解普通面试题时先掌握上面的分支已经足够。

---

## 12. JavaScript 的 `-`、`*`、`/`：数值转换

这些运算符没有字符串拼接含义，普通情况下会要求数值操作数：

```javascript
"5" - 2 // 3
"5" * 2 // 10
"6" / 2 // 3
```

简化过程：

```text
"5" - 2
→ "5" 转为数字 5
→ 5 - 2
→ 数字 3
```

如果字符串不能转换成有效数字：

```javascript
"hello" - 2 // NaN
```

`NaN` 表示这次数值计算没有得到有效数字，但它仍属于 JavaScript 的 `number` 类型：

```javascript
typeof NaN // "number"
```

这看起来奇怪，是因为 `NaN` 是数字类型中的特殊值，不是一个独立的类型名称。

## 13. JavaScript 连续 `+` 为什么顺序重要

运算按结合和求值顺序逐步产生中间结果：

```javascript
1 + 2 + "3"
```

过程：

```text
1 + 2
→ 数字 3

3 + "3"
→ 字符串 "33"
```

而：

```javascript
"1" + 2 + 3
```

过程：

```text
"1" + 2
→ 字符串 "12"

"12" + 3
→ 字符串 "123"
```

因此不能只数最终有哪些操作数，还要追踪每一步中间值的类型。

## 14. JavaScript 的 `==` 与 `===`

### 14.1 宽松相等 `==`

`==` 会在一些类型组合之间执行转换：

```javascript
0 == false       // true
"" == false      // true
null == undefined // true
```

这些结果来自 JavaScript 的抽象相等规则，不是简单把双方都转成布尔值。完整规则分支较多，业务代码不应靠猜测。

### 14.2 严格相等 `===`

`===` 不进行上述跨类型相等转换：

```javascript
0 === false // false
"5" === 5  // false
```

现代 JavaScript 项目通常默认使用 `===` 和 `!==`。

### 14.3 严格相等对 `NaN` 与 `-0` 的处理

```javascript
NaN === NaN // false
0 === -0    // true
```

需要区分这些特殊数值时，可以了解 `Object.is()`：

```javascript
Object.is(NaN, NaN) // true
Object.is(0, -0)    // false
```

这不表示普通代码都要改用 `Object.is()`。大多数相等判断仍优先使用 `===`，特殊数值语义再按需求选择。

## 15. 怎样减少 JavaScript 隐式转换问题

### 15.1 显式转换

```javascript
const total = Number("5") + 2;
const message = String(5) + " items";
```

### 15.2 模板字符串

```javascript
const count = 5;
const message = `count=${count}`;
```

### 15.3 严格相等

```javascript
if (value === 0) {
    // 明确要求数字零
}
```

### 15.4 TypeScript、ESLint 与输入校验

- TypeScript 提供编译期类型检查。
- ESLint 可以禁止高风险写法。
- 单元测试覆盖边界输入。
- 接口层显式解析字符串、数字和布尔值。

TypeScript 只能提前发现一部分问题，不能改变外部数据和最终 JavaScript 运行时的真实类型，因此运行时输入校验仍然需要。

## 16. TypeScript 为什么叫渐进式静态类型

TypeScript 在 JavaScript 语法上增加类型检查：

```typescript
let value: number = 10;
// value = "ten"; // 类型检查失败
```

但它允许在已有 JavaScript 项目中逐步增加类型，并提供 `any`、类型断言等逃生口：

```typescript
let value: any = 10;
value = "ten";
```

编译后，许多类型信息会被移除：

```text
TypeScript 源码
→ 编译期类型检查
→ 生成 JavaScript
→ JavaScript 运行时执行
```

因此：

- TypeScript 的类型检查主要发生在开发和编译阶段。
- 运行时收到的 JSON、表单或网络数据仍需验证。
- 使用 `any` 过多会显著削弱检查效果。
- 类型断言是告诉检查器“相信我”，不等于自动转换数据。

TypeScript 常被称为渐进式、结构化的静态类型系统。本章只需要掌握“编译期护栏，运行时仍是 JavaScript”这一核心。

## 17. C 与 C++ 的类型检查与转换规则

### 17.1 C

C 是静态类型语言，但允许较多隐式转换和底层操作：

```c
int value = 3.9;
// value 通常得到 3，编译器可能给出警告
```

指针转换和直接内存操作还能绕过许多高级语言中的类型保护。因此有人把 C 称为相对弱类型，也有人认为“静态且有明确转换规则”不应简单归入弱类型。

### 17.2 C++

C++ 有强大的静态类型系统、模板和重载，同时也继承底层指针能力，并提供多种显式转换和用户自定义转换。

所以面试中更稳妥的说法是：

> C++ 是静态类型语言；强弱分类取决于定义，它的静态约束较强，但也提供较多隐式转换和绕过机制。

这比只回答“C++ 是强类型”或“C++ 是弱类型”更能体现你知道分类边界。

## 18. Go 与 Rust 的显式数值转换

### 18.1 Go

```go
var count int = 10
var ratio float64 = 2.5

// result := count + ratio
result := float64(count) + ratio
```

Go 的 `:=` 是类型推断，变量仍具有静态类型。不同数值类型通常要求显式转换。

### 18.2 Rust

```rust
let left: i32 = 10;
let right: f64 = 2.5;

// let result = left + right;
let result = left as f64 + right;
```

Rust 不仅严格检查类型，还把所有权、借用和生命周期纳入编译分析。很多在其他语言中可能成为运行时内存错误的问题，会提前被拒绝。

严格并不自动表示开发效率低，动态也不自动表示代码质量差。选择取决于项目规模、运行环境、性能目标、团队经验和工具生态。

## 19. 代码执行方式与类型检查时机

“编译或解释”讨论代码怎样执行；“静态或动态类型”讨论类型何时确定和检查。

例如：

- Java 是静态类型，通常编译为 JVM 字节码，再由虚拟机执行或即时编译。
- Python 是动态类型，CPython 也会先把源码编译为字节码。
- JavaScript 是动态类型，现代引擎经常使用 JIT 即时编译优化热点代码。
- TypeScript 进行静态类型检查，随后生成 JavaScript。

因此“有编译步骤”不能证明语言是静态类型，“由解释器执行”也不能证明语言是动态类型。

## 20. 动态分派、类型注解与显式转换

### 20.1 动态分派不等于动态类型

Java 等静态类型语言可以在运行时根据对象实际类型选择重写方法，这叫动态分派或运行时多态。它不改变表达式已经接受静态类型检查的事实。

### 20.2 类型注解不等于运行时强制

Python 注解：

```python
def add(left: int, right: int) -> int:
    return left + right
```

普通 Python 不会只因为注解就阻止：

```python
add("a", "b") # "ab"
```

静态检查工具可以报告不符合约定的调用，但运行时是否验证取决于程序或框架是否额外实现。

### 20.3 显式转换不等于改变原对象

```python
text = "10"
number = int(text)
```

这通常创建或取得一个整数对象，并让 `number` 指向它；不是把原字符串对象原地变成整数。

## 21. 不可变性、可哈希性与字典键的条件

### 21.1 字典键真正要求的是可哈希

容易记住但不够准确的说法是：

```text
不可变对象才能作为字典键
```

准确规则是：

```text
可哈希对象才能作为字典键或集合元素
```

一个对象要稳定参与哈希容器，至少需要满足：

1. 可以取得哈希值。
2. 对象作为键期间，哈希值保持稳定。
3. 如果两个对象满足 `left == right`，它们必须满足 `hash(left) == hash(right)`。

反方向不成立。两个对象哈希值相同，只表示发生了哈希冲突，不代表它们一定相等。

“不可变”是判断内置对象能否稳定哈希的重要线索，但不是“可哈希”的同义词。

### 21.2 元组不可变，到底是什么不能变

观察：

```python
record = ("task", [80, 90])
```

元组保存的是两个对象引用：

```text
元组第 0 个位置 ──→ 字符串对象 "task"
元组第 1 个位置 ──→ 列表对象 [80, 90]
```

元组不可变，表示元组自身的位置不能被替换、增加或删除。因此下面不允许：

```python
record[1] = [100]
# TypeError
```

但是可以通过元组保存的引用找到列表，再修改列表对象：

```python
record[1].append(100)
print(record)  # ('task', [80, 90, 100])
```

状态变化是：

```text
修改前：record[1] ──→ 列表对象 [80, 90]

修改后：record[1] ──→ 同一个列表对象 [80, 90, 100]
```

元组第 1 个位置仍然保存原来的列表引用，变化发生在列表内部。因此“元组不可变”不等于“它引用的所有对象都不可变”。

### 21.3 含列表的元组不能作为字典键

下面的想法不能绕过字典键限制：

```python
record = ("task", [80, 90])

# mapping = {record: "value"}
# TypeError: unhashable type: 'list'
```

也可以直接观察：

```python
# hash(record)
# TypeError: unhashable type: 'list'
```

元组的哈希需要结合内部元素的哈希值。字符串 `"task"` 可以哈希，但列表 `[80, 90]` 不可哈希，所以整个元组也不可哈希。

对比：

```python
hash(("task", (80, 90)))  # 可以
# hash(("task", [80, 90]))  # TypeError
```

第一个外层元组只包含可哈希元素，通常可以作为键：

```python
record = ("task", (80, 90))
mapping = {record: "value"}

print(mapping[record])  # value
```

所以“元组不可变”不能直接推出“任何元组都可哈希”。必须继续检查它包含的每个元素。

### 21.4 为什么不能让键的哈希依据随意变化

字典查找可以先用下面的简化过程理解：

```text
键
→ 计算哈希值
→ 根据哈希值缩小候选位置
→ 使用相等性协议确认真正的键
```

假设一个键插入时按旧内容得到位置 A，修改后又按新内容得到位置 B：

```text
插入时：hash(旧状态) → 候选位置 A
修改后：hash(新状态) → 候选位置 B
```

数据仍存放在原来的位置附近，但新查询却从另一处开始，字典可能无法可靠找到它。普通 `list`、`dict` 和 `set` 都会原地改变内容，因此 Python 直接让这些内置类型不可哈希。

列表也不能在保留现有内容相等规则的同时简单改用对象身份哈希。两个不同列表可能满足 `[1, 2] == [1, 2]`，但它们的对象身份不同；若身份哈希也不同，就违反了“相等对象必须具有相同哈希值”的约束。

这也解释了为什么只说“字典键不能改”仍然不够准确。真正必须保持稳定的是参与哈希和相等判断的语义。

### 21.5 常见内置对象能否作为键

| 对象 | 通常是否可哈希 | 说明 |
|---|---|---|
| `int` | 是 | 数值不可变 |
| `str` | 是 | 字符串不可变 |
| `None` | 是 | 单例且可哈希 |
| 只含可哈希元素的 `tuple` | 是 | 例如 `(1, "A")` |
| 含列表的 `tuple` | 否 | 内部列表不可哈希 |
| `list` | 否 | 内容可以原地改变 |
| `dict` | 否 | 条目可以原地改变 |
| `set` | 否 | 元素集合可以原地改变 |
| `frozenset` | 通常是 | 自身不可变，元素必须可哈希 |

不要把这张表扩展成“所有不可变对象必定可哈希”。自定义类型是否可哈希，还取决于它怎样定义相等与哈希行为。

### 21.6 能不能设计属性可变但仍可哈希的对象

可以，但不是通过“把列表藏进元组”实现。

某些自定义对象即使有可变属性，仍然可以按照对象身份进行相等与哈希。只要修改的属性不改变该对象作为键时的哈希和相等语义，它仍可能稳定作为键。

反过来，如果自定义对象的哈希值依赖某个可变属性，放入字典后又修改该属性，就可能破坏查找。Python 无法替所有自定义类判断业务上哪些属性将来会变化，因此设计者必须维护规则。

这部分与以下特殊方法有关：

- `__eq__()`：定义对象在什么条件下相等。
- `__hash__()`：提供对象的哈希值。

它们的完整实现、默认行为以及为什么重写 `__eq__()` 会影响可哈希性，将在第 6 章学习。

### 21.7 如果键所表达的内容需要改变

对于由不可变数据组成的键，通常创建新键，再移动对应值：

```python
old_key = ("task", (80, 90))
mapping = {old_key: "value"}

new_key = ("task", (80, 90, 100))
mapping[new_key] = mapping.pop(old_key)
```

过程是：

```text
删除旧键
→ 创建具有新内容的新键
→ 把原值关联到新键
```

这没有修改原元组键，而是明确改变字典中的键关系。

### 21.8 可哈希条件与元组内部可变对象总结

```text
不可变对象才能作为字典键？
不准确。可哈希对象才能作为字典键。

元组不可变，是里面的引用不能变？
对。元组的位置不能改为指向其他对象，但被引用的可变对象仍可改变。

含列表的元组能否作为键，再修改列表实现“可变键”？
不能。包含列表的元组整体不可哈希，插入字典时就会报错。
```

第 2 章会从哈希表查找角度继续解释可哈希对象；第 6 章会完整解释 `__eq__()` 与 `__hash__()` 的设计约束。

## 22. 面试中怎样回答类型系统问题

### 22.1 回答 Python 为什么是动态强类型

```text
先说这是两个维度
→ 动态：名字可在运行时绑定不同类型对象，许多检查在运行时发生
→ 较强：不兼容类型通常不被任意隐式转换
→ 分别给一段代码
→ 补充强弱分类不是绝对标准
```

### 22.2 回答某门语言是强还是弱

不要只报标签。可以说：

> 按隐式转换和绕过类型规则的常见定义，这门语言相对严格或宽松。例如……。不过强弱没有完全统一的分类标准。

随后给具体操作，而不是继续争论词语。

### 22.3 回答 JavaScript 转换题

```text
先确定当前运算符
→ 跟踪每个操作数当前类型
→ 应用该运算符的转换规则
→ 得到中间值
→ 再继续后面的运算
→ 最后用 typeof 说明结果类型
```

例如：

```javascript
1 + 2 + "3"
```

先得到数字 `3`，再与字符串拼接，最终是字符串 `"33"`。

## 23. 本专题总结

1. 静态/动态与强/弱是不同维度，不是二选一。
2. 静态类型主要在运行前确定和检查类型，动态类型主要在运行时根据对象决定行为。
3. 类型推断只是省略显式声明，不等于动态类型。
4. 强弱类型没有统一绝对边界，应结合隐式转换和绕过规则的具体行为说明。
5. Python 通常被描述为动态且较强；对象有类型，名字可以重新绑定。
6. JavaScript 的隐式转换由运算符规则决定，不是随机行为。
7. JavaScript 的 `+` 同时承担数值加法与字符串拼接，`-`、`*`、`/` 通常走数值转换。
8. `===` 避免宽松相等中的跨类型转换，但仍需了解 `NaN` 和 `-0` 等边界。
9. TypeScript 提供渐进式编译期检查，最终运行时仍遵循 JavaScript 规则。
10. 编译/解释、静态/动态、类型推断和动态分派分别是不同问题。
11. 字典键要求可哈希，不是只要求表面上不可变；含列表的元组整体不可哈希。
12. 元组不可变表示它保存的引用位置不能更换，不代表被引用的可变对象不能改变。

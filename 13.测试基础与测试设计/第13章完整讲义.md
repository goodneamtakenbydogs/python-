# 第 13 章完整讲义：测试基础与测试设计

第 11 章已经会用断言和测试框架检查行为，第 12 章已经会处理文件、数据和外部表示。本章继续回答：应该测哪些条件，预期结果怎样确定，有限时间先测什么，以及结果能够支持多大的结论。

案例全部为通用需求和虚构数据。Python 代码以当前 **CPython 3.12.13** 为验证基线，使用兼容 Python 3.11 及以上的标准语法，不连接真实系统。代码用来观察测试选择和断言的效果；测试理由、需求解释和风险判断还需要人工复述与评审。

## 1. 测试的目的与证据范围

**软件测试**通过评审、分析和执行等活动，发现问题、评价行为与约定是否一致，并提供质量和风险信息。运行一项测试只是其中一种活动。

例如“导出零条记录时也生成含表头的文件”是一项明确约定。只测过十条记录，最多说明那组条件下观察到的结果，不直接说明零条、错误数据、依赖失败或重复执行都正确。

测试可以暴露某种失败，没有发现失败不等于证明所有输入都没有缺陷。有效结论应同时带上范围：哪个版本、哪些条件、检查了什么、哪些还没检查。测试数量多也不自动等于选择有代表性。

## 2. 人的错误、程序缺陷与运行失败

**人的错误**指理解、设计或实现中的失误；**缺陷**是需求、代码或其他产物中的问题；**失败**是运行时表现与应满足的要求不一致。它们有关联，但不是一一对应。

开发者把包含上界写成不包含上界，是一个可能来源；错误比较条件是代码缺陷；恰好输入上界时被拒绝是失败表现。其他输入可能不触发该缺陷，所以缺陷存在与本次失败是不同事实。

Python 异常也不总代表测试失败。接口要求非法输入抛 ValueError，收到该异常可能正是正确行为。反之，没有异常也可能返回错误结果或破坏状态。测试代码、环境和需求描述自身同样可能有问题，不能看到红色结果就直接归责被测代码。

## 3. 测试与需求、开发和修复的关系

测试设计可以从阅读需求开始，而不是等程序完成。通过检查输入范围、状态和失败规则，常能在写代码之前发现歧义。

**静态测试**在不执行目标程序的情况下评审或分析产物，例如检查需求中的单位；**动态测试**实际执行程序并观察结果。它们按是否执行目标分类，不是按工具是否高级分类。

一次小修改可以经历：明确约定、评审测试点、开发与测试、执行并记录、定位失败、修复后确认及回归。实际工作可能多次循环，流程不是保证质量的固定仪式。重要的是每次改变后，相关约定和证据能继续对应。

## 4. 测试层次、目标与观察方式

先说明分类维度，才能避免把不同属性当成互斥类别。

| 维度 | 常见说法 | 关注什么 |
|---|---|---|
| 对象与集成边界 | 单元、集成、系统、端到端 | 验证哪个部分与哪些协作者 |
| 质量目标 | 功能、性能、可靠性等 | 希望评价哪种性质 |
| 设计或观察依据 | 黑盒、白盒 | 主要依据外部约定还是内部结构 |
| 执行目的或时机 | 冒烟、确认修复、回归等 | 本轮为什么选择这些检查 |

单元测试聚焦较小逻辑，集成测试验证组件协作，系统测试面向规定的系统整体；端到端强调从业务入口到最终结果的完整链路，可能跨越系统边界。不能只按调用了几个函数分类。

**黑盒**主要根据输入输出和外部规则设计，**白盒**利用代码分支、数据路径等内部信息。一个测试可以同时是集成、功能、回归测试，并使用黑盒方法选择输入。这些维度并不互相排斥。

## 5. 冒烟、确认修复、回归与探索

**冒烟测试**用较小的高价值集合检查当前版本是否具备继续测试的基本条件，例如能否启动、读取有效配置并生成最小结果。范围由产品和风险决定，不存在所有工程通用的一组必选动作。

**确认修复测试**重新验证原失败是否得到修复；**回归测试**检查修改是否破坏原本应正常工作的行为。二者可能复用用例，但目的不同。修复空输入问题后，只重跑原空输入不足以检查非空输入是否被新修改破坏。

**探索式测试**把学习、设计与执行结合，通过有目标的观察不断调整下一步。可以用限时任务说明目标、数据和记录方式；它也需要证据与复盘，不等于随意点击。稳定、重复、高频的规则适合自动化，尚不清楚的使用体验和新风险仍需要人的观察。

## 6. 不同测试层次的成本与反馈

**测试金字塔**是一种讨论测试组合的模型：较小边界的测试通常更快、定位更直接，完整链路通常更依赖环境、数据与维护。它帮助权衡反馈与真实程度，不规定任何项目必须使用固定百分比。

例如单独检查 CSV 字段转换可以快速覆盖许多边界；实际文件读写验证编码和接口协作；完整命令执行再验证入口与退出状态。只保留最外层测试，失败可能很难定位；全部用替身，又可能遗漏真实集成问题。

选择层次应看风险在哪里发生。第 14 章负责把这些检查组织为可运行工程，本章先说明每一层希望得到哪项证据。

## 7. 从需求中提取输入、规则与状态

拿到一句需求，先拆出输入、输出、前置条件、业务规则、可观察状态和限制。**前置条件**是操作开始前应成立的状态，例如已有可导出的记录；它不同于“执行到一半再顺便创建”的步骤。

假设教学需求是：“接收整数数量，允许 1～5，返回是否可提交；拒绝不应改变已有记录。”可以拆成：

| 项目 | 当前约定 |
|---|---|
| 输入 | 精确整数，布尔值不作为数量 |
| 范围 | 1 与 5 都包含 |
| 成功结果 | 可提交关系成立 |
| 拒绝结果 | 明确拒绝，已有记录保持 |
| 还需确认 | 拒绝是返回状态还是抛异常，具体接口需补充 |

不要因为已经能写判断式，就自行决定未说明的异常、默认值或副作用。缺少约定本身可以成为评审问题；后续代码实验会给出各题自己的完整接口。

## 8. 需求歧义与可测试的表述

“数量不能太大”“操作应该很快”“失败后状态正常”都需要进一步澄清。可测试表述要说明单位、边界、观察位置、时间条件和失败规则。

例如长度是字符数、UTF-8 字节数还是记录数？上限是否包含？空文本、None 和零是否不同？“五秒内可查询”从提交开始还是从任务启动开始？第 12 章的编码和时间口径会直接影响预期。

尚未确认时，把问题、临时假设及其影响单独记录。不要把临时假设默默写成测试答案，再根据它报告实现有缺陷。测试与实现也可能共同误解同一条需求。

## 9. 测试点、场景、用例与步骤

**测试点**是希望验证的一项性质；**测试场景**提供相关业务背景或过程；**测试用例**明确条件、输入、操作与预期；**步骤**把操作展开为可执行顺序。各团队文档粒度可能不同，但这些责任要清楚。

```text
测试点：不允许超出数量上界。
场景：已有记录未变，尝试提交超过限制的数量。
用例：在指定版本与干净状态下输入 6，预期拒绝且记录保持。
步骤：准备状态 → 提交 → 检查拒绝结果 → 核对状态 → 清理本次数据。
```

“测试数量”不是完整用例，“点击提交”也不是完整预期。步骤不必机械详细到每一次键盘动作，但应足以让另一位读者建立相同条件并观察同一性质。

## 10. 预期结果的来源

用来判断实际结果是否正确的依据常称为**测试判定依据**，也会看到 oracle 这一术语。来源可以是已确认需求、独立业务规则、可信参考或数据不变量。

**不变量**是在指定操作范围必须保持的性质。例如拒绝非法数量后原记录不变，或转移操作前后总数保持。它能补充具体值断言，但前提仍需明确；并非任意程序都应满足同一种守恒关系。

```python
def wrong_total(price, quantity):
    return price + quantity

actual = wrong_total(10, 3)
copied_expectation = 10 + 3
independent_expectation = 30  # 来自每件 10、三件合计的明确规则
print(actual == copied_expectation)  # True
print(actual == independent_expectation)  # False
```

复制实现求预期，可能让两者一致地错。参考实现也需要可信来源和适用边界。对难以直接求值的问题，可以验证输入重排后结果关系等性质，但必须先证明该关系属于需求，不能凭直觉套用。

## 11. 接口成功与业务正确

一个操作返回 accepted=True，最多说明它报告接收成功，不能直接证明最终数据正确。需要区分执行层结果、业务结果和持久或可查询状态。

```python
response = {"accepted": True, "written": 0}
expected_rows = 2
print(response["accepted"])  # True
print(response["written"] == expected_rows)  # False
```

本例只是内存记录，不要求学习网络协议。若约定是异步接收，立即写入零条也未必是缺陷，应按约定等待最终状态。关键是确认当前接口到底承诺了哪一层结果，不能使用一个成功标志代替全部业务断言。

## 12. 测试用例记录与需求关联

一条可复查用例通常记录编号、目标规则、前置状态、输入、步骤、预期结果、数据清理和实际执行证据。版本与环境条件应足以解释差异，公开教学使用虚构标识与数据。

**可追溯性**表示需求、测试、执行结果与缺陷之间的关联。例如规则 R-1 对应哪些用例，其中哪些已运行，哪些因环境阻塞还未完成。建立关联有助于发现缺口，但“已关联”本身不代表断言正确或测试已通过。

用例设计表与执行记录有不同生命周期。设计说明为什么这样测，执行记录说明某个版本在某次条件下发生了什么；不要把尚未执行的用例预先填写为通过。

## 13. 等价类与代表性输入

**等价类划分**按某项规则把预计会得到相同类别处理的输入分组，再选代表值。等价是针对当前测试目标与假设，不是说同组所有输入已被证明永远表现相同。

对整数范围 1～5，可先区分小于 1、在区间内、大于 5。类型不符、格式错误、缺失值等通常还需要独立考虑，不能把全部无效输入只留一个例子。

```python
def classify(value):
    if type(value) is not int:
        return "invalid type"
    if value < 1:
        return "below"
    if value > 5:
        return "above"
    return "inside"

print([classify(value) for value in [0, 3, 6, True, None]])
# ['below', 'inside', 'above', 'invalid type', 'invalid type']
```

bool 是 int 子类，但本例需求选择精确整数，因此显式拒绝。分组先由需求确定，代码只是观察模型；不能先看实现分了几支，就认定需求只需要这些类。

## 14. 离散边界与连续数值

**边界值分析**优先检查规则变化附近的数据。对步长为 1 的整数闭区间，可检查下界前一项、下界、下界后一项，以及上界附近对应位置；重合时按目标去重。

```python
lower, upper = 1, 5
candidates = sorted({lower - 1, lower, lower + 1, upper - 1, upper, upper + 1})
print(candidates)  # [0, 1, 2, 4, 5, 6]
print([lower <= value <= upper for value in candidates])
# [False, True, True, True, True, False]
```

这些点能针对常见的 < 与 <=、上下界或偏移错误。若上下界相等，某些“内侧相邻值”会落到区间外，预期仍按实际规则判断，不能因名字叫内侧就硬写通过。

对金额、时间或连续数值，所谓相邻值取决于精度与单位，不是所有边界都机械加减 1。字符串长度还需明确按字符、字节或其他单位。边界测试也不代替类型、格式和状态场景。

## 15. 单项无效输入与规则优先级

当一个输入同时违反多个规则，程序可能先报告其中一项，掩盖另一项。为了定位，每项无效条件通常应在其他必要条件有效时单独测试，再补有业务意义的交互。

例如未获得权限且数量超限，只看到权限拒绝不能证明数量检查正确。应分别验证有权限的超限输入、数量有效的无权限输入，再确认两个问题同时存在时接口约定的错误优先级。

这不是要求所有失败都只能测一个条件。批量错误汇总、优先级和组合约束本身也是需求；选择应有理由，而不是把“最复杂输入”当作自动覆盖全部规则。

## 16. 判定表与多条件规则

**判定表**把条件组合与预期动作对应起来，适合权限、配置选择等多条件规则。先明确条件含义、是否独立和哪些组合可发生，再列出动作。

假设报告读取规则为：身份验证有效，并且是报告所有者或拥有管理权限，才允许读取。三个输入均为布尔值；即使会话失效，仍可能知道原账号的所有者关系，因此本教学模型允许全部八种组合。

| 身份有效 | 所有者 | 管理权限 | 允许读取 |
|---|---|---|---|
| 否 | 否 | 否 | 否 |
| 否 | 否 | 是 | 否 |
| 否 | 是 | 否 | 否 |
| 否 | 是 | 是 | 否 |
| 是 | 否 | 否 | 否 |
| 是 | 否 | 是 | 是 |
| 是 | 是 | 否 | 是 |
| 是 | 是 | 是 | 是 |

```python
from itertools import product

rows = []
for authenticated, owner, admin in product([False, True], repeat=3):
    expected = authenticated and (owner or admin)
    rows.append((authenticated, owner, admin, expected))
print(sum(row[3] for row in rows), len(rows))  # 3 8
```

这里的表达式是对已声明需求的示范实现。设计时先核对判定表，再决定如何编码预期，避免与被测代码共享同一错误帮助函数。

## 17. 条件无关项与判定表简化

身份无效时，另外两个条件不影响结果，可以把四行合成一条含“无关项”的规则。无关表示在当前动作判定中不影响结果，不表示那个输入永远无意义或一定不可发生。

合并后要能解释覆盖哪些原始组合；如果不同组合还有不同审计记录或错误优先级，可能不能合并。也不能把两个动作不同的组合误合成一条。

测试 owner=True、admin=True、authenticated=True 一组时，错误实现只检查 owner 也会通过。增加只有管理权限的合法场景，才有机会暴露该遗漏。这称为条件间的**掩盖**：一个条件的值让另一个条件错误暂时不显现。

## 18. 状态、事件与合法迁移

**状态**是当前保存的可观察阶段，**事件**是要求某项变化的输入，**状态迁移**描述在指定状态收到事件后怎样变化。只检查最终字符串，可能漏掉非法动作和中间状态。

教学任务的状态为 draft、queued、running、done、failed、cancelled，分别表示草稿、排队、运行、成功结束、失败结束和取消。合法迁移只有：

| 当前状态 | 事件 | 下一状态 |
|---|---|---|
| draft | submit | queued |
| queued | start | running |
| queued | cancel | cancelled |
| running | finish | done |
| running | fail | failed |
| running | cancel | cancelled |

其余动作拒绝且保持状态。done、failed、cancelled 是本模型的终止状态，不再接受上述动作。这是明确的教学约定，不代表所有任务系统都采用同样流程。

```python
transitions = {("draft", "submit"): "queued", ("queued", "start"): "running"}
state = "draft"
trace = [state]
for event in ["submit", "start"]:
    state = transitions[(state, event)]
    trace.append(state)
print(trace)  # ['draft', 'queued', 'running']
```

代码只展示两步合法过程；完整测试还要检查表中其他迁移与表外拒绝。

## 19. 状态覆盖、迁移覆盖与序列

**状态覆盖**关注有没有到达各状态，**迁移覆盖**关注有没有执行规定的边；二者分母不同。多条路径到达同一终止状态时，状态都见过仍可能漏掉其中一条迁移。

例如经过排队取消已经到达 cancelled，但运行中取消仍未测试。迁移覆盖也不自动覆盖所有长序列：先失败再重试、重复提交和连续取消可能产生不同上下文，需按真实规则补充。

测试系统通常应通过合法前缀到达目标状态，而不是无依据直接修改内部属性。纯模型练习可以允许指定初始状态，但要在题面说明。拒绝后的状态和资源是否保持，也应有断言，不只检查有没有异常。

## 20. 组合测试与两两覆盖

多个选项全部组合的数量可能快速增长。**两两组合覆盖**要求每一对因素的可行取值组合至少出现一次，可减少部分组合数量，但不保证发现三项或更多条件同时触发的问题。

```python
from itertools import combinations, product

selected = [(False, False, False), (False, True, True),
            (True, False, True), (True, True, False)]
pairs = set()
for row in selected:
    for left, right in combinations(range(3), 2):
        pairs.add((left, row[left], right, row[right]))
print(len(pairs))  # 12，三对因素各有四种组合
print((True, True, True) in selected)  # False
print(len(selected), len(list(product([False, True], repeat=3))))  # 4 8
```

四组输入覆盖了两两关系，仍漏掉全真三项组合。如果已知风险要求某个三项组合，就必须明确补充。组合强度根据风险、历史缺陷和约束选择，不是机械追求最少用例。

## 21. 组合约束与不可达输入

真实选项可能有依赖，例如某两种模式不能同时启用。应先定义可行集合，再计算需要覆盖的关系，不能用不可行组合虚增目标或覆盖。

如果 A=True 与 B=True 不允许，A、B 这一对只有三种可行关系，其他因素对可能仍有四种。也要区分“配置明确禁止但要验证拒绝”和“系统不可能产生”：前者可以是负向用例，不能因它不可作为正常配置就完全忽略。

组合工具可以辅助列数据，不能替代需求分析。约束写错时，工具可能非常完整地覆盖了错误模型。

## 22. 依赖失败与异常路径设计

**失败注入**是在受控边界让依赖返回错误或抛出异常，观察被测逻辑的失败处理。第 11 章的替身可用来控制读取、保存、时间或外部调用，不需要真实系统恰好故障。

至少区分失败发生在动作之前、部分状态已经变化之后，以及动作完成但响应尚未送达之后。它们可能需要不同预期。输入不合法通常要求拒绝，依赖暂时不可用可能要求报告或有限重试，不能所有错误都自动吞掉。

```python
state = {"limit": 1, "timeout": 2}
before = state.copy()
try:
    state["limit"] = 3
    if -1 <= 0:
        raise ValueError("invalid timeout")
    state["timeout"] = -1
except ValueError:
    pass
print(state == before)  # False
```

若需求要求更新被拒绝时保持原配置，本例失败处理有缺口。异常确实发生并被捕获，仍不代表状态正确。修复方案要按实际事务和所有权设计，本章先训练如何提出并验证约束。

## 23. 权限、资源与数据一致性

权限测试要说明主体、对象、允许动作与拒绝后的状态，而不只给一个角色名字。主体可以是虚构账号，对象可以是虚构报告；“能读取自己的报告”不自动覆盖“不能读取别人的报告”。

资源或数据检查同样要有观察点。例如成功提交是否只创建一条记录，拒绝后原列表是否保持，清理是否仅删除本次数据。数据一致性是指定关系满足约定，不意味着每次都必须查询某种数据库。

在 Python 小模型中可以检查字典、队列或文件内容。真实系统中则按明确接口选择证据；替身测试通过不证明外部系统本身符合这些规则。

## 24. 并发场景与受控交错

第 10 章已经讲过共享状态与调度。本章的设计目标是明确参与者、共同资源、允许结果和必须保持的不变量，再安排可能暴露错误的交错。

```python
stock = 1
old_a = stock
old_b = stock
stock = old_a - 1
successes = 1
stock = old_b - 1
successes += 1
print(stock, successes)  # 0 2
print(stock == 1 - successes)  # False
```

这是两名参与者都先读取旧库存的顺序模型，没有启动线程。库存没有显示负数，却接受了两个成功操作，所以只检查“库存非负”会漏掉业务错误。真实并发测试可用事件或屏障复现，不依赖固定休眠碰运气。

## 25. 超时、部分成功与重试

超时通常表示在指定预算内没有取得结果，不表示远端动作一定没有发生。重复执行可能造成重复记录，测试要观察操作标识、已提交状态和接口的幂等约定。

```python
records = []

def create_then_timeout(request_id):
    records.append(request_id)
    raise TimeoutError("response not received")

for _ in range(2):
    try:
        create_then_timeout("REQ-A")
    except TimeoutError:
        pass
print(records)  # ['REQ-A', 'REQ-A']
```

这只是教学替身，说明“请求报错”与“没有副作用”不是同一个事实。测试还应区分同一标识重试、不同标识的新操作、失败后清理，以及结果未知时如何保留证据。重试次数和总预算要明确，具体脚本实现放在第 15 章。

## 26. 异步结果与有界观察

异步任务可能先接收后完成，不同读取视图也可能延后观察到更新。**最终一致性**强调在没有后续更新等前提下，状态按约定最终收敛；它不是所有异步任务的别名。测试应明确初始响应、最终条件、允许时间和失败证据，不是收到响应就直接断言最终完成。

```python
states = iter(["pending", "pending", "ready"])
observed = []
for _ in range(3):
    current = next(states)
    observed.append(current)
    if current == "ready":
        break
print(observed)  # ['pending', 'pending', 'ready']
```

这里用有限序列代替时间，不做真实休眠。实际轮询需要总预算和间隔，条件未满足时应报告最后状态与证据；某次未观察到也不能扩大成“它永远不会完成”。固定 sleep 后不检查状态，既可能太短也可能浪费时间。

## 27. 数据代表性、隔离与清理

测试数据应能代表目标规则，且执行条件可恢复。空、零、缺失、重复、长度、编码或顺序的含义都要按接口确定，不把“随机生成很多条”当作覆盖依据。

使用独立工厂、临时目录和可控依赖减少污染。重复编号、共享嵌套容器、遗留文件和全局缓存，都可能让用例单独通过、整组失败。清理要明确本次拥有的数据，失败时仍能保留必要证据。

固定随机种子只控制相应发生器的数据序列，不控制线程调度和远端状态。公开资料的输入、日志与缺陷示例使用虚构内容，不能把真实身份和内部环境当作练习素材。

## 28. 风险与有限时间下的选择

**风险**可以理解为某种不利情况发生的可能性及影响。测试优先级还会考虑变化范围、使用频率、历史缺陷、依赖关系、时间和当前不确定性。

可以用影响与可能性等级辅助排序，但等级相乘只是约定的评分模型，不是经过验证的精确失败概率。强制覆盖的关键规则也不能因执行时间长，就被一个简单的分数除以耗时排到永远不测。

例如先确认工具能启动与读取合法输入，再检查本次修改影响的核心边界；其余范围按风险安排，并记录未覆盖原因。时间不足时需要明确缩减范围及剩余风险，不能把删掉失败用例当作风险已经消失。

## 29. 需求覆盖、执行范围与结果状态

覆盖率需要先说明分母。设计用例关联了所有需求，与这些用例已经执行、通过不是同一口径。需求本身若缺失或表述不全，关联率高也不能证明没有漏掉业务风险。

用例结果可以区分通过、失败、阻塞、跳过和未执行。**阻塞**表示因缺少前置条件等无法完成本次检查；**跳过**表示按明确条件不执行；它们不应默认计入通过。

```python
requirements = {"R-1", "R-2", "R-3"}
cases = [("R-1", "passed"), ("R-2", "blocked"), ("R-3", "not run")]
designed = {requirement for requirement, _ in cases}
passed = {requirement for requirement, result in cases if result == "passed"}
print(designed == requirements)  # True
print(passed == requirements)  # False
```

失败原因、阻塞条件和未覆盖规则应可查询。报告“通过率 100%”时还需说明多少项实际执行、是否排除了失败或跳过、检查的版本和数据是什么。

## 30. 语句、分支与业务覆盖

**语句覆盖**关注目标范围内哪些可执行语句运行过，**分支覆盖**关注控制流的哪些方向运行过。具体统计应说明工具、目标代码和排除规则，不能随意把教学标签数当作工具测量。

```python
def discounted_total(total):
    amount = total
    if total > 100:
        amount = total - 10
    return amount

# 需求其实要求“满 100 减 10”，实现故意写错包含关系。
assert discounted_total(120) == 110
assert discounted_total(80) == 80
print(discounted_total(100))  # 100，需求预期应为 90
```

120 能运行函数内所有这些可执行语句；再加 80 还能走到条件两个方向，但边界 100 仍没有被正确验证。因此高语句或分支覆盖率不代替输入选择、需求覆盖和正确断言。

真实工具对分支、短路、异常和不可达代码的统计可能有具体规则。覆盖信息适合寻找没走过的区域与补充问题，不能直接转换成产品正确率。

## 31. 断言质量与测试自身缺陷

断言 actual == actual、只检查结果为真、捕获任意异常都算通过，都可能让错误实现通过。测试也需要评审和验证。

```python
def broken(value):
    return value + 1

actual = broken(3)
print(actual == actual)  # True
print(actual == 3)  # False，接口约定应原样返回输入
```

先确认预期有独立来源，再检查测试确实执行了目标、断言了相关状态。为异常设计“没有抛错也会失败”的出口，避免空 try/except 测试悄悄正常结束。第 11 章的框架断言能力在这里服务于明确规则。

## 32. 用典型错误检验用例区分能力

**变异测试**通过对实现做受控小改动，观察现有测试能否暴露差异。本章用少量故意错误的候选函数训练这一思路，不要求搭建变异工具。

正确实现必须先通过；随后检查把 <= 写成 <、漏掉权限条件、丢失字段或改变结果类型等典型错误是否被拒绝。若测试对正确实现也总报错，不能把“所有错误都拒绝了”当作好测试。

有些变异在目标输入范围内等价，有些差异并不属于需求，不能把所有存活者简单算成缺陷。发现测试放过典型错误，应回到输入、预期和断言范围找原因，而不是为了杀死某个候选硬编码函数名字。

## 33. 缺陷报告中的可复现信息

一份缺陷报告应让读者知道如何复现、为什么不符合约定、实际发生了什么。通常包括简明标题、版本与必要环境、前置数据、最小步骤、预期、实际结果、频率和证据。

假设虚构工具 `sample-export` 的公开教学版本 0.1 规定零条也保留表头。清楚的报告可以写成：

```text
标题：零条记录导出时缺少规定表头
前置：虚构版本 0.1，输入为空集合，输出模式为 CSV
步骤：准备空输入 → 执行导出 → 打开输出检查表头
预期：成功生成含 case_id,status 表头、无数据行的 CSV
实际：输出为空文本，表头不存在
复现：同一条件下连续两次出现
证据：最小输入、执行结果、输出内容与对应需求编号
```

这是教学示例，不是实际项目记录。避免“偶尔不对，请优化”这类缺少依据的描述，也不要直接把未经确认的根因当作标题。公开材料不使用真实内部日志、账号或路径。

## 34. 严重程度与处理优先级

**严重程度**主要描述缺陷影响，**处理优先级**描述当前应多快处理。字段命名与等级按团队约定，不存在所有组织通用的 P1、S1 含义。

例如静默丢失大量数据可能影响严重；某个可读性问题影响较小，但若立即影响规定交付，也可能需要较快处理。优先级还考虑范围、频率、替代办法、时间和关联风险，不能只凭截图大小判断。

测试可以提供影响与复现证据，并提出建议；最终排序通常涉及相应责任人共同决策。本章的示意评分不代替真实决策权限。

## 35. 失败定位、确认修复与回归范围

发现失败后先保存必要证据，再区分被测实现、测试代码、数据、环境或需求解释的问题。不要先无条件重试到通过，覆盖掉第一次失败现场。

最小复现要保留触发条件，移除无关步骤。修复后先确认原失败，再按变化影响补回归；如果新用例在错误版本上也通过，就需要检查它是否真正针对原问题。

运行次数和复现频率要说明样本与条件。一次没复现不等于缺陷不存在，重复运行也不自动给出独立统计样本。并发或外部依赖问题可用可控模型缩小，再回到相应层次验证。

## 36. 测试结果、剩余风险与建议

结果报告应说明范围、版本、执行状态、关键发现、阻塞与未测项，以及证据能够支持的结论。**剩余风险**是当前验证之后仍存在或尚未充分评价的风险，不只是已知缺陷列表。

例如本轮验证了本地解析与输出，真实远程依赖尚未接入，就只能给出该范围的结论。不能把替身场景通过写成端到端已经可靠，也不能把未执行项默认为低风险。

是否发布属于相应决策流程；测试提供证据和建议。公开学习资料中练习的是表达依据、限制和后续检查，不虚构真实项目经历与交付结果。

## 37. 自动化选择与人工观察

重复、规则稳定、输入可控、预期明确且结果可观察的场景，通常更适合自动化。编写与维护成本、环境准备、失败定位和实际反馈价值都需要计算。

探索新需求、评价使用体验、判断文案是否造成误解等，往往还需要人工观察。自动化也可以辅助生成数据、收集证据，人工测试同样可以使用工具，二者不是按有没有脚本绝对分开。

把未明确的需求立即自动化，可能只是固定了一个未经确认的假设。先让一个小用例有清楚约定并能独立复现，再逐步组织成第 14 章的工程。

## 38. 综合案例：小型报告导出的测试设计

假设一个纯 Python 教学工具接收记录集合和输出模式，约定最多三条；允许空集合；支持 JSON、CSV；只有获得授权才导出；输入或输出失败时保留已有报告。所有数据都在临时目录或内存中。

先拆出规则：数量范围与类型、格式选择、授权关系、输出内容、旧文件保护和失败证据。再从规则选择用例，而不是先写一串工具调用。

数量至少考虑空、普通、上界、上界外；格式检查具体结构与字段；无授权时确认拒绝且旧报告保持；依赖注入可模拟写入失败。多条件时先建立优先级或判定关系，部分成功与重复执行则按接口约定补充。

预计 JSON 的 records 数量、CSV 的表头与逻辑行来自需求，而不取当前实现输出作为答案。类型和编码由第 11、12 章提供基础；本章的产出是有理由的测试方案。具体框架组织、脚本和工具组合分别在第 14～16 章展开。

## 39. 设计评审与完成判断

完成一份用例集合后，逐项检查目标规则、预期来源、代表性输入、必要状态、失败证据和清理责任。再问：哪些遗漏最可能影响结论，哪些假设仍未确认，哪些用例只是重复同一种性质？

检查器可以核对有限判定表、边界点、模型轨迹和测试区分能力，不能自动证明理由正确、需求完整或风险评价合理。综合方案、缺陷报告和结论应人工复述；没有实际经历时，就按明确的虚构案例练习，不编造项目故事。

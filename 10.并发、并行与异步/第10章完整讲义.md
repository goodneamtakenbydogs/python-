# 第 10 章完整讲义：并发、并行与异步

前九章主要跟踪一条执行路径：名字怎样绑定对象、函数怎样调用、异常怎样传播、资源何时释放。本章增加一个问题：多个任务的执行时间重叠时，谁可以继续运行，谁正在等待，谁能修改同一份数据？

本章以 **CPython 3.12.13 的常规 GIL 构建**为实验基线，核心代码使用 Python 3.11 及以上语法。GIL 即全局解释器锁，用来协调解释器内部的线程执行，第 6 节会展开它的限制。自由线程构建、启动进程的默认方式和新版本接口会单独说明。讲义中标为 `python` 的代码块都是完整脚本；异步示例中的 `asyncio.run(...)` 用于普通 `.py` 脚本。Jupyter 已有事件循环，Notebook 使用单元格顶层的 `await`，具体见第 25 节。

## 1. 批量任务为什么需要并发

假设一个测试工具要读取三份报告。每份报告都要先等待磁盘或远端返回，再做少量计算。如果工具等待第一份时完全不处理其他报告，很多时间会花在等待上。

**任务**是这里要完成的一份工作，不一定对应操作系统中的某个对象。“检查一个接口”“解析一份报告”都可以是一项任务。**调度**是决定哪个执行单元此刻获得运行机会。理解并发的第一步，是区分任务所需的计算和等待：

```text
顺序处理：A 计算 → A 等待 → A 完成 → B 计算 → B 等待 → B 完成
重叠处理：A 等待期间，让 B 或 C 取得进展
```

这里的图只表示时间关系，不保证具体耗时。并发能利用一些等待时间，但需要增加调度、通信和资源管理成本。任务很短、资源已经饱和，或顺序本身有业务要求时，顺序执行可能更合适。

## 2. 并发与并行的区别

**并发**强调多个任务在一段重叠时间内取得进展。任务可以轮流执行，并不要求同一个瞬间都在计算。

**并行**强调同一个瞬间有多个执行单元实际运行。例如两个 CPU 核心分别执行一项计算。CPU 是执行指令的处理器，核心是其中能够承担指令执行的单元；这里不展开硬件内部结构。

```text
单个执行单元上的并发：A 一段 → B 一段 → A 一段 → B 一段
多个执行单元上的并行：核心 1：A A A A
                       核心 2：B B B B
```

“同时发起多项工作”不能单独证明它们在多个核心上并行计算。测试工具同时等待多个响应属于并发，之后是否并行解析数据，要看线程、进程、解释器和实际计算实现。

## 3. 同步、异步、阻塞与非阻塞的分类维度

这两组术语从不同角度描述操作，不能简单排成四种互斥方案。

| 维度 | 术语 | 关注的问题 |
|---|---|---|
| 调用与结果的关系 | 同步 / 异步 | 当前调用流程是否直接等到结果，还是提交后通过稍后的等待、回调等取得结果 |
| 当前执行单元能否继续 | 阻塞 / 非阻塞 | 条件不满足时，当前线程是否停在那里等待，还是立即得到“尚未就绪”等结果 |

例如普通阻塞读取会让当前线程等数据；把它交给线程池后，提交方可以先做别的事，但工作线程里的读取仍然是阻塞的。异步代码使用 `await` 等待一个尚未完成的异步操作时，可以暂停当前协程，让事件循环运行其他任务；这不意味着那个协程已经拿到结果。

**回调**沿用第 4 章的含义：把函数交给其他代码，在约定时刻由接收方调用。异步接口也可能通过回调通知结果，不是所有异步接口都使用 `async` 语法。

“同步”还常用于“线程同步”，表示协调访问或执行时机。这个用法与“同步函数调用”语境不同，看到术语时要先确定讨论维度。

## 4. 进程、线程与协程分别是什么

**进程**是操作系统管理的一份运行中程序环境。普通进程有自己的地址空间，也就是它能访问的内存范围和映射。同一文件被两个 Python 进程加载，会分别产生各自的普通模块状态。

**线程**是进程内由操作系统调度的执行单元。同一进程中的线程通常共享普通 Python 对象，但各有执行位置和调用现场。一个线程的局部名字不会自动变成另一个线程的局部名字；若形参或属性指向同一可变对象，对象仍会共享。

**协程**是能够暂停、以后从暂停处继续执行的程序单元。本章使用 `async def` 定义的原生协程。**事件循环**是组织异步任务、观察操作何时就绪并安排继续执行的运行机制。同一个事件循环通常在一个线程中运行；当前协程没有让出执行机会时，其他普通任务不能在该线程中抢占它。

| 方面 | 进程 | 线程 | 本章的 asyncio 协程任务 |
|---|---|---|---|
| 普通内存 | 默认隔离 | 同进程共享 | 同一进程内仍可共享对象 |
| 主要调度者 | 操作系统 | 操作系统 | 事件循环，协作式执行 |
| 常见成本 | 启动、传输和独立运行环境 | 线程创建、切换和锁 | 任务对象、等待状态和循环调度 |
| 常见用途 | 常规 GIL 构建中的纯 Python 并行计算 | 阻塞式 I/O 并发 | 使用异步接口的大量等待任务 |

进程也能使用线程和事件循环。这三种机制不是程序只能三选一的标签；先学单一模型，再考虑组合，才能说清资源责任。

## 5. CPU 密集型与 I/O 密集型任务

**CPU 密集型**表示主要时间花在计算，例如用 Python 循环比较大量数据。**I/O 密集型**表示主要时间花在输入输出等待，例如网络、文件或数据库访问。输入输出通常缩写为 I/O。

这描述实际瓶颈，而不是文件扩展名。下载后解压和解析的大任务，可能前半段等网络，后半段耗 CPU。某个数值库虽然由 Python 调用，主要计算却可能在释放 GIL 的本地扩展中完成。

选择方案前，先用有代表性的数据观察计算、等待、内存和外部资源。不能因为函数叫 `fetch` 就认定一定适合协程，也不能因为使用线程就断言一定提速。代码性能测量在第 11 章学习，系统负载和容量评估在第 16 章学习。

## 6. CPython 的 GIL 与自由线程构建

### 6.1 常规构建中的 GIL

**GIL** 是 Global Interpreter Lock，即全局解释器锁。在本章常规 CPython 构建中，一个解释器里的线程需要取得 GIL 才能执行 Python 字节码等受其保护的解释器操作。因此，多个线程通常不能同时在多个核心上执行这个解释器里的纯 Python 字节码。

第 1 章讲过字节码是解释器执行的中间指令。GIL 服务于解释器内部运行和对象管理，不是针对每个业务记录建立的锁。

许多阻塞 I/O 操作会在等待期间释放 GIL，一些本地扩展也会在计算时释放它，所以线程仍可能让 I/O 任务重叠，并让部分扩展计算并行。不能从 GIL 推出“Python 线程任何时候都不可能并行”。

### 6.2 GIL 不保证业务状态正确

“检查余额，再扣款”包含多个步骤。即使某个瞬间只有一个线程执行字节码，线程也可能在这几个步骤之间换人。GIL 不会把整项业务操作自动变成不可分割事务，第 9 节会给出确定可复现的例子。

Python 语言没有规定必须存在 GIL。CPython 从 3.13 起提供可选的**自由线程构建**，可以在禁用 GIL 的状态下运行线程；它不等于所有新版本 Python 默认都没有 GIL。某些不兼容扩展还可能使 GIL 重新启用。诊断时应核对解释器、构建和运行状态，不只看版本号。

自由线程构建对部分内置对象提供内部保护，也不能代替跨多个操作的业务同步。本章不依赖 `list.append` 或 `dict` 单次操作的某种实现原子性来实现线程安全。**原子性**指在讨论的观察范围内，一个操作不会被看成只做了一半；它总要说明针对什么操作和观察者。

## 7. 使用 `threading.Thread` 启动和等待线程

先观察“交出函数对象”和“调用函数”的区别：

```python
from queue import Queue
from threading import Thread

results = Queue()

def work(number):
    results.put(number * 2)

thread = Thread(target=work, args=(6,))
thread.start()
thread.join()
print(results.get())  # 12
```

`target=work` 交出函数对象；`args=(6,)` 交出位置实参元组。创建 `Thread` 对象还没有运行 `work`，`start()` 才安排新线程执行它；同一个线程对象不能反复 `start()`。若写成 `target=work(6)`，函数会在当前线程中先执行，交出去的是返回结果。

`join()` 等待目标线程结束，不会启动它，也不会返回工作函数的返回值。这里用线程安全的 `Queue` 传结果，后面会完整解释。`join(timeout=...)` 等待超时后也返回 `None`，应再看 `is_alive()`，不能根据返回值认定工作已结束。

普通线程里未捕获的异常不会因为主线程调用 `join()` 就在主线程重新抛出。需要取得返回值和异常时，优先考虑第 17 节的线程池。**守护线程**是不会单独阻止解释器退出的线程；退出时可能突然停止，不能用它负责必须完成的数据写入和资源清理。

## 8. 线程中的局部名字与共享对象

```python
from threading import Thread

records = []

def work(items):
    items.append("written")
    items = ["local only"]

thread = Thread(target=work, args=(records,))
thread.start()
thread.join()
print(records)  # ['written']
```

工作线程的局部形参 `items` 最初与调用处的 `records` 指向同一列表。`append()` 修改共享列表；下一行只重新绑定工作函数的局部名字 `items`。主线程等待结束后看到共享对象的修改，却不会跟着局部名字改指新列表。

本例只有工作线程修改列表，主线程在 `join()` 后读取。它用于解释引用关系，不是证明多个线程随意修改任意容器都安全。第 9 章的浅拷贝也不会自动隔离嵌套列表，给线程分发数据前必须确定共享边界。

## 9. 用屏障复现读取后写回的竞态

**竞态条件**表示结果依赖多个执行单元的交错时机，某种允许的交错会破坏正确性。下面的 `Barrier(2)` 是**屏障**：两个参与者都到达后才继续；`timeout=5` 是失败保护，不是控制正常调度的休眠。

```python
from threading import Barrier, Thread

state = {"count": 0}
both_read = Barrier(2, timeout=5)

def increase():
    old = state["count"]
    both_read.wait()
    state["count"] = old + 1

threads = [Thread(target=increase) for _ in range(2)]
for thread in threads:
    thread.start()
for thread in threads:
    thread.join()
print(state["count"])  # 1
```

两名参与者都先读到 `0`。屏障之后，各自把共享字典中的值写成 `1`，而不是共同累加到 `2`。这称为**丢失更新**。变化的是字典条目的绑定，各自的局部 `old` 仍是先前读到的整数。

```text
线程 A：读取 0 ── 等待屏障 ── 写回 1
线程 B：读取 0 ── 等待屏障 ── 写回 1
```

这个实验主动安排了错误交错，不要求操作系统碰巧在某行切换。没有屏障的 `count += 1` 在某次运行中恰好正确，也不能证明它是跨解释器、跨版本的同步方案。

## 10. `Lock` 保护整个临界区

**临界区**是必须协调访问的那段共享状态操作。**互斥锁**让同一时刻只有一个持有者进入约定的区域。先把读取、计算和写回一起保护：

```python
from threading import Lock, Thread

state = {"count": 0}
lock = Lock()

def increase():
    for _ in range(100):
        with lock:
            state["count"] = state["count"] + 1

threads = [Thread(target=increase) for _ in range(2)]
for thread in threads:
    thread.start()
for thread in threads:
    thread.join()
print(state["count"])  # 200
```

`with lock` 进入时取得锁，正常或异常退出时释放。其他访问者也必须使用同一把锁保护同一项约束；只锁住写回、读取时不用锁，仍可能使用过期的旧值。若业务要求两个账户总额不变，保护范围就应包含相关检查和转移，而不只是某一次赋值。

锁保护范围越大，等待和串行部分通常越多；范围过小又可能破坏约束。不要持有锁等待一个还需要这把锁才能完成的任务，也尽量避免锁内进行长时间网络等待。**线程安全**是接口在约定并发使用方式下仍满足正确行为，不等于“某个底层操作不会破坏解释器”。

## 11. `RLock` 与同一线程的重复加锁

普通 `Lock` 不提供同一线程重复进入的能力。`RLock` 是**可重入锁**：持有线程能再次取得它，每次成功取得都需要对应释放。

```python
from threading import Lock, RLock

plain = Lock()
with plain:
    print(plain.acquire(blocking=False))  # False

reentrant = RLock()
with reentrant:
    again = reentrant.acquire(blocking=False)
    print(again)  # True
    if again:
        reentrant.release()
```

`blocking=False` 表示拿不到就立即返回，不在这里永久等待。同一个对象的方法互相调用，而且都需要同一把锁时，可能需要 `RLock`，也可以重构为“外层持锁、内部方法明确要求已持锁”。

`RLock` 不让两个线程同时进来，也不能解决两把不同锁的顺序冲突。它解决的是同一线程嵌套取得同一把锁的问题。

## 12. 死锁的常见形成方式

**死锁**表示参与者互相等待对方持有的资源，谁也不能继续释放自己持有的资源。例如：

```text
线程 A 已持有账户锁，等待报告锁。
线程 B 已持有报告锁，等待账户锁。
两者都不肯在取得第二把锁之前释放第一把锁。
```

这段是等待关系示意，不能作为可运行实验。其他常见原因包括普通锁的重复进入、持锁调用 `join()` 等待依赖该锁的线程，以及单工作线程的线程池任务等待同池里尚未运行的任务。

常见处理是统一锁顺序、缩短持锁范围、避免持锁等待外部工作，以及在无法取得资源时释放已有资源并报告。超时能帮助发现卡住，却不会自动恢复被破坏的业务状态。`RLock` 只处理其中一种原因。

## 13. `Event` 表达状态通知和协作停止

`threading.Event` 保存一个可设置、可清除的标志。`set()` 使标志为真并唤醒等待者；`wait()` 等标志为真；`clear()` 重新清除。它不是记录每一次通知数量的队列。

```python
from queue import Queue
from threading import Event, Thread

stop = Event()
ready = Event()
results = Queue()

def work():
    ready.set()
    stop.wait()
    results.put("cleaned")

thread = Thread(target=work)
thread.start()
try:
    if not ready.wait(timeout=5):
        raise RuntimeError("工作线程没有就绪")
finally:
    stop.set()
    thread.join()
print(results.get())  # cleaned
```

真实循环可以定期检查停止标志，并使用带超时的外部操作，避免永远卡在无法观察标志的调用里。Python 不提供通用安全的强制终止线程接口。停止请求、任务已经结束、资源已经释放是三个需要分别确认的状态。

## 14. `Semaphore` 限制同时使用资源的数量

**信号量**维护可用名额。取得一个名额后数量减少，释放后增加，没名额时可以等待。比如只有三个可用测试账号时，同时占用账号的工作应不超过三个。

```python
from threading import BoundedSemaphore

slots = BoundedSemaphore(2)
print(slots.acquire(blocking=False))  # True
print(slots.acquire(blocking=False))  # True
print(slots.acquire(blocking=False))  # False
slots.release()
slots.release()
try:
    slots.release()
except ValueError:
    print("释放次数超过最初名额")
```

`BoundedSemaphore` 额外检测可用数量是否超过初始上限，帮助发现多释放的问题。正常使用优先写 `with slots:`，让释放跟随作用范围。

信号量限制的是进入受保护区域的数量，不是每秒请求数。三个名额在请求很快时仍可能每秒发送很多次请求。**限流**约束单位时间的速率，需要另外设计；也不能因为有名额就让多个工作者共用同一份可变账号状态。

## 15. `Condition` 在锁保护下等待共享条件

有时需要等待“缓冲区非空”，而不是只等待一个独立标志。**条件变量** `Condition` 把锁和等待通知组织在一起。检查条件时要持锁，等待时会暂时释放关联锁，被唤醒后重新取得锁再检查。

```python
from queue import Queue
from threading import Condition, Thread

condition = Condition()
buffer = []
results = Queue()

def consume():
    with condition:
        available = condition.wait_for(lambda: bool(buffer), timeout=5)
        if available:
            results.put(buffer.pop())
        else:
            results.put("no data")

thread = Thread(target=consume)
thread.start()
with condition:
    buffer.append("report")
    condition.notify()
thread.join()
print(results.get())  # report
```

`lambda: bool(buffer)` 是返回当前条件的函数，`wait_for()` 会重新检查它。生产者即使先放入数据，消费者之后也能通过条件判断继续，不依赖一定先收到一次通知。

`notify()` 不会立即释放锁，等生产者退出 `with` 后消费者才有机会取得它。手写 `wait()` 时应放在条件循环中，不能把“被唤醒”当作“条件一定成立”：其他消费者可能先拿走数据，等待也必须遵守接口的重新检查规则。

## 16. `queue.Queue` 与生产者、消费者

**生产者**产生待处理项，**消费者**取得并处理它们。线程安全的 `queue.Queue` 已封装必要协调；`maxsize` 限制队列中等待项的数量。队列满时生产者等待，称为**背压**：下游处理不过来时，限制上游继续堆积。

```python
from queue import Queue
from threading import Thread

jobs = Queue(maxsize=2)
results = Queue()
stop = object()

def consume():
    while True:
        item = jobs.get()
        try:
            if item is stop:
                return
            results.put(item * item)
        finally:
            jobs.task_done()

thread = Thread(target=consume)
thread.start()
for number in [2, 3]:
    jobs.put(number)
jobs.put(stop)
jobs.join()
thread.join()
print(sorted([results.get(), results.get()]))  # [4, 9]
```

`get()` 取出项，不等于该项处理完成；`task_done()` 表示完成一次已取出的项；`join()` 等待所有已入队项都收到对应完成通知，不会收集结果，也不等于所有业务均成功。这里把专用对象作为**结束标记**，普通数据不会与它相同；每个消费者都需要自己的结束机会。

本例的处理不会抛出业务异常。实际消费者必须把失败保存为结果或按策略继续；若线程意外退出而队列还有未处理项，`jobs.join()` 可能一直等待。`empty()`、`full()` 和 `qsize()` 都不能作为“检查后一定还能取或放”的承诺，直接调用带超时的操作并处理对应结果更可靠。

## 17. 线程池与 `concurrent.futures.Future`

每份小工作都新建线程，会重复付出创建和回收成本。**线程池**维护一组工作线程，复用它们执行提交的工作。标准库 `concurrent.futures` 提供统一的提交、结果和异常接口。

**Future** 是代表某项工作未来完成状态的对象，不是工作函数的结果本身。下面观察提交、取结果和异常：

```python
from concurrent.futures import ThreadPoolExecutor

def convert(text):
    return int(text)

with ThreadPoolExecutor(max_workers=2) as pool:
    good = pool.submit(convert, "42")
    bad = pool.submit(convert, "invalid")
    print(good.result())  # 42
    try:
        bad.result()
    except ValueError:
        print("调用方收到工作中的异常")
```

`submit(convert, "42")` 把函数和实参交给池，返回 Future；`result()` 在调用线程等待完成，成功则返回结果，失败则在调用位置重新抛出所保存的异常。`done()` 只说明已经结束或取消，不代表成功。

`max_workers=2` 限制工作线程数，不限制累计提交数量。一次提交百万项仍可能保存百万个 Future 和输入。线程池不会自动解决任务内共享状态和第三方客户端的线程安全问题。

## 18. 输入顺序、完成顺序与结果关联

`Executor.map()` 返回的迭代结果按输入位置组织。即使后一个任务更早完成，消费方也可能在前一个位置等它。`as_completed()` 按完成情况提供 Future，适合尽早处理已完成工作；多个工作在观察前已经完成时，不应要求它们具有额外的精确先后保证。

下面用事件让 `fast` 确实先结束，不根据休眠长度猜顺序：

```python
from concurrent.futures import ThreadPoolExecutor, as_completed
from threading import Event

release = Event()

def slow():
    if not release.wait(timeout=5):
        raise TimeoutError("等待释放超时")
    return "slow"

def fast():
    return "fast"

with ThreadPoolExecutor(max_workers=2) as pool:
    first = pool.submit(slow)
    second = pool.submit(fast)
    completed = as_completed([first, second])
    try:
        print(next(completed).result())  # fast
    finally:
        release.set()
    print(next(completed).result())  # slow
```

在测试工具中，应把每个 Future 关联到用例编号或输入位置，不把“第一个收到的结果”误当“第一条用例的结果”。结果是否按输入排序，是接口约定；完成顺序只是运行过程。

## 19. Future 的超时、取消与线程池退出

`future.result(timeout=...)` 超时表示这次等待没有及时拿到结果，通常抛出内置 `TimeoutError`；工作可能还在后台运行。它不会自动杀掉线程。

`future.cancel()` 尝试取消尚未开始的工作。取消成功返回 `True`，随后取结果会抛出 `concurrent.futures.CancelledError`。工作已经运行时通常返回 `False`，需要第 13 节的协作停止。这个异常类与 `asyncio.CancelledError` 不是同一个类。

线程池的 `with` 退出默认等待工作结束，所以“在 `with` 里等结果超时并捕获”不保证整个函数马上返回。`shutdown(cancel_futures=True)` 可以取消尚未开始的排队工作，不会强行停止正在运行的工作。`wait=False` 也不能让必须继续运行的线程凭空消失，解释器退出仍涉及未结束工作。

同池工作互相等待尤其危险：只有一个工作线程时，A 占着线程等待 B，而 B 正排队等待这同一个线程，就形成执行资源上的死锁。把任务依赖放在外层组织，避免池内阻塞等待同池尚未完成的工作。

## 20. 多进程为什么需要通信和可导入的入口

多进程的普通对象默认不是共享对象。把一份列表作为输入交给新进程，不表示两边仍能通过那份普通列表互相修改。**进程间通信**通常缩写 IPC，指进程使用管道、队列等机制交换数据。

**序列化**是把对象状态变成可保存或传输的表示；**反序列化**是从这种表示重建对象。进程参数和结果常需要序列化，接收端取得的是另一个进程中的对象。第 12 章会完整比较 JSON、pickle 和文件表示；当前只需理解“跨进程传数据不是传入一个可直接共享使用的普通引用”。

使用 `spawn` 启动时，新解释器需要导入主模块以准备运行环境。进程入口放在模块顶层可导入函数中，启动动作放入 `if __name__ == "__main__":`，防止导入时又递归创建进程。这与第 8 章的导入副作用直接相连。

## 21. 使用 `spawn` 观察进程状态隔离

下面代码请保存为一份 `.py` 文件后运行。整个代码块自包含，但不能直接把工作函数留在 Notebook 单元格中再假定子进程可以导入它。`Pipe()` 创建两端通信连接，`send()` 发送，`recv()` 接收；`duplex=False` 创建单向管道。

```python
import multiprocessing as mp

def change(items, sender):
    try:
        items.append("child")
        sender.send(items)
    finally:
        sender.close()

if __name__ == "__main__":
    context = mp.get_context("spawn")
    receiver, sender = context.Pipe(duplex=False)
    original = ["parent"]
    process = context.Process(target=change, args=(original, sender))
    process.start()
    sender.close()
    try:
        if not receiver.poll(10):
            raise TimeoutError("子进程未返回结果")
        received = receiver.recv()
    finally:
        receiver.close()
        process.join(timeout=10)
        if process.is_alive():
            process.terminate()
            process.join()
        exit_code = process.exitcode
        process.close()
    print(original)  # ['parent']
    print(received)  # ['parent', 'child']
    print(exit_code)  # 0
```

父进程的列表没有被追加；子进程修改其本地列表，再把内容经管道传回。示例在错误路径终止自己创建的独立子进程，用于防止实验遗留进程。`terminate()` 是强制停止，不能承诺子进程正常执行 `finally`；实际共享锁、队列和事务可能因此损坏，应优先设计协作退出。

这里显式选择 `spawn`，不改变全局启动设置。Windows 使用 `spawn`，macOS 的现代默认方式也是 `spawn`；Python 3.14 在支持的 POSIX 平台把主要默认方式改为 `forkserver`，`fork` 不再是任何平台的默认方式。**POSIX** 是一组类 Unix 系统接口约定；`fork` 从现有进程创建子进程，`forkserver` 通过专用服务进程创建。具体补丁和运行条件还可能影响默认选择，例如 3.14.9 在没有可写临时目录时改用 `spawn`。默认方式应通过官方版本说明和 `multiprocessing.get_start_method()` 核对，不能背“Linux 永远默认 fork”。

## 22. `ProcessPoolExecutor` 与参数传输

**进程池**复用多个工作进程，适合一部分可以独立处理的 CPU 任务。下面也是完整 `.py` 脚本：

```python
import multiprocessing as mp
from concurrent.futures import ProcessPoolExecutor

def sum_squares(limit):
    return sum(number * number for number in range(limit))

if __name__ == "__main__":
    with ProcessPoolExecutor(
        max_workers=2, mp_context=mp.get_context("spawn")
    ) as pool:
        results = list(pool.map(sum_squares, [3, 4]))
    print(results)  # [5, 14]
```

这里的 `map()` 同样按输入顺序给出结果，异常要在消费结果时观察。常规进程池要求提交对象和结果能够通过相应的 pickle 机制传输；普通函数通常按模块和名字找到，而不是复制当前调用现场。模块顶层的命名函数是可靠起点，Notebook 中的局部函数、闭包和 `lambda` 通常不能作为标准进程池的可导入入口。

打开的文件、普通线程锁、数据库连接或浏览器对象不应直接当作可复制资源传给工作进程。通常传配置和必要数据，在工作进程中建立其拥有的资源，再明确关闭。

## 23. 进程队列、共享内存和管理器的取舍

`multiprocessing.Queue` 用于进程间传输对象，与线程的 `queue.Queue` 不同。普通队列项会经过序列化；把 `object()` 当作结束标记再在接收端用 `is` 判断，不能假定跨进程重建后仍有同一身份。可使用明确约定且不与数据冲突的值或消息结构。

`multiprocessing.Value`、`Array` 或共享内存可以表达特定共享数据，`Manager` 通过管理进程和代理对象提供访问。**代理**表示本地对象把操作转交给另一处执行，并不等于本地普通字典。通信、锁和生命周期都带来成本。

共享计数器的读取、加一、写回仍是组合操作。即使共享对象的单次读写有保护，也不能直接认定 `value.value += 1` 整体原子，应按该对象提供的锁保护整个更新。

还要避免父进程先等子进程结束、却一直不消费子进程正在发送的大量数据。管道缓冲区有限，发送方可能等待消费，接收方又在 `join()`，形成等待环。前面的管道例子先接收结果，再确认进程退出。

## 24. 并行计算为什么不一定更快

总成本至少包括启动、序列化、进程间传输、调度、计算、汇总和内存。把非常小的加法拆成几万个跨进程任务，通信可能比计算更贵。输入或输出非常大时，多份数据还可能放大峰值内存。

常见改进是把足够多的独立计算组成一份工作、减少跨进程数据、复用池，并测量有代表性的整体耗时。工作单元过大又会影响均衡和取消响应。主程序本来有顺序依赖的部分，也不会因为增加工作进程就自动并行。

CPython 3.14 的标准库还提供 `InterpreterPoolExecutor`，使用独立解释器执行工作；它不是本章 3.12 环境可运行的接口。初学阶段先掌握线程、进程和异步三条主线，不把某个新增 API 当作所有环境的默认方案。

## 25. `async def`、协程对象与 `await`

第 5 章的生成器能暂停并保存局部状态，原生协程也能暂停，但协议和用途不同。普通生成器不是因为用了 `yield` 就自动变成 asyncio 任务。

**协程函数**由 `async def` 定义。调用它得到**协程对象**，通常还不会执行函数体。`await expression` 等待一个**可等待对象**，得到其完成结果；可等待对象包括协程、Task 和 asyncio 的 Future。

```python
import asyncio

async def double(number):
    return number * 2

async def main():
    pending = double(6)
    print(await pending)  # 12

if __name__ == "__main__":
    asyncio.run(main())
```

执行过程是：调用 `main()` 得到协程对象，`asyncio.run()` 建立并管理事件循环，驱动主协程；主协程等待 `double` 协程，最后取得结果。普通协程对象不能在耗尽后重复等待，想再次运行应重新调用协程函数。

`asyncio.run()` 负责循环的建立和退出，不能在同一线程已有运行中的事件循环时再调用。Jupyter 通常已有循环，因此配套 Notebook 使用 `await main()`。若在脚本中直接写顶层 `await main()`，则不符合普通 Python 脚本语法。两种入口要分清，不用修改事件循环内部状态来掩盖入口错误。

## 26. `await` 不自动创建并发

先看两项工作顺序等待：

```python
import asyncio

async def work(label, events):
    events.append(label + " start")
    await asyncio.sleep(0)
    events.append(label + " end")
    return label

async def main():
    events = []
    await work("A", events)
    await work("B", events)
    print(events)  # ['A start', 'A end', 'B start', 'B end']

if __name__ == "__main__":
    asyncio.run(main())
```

`asyncio.sleep(0)` 暂停当前任务，让其他就绪工作有机会运行；这里还没有建立 B 的独立任务，所以 A 完成之后才进入 B。写了两个 `await`，不能据此称为两个任务并发运行。

此外，`await` 也不保证每次都把执行机会交给其他任务：等待的对象已完成，或被等待的协程无需实际暂停就返回时，当前任务可以继续。分析共享状态时，要确定哪里真的可能暂停，不能把每个 `await` 当作固定线程切换点。

## 27. `create_task()` 建立受调度的任务

`asyncio.Task` 包装并驱动一份协程的执行。`create_task()` 把协程安排到当前运行的循环，使它能够与其他任务交错。

```python
import asyncio

async def work(label, ready, gate):
    ready.set()
    await gate.wait()
    return label

async def main():
    gate = asyncio.Event()
    ready_a = asyncio.Event()
    ready_b = asyncio.Event()
    task_a = asyncio.create_task(work("A", ready_a, gate))
    task_b = asyncio.create_task(work("B", ready_b, gate))
    await ready_a.wait()
    await ready_b.wait()
    print(task_a.done(), task_b.done())  # False False
    gate.set()
    print(await task_a, await task_b)  # A B

if __name__ == "__main__":
    asyncio.run(main())
```

这里的 `asyncio.Event` 面向同一循环中的任务，不是 `threading.Event`。任务等待 `gate` 时暂停，循环因此能运行其他就绪任务。局部名字 `task_a`、`task_b` 保留任务引用，最后显式等待，确保结果和异常有人接收。

不要只创建后台任务就离开它的拥有范围。未接收的异常可能迟到才被报告，资源也难以确定何时清理。需要把一组任务绑定到作用范围时，使用第 29 节的 TaskGroup。默认任务调度行为也不应推广为所有自定义任务工厂的行为；本章不使用提前执行协程的特殊任务工厂。

## 28. `gather()` 的结果顺序与失败行为

`asyncio.gather()` 可把多项可等待工作组合起来；传入协程时会安排执行，成功结果按传入位置排列。

```python
import asyncio

async def work(number):
    await asyncio.sleep(0)
    return number * 10

async def main():
    results = await asyncio.gather(work(3), work(1), work(2))
    print(results)  # [30, 10, 20]

if __name__ == "__main__":
    asyncio.run(main())
```

默认情况下，某项工作抛出普通异常，`gather()` 会把首先观察到的异常传播给等待者，但不会因为这一点自动取消其他仍在运行的工作。它们可能继续产生副作用。不要把随后 `asyncio.run()` 退出时对遗留任务的清理，误当作 `gather` 本身的失败策略。

`return_exceptions=True` 把普通结果和异常对象放进对应位置，适合每项独立、需要收集全部结果的场景；调用者必须逐项区分结果和异常，不能把“列表已返回”当作全部成功。外层取消 gather 与某个成员自身被取消也有不同传播规则；有共同生命周期的一组相关任务，通常优先考虑 TaskGroup。

## 29. `TaskGroup` 管理一组任务的共同生命周期

Python 3.11 引入 `asyncio.TaskGroup`。离开任务组的作用范围前，它会等待成员结束；成员发生非取消类失败时，会取消其他成员并等待清理，随后传播相关异常。这种让子任务的生命周期服从外层结构的方式称为**结构化并发**。

下面先确保一个成员已开始等待，再由另一个成员失败：

```python
import asyncio

async def main():
    started = asyncio.Event()
    cleaned = []

    async def wait_for_work():
        try:
            started.set()
            await asyncio.Event().wait()
        finally:
            cleaned.append("released")

    async def fail():
        await started.wait()
        raise ValueError("bad case")

    try:
        async with asyncio.TaskGroup() as group:
            group.create_task(wait_for_work())
            group.create_task(fail())
    except* ValueError as errors:
        print(len(errors.exceptions))  # 1
    print(cleaned)  # ['released']

if __name__ == "__main__":
    asyncio.run(main())
```

`async with` 是异步上下文管理语法，允许进入和退出时等待，第 35 节会解释协议。**异常组** `ExceptionGroup` 能组合多个相关异常；Python 3.11 的 `except* ValueError` 按成员类型处理异常组中的匹配部分，与第 7 章处理单个异常的 `except` 不同。不能在同一个 `try` 上混写 `except` 与 `except*`。

任务组的“失败时取消”不等于撤销已成功的写入。它保证的是成员收尾和错误传播规则，不是数据库事务。若成员不响应取消、阻塞循环或清理长时间不结束，任务组退出也会等待。单个成员被正常取消，与成员发生普通失败也不是同一触发条件。

## 30. 异步函数里的阻塞调用

`async def` 只定义协程协议，不会把函数体里的任何同步调用自动变成异步 I/O。`time.sleep()`、普通同步 HTTP 客户端和长时间 Python 循环都可能占住循环线程。

```python
import asyncio
import time

def blocking_read():
    time.sleep(0.01)
    return "report"

async def main():
    result = await asyncio.to_thread(blocking_read)
    print(result)  # report

if __name__ == "__main__":
    asyncio.run(main())
```

`asyncio.to_thread()` 把同步函数交给线程执行，再提供可等待的结果；当前循环能在等待时运行别的任务。它不会改变同步函数的线程安全要求，也不会在常规 GIL 构建下让纯 Python 计算自动获得多核加速。

取消等待 `to_thread()` 的协程，通常不停止已经运行的底层线程。线程仍可能继续写数据，因此外部操作仍需自己的超时和停止策略。若已有原生异步客户端，一般优先使用其异步接口；第 15 章会讨论 HTTP 客户端和连接生命周期。

## 31. 协程的共享状态与异步锁

同一循环中的协程通常不同时执行 Python 代码，但仍可能在暂停前后读写同一状态。下面先保存旧值，再显式让出执行机会，就存在过期读取问题。正确更新把整个约束放进异步锁：

```python
import asyncio

async def main():
    state = {"count": 0}
    lock = asyncio.Lock()

    async def increase():
        async with lock:
            old = state["count"]
            await asyncio.sleep(0)
            state["count"] = old + 1

    await asyncio.gather(increase(), increase())
    print(state["count"])  # 2

if __name__ == "__main__":
    asyncio.run(main())
```

`asyncio.Lock` 获取不到时暂停当前任务，不阻塞整个循环线程。它用于 asyncio 任务，不是跨线程或跨进程锁；也不是可重入锁。同样提供 `asyncio.Semaphore`、`Event`、`Condition`，用途与线程版本相近，等待方式和适用范围不同。

不要让某个协程持有 `threading.Lock` 后暂停，又让同一循环的另一个协程阻塞着取得它。第二个协程会阻塞循环线程，原持有者也不能恢复并释放锁。若两个协程都用同线程可重入锁，则又可能根本没有产生期望的协程互斥。应按共享状态所在的执行模型选择工具。

在同一循环、没有重入回调和其他线程访问的普通片段中，不发生暂停时通常不会穿插其他普通任务。但这只是明确前提下的分析，不能简化为“协程永远没有竞态”。

## 32. `asyncio.Queue` 与固定数量的消费者

`asyncio.Queue` 供同一事件循环中的任务协调，不是线程安全队列。`await put()`、`await get()` 在需要等待时暂停当前任务。固定数量消费者配合有界队列，可以同时限制执行任务和待处理项。

```python
import asyncio

async def main():
    jobs = asyncio.Queue(maxsize=2)
    results = []
    stop = object()

    async def consume():
        while True:
            item = await jobs.get()
            try:
                if item is stop:
                    return
                await asyncio.sleep(0)
                results.append(item * 10)
            finally:
                jobs.task_done()

    async with asyncio.TaskGroup() as group:
        for _ in range(2):
            group.create_task(consume())
        for number in [1, 2, 3]:
            await jobs.put(number)
        for _ in range(2):
            await jobs.put(stop)
        await jobs.join()
    print(sorted(results))  # [10, 20, 30]

if __name__ == "__main__":
    asyncio.run(main())
```

两名消费者需要两个结束标记。`finally` 使成功取出的项即使处理失败也能结束队列计数责任，但“确认已经处理过”不等于“结果成功”，失败仍要传播或单独保存。任务组在普通失败时取消相关成员，避免生产者和消费者各自遗留。

`Semaphore(limit)` 包住操作也能限制同时执行量，但若已经为百万个输入建立百万个 Task，任务对象内存仍会增长。并发上限、排队上限和总任务数量是三个不同指标。

## 33. `wait_for()` 与 `asyncio.timeout()`

`asyncio.wait_for(operation, timeout=...)` 等待给定工作，超时时会请求取消被等待的任务，并等待其取消处理，再向外抛出 `TimeoutError`。Python 3.11 及以后，这里使用内置 `TimeoutError`。

```python
import asyncio

async def main():
    entered = asyncio.Event()
    cleaned = []

    async def work():
        try:
            entered.set()
            await asyncio.Event().wait()
        finally:
            cleaned.append("released")

    task = asyncio.create_task(work())
    await entered.wait()
    try:
        await asyncio.wait_for(task, timeout=0.01)
    except TimeoutError:
        print("timed out")
    print(task.cancelled(), cleaned)  # True ['released']

if __name__ == "__main__":
    asyncio.run(main())
```

这个实验等待的是不会自行就绪的事件，不根据机器速度判断超时。实际函数清理需要时间，或捕获后不接受取消时，`wait_for` 的总耗时可能超过指定时长；它不是操作系统级的强制截止。

`asyncio.timeout(seconds)` 是 Python 3.11 引入的异步上下文管理器，为一段包含多次等待的操作设置预算。它通过取消当前任务实现超时，在范围外把相应取消转换成 `TimeoutError`，所以应在 `async with` 外捕获该超时。

```python
import asyncio

async def main():
    try:
        async with asyncio.timeout(0.01):
            await asyncio.Event().wait()
    except TimeoutError:
        print("整段操作超时")

if __name__ == "__main__":
    asyncio.run(main())
```

每一次重试都重新给予完整超时，可能使总耗时成倍增长。工具应区分单次尝试预算和整项任务预算。异步超时也不会回滚已经发出的远端请求，第 15 章会继续讨论超时与重复提交。

## 34. 任务取消、`CancelledError` 与清理

`task.cancel()` 发出取消请求，不表示调用后任务已经完成。协程通常在下一次能接收取消的执行机会中得到 `asyncio.CancelledError`。这个异常继承 `BaseException`，普通 `except Exception` 不会捕获它。

```python
import asyncio

async def main():
    started = asyncio.Event()
    events = []

    async def work():
        try:
            started.set()
            await asyncio.Event().wait()
        finally:
            events.append("cleanup")

    task = asyncio.create_task(work())
    await started.wait()
    requested = task.cancel()
    try:
        await task
    except asyncio.CancelledError:
        events.append("caller observed cancellation")
    print(requested, task.cancelled())  # True True
    print(events)  # ['cleanup', 'caller observed cancellation']

if __name__ == "__main__":
    asyncio.run(main())
```

发出取消后继续等待，才能确认 `finally` 执行并接收最终状态。如果确实需要捕获取消做记录，一般清理后用裸 `raise` 继续传播，不应把取消当作可忽略的业务错误无限重试。

`asyncio.shield()` 可以使一次外层等待的取消不直接取消内部任务，但外层仍可能收到取消，内部任务仍需要有人持有和等待。它不是“一加上就保证操作完成”的开关，当前阶段不要用它掩盖生命周期不清的问题。

## 35. `async with` 与异步资源生命周期

普通 `with` 调用 `__enter__()`、`__exit__()`；`async with` 等待 `__aenter__()`、`__aexit__()`。后者适合进入和退出也需要异步等待的资源，例如异步客户端连接。它不会自动替任何普通同步管理器生成异步协议。

```python
import asyncio
from contextlib import asynccontextmanager

@asynccontextmanager
async def session(events):
    events.append("open")
    try:
        yield "connection"
    finally:
        await asyncio.sleep(0)
        events.append("close")

async def main():
    events = []
    async with session(events) as connection:
        events.append(connection)
    print(events)  # ['open', 'connection', 'close']

if __name__ == "__main__":
    asyncio.run(main())
```

第 7 章的 `contextmanager` 通过一次 `yield` 分隔进入与退出；`asynccontextmanager` 对这里的异步生成器提供相应封装。异步生成器由 `async def` 和 `yield` 共同定义，产生元素也可能需要等待；本章只用它表达资源范围，不展开完整异步迭代专题。

工作任务应在连接退出前结束，否则任务可能在资源关闭后继续访问。取消期间也要安排清理，但反复取消、清理自身失败或解释器被强制停止，仍可能影响清理完成。明确的作用范围比等待对象被垃圾回收更可靠。

## 36. 线程与事件循环之间的调用边界

asyncio 的队列、锁和多数对象不能直接拿来给其他线程修改。其他线程需要向循环提交普通回调时，可以使用 `loop.call_soon_threadsafe(callback, ...)`；提交协程时可使用 `asyncio.run_coroutine_threadsafe(coroutine, loop)`。

后者返回的是 `concurrent.futures.Future`，可以让提交线程等待；不能在事件循环自己的线程里阻塞调用它的 `result()`，否则循环无法执行正被等待的协程。反方向把同步工作交给线程，可以使用 `await asyncio.to_thread(...)`。

这几种 Future、Task、锁和队列虽然名称接近，仍有不同归属和等待方式。涉及跨线程桥接时，先画出“哪个线程运行循环、谁提交、谁等待、结果由谁接收”。

## 37. 测试开发中的批量任务设计

批量检查报告、读取日志或执行独立接口用例时，可以先声明以下接口约定：每项输入有稳定编号；结果能关联回输入；并发和排队有上限；失败与取消有明确状态；任务结束前已处理自己的资源。

例如两个用例分别修改同一个账号的余额，它们虽然能同时启动，却不满足“独立工作”的假设。应给不同工作者分配账号、数据前缀、目录或端口，或把确有顺序要求的操作明确串行。只给结果列表加锁，不能隔离远端系统中的共享业务状态。

遇到部分失败时，先选择语义：收集所有独立结果，还是一项失败就取消其他相关工作？前者可采用逐项捕获普通异常并形成结果记录；后者可以利用 TaskGroup。两者都不能吞掉外层取消，也不能把基础设施失败伪装成断言通过。

重试之前还要判断操作是否**幂等**：重复执行是否仍达到同一预期效果。查询和重复创建订单的风险不同；客户端超时不表示服务器没有创建订单。并发、重试与业务断言的系统实践安排在第 14～16 章，本章先建立执行模型。

## 38. 并发问题的排查与可复现实验

排查错误结果时，先写出必须成立的约束，再列出参与者、共享对象和所有访问位置。把读取、检查、等待和写回拆开，寻找可能破坏约束的交错。用屏障、事件或可控测试替身复现，不依赖“多睡一会儿应该就好了”。

排查卡住时，画等待关系：谁持有什么、正在等谁、对方是否还可能运行。线程栈、任务栈和用例编号有助于定位；`faulthandler` 是能辅助输出线程调用现场的标准库工具，日志和调试方法会在第 11 章展开。不要只观察 CPU 使用率低就认定程序没问题，它可能正处于死锁或无限等待。

观测日志可能改变调度，固定随机种子也不能固定操作系统调度。单次成功不是线程安全证明，单次耗时变短也不是性能结论。检查器应核对数据约束、资源回收和允许的执行顺序，不断言机器必须在精确毫秒数内完成正常计算。

## 39. 进程、线程与协程的选择顺序

| 任务条件 | 起点方案 | 必须继续确认 |
|---|---|---|
| 工作很少或有明确先后依赖 | 顺序执行 | 是否确实需要并发 |
| 使用阻塞库，主要等待 I/O | 有界线程池 | 库的线程安全、外部超时、数据隔离 |
| 已有异步接口，大量等待 | asyncio 与有界任务组织 | 循环内无阻塞、取消和资源范围 |
| 常规 GIL 构建的独立纯 Python 计算 | 进程池 | 计算粒度、序列化成本、内存与入口 |
| 本地扩展释放 GIL，或自由线程构建 | 根据库和构建测量线程方案 | 扩展兼容性、内部线程数和同步 |

并发工作数也不是“越大越好”。CPU 核心、连接池、测试账号、数据库和被测服务都有容量约束。并发量、单位时间请求量、延迟与吞吐量在第 16 章会分开测量，本章不把线程数直接当成服务容量。

# 第 10 章参考回答：并发、并行与异步

与面试题的 45 道题逐题对应。参考回答用于校正模型和组织表达，不是逐字背诵稿。默认以常规 CPython 3.12 为基线；自由线程和启动方式另标边界。并发代码应同时解释共享状态、等待、结果、失败和收尾。

## 一、基础与线程

### 第 1 题：并发与并行

**首轮结论：** 并发是多个任务在重叠时间中取得进展，并行是同一瞬间有多个执行单元实际运行。

单核心可以 A 一段、B 一段地交错，让两项工作在整体时间上重叠；两个核心分别计算 A 和 B 才是并行的典型例子。提交只是把工作交给执行机制，不能证明已经开始，也不能证明纯 Python 代码正在多核计算。还要检查调度、GIL、外部资源和实际瓶颈。

**常见误答：** 把并发定义为多个 CPU 同时计算，或把并行简单定义成启动很多线程。

**继续追问：** 网络等待期间的并发为什么也能提高整体完成速度？

**回答边界：** 用时间关系和一个例子区分即可，不必展开 CPU 微架构。

### 第 2 题：同步异步与阻塞非阻塞

**首轮结论：** 两组术语关注不同维度：结果怎样交付，以及当前执行单元是否必须停下等待。

调用方提交线程池工作后可以继续做别的事，稍后从 Future 取得结果；工作线程执行的读取仍可能阻塞。异步协程等待未就绪的操作时暂停的是该任务，事件循环可以推进其他工作。线程同步中的“同步”又指协调访问，不能与同步调用不加区分地混用。

**常见误答：** 认为函数里出现 async 就不会阻塞，或认为异步调用方已经立即得到业务结果。

**继续追问：** 异步接口为什么也可能使用回调而不是 await？

**回答边界：** 分清调用、结果和线程三个观察角度。

### 第 3 题：进程、线程与协程

**首轮结论：** 进程提供普通地址空间隔离，线程在进程内共享普通内存并由操作系统调度，asyncio 协程任务由事件循环协作调度。

两线程拿到同一列表时可能互相观察修改；两普通进程各自拿到传输后的列表时默认不共享修改。单循环中的两个任务可以在等待处交错，但不因此在两个核心上执行 Python 代码。进程启动与传输通常较重，线程需要协调共享状态，协程需要兼容的异步接口和生命周期管理。一个进程能有多线程，每个线程还可能有自己的事件循环。

**常见误答：** 把协程等同于更快的线程，或说每个协程都有独立进程内存。

**继续追问：** 协程局部名字各自独立，为什么仍可能共享同一个字典？

**回答边界：** 说明普通模型及约束，不背无条件的数量级性能比。

### 第 4 题：CPU 密集型与 I/O 密集型

**首轮结论：** 按代表性工作中的实际耗时与资源瓶颈判断，不能只看函数名或任务类别。

下载报告可能主要等网络，下载后逐条做 Python 校验可能主要耗 CPU。常规 GIL 构建中的阻塞 I/O 可先考虑线程，已有异步客户端可考虑 asyncio，独立的纯 Python 计算可考虑进程。释放 GIL 的本地扩展有不同并行条件。先测整体，再评估启动、通信、内存与外部容量。

**常见误答：** 所有网络函数都一定适合协程，所有 Python 发起的计算都只能单核。

**继续追问：** 如果网络阶段和解析阶段的瓶颈不同，如何拆分责任？

**回答边界：** 解释一项具体工作并提出测量依据即可。

### 第 5 题：常规 CPython 的 GIL

**首轮结论：** GIL 限制同一解释器中的线程同时执行受其保护的 Python 操作，但不把多步业务操作自动变成事务。

两个纯 Python 计算线程通常不能在该解释器里同时执行字节码；许多 I/O 等待和部分本地扩展会释放 GIL，因此线程仍能重叠等待或并行运行相应扩展。余额读取、条件判断和写回可以在步骤间交错，必须针对整个业务约束设计锁或事务。

**常见误答：** 有 GIL 就没有线程安全问题，或 Python 线程在任何工作中都不可能并行。

**继续追问：** 为什么一次运行 count += 1 正确不能证明其通用安全性？

**回答边界：** 明确实现与构建前提，并区分解释器保护与业务保护。

### 第 6 题：自由线程构建的版本边界

**首轮结论：** CPython 从 3.13 起提供可选自由线程构建；版本号本身不能说明当前运行是否禁用了 GIL。

需要核对解释器、构建和实际状态，第三方扩展也可能使 GIL 重新启用。即使内置容器有内部锁，先检查字典是否存在键、再创建或修改值仍是多步约束。例如两个线程分别看到账号空闲后都领取，单次字典访问不损坏也不能阻止重复领取。

**常见误答：** 新 Python 全部默认无 GIL，或内置容器有锁就不需要业务同步。

**继续追问：** 为什么升级构建后仍要验证依赖兼容性与真实速度？

**回答边界：** 掌握可选构建、实际状态和组合操作三个边界，不背内部锁实现。

### 第 7 题：Thread 的构造、启动与等待

**首轮结论：** target 接收可调用对象，start 安排线程执行，join 等待结束；超时后要再检查存活状态。

target=work() 会先在当前线程调用 work，再把返回对象作为 target。args=(value,) 提供位置实参；创建 Thread 对象本身还未运行工作，同一个线程对象也不能重复启动。join 的结果不是工作函数返回值，结束和等待超时时都可能返回 None，因此用 is_alive 判断。

**常见误答：** join 启动线程，或 join 的返回值就是业务函数的返回值。

**继续追问：** 怎样把普通线程的返回值交回调用方？

**回答边界：** 能逐步解释一次调用的顺序即可。

### 第 8 题：线程异常与守护线程

**首轮结论：** join 不会自动在等待线程重新抛出工作异常；守护线程也不能保证退出时完成清理。

普通工作线程失败后，主线程需要通过队列、自定义结果记录等取得状态；线程池 Future.result 提供更直接的结果和异常通道。守护线程不会单独阻止解释器退出，可能被突然停止，例如正在写报告时只留下部分文件。重要工作应有停止请求、等待确认与明确资源范围。

**常见误答：** join 一定替主线程捕获异常，或守护线程退出时一定正常执行 finally。

**继续追问：** 重要后台工作无法响应停止时，怎样定位它的等待位置？

**回答边界：** 区分错误通道、退出条件和清理责任。

### 第 9 题：局部形参与线程共享对象

**首轮结论：** 每次调用有自己的局部名字，但这些名字可以共同指向同一可变对象。

work(items) 中执行 items.append(1) 修改共享列表；执行 items = [] 只重新绑定当前调用的局部形参，不改变调用处名字与原列表之间的关系。共享问题取决于对象图，而不是局部名字拼写相同。浅拷贝外层也可能仍共享内部字典。

**常见误答：** 线程有独立栈帧，所以传入的任何对象都自动独立。

**继续追问：** 多个测试用例共享嵌套配置时应确认哪一层可变状态？

**回答边界：** 画出两个局部名字到同一对象的箭头。

### 第 10 题：竞态、临界区与原子性

**首轮结论：** 竞态是错误依赖交错时机，临界区是需要协调的操作范围，原子性是某个操作在约定观察范围内不可被拆看。

两个工作者先各读到 count=0，之后都写回 1，就丢失一次更新。读和写各自不损坏对象，组合结果仍错误。用屏障要求两者都先完成读取，可以确定地复现这条交错；锁应覆盖读取、计算和写回，不只保护最后一次赋值。

**常见误答：** 只要单步操作是原子的，任意组合也都是原子的。

**继续追问：** 检查空闲账号再领取为什么是类似问题？

**回答边界：** 明确约束和一条错误交错，比背名词更重要。

### 第 11 题：锁的保护范围

**首轮结论：** 锁的范围应覆盖必须共同保持的状态约束，而且相关访问者必须遵守同一约定。

若要求两个账户总额不变，只单独锁各次赋值可能让其他观察者看到中间状态。范围过小会留下竞态，过大会增加等待和串行开销。持锁做网络请求还会延长等待，并可能与回调依赖形成死锁。用 with 确保退出释放，先确定正确性，再优化粒度。

**常见误答：** 每个函数各创建一把新锁就能保护同一共享对象。

**继续追问：** 读取者完全不加锁，会不会观察到不符合组合约束的状态？

**回答边界：** 说明共享状态、同一锁和完整范围。

### 第 12 题：Lock 与 RLock

**首轮结论：** RLock 允许持有线程再次取得同一把锁，并要求配对释放；它不解决所有等待环。

一个持锁的公开方法调用同样加锁的内部方法，普通 Lock 可能让同一线程等待自己。可改用 RLock，或明确让内部方法在调用方已持锁的前提下工作。两个线程按相反顺序取得 A、B 两把 RLock，仍可能互相等待。

**常见误答：** 可重入表示允许多个线程同时进入。

**继续追问：** 同一事件循环中的协程能用同线程 RLock 实现互斥吗？

**回答边界：** 说明同一线程、同一把锁与释放计数。

### 第 13 题：死锁与等待关系

**首轮结论：** 先画谁持有什么、正在等谁；等待形成无法推进的环时，就可能死锁。

A 持资源一等资源二，B 持资源二等资源一，是典型循环。持锁 join 一个需要该锁的线程也一样。单工作线程池中，当前工作等待尚未开始的另一项工作，则执行资源被自己占住。统一锁顺序、避免持锁等待依赖工作、在外层组织任务依赖是常见预防。超时仅提供放弃机会，仍要清理已取得资源。

**常见误答：** 看到卡住就增加 sleep，或把全部锁换成 RLock。

**继续追问：** 如何用线程或任务调用现场确定卡在哪个等待点？

**回答边界：** 给出等待环及能打破环的具体修改。

### 第 14 题：Event 与协作停止

**首轮结论：** Event 保存标志状态，适合就绪和停止通知；工作必须主动观察并退出。

连续 set 两次不会积累两条消息。线程可在循环里检查标志，或使用 stop.wait(timeout) 在等待中响应。若工作卡在没有超时的外部调用里，它暂时看不到停止标志。调用方应发请求后 join，再确认清理和结果，不能把 set 当作强杀线程。

**常见误答：** 每次 set 都代表一份独立消息，或 set 会强制让目标线程立即退出。

**继续追问：** 需要保存每项任务时为什么更适合队列？

**回答边界：** 分清状态标志、合作观察与结束确认。

### 第 15 题：信号量与请求速率

**首轮结论：** 信号量限制同时占用的名额，锁通常表达互斥；有界信号量还检测过度释放。

三个名额可表示三个连接或账号。每次操作很快，名额在一秒内能被反复使用，所以速率可能远高于三次。速率控制要考虑时间窗口或发放节奏。名额取得后应在 finally 或 with 中释放，不能失败时漏还，也不能未取得就归还。

**常见误答：** 信号量天然实现每秒限流，或无限增大名额一定加速。

**继续追问：** 名额受限后，排队工作仍可能无限占用内存吗？

**回答边界：** 区分同时量、速率和排队量。

### 第 16 题：Condition 的检查与通知

**首轮结论：** 在锁下检查共享条件，等待时释放锁，恢复时重新取得并检查；通知不是条件的永久承诺。

消费者等待 buffer 非空，生产者在同一锁下放入数据并 notify。若数据先存在，消费者检查条件就能继续，无需等一条已经错过的通知。notify 本身不释放锁；其他消费者还可能先取走数据，所以用 wait_for(predicate) 或条件循环。

**常见误答：** wait 全程持锁，或被唤醒就可跳过条件检查。

**继续追问：** 条件不成立时使用 Event 与 Condition 各要怎样维护状态关系？

**回答边界：** 解释锁、共享条件和通知三者的责任。

### 第 17 题：线程队列的完成语义

**首轮结论：** 取出、完成通知和业务结果是不同事实；join 只等待相应任务计数结束。

取出一项后应配对一次 task_done，finally 可保证路径完整。成功和失败都可能结束处理计数，业务失败应另行记录或传播。消费者退出而队列仍有未确认项时，join 可能一直等。maxsize 提供排队背压，empty 只是观察时刻的状态，不能替代带超时的 get。

**常见误答：** get 就代表处理完成，或 join 返回结果列表且证明全部通过。

**继续追问：** 多个消费者怎样选择不与普通数据冲突的结束标记？

**回答边界：** 逐项跟踪入队、取出、确认和结果。

### 第 18 题：线程池与 Future

**首轮结论：** submit 返回代表未来状态的 Future，result 才取得返回值或在调用位置传播工作异常。

done 可对应成功、失败或取消，不等同于通过。exception 用于取得已完成工作的异常信息，必要时也会等待；已取消的状态还需按取消接口处理。池只组织工作线程，不替工作函数保护共享字典、文件和远端账号。例子是提交 int('bad') 后，异常保存在 Future 中，消费 result 时才能在调用方处理。

**常见误答：** submit 的返回值就是业务结果，或 max_workers 已解决所有线程安全问题。

**继续追问：** 提交百万项但只开四个线程，内存为何仍可能增长？

**回答边界：** 说明提交对象、状态和结果通道。

### 第 19 题：map 与 as_completed 的顺序

**首轮结论：** map 按输入位置提供结果，as_completed 提供已完成 Future；需要另外保存输入关联。

A 慢、B 快时，map 的第一个位置仍对应 A，所以消费会等 A；as_completed 可以先交出 B，但多个工作已完成后不应要求额外的精确时序。可保存 future 到 case_id 或输入下标的映射，再写入对应结果位置，不把到达位置当作输入位置。

**常见误答：** map 的列表顺序必定等于实际完成顺序。

**继续追问：** 若要先显示结果但最后按用例编号输出，应怎样组织？

**回答边界：** 说清顺序契约和关联信息。

### 第 20 题：Future 的超时与取消

**首轮结论：** Future 的等待超时不自动停止工作，cancel 主要取消尚未开始的工作；两套取消异常属于不同 API。

线程已开始阻塞读取时，result 超时只是调用方暂时等不到，后台仍可能继续写文件。排队工作取消成功后，取结果抛出 concurrent.futures.CancelledError；运行中工作通常需要协作停止。asyncio.CancelledError 面向异步任务的取消传播，不能靠名称相同混用捕获。

**常见误答：** TimeoutError 表示线程已经结束，或 cancel 返回就代表任何工作都被强杀。

**继续追问：** 为什么连接和网络操作还需要自己的超时？

**回答边界：** 分别说明等待状态和工作状态。

### 第 21 题：线程池退出与任务依赖

**首轮结论：** 上下文退出默认等待工作结束，取消排队项不能强制停止正在运行项。

即使 with 内已捕获等待超时，退出仍可能等阻塞工作结束。shutdown(cancel_futures=True) 处理尚未开始的工作；wait=False 也不意味着线程或解释器退出责任消失。池内任务若阻塞等待同池尚无执行机会的工作，还可能卡住所有退出流程。应减少池内依赖等待，并为外部操作设置可响应的结束策略。

**常见误答：** 加 wait=False 就一定可以立即结束整个 Python 程序。

**继续追问：** 为了尽早返回而遗留运行任务，会怎样影响测试数据与报告？

**回答边界：** 说清外层函数、池和工作三个生命周期。

## 二、多进程

### 第 22 题：进程状态隔离与通信

**首轮结论：** 普通进程状态默认隔离，修改子进程对象不直接修改父进程普通列表；通过 IPC 传回数据才可观察内容。

在 spawn 中，父进程列表状态经传输后在子进程重建；子进程修改后再 send，父进程 recv 得到接收端对象。它不是跨进程可随意共同解引用的原始指针。显式共享内存和代理对象另有契约，不能从普通列表外推。

**常见误答：** 把列表作为实参传入就必定在父子进程间共享内存。

**继续追问：** 为什么跨进程的 object() 结束标记不能简单继续用 is 判断？

**回答边界：** 区分普通传输、共享状态和身份。

### 第 23 题：spawn、主入口与 Notebook

**首轮结论：** 入口保护防止新解释器导入主模块时递归启动，工作函数本身还必须能在子进程中可靠找到。

把顶层命名函数写入真实模块，启动动作放到主入口保护中。Notebook 单元格的交互状态通常不构成子进程可导入的同名主模块，因此仅补 if 不能复制那份内存现场。本章实验把完整可见源码写入临时 .py，再用当前解释器运行并清理。另一种实践是把工作函数放入专用可导入模块。

**常见误答：** 只加 main 判断就保证任意 Notebook lambda 可提交给进程池。

**继续追问：** 为何导入模块时不应直接连接服务并创建线程或进程？

**回答边界：** 分开解释启动保护与入口可导入性。

### 第 24 题：进程启动方式的版本差异

**首轮结论：** 默认方式取决于平台、版本和可用条件，明确上下文能使教学前提稳定，不能把平台简称当永久契约。

Windows 和现代 macOS 通常用 spawn；Python 3.14 在支持的 POSIX 平台将主要默认改成 forkserver，fork 不再是任何平台的默认。具体补丁和环境仍应核对官方说明与实际启动方式。get_context('spawn') 为本次对象选择一致上下文，避免修改全局启动设置。不同上下文产生的同步资源也不应随意混传。

**常见误答：** Linux 永远默认 fork，或 Python 3.14 所有平台默认同一种方式。

**继续追问：** 使用 fork 从多线程进程复制状态为什么需要谨慎？

**回答边界：** 会标明版本和上下文即可，不要求背全平台历史。

### 第 25 题：进程池的序列化边界

**首轮结论：** 标准进程池要传输可序列化的调用与结果，并在工作进程恢复相应入口和数据。

普通函数通常按模块与名称定位，不是把整个交互现场打包。闭包和局部名字往往没有同样的可导入入口，运行资源也不等于普通数据状态。通常传简单配置和必要输入，在工作进程建立、使用并关闭自己的连接。pickle 的完整机制和不可信数据风险在第 12 章展开。

**常见误答：** 任何 Python 对象都可以靠深拷贝或 pickle 复制成另一个有效连接。

**继续追问：** 输入大、输出也大时，多进程的通信成本怎样影响选型？

**回答边界：** 说明可导入调用与数据、资源的区别。

### 第 26 题：共享计数与进程通信等待

**首轮结论：** 单次访问保护不能自动覆盖读取后写回；通信缓冲有限，错误的等待顺序也会形成相互等待。

共享值更新仍可能先读旧值再写新值，应在共享对象提供的锁范围里完成完整操作。子进程发送大量数据可能等缓冲被消费；父进程若先 join 等子进程结束，就可能双方都不推进。应及时消费通信，再确认退出，并按所有权关闭通信端。Manager 代理还增加远程调用成本，不是本地普通字典。

**常见误答：** 用了共享类型就所有表达式都原子，或父进程先等待一定更安全。

**继续追问：** 强制 terminate 持有共享锁的进程可能留下什么状态？

**回答边界：** 分别解释组合更新和通信等待环。

### 第 27 题：进程池的性能成本

**首轮结论：** 增加并行工作者也增加协调成本，并且不能消除原有顺序依赖和外部瓶颈。

一百万次微小加法逐项跨进程传输，可能比直接循环更慢；几份较大的独立分析任务才更可能摊薄成本。结果汇总、输入复制和不均衡也会限制收益。应测同一代表性工作量下的整体耗时和资源，不能只量工作函数内部，忽略启动和收尾。

**常见误答：** 进程数等于加速倍数，或越多进程越快。

**继续追问：** 本地扩展内部已有多个线程时，外层再多进程会怎样？

**回答边界：** 列出关键成本并说明测量范围。

## 三、协程与异步

### 第 28 题：协程函数、协程对象、Task 与 Future

**首轮结论：** 协程函数定义行为，调用产生可等待的协程对象，Task 驱动其受循环调度；Future 表达未来状态，但不同模块有不同等待接口。

pending=work() 通常只创建协程对象；await pending 可以沿当前任务执行它，create_task(pending) 则建立独立调度任务。asyncio.Task 属于 asyncio 可等待体系，普通 concurrent Future 的 result 在调用线程阻塞等待，不能在循环线程里随意拿来阻塞。需要跨模型时使用正式桥接接口。

**常见误答：** 每个协程对象都已经在后台运行，或两种 Future 完全可以互换。

**继续追问：** 同一个已耗尽协程对象为什么不能再次运行？

**回答边界：** 分清创建、调度和结果三个阶段。

### 第 29 题：依次 await 与实际暂停

**首轮结论：** 依次等待仍按当前控制流运行，await 也不保证一定交出执行机会。

第一项结束后才调用第二项，B 就没有提前开始。独立创建 Task 或交给 gather、TaskGroup 才能组织重叠进展。被等待对象已就绪或协程无需暂停便返回时，当前任务可直接继续。分析共享状态要定位真正能暂停或重入的位置，不只是数 await 关键字。

**常见误答：** 写两个 await 就自动并行，或所有 await 都是固定调度切换点。

**继续追问：** 当前任务长期无等待地计算会如何影响超时处理？

**回答边界：** 能按一次实际执行流程解释。

### 第 30 题：异步函数中的阻塞工作

**首轮结论：** 同步阻塞或持续计算会占住循环线程；to_thread 使同步工作在线程中执行，但不改变其资源和取消语义。

其他任务、心跳与超时回调都依赖循环取得执行机会，不能因为函数用了 async 就自动推进。可以使用原生异步接口，或把合适的阻塞 I/O 交给 to_thread。常规 GIL 下纯 Python 计算不会因此自动多核，取消外层等待通常也不会强制停止已运行线程。

**常见误答：** to_thread 让函数变成完全可取消的原生协程，或使纯 Python 计算自动提速。

**继续追问：** 同步客户端对象若不是线程安全的，交给线程后该怎样管理？

**回答边界：** 说明循环线程、底层线程与取消三个边界。

### 第 31 题：gather 的结果与异常

**首轮结论：** 结果按传入位置排列；默认传播首先观察到的异常，但不会因某项普通失败自动取消其余成员。

A 输入在前但运行慢，结果的第一项仍对应 A。若 B 失败，A 可能继续运行并产生副作用；调用方必须明确接管剩余成员。return_exceptions=True 把异常也放进对应位置，需要逐项分类。外层 gather 本身被取消又有向成员传播取消的规则，不能把所有失败混成一种情况。

**常见误答：** gather 默认一项失败就自动取消所有其他任务。

**继续追问：** 为什么在简短脚本中可能误观察到其他任务也被取消？

**回答边界：** 解释 gather 与 asyncio.run 退出清理的区别。

### 第 32 题：TaskGroup 与异常组

**首轮结论：** TaskGroup 把成员绑定到共同作用范围，非取消类失败通常取消其余成员，等待收尾后传播异常组；它不回滚副作用。

一项校验失败，另一项正在异步等待时会收到取消并运行 finally。ExceptionGroup 组合多个相关失败，except* 按成员类型匹配，不能在同一个 try 上与普通 except 混写。成员若不响应取消或阻塞循环，退出仍可能延迟；单项正常取消与普通失败也有不同规则。

**常见误答：** 任务组失败自动撤销已经创建的订单，或退出不需要等其他成员。

**继续追问：** 成员的清理又抛异常时，应怎样保留失败证据？

**回答边界：** 说清失败传播、收尾和非事务边界。

### 第 33 题：协程共享状态与锁的适用范围

**首轮结论：** 协程在暂停前后仍会交错访问共享状态，应使用符合任务模型的同步工具。

两任务先读 count，再 await，恢复时都写 old+1，就能丢失更新。asyncio.Lock 竞争时暂停任务，普通 threading.Lock 竞争时可能阻塞整个循环，导致持锁但暂停的协程无法恢复；同线程 RLock 又不能提供预期协程互斥。异步锁也不提供跨线程保护。

**常见误答：** 协程只有一个线程，所以永远不需要锁。

**继续追问：** 没有实际暂停且无其他线程访问的普通片段可以怎样分析？

**回答边界：** 明确共享对象、暂停点和锁归属。

### 第 34 题：异步队列与任务数量

**首轮结论：** 信号量限制操作区域的同时量，不限制已经创建的任务数量；固定消费者和有界队列分别控制执行与积压。

先为百万项建 Task，再在每项里等信号量，仍持有百万份任务状态。固定五名消费者配合容量十的队列，则能让运行工作者数量稳定，生产者满队列时等待。仍要统计保留的输入和结果内存，不能据此宣称整个程序只有常数空间。

**常见误答：** 任何加了 Semaphore 的程序都已限制全部内存。

**继续追问：** 消费者失败、取消或收到结束标记后，task_done 的责任如何安排？

**回答边界：** 区分运行量、排队量、任务数与数据空间。

### 第 35 题：异步超时的范围与时长

**首轮结论：** wait_for 对被等待工作请求取消并等待处理，timeout 为当前任务的一段范围设置预算；两者都不是强制实时截止。

工作收到取消后执行 finally 需要时间，循环被同步工作阻塞时超时回调也难以及时运行。timeout 将相应取消转换成 TimeoutError，应在上下文外捕获。远端请求可能已成功，客户端停止等待不能撤销它。每次重试重新给予完整超时，还可能放大总预算。

**常见误答：** 超时时刻就是底层工作被强制杀掉的时刻。

**继续追问：** 怎样区分一次尝试超时与整个批次超时？

**回答边界：** 解释取消、清理、范围和远端状态。

### 第 36 题：取消请求与最终取消状态

**首轮结论：** cancel 发出请求，等待任务才能确认清理和最终状态；asyncio.CancelledError 继承 BaseException，不应作为普通可重试失败吞掉。

任务在可接收取消的执行机会中得到取消异常，finally 可以关闭资源。若任务抑制取消，它甚至可能继续或正常返回，所以 cancel 成功不等同于最终 cancelled 为真。通常只在确需记录时捕获取消，清理后重新抛出；拥有者在边界等待并处理该状态。

**常见误答：** cancel 后立即丢弃句柄，或裸 except 后无限重试。

**继续追问：** shield 是否保证内部工作必定完成？

**回答边界：** 说清请求、响应、等待与传播。

### 第 37 题：async with 与异步资源

**首轮结论：** async with 等待异步进入和退出方法，让资源的取得与清理能够暂停；它不是普通 with 的自动加速版本。

同步协议使用 __enter__ 和 __exit__，异步协议使用 __aenter__ 和 __aexit__。连接退出后仍有任务使用它，就可能出现已关闭资源错误。将任务组放在客户端资源范围内，先等组内任务收尾，再关闭连接，可使责任顺序清楚。取消与清理自身失败仍要记录，不能依赖垃圾回收补救。

**常见误答：** 任何同步对象加上 async with 都会自动变成异步资源。

**继续追问：** asynccontextmanager 的 yield 前后分别承担什么责任？

**回答边界：** 说明协议与退出顺序即可。

### 第 38 题：跨线程提交异步工作

**首轮结论：** 使用 call_soon_threadsafe 或 run_coroutine_threadsafe 正式桥接，不能让循环线程阻塞等待自己的执行结果。

其他线程提交协程后，可以从 concurrent Future 等待；若循环线程自己调用阻塞 result，循环就无法继续执行那个协程，形成等待自身。反方向需要把同步 I/O 移出循环时，可用 to_thread。asyncio.Queue 等对象也不应由其他线程任意直接操作。

**常见误答：** 带 threadsafe 的函数返回后，在任何线程阻塞等结果都安全。

**继续追问：** 同时使用线程队列和异步队列时怎样标出所有者？

**回答边界：** 画出提交线程、循环线程和结果等待关系。

## 四、代码分析与测试开发场景

### 第 39 题：屏障控制的线程输出

**首轮结论：** 输出 `1`，因为两个线程都先把自己的 old 绑定到 0，然后各写回 1。

屏障让“两次读取都已发生”先于任意一次写回，因此不需要依赖碰巧的切换。GIL 不把读取和之后写回合成事务。修复可去掉用于复现的屏障，用同一把锁保护完整更新；不能把屏障留在互斥区内，让第一个线程持锁等待第二个线程进入同一区域。

**常见误答：** 直接按线程数回答 2，或把屏障看成自动加锁累加。

**继续追问：** 如果把 barrier.wait 放进同一把互斥锁中，会形成什么等待关系？

**回答边界：** 逐行标出两个 old 与共享条目即可。

### 第 40 题：gather 失败后的任务状态

**首轮结论：** 依次输出 `caught`、`False` 和 `done`。

fail 只在 work 已启动后失败，work 仍等待 release。gather 传播 ValueError 不自动取消它，所以检查时尚未结束。之后 set 允许工作继续，显式 await 收到结果。本例主协程没有直接退出，因此不会把循环退出对遗留任务的取消误看成 gather 行为。

**常见误答：** 回答 task 已取消，或认为 catch 后所有成员都已成功结束。

**继续追问：** 若换成 TaskGroup，怎样观察 finally 与异常组？

**回答边界：** 按事件和错误传播推导，不根据时间长短猜测。

### 第 41 题：修复异步函数中的阻塞调用

**首轮结论：** 同步 read_report 直接占住循环线程；可把合适的阻塞 I/O 交给线程，或采用真正异步的读取接口。

修改后的最小脚本如下。原函数仍是同步阻塞函数，取消其外层等待通常不会强制停止已运行线程。

```python
import asyncio
import time

def read_report():
    time.sleep(0.02)
    return "report"

async def inspect_report():
    return await asyncio.to_thread(read_report)

async def main():
    print(await asyncio.gather(inspect_report(), inspect_report()))

if __name__ == "__main__":
    asyncio.run(main())
```

真实客户端还要核对线程安全、连接归属和内部超时，不能用这个演示宣称所有工作都应进线程池。

**常见误答：** 只给 read_report 再套一层 async def，却仍直接调用 time.sleep。

**继续追问：** 若 read_report 主要是纯 Python 计算，应重新评估什么？

**回答边界：** 说明循环为何被阻塞，再给出有边界的改法。

### 第 42 题：批量接口检查的模型选择

**首轮结论：** 先确认主要是 I/O 等待及工作独立性，阻塞客户端可先考虑有界线程池，异步客户端可考虑有界 asyncio 工作者。

并发上限根据连接、账号、被测服务和客户端线程安全确定；分别设计请求超时、批次预算、输入编号、业务断言、数据隔离和失败结果。异步方案避免循环中混入阻塞操作，不能先建无限任务。普通失败是收集全部还是取消相关任务，要按业务语义选择。

**常见误答：** 所有接口自动开 200 个线程，或使用协程就无需连接上限与数据隔离。

**继续追问：** 请求超时后服务器可能已经成功时，重试前还要考虑什么？

**回答边界：** 把选型依据与资源、失败约束连起来。

### 第 43 题：大量日志的计算与传输

**首轮结论：** 对常规 GIL 构建中的独立纯 Python 计算，可以评估进程池，但工作粒度和传输量必须一起考虑。

先按文件或适当批次分工，传最小必要配置与数据，在进程中读取其拥有的资源，再返回摘要。每行都序列化发送可能把通信变成瓶颈；批次太大又可能造成不均衡和取消迟钝。测整体耗时、峰值内存、错误处理与结果一致性，保留顺序版本作为对照。

**常见误答：** CPU 满就把进程数设成行数，或忽略父进程汇总成本。

**继续追问：** 若日志解析库释放 GIL，线程方案是否值得重新测量？

**回答边界：** 说明独立性、粒度、资源与验证。

### 第 44 题：并行用例的不稳定失败

**首轮结论：** 从共享资源和失败约束入手建立可复现证据，不能用随机种子或固定休眠替代隔离与同步。

记录用例编号、工作者、数据标识、请求与状态，检查账号、目录、端口和缓存是否共享；用可控事件安排冲突，确认冲突发生在测试代码还是被测系统。随机种子只固定部分数据产生，不固定操作系统调度。等待明确状态并设置上限比盲目延长休眠可靠，重跑成功也不能直接掩盖原始失败。

**常见误答：** 并行失败一律当作环境问题，或统一增加 sleep 和重试。

**继续追问：** 如何设计最小复现，并在修复后证明隔离约束恢复？

**回答边界：** 给排查顺序、具体证据和一个复现实验。

### 第 45 题：批量执行器的完整生命周期

**首轮结论：** 先定义每项工作的状态与拥有者，再选择执行模型；结果正确和退出完整都属于接口。

为每项输入分配稳定编号，选择有界池或固定消费者；明确收集全部独立结果还是首个普通失败取消相关工作。区分单次等待超时与总预算，取消后等待工作收尾，按资源拥有范围关闭连接、队列和进程。重试限定异常与次数，并先确认幂等性，不重试取消。验证空输入、重复输入、顺序、失败、外部取消、任务数和资源隔离。项目回答只描述真实做过的事情，给出当时约束与能证明的效果。

**常见误答：** 只列工具名称，忽略失败后还在运行的工作与外部数据状态。

**继续追问：** 如果结果本身很大，应如何改变存储和汇总方式？

**回答边界：** 能画出从提交到完成或取消的一条完整责任链。

# 第 16 章参考回答：Python 测试工具开发

与 45 道题逐题对应。先给结论，再解释数据流、状态和验证，最后说明限制。这是表达参考，不是唯一话术；设计和兼容策略仍需自己复述。

## 一、需求、模块与模型

### 第 1 题：工具目标与完成条件

**首轮结论：** 先确认目标使用者、最小功能、输入输出、失败与交付约定，再确定验证范围。

例如汇总器要规定记录协议、筛选、唯一编号、统计含义和报告保存。完成不仅是正常函数返回，还包括坏输入、资源收尾及他人在声明环境中能安装和调用。

测试工具自身也可能算错或漏字段，不能因为它用于测试就默认可信。

**常见误答：** 先做一个万能平台，细节以后自然会有。

**继续追问：** 哪项需求足以形成第一轮可独立验证的功能？

**回答边界：** 给出一个小工具的输入、结果和错误完成条件。

### 第 2 题：最小功能与扩展边界

**首轮结论：** 先完成有独立价值的小功能，扩展由明确需求和验证成本决定。

读取本地记录、筛选、汇总和保存已经形成完整数据流。远程执行和账号会引入新的协议、状态和安全责任，不是增加几个类就能可靠解决。

本例并发组件独立演示，主汇总无需并行。后续按 Python 学习目标扩展，完整领域课程另行学习。

**常见误答：** 功能越多越工程化，或目录中有 batch 就代表所有路径并行。

**继续追问：** 一个扩展什么时候值得独立成章？

**回答边界：** 说明目标、非目标和具体扩展触发条件。

### 第 3 题：数据流与依赖方向

**首轮结论：** 入口把外部文本适配为明确值，核心按接口处理，结果再由报告层输出。

CLI 选择配置与来源，reader 解析记录，engine 验证和汇总，report 生成稳定结构并提交。核心可以被其他调用者复用，不要求先构造终端对象。

若核心直接读取命令行或全局环境，同一函数行为会依赖隐含状态，测试和复用更难。

**常见误答：** 只要拆成多个文件就有良好依赖方向。

**继续追问：** 把配置放进一个全局模块是否就解决耦合？

**回答边界：** 沿一条真实输入画出调用和返回方向。

### 第 4 题：模块职责与拆分时机

**首轮结论：** 按职责、失败边界和变化原因划分，不按机械行数或函数数量。

reader 管理文件和行协议，engine 负责验证范围和统计，report 表达格式与提交。几项相关函数可同模块，确有复用或替换需求再拆。

抽取后仍需稳定接口和测试，不应让各模块通过隐含全局变量相互影响。

**常见误答：** 文件越多越清晰，或者所有公共函数都放 utils。

**继续追问：** 一种报告格式新增时，哪些层应当受影响？

**回答边界：** 给出一个变化原因与相应模块。

### 第 5 题：公共接口与内部名字

**首轮结论：** 公共接口是可依赖的行为承诺，导出列表不构成权限边界。

说明输入、返回、异常、副作用与版本范围。本例顶层公开记录、汇总结果和 summarize，使用者不需依赖 CLI 内部对象。

Python 中内部名字常仍可访问；是否受兼容承诺由文档与命名约定说明。__all__ 主要影响星号导出，不防止显式访问。

**常见误答：** 只要没写进 __all__ 就绝对不可访问。

**继续追问：** 内部重构怎样避免破坏公共调用者？

**回答边界：** 区分技术可访问与受支持接口。

### 第 6 题：数据类、标注与运行时约束

**首轮结论：** dataclass 和标注不会默认强制字段类型，需要明确校验才能建立运行时约束。

输出 bool。True 可以被普通生成的初始化方法保存，: int 不会自动拒绝。可以在 __post_init__ 检查精确类型和范围，再统一规范化。

静态检查提供运行前提示，运行时接口面对外部数据仍需要验证。

**常见误答：** dataclass 根据标注自动转换并拒绝所有错误输入。

**继续追问：** 为什么耗时除了类型还需有限性与单位约定？

**回答边界：** 说明生成行为和业务约束的区别。

### 第 7 题：frozen 与内部可变对象

**首轮结论：** frozen 限制普通字段重新赋值，不会递归冻结内部对象。

输出 ['A']。tags 仍绑定原列表，append 改变列表内容，没有重新绑定字段。若配置需要稳定值，可使用不可变元组，并说明嵌套成员是否也不可变。

普通数据复制可按边界设计，连接、锁和文件则需要资源接口。

**常见误答：** frozen 等于对任意对象图做深度冻结。

**继续追问：** 两个配置实例共享同一个列表时会出现什么？

**回答边界：** 沿字段绑定与列表内容分别解释。

### 第 8 题：结构化错误与原因链

**首轮结论：** 错误类别与字段供程序判断，文本供人阅读，原因链保留底层来源。

InputError.line 能稳定表达物理位置，消息修改语言或措辞不改变定位字段。转换 JSON、编码或文件错误时保留 cause，避免丢掉原异常。

返回空列表会混淆合法空输入与读取失败；所有异常统一吞掉会使失败无证据。

**常见误答：** 错误消息足够长就不需要类型或字段。

**继续追问：** 报告提交失败又清理失败时，应保留哪项主原因？

**回答边界：** 给出类别、字段与底层 cause 的分工。

## 二、配置、输入与汇总

### 第 9 题：配置来源与显式空选择

**首轮结论：** 空选择可以是明确请求，未提供才使用默认，语义由接口规定。

本例空数组转为空元组，选择零项但仍验证输入；CLI None 表示未提供。or 会把空选择误改为默认全部，改变统计范围。

文件 null、未知字段和非法前层都应按约定报错，不能被后层偶然覆盖隐藏。

**常见误答：** 所有假值都表示没有配置。

**继续追问：** 环境变量为什么只读取声明的键？

**回答边界：** 说明来源、优先级和缺失标记。

### 第 10 题：输入校验与合法范围

**首轮结论：** 类型、值域、有限性、单位和跨字段约束共同构成接口。

max_records 要求精确整数与上限，duration 要求有限秒数且范围明确，status 属于允许集合，编号非空并在规范化后唯一。bool 与 int 的继承关系需要特别区分。

外部 JSON 的数据不因带了注解就可靠；模型与配置应在引发实际副作用前验证。

**常见误答：** json.loads 或类型标注已经做了全部业务检查。

**继续追问：** 为什么重复编号不只是单条记录字段的类型问题？

**回答边界：** 覆盖单条和整组两类约束。

### 第 11 题：规范化与唯一编号

**首轮结论：** 先按明确规则规范化，再按统一标识检查唯一性。

本例去掉编号首尾空白，两者变成同一标识；先比较原字符串可能放过重复。状态则按精确允许值验证，不任意猜大小写或别名。

规范化影响接口语义，应测试并记录；不是所有业务都应删除空白或忽略大小写。

**常见误答：** 规范化只是显示问题，不会影响数据关系。

**继续追问：** 如果以后支持多次尝试，编号需要增加哪个维度？

**回答边界：** 说明具体规则与重复判断时点。

### 第 12 题：JSONL 与物理行号

**首轮结论：** 本例按物理位置报告第三行，解析后还需验证记录协议。

空白行不生成记录，但不应让后续位置重新从一开始编号。JSON 可表示列表、布尔或空值，合法语法不保证是要求的字段对象。

读文件、解码和解析有不同失败原因，保留行号与 cause，不默认打印真实原始内容。

**常见误答：** 只统计成功对象，或者 JSON 能解析就一定是合法记录。

**继续追问：** 多行 JSON 文档为什么不能直接当一行一对象的 JSONL？

**回答边界：** 区分物理来源、语法和协议。

### 第 13 题：单行字节限制与流式处理

**首轮结论：** 总条目数不限制单项体积，字节上限要在无界分配之前检查。

一条超长行也可能占大量内存。用有长度限制的二进制读取，包含换行字节，先判断超限再解码；中文字符常占多个 UTF-8 字节。

逐行生成器只控制读取方式，后续集合和输出仍有成本，因此不能直接称为常数内存。

**常见误答：** 最多一千条就不可能占用大内存，或 len(str) 等于 UTF-8 字节数。

**继续追问：** 读取上限加一字节有什么判断作用？

**回答边界：** 说明条目数、单项体积和解码时机。

### 第 14 题：校验与筛选顺序

**首轮结论：** 输入质量约束覆盖整份来源，筛选只决定统计范围。

所有记录先按协议验证、计入总数并检查唯一性，再选择统计。否则用户换一个条件就能隐藏坏文件，input_total 含义也会漂移。

其他工具可以有不同策略，但必须明确验证范围并提供相应证据，不能默默改变。

**常见误答：** 未选数据永远没有任何验证责任。

**继续追问：** 为什么总记录限制也要包括未选项？

**回答边界：** 解释本例策略与范围。

### 第 15 题：字典覆盖与业务去重

**首轮结论：** 字典会保留同键最后值，这只是容器行为，不是业务去重协议。

输出 2、1、failed，原有一项信息被覆盖。本例拒绝重复，若需求允许多次尝试，就需 attempt、时间或明确合并规则。

不能只看返回字典没有异常就认为没有丢失数据。

**常见误答：** dict 自动选择了正确结果，所以不需额外约定。

**继续追问：** 保留最后一次是否等于最终状态一定正确？

**回答边界：** 说明信息丢失和业务依据。

### 第 16 题：输入总数与选中计数

**首轮结论：** 总数描述输入验证范围，选中数和分类计数描述当前结果范围。

本例 input_total=3、selected_total=1，counts 中 passed=1，其余为零，耗时也仅属于选中项。报告应同时保留这些维度，而不把过滤后范围冒充全部。

退出 0 是汇总器的入口约定，不能推导真实产品无缺陷或未选项通过。

**常见误答：** 所有 total 都应该写成同一个数字。

**继续追问：** 如何给过滤后的通过结论加上清楚范围？

**回答边界：** 给出字段值与结论限制。

### 第 17 题：空输入与空选中集合

**首轮结论：** 保留输入与选中两个数量，工具成功不等于测试质量结论。

空输入二者都为零；有输入但空选择时 input_total 大于零、selected_total 为零。分类字段仍保留完整零值，便于调用方读取稳定结构。

不应计算缺乏口径的百分比或把没有验证的范围当通过。

**常见误答：** 零失败就是所有测试通过，包括零执行。

**继续追问：** 若以后加入通过率，分母和 skipped 应怎样说明？

**回答边界：** 明确空范围与统计口径。

### 第 18 题：一次性迭代与重复消费

**首轮结论：** 迭代器消费后会耗尽，核心应一次完成需要的验证和统计。

输出 6 和空列表。生成器保留的是一次消费状态，不保证重放；再次读取文件要新建来源，而不是复用耗尽对象。

接口若接受一般 Iterable，也不能默认 len、下标或两次遍历都可用。

**常见误答：** 只要原始列表没变，生成器就自动恢复。

**继续追问：** 需要稳定快照时保存列表会付出什么成本？

**回答边界：** 说明状态推进与接口能力。

### 第 19 题：汇总的时间与空间成本

**首轮结论：** 保留的数据结构决定空间成本，流式读取本身不消除它们。

常见哈希假设下处理 n 条记录通常线性时间，编号与耗时保留最多线性空间。本例限制总数和单行字节，约束输入范围。

若扩大规模，应明确误差、去重存储和分块策略；不能用一句生成器省内存替代完整分析。

**常见误答：** 用了 yield 就保证任意规模常数内存。

**继续追问：** 并发 Future 和已完成未消费结果是否也算内存？

**回答边界：** 分析至少输入、集合和输出三个范围。

### 第 20 题：组合与依赖注入的取舍

**首轮结论：** 先按责任和替换需求组合，小接口优先，抽象程度与实际变化匹配。

固定计算可用函数，外部读写与测试成本明显时注入协作者。多种实现共用稳定行为时可用 Callable 或 Protocol 描述，不要求全部继承一个万能基类。

类型接口不自动证明响应语义，替身也不能替代全部真实集成。

**常见误答：** 所有工具都必须先用复杂依赖容器，或注入就代表系统已完整验证。

**继续追问：** 什么情况会让过多回调降低可读性？

**回答边界：** 给一个实际替换边界和维护成本。

## 三、报告与资源

### 第 21 题：结果通道与结构化日志

**首轮结论：** 稳定结果与过程事件分开，运行编号关联本轮，记录编号关联输入对象。

本例 stdout 一份报告，stderr 事件带 run_id、类别和必要统计。case_id 在输入内唯一，run_id 区分不同汇总调用，二者不能互换。

调试文本混进 JSON 会破坏机器读取；日志也不默认包含完整原始数据或环境。

**常见误答：** 人能看懂就可以任意混合通道，或时间相近就足以关联并发记录。

**继续追问：** 报告保存失败时如何避免读取旧 run_id 造成误会？

**回答边界：** 说明通道、编号与证据范围。

### 第 22 题：报告格式版本与发行版本

**首轮结论：** 软件发布与数据格式有不同兼容边界，应分别维护。

内部修复可以保持报告字段，格式含义、单位或字段变化则可能影响读取者。新增字段是否兼容取决于协议，不由版本号本身证明。

版本一致性需要测试和文档，不能只把字符串加一就声称旧调用可用。

**常见误答：** 两个版本永远必须相等，或数字变大就自动兼容。

**继续追问：** 删除旧字段时应怎样安排迁移和回归？

**回答边界：** 给出一个软件变化和一个格式变化。

### 第 23 题：报告提交与旧目标保护

**首轮结论：** 准备完成后才提交，失败保留旧目标和主原因，资源清理受所有权约束。

先序列化避免类型错误截断旧文件，再同目录写临时文件、关闭并替换。失败只删除本次取得的文件，其他 keep.tmp 不属于当前任务。

清理失败要保留证据，不能覆盖原提交错误；替换也不保证断电持久性、多文件事务或并发仲裁。

**常见误答：** 退出时删光所有 tmp 最干净，或 os.replace 是通用事务。

**继续追问：** 为什么目标与输入或配置相同时要提前拒绝？

**回答边界：** 说明提交点、所有权与限制。

### 第 24 题：部分输入失败与发布策略

**首轮结论：** 本例整体输入失败不发布新报告；部分结果必须有另外的明确协议。

内存中已做过一些工作不等于形成可接受的最终结果。CLI 关闭自身取得的 reader，保留旧目标，返回输入错误。

若支持部分结果，需表示完成、失败、取消、未读取范围与运行关联，不能只返回成功项而丢掉其余状态。

**常见误答：** 发生异常就说明之前没处理任何内容，或可以静默只报成功部分。

**继续追问：** 旧报告仍存在时如何判断它是不是本次？

**回答边界：** 区分准备状态与发布证据。

### 第 25 题：线程数与在途 Future 上限

**首轮结论：** 运行数量和已提交未交付数量是不同资源范围。

线程池限制同时运行工作，提交一百万个 Future 仍可保留大量输入与状态。本例只在 pending 未满时继续读和提交，以完成记录交付后再补充。

结果按输入 index 关联，不假设完成顺序。主汇总是顺序读取，不把并发组件误说成所有路径的执行方式。

**常见误答：** 线程有限就自动保证所有内存有界。

**继续追问：** 输出特别大或消费者很慢时，还应观察什么？

**回答边界：** 区分运行、排队和已完成未消费。

### 第 26 题：取消、预算与实际收尾

**首轮结论：** 预算约束调度和结果接受，正在运行工作需要协作和底层限时，收尾可越过预算。

取消未开始项较直接，运行中 Future 通常不能靠 cancel 强制中断。输入迭代也可能阻塞，必须声明来源与 worker 可收尾前提。

本例 finally 取消排队项、等待已开始项并关闭输入；这保证责任明确，不是硬实时进程终止。

**常见误答：** 主循环超时就代表任意线程、远端任务与副作用全部回滚。

**继续追问：** 如果确实需要强制终止，应新增什么平台边界？

**回答边界：** 说明停止请求、结果接受和实际资源结束。

### 第 27 题：生成器部分消费与关闭

**首轮结论：** 资源持有到消费范围，提前停止时需由拥有者显式结束。

生成器暂停期间 finally 尚未完成，线程池和来源可能仍被持有。用 closing 或 try/finally 调 close，才能按接口安排取消与收尾。

for 的 break 不等于对任意迭代器调用 close，不能依赖某个实现恰好立即销毁对象。

**常见误答：** break 总会执行所有来源的关闭方法。

**继续追问：** 尚未消费就关闭生成器与消费到第一项后关闭，有何执行差异？

**回答边界：** 跟踪取得、暂停和退出时点。

## 四、自身测试与测量

### 第 28 题：单元、集成、入口与安装测试

**首轮结论：** 不同测试边界提供互补证据，不能相互替代。

核心单测覆盖规则，文件集成覆盖编码和生命周期，main 测试参数与组件协作，真实命令和干净安装再验证入口与分发配置。

不能按调用函数个数分类，也不能因为 mock 全通过就认定真实安装和文件读取可用。

**常见误答：** 测试越靠外层就可以删除所有内部测试，或一个 pytest 名字固定测试层次。

**继续追问：** 哪一层最容易发现漏打包文件？

**回答边界：** 给出每层一项独立证据。

### 第 29 题：核心汇总的高价值边界

**首轮结论：** 覆盖空、类型、范围、规范化、重复、筛选、总量和一次性消费。

选择合法零耗时、上界、bool、非有限值、空编号、未知状态；再测未选项重复和上限、空选择、三类零字段与生成器。每条预期来自明确接口。

只随机生成许多正常记录不能替代关键边界。输入不被修改、返回不共享也属于客观接口。

**常见误答：** 测过一份正常文件就说明所有状态和边界都正确。

**继续追问：** 同样数量的用例，为什么应优先覆盖规范化后重复？

**回答边界：** 把每组输入关联到一种缺陷风险。

### 第 30 题：CLI 注入与真实入口证据

**首轮结论：** 注入验证适配逻辑，真实入口验证安装器生成的命令和实际导入来源。

main 可快速检查参数、退出、通道和写入调用，但可能完全没执行 __main__.py 或安装脚本。仓库工作目录也可能掩盖未安装源码。

从外部目录用新环境执行命令，并检查 __file__ 与发行版本，才能补交付证据。

**常见误答：** 调用过 main 就说明任何人安装后都能运行命令。

**继续追问：** 为什么只测试 python -m 仍不能完全代替 console script？

**回答边界：** 区分两个入口及其配置来源。

### 第 31 题：故障注入与原始错误

**首轮结论：** 核对主失败、旧内容、资源状态和清理证据，避免覆盖最初原因。

注入替换错误，确认旧报告保持、本次临时文件清理或有明确清理失败记录，其他文件不变，异常链仍指向原提交失败。

成功结果也要有测试，不能用一个总是抛错的实现冒充有效防护。并发测试用受控事件建立顺序，避免偶然 sleep。

**常见误答：** 最后一个异常最容易看到，所以原错误不重要。

**继续追问：** 输入中途失败时 writer 不应被调用，怎样检查？

**回答边界：** 说明状态、交互和原因链。

### 第 32 题：回归测试与错误候选

**首轮结论：** 执行过代码不等于断言正确，受控错误候选能暴露缺少的检查。

测试可能只比较 truthy、actual 自身或几种正常结果。让正确候选通过，再故意漏掉重复、bool 计数或一次性输入，观察是否失败。

候选只是有限检查，不能宣称需求完整。修复后保留原触发条件及相关回归，不为迎合当前实现改 expected。

**常见误答：** 覆盖率百分之百就证明所有需求正确。

**继续追问：** 等价变异为什么不应简单当作测试缺陷？

**回答边界：** 给出一项会被弱断言放过的错误。

### 第 33 题：性能测量的明确范围

**首轮结论：** 只能对已说明的输入、环境和代码范围提供测量证据。

本例测记录构造与内存汇总，包含 tracemalloc 开销，不含文件、网络或安装。需要代表性规模、重复和比较条件，再解释波动。

Python 工具测量与系统压力、硬件稳定性属于不同目标，不把一个短计时推广成全局结论。

**常见误答：** 一次跑得快就是所有输入都更快，或峰值小等于系统没有内存问题。

**继续追问：** 若真正瓶颈是磁盘读取，纯核心计时能说明什么？

**回答边界：** 列出包含和排除的开销。

### 第 34 题：热点与内存工具的限制

**首轮结论：** 计时、调用热点、Python 分配和进程资源是不同观察口径。

timeit 便于重复局部代码，cProfile 看调用累计成本，tracemalloc 看追踪到的分配与峰值，不等于全部原生内存。测量自身也有开销。

定位后优化实际热点，并重验行为、错误与资源约定。不要为了降低一项指标破坏证据和接口。

**常见误答：** tracemalloc 峰值就是整机或进程所有内存。

**继续追问：** 对象释放后进程指标不降，为何不能立刻证明泄漏？

**回答边界：** 说明至少两种指标及不能推出的结论。

## 五、安装、交付与维护

### 第 35 题：运行、开发与构建依赖

**首轮结论：** 使用、开发验证和生成分发物有不同依赖集合。

工具运行只用标准库；pytest、Ruff 供测试检查；Hatchling 是构建后端。它们的声明和锁定角色不同，不能把开发环境所有库都列成用户必需。

锁文件提高复现性，仍要更新、兼容与安全维护。复制 .venv 也不是可靠分发方式。

**常见误答：** 所有安装过的库都是运行依赖，或锁文件自动证明兼容。

**继续追问：** 构建隔离环境从哪里获得后端？

**回答边界：** 说明三类依赖及对应使用时机。

### 第 36 题：src 布局与导入路径

**首轮结论：** 减少仓库根目录带来的偶然导入，不代替构建物验证。

源码放 src 下，通常需要正确安装才能 import；这有助于发现依赖路径缺失。但可编辑安装仍关联源码，漏打包资源等问题可能未暴露。

最终从仓库外新环境运行 wheel，检查实际导入位置，才能排除更多路径干扰。

**常见误答：** src 自动修复所有导入和分发错误。

**继续追问：** PYTHONPATH 指向源码时会掩盖什么？

**回答边界：** 说明布局作用和独立验证必要性。

### 第 37 题：可编辑安装与交付物

**首轮结论：** 可编辑安装借用源码，wheel 仅包含构建时明确收集的文件与元数据。

遗漏模块、资源、入口或运行依赖时，开发环境仍可能工作。构建后检查 wheel，并在新环境只安装它，不再依赖 checkout。

构建成功也只是产物生成，不等于普通用户可以按文档运行。

**常见误答：** 能 editable install 就等于正式发行正确。

**继续追问：** 从 sdist 再构建 wheel 为什么还能补一层检查？

**回答边界：** 给一个被源码关联掩盖的错误例子。

### 第 38 题：发行包、导入包与命令名

**首轮结论：** 它们分别是安装名、导入名和终端命令名，由项目元数据建立联系。

发行包安装导入包及元数据，[project.scripts] 指向 study_results.cli:main，安装器生成相应命令；__main__.py 支持模块入口。

三种名字不必相同，重命名文件夹也不自动更新声明。真实命令生成与帮助、错误退出需要运行测试。

**常见误答：** 安装名必须可原样写进 import，或只有命令名才算包名。

**继续追问：** 为什么连字符发行名与下划线导入名常见？

**回答边界：** 按使用位置区分三种名字。

### 第 39 题：构建后端与分发格式

**首轮结论：** 构建工具调用后端生成源码或已构建分发物，标签不替代兼容测试。

本例 uv build 先构建 sdist，再从它生成 wheel；Hatchling 按配置收集文件和元数据。wheel 便于安装，sdist 供源码构建。

标签表达分发兼容声明，不保证所有 Python 和系统已经验证，也不意味着所有外部行为都跨平台相同。

**常见误答：** wheel 就是源码改个扩展名，或 any 表示无需测试。

**继续追问：** 为何验收模式要恰好匹配一个 wheel？

**回答边界：** 说明流程、产物和证据范围。

### 第 40 题：干净安装的验证条件

**首轮结论：** 在仓库之外的新环境只安装目标产物，移除路径干扰并检查真实来源和入口。

确认导入 __file__ 在新环境，发行版本一致，console script 和 python -m 均可运行，再检查正常、空输入与错误退出。父进程环境的 PYTHONPATH 等不能悄悄指回源码。

脚本应有临时资源和子进程上限；本地通过只对应实际平台与版本，不预填其他组合的结果。

**常见误答：** 新开一个终端就算干净环境，或在源码根目录 import 成功就足够。

**继续追问：** 为何卸载开发包后仍在根目录运行可能继续假成功？

**回答边界：** 给出环境、目录、安装和来源四项条件。

### 第 41 题：最低版本与平台兼容

**首轮结论：** 声明表达支持范围，实际测试提供对应组合的证据，两者应对齐。

需要在最低版本和目标平台运行关键路径，特别是语法、文件句柄、路径和命令脚本。CI 可以提供矩阵验证，但配置文件存在不等于 job 通过。

未测范围应明确，新增依赖或 API 后重新核对最低版本，不把新环境接口写成所有版本都有。

**常见误答：** 高版本能跑就自动证明低版本，或声明大于等于代表未来全部版本永远兼容。

**继续追问：** Windows 与 Linux 的报告替换为什么都值得验证？

**回答边界：** 区分声明、实际证据与未来维护。

### 第 42 题：静态检查、测试、构建与 CI

**首轮结论：** 各检查层解决不同问题，CI 把它们按对应提交自动执行。

静态检查找源代码问题，测试看行为，构建看产物生成，安装看分发可用；CI 准备环境并保存结果。任一层通过不补齐其他层证据。

应按失败步骤定位，而不是只看一个绿灯。自动执行也不会自动设计独立预期和合理风险范围。

**常见误答：** 有 CI 就可以不写本地可运行测试，或 Ruff 通过代表业务正确。

**继续追问：** CI 与本地结果不同时，首先比较哪些环境和命令？

**回答边界：** 给出各层至少一种独立失败。

### 第 43 题：对应提交与检查产物

**首轮结论：** 核对提交、job、版本、退出与产物，不能把配置或旧运行当新证据。

检查矩阵各项状态和失败步骤，保留 JUnit XML、构建文件及相应运行。artifact 只是本轮文件集合，不自动证明内容或上传范围正确。

公开日志与数据使用虚构内容，不上传凭证和个人环境；本地构建与远端结果各自标注。

**常见误答：** 仓库里有 YAML 就说明所有平台都过了，或旧绿色运行代表新提交。

**继续追问：** 失败时仍保存报告对定位有什么帮助？

**回答边界：** 指出对应关系与最小证据。

### 第 44 题：兼容维护与适度抽象

**首轮结论：** 围绕稳定接口说明变化，补回归与文档，按真实需要增加抽象。

检查调用签名、字段含义、单位、默认和错误类别，区分数据格式与发行版本。先通过组合替换边界，多工程确有复用再提插件或公共包。

维护还包括依赖更新、失败证据、安装和使用文档，不只是第一次代码行数。

**常见误答：** 提前搭好所有扩展点就没有维护成本，或版本号变化自动解决旧用户问题。

**继续追问：** 什么时候拆成独立插件课比继续塞入当前章节更合适？

**回答边界：** 给出具体变化、受影响使用者与验证。

### 第 45 题：从需求到交付的学习复盘

**首轮结论：** 用可核对的接口和执行证据说明全过程，不靠罗列工具名或虚构工作经历。

先讲输入协议、筛选与结果范围，再沿模型、配置、读取、核心、报告、CLI 解释职责和错误。说明记录、字节、并发与在途上限，取消和提交如何收尾。

给出核心与文件测试、故障注入、Ruff、构建和干净安装证据，区分本地与 CI。说明未实现的远程执行、强制线程终止、事务和持久性，后续按独立目标扩展。

**常见误答：** 只说用了 pytest、线程池和打包，就等同解释了工具质量。

**继续追问：** 如果只允许再补一项检查，哪种剩余风险最值得优先？

**回答边界：** 沿一次真实学习运行解释原因、证据和限制。

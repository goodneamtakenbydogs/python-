# 第 16 章完整讲义：Python 测试工具开发

第 15 章已经把执行、解析、预算和清理组合成小脚本。本章继续把明确需求组织为有公共接口、自身测试、安装入口和交付验证的 Python 工具。**工具**是一组供使用者稳定调用的功能；**交付**不仅是把源码发出去，还包括依赖、构建产物、运行方式和证据。

主线案例是 [测试结果汇总工具](./示例工具/README.md)：读取本地虚构 JSONL，校验、筛选、汇总并生成报告。JSONL 指每个非空行是一份 JSON 值，本例要求每行一个记录对象。它不连接真实系统。资料与 Notebook 使用 CPython 3.12.13；示例工具的独立开发环境以 uv.lock 固定，当前为 pytest 9.2.0、Ruff 0.16.10。源码声明 Python 3.11 及以上，本地证据与持续集成版本范围分别说明。

## 1. 工具需求与目标使用者

先问谁会用、输入是什么、希望得到什么，以及怎样判断完成。对于一位希望比较小批量测试结果的使用者，“读记录、按状态选取、输出数量与耗时”是可验证需求；“做一个通用测试平台”还不是足够小的目标。

本例要求编号唯一、状态明确、输入有上限，坏数据不能被筛选条件隐藏；报告带运行编号，保存失败不发布半份新结果。**完成条件**包括业务行为、错误路径和安装后的入口，而不是只看开发者机器上某个文件能运行。

不先引入账号、页面、数据库和分布式服务。后续确有独立需求时再扩展，当前案例保持 Python 工具开发主线。

## 2. 最小功能与非目标

**最小功能**是能独立解决一项明确任务的范围。本例从三种状态 passed、failed、skipped 开始，只读本地记录，提供状态筛选、总数限制和 JSON 报告。

它没有自动执行测试、判断真实产品质量或查询远程任务。主汇总流程也不需要把每行数据交给线程池；额外的 batch 模块专门用于观察有限批量组件，不能因为目录里有并发代码就声称主命令会并行。

先完成一个小功能，再增加配置、结果和测试，最后验证安装。抽象和依赖都应服务于当前需求，避免尚未使用就预建大量层级。

## 3. 从输入到报告的数据流

**数据流**描述数据经过哪些步骤、每一步产生什么。先画出实际过程，才能检查模块是否混入不属于自己的责任。

```text
CLI 实参、配置文件与指定环境变量
→ Config：确定筛选状态与记录上限
→ reader：按行读取并解析 CaseRecord
→ engine：验证重复和上限，筛选并生成 Summary
→ report：转为带 schema_version、run_id 的报告
→ stdout 或显式文件目标
```

CLI 是 command-line interface，即命令行适配层。它负责输入文本、环境、输出通道和退出状态；核心汇总函数不应反过来读取 sys.argv 或调用 sys.exit。**依赖方向**是代码调用和导入朝向的关系，通常让入口依赖核心，让核心不依赖入口。

## 4. 模块职责与目录结构

模块是组织相关名字和行为的单元。本例采用 src 布局，把可安装源码与仓库其他文件分开，避免从根目录运行时碰巧导入了未安装源码。

```text
示例工具/
├── pyproject.toml、uv.lock
├── src/study_results/
│   ├── models.py、errors.py       数据与稳定错误类别
│   ├── config.py                 配置值的解析和校验
│   ├── reader.py、engine.py      文件协议与汇总规则
│   ├── report.py、cli.py         报告提交与终端适配
│   ├── batch.py                  独立的有限批量组件
│   └── __init__.py、__main__.py
├── tests/、examples/
└── scripts/                      安装验收与测量
```

一个职责不必对应一个类，几个紧密相关函数也可以在同一模块。这里拆分是因为文件、配置、核心规则和输出有不同失败方式与测试边界，而不是因为“文件越多越专业”。

## 5. 公共接口与内部实现

**公共接口**是使用者被允许依赖的名字与行为，包括输入、结果、异常和副作用。__all__ 可描述星号导出，不是阻止访问内部实现的权限机制。

本例顶层导出 CaseRecord、Summary 和 summarize。命令行形式可以变化，但普通调用者不必先构造 argparse.Namespace 才能汇总。内部帮助函数仍可能被技术上访问，是否受兼容承诺要在文档说明。

```python
def summarize_values(values):
    return {"count": len(values), "total": sum(values)}

data = [2, 3]
result = summarize_values(data)
print(result, data)
```

例子只展示“输入与返回记录”的接口思路。实际工具进一步支持一次性迭代输入，并表达更明确的数据模型。

## 6. 数据类与运行时约束

**数据模型**规定字段和语义；dataclass 根据字段生成初始化、表示和比较等方法，但类型标注本身不等于运行时校验。

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Record:
    case_id: str
    count: int
    def __post_init__(self):
        if type(self.case_id) is not str or not self.case_id:
            raise ValueError("case_id")
        if type(self.count) is not int or self.count < 0:
            raise ValueError("count")

record = Record("C-demo", 0)
print(record)
try:
    Record("C-demo", True)
except ValueError:
    print("invalid count rejected")
```

本例 CaseRecord 还统一去除编号首尾空白，将耗时转为有限非负 float，并限制到 86400 秒。这是教学协议的明确范围，不是所有测试记录的通用标准。校验集中在模型，直接调用和文件解析都能建立同一约束。

## 7. 不可变外层与嵌套共享

frozen=True 限制普通字段重新赋值，不会递归冻结字段中的列表或字典。Config 使用元组保存状态，Summary 使用数值，减少跨调用意外共享。

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Options:
    tags: list

options = Options([])
options.tags.append("local")
print(options.tags)
```

修改列表内容没有重新绑定 tags 属性，因此仍可发生。需要独立可变状态时按明确边界新建或复制；文件、锁和连接需要生命周期接口，不能机械 deepcopy。第 9 章的对象图仍适用于多模块工具。

## 8. 错误类别与结构化定位

**结构化错误**把可供程序使用的信息放在字段中，不要求调用方解析人类消息。例如 InputError 保留物理行号 line，ConfigError、ReportError、Cancelled 分别表达配置、提交和取消。

```python
class InputError(ValueError):
    def __init__(self, message, *, line):
        super().__init__(message)
        self.line = line

try:
    raise InputError("invalid record", line=7)
except InputError as error:
    print(error.line, str(error))
```

转换底层错误时用 raise ... from ... 保留原因。错误类别用于分支，消息用于说明，traceback 是异常调用路径。不要把所有失败改成空列表，否则“合法空输入”与“读取失败”会混在一起。

## 9. 配置值与配置来源分离

配置解析函数接收已经取得的文件内容、环境映射和 CLI 覆盖，不在导入模块时读取真实环境。本例规定默认 → 文件 → 指定环境变量 → 显式 CLI，并校验每层实际提供值。

```python
defaults = {"statuses": ("passed", "failed", "skipped")}
provided = {"statuses": []}
chosen = defaults["statuses"] if provided.get("statuses") is None else tuple(provided["statuses"])
print(chosen)
```

空数组明确表示选择零项，不能因是假值就变回默认全部。文件 null、未知字段或非法前层不因为后面覆盖就忽略。仅识别指定环境变量，记录生效来源时也不打印完整环境。

## 10. 配置不可变与规范化

**规范化**把等价输入变成统一表示，例如状态数组转为约定顺序的元组，编号去首尾空白。先验证再规范化，避免把非法状态悄悄修成另一项合法含义。

Config 的 max_records 要求 1～10000 的精确整数，不接受 True。CLI 未提供可用 None 表达，文件中的 None 则不是有效上限。配置对象创建后作为值传递，核心不依赖一个随处可修改的全局配置字典。

规范化还影响唯一性：C-A 与首尾带空白的 C-A 在本例中属于同一编号，重复检查必须用规范化后的值。

## 11. 按行解析与物理行号

JSONL 逐行提供记录，空白行是否跳过由协议规定。本例跳过空白行，但错误仍指向文件中的物理位置，而非“这是第几个有效对象”。

```python
import json

lines = ["\n", '{"case_id":"C-A"}\n', "bad\n"]
for number, text in enumerate(lines, 1):
    if not text.strip():
        continue
    try:
        data = json.loads(text)
    except ValueError:
        print("invalid line", number)
    else:
        print(number, data["case_id"])
```

json.loads 成功只说明文本能解释为某个 JSON 值，还要检查顶层、字段、类型和范围。文件层明确 UTF-8，解析错误保留行号，不把真实原始行默认写入公共日志。

## 12. 流式读取与单行上限

**流式处理**是在需要时逐步读取和消费，不先把全部输入留在内存。本例用二进制 readline(MAX_LINE_BYTES+1)，先判断单行字节上限，再解码与解析。

如果直接无界 readline，一行特别大仍可能占大量内存；只限制最终记录数不能解决这一问题。65536 字节包含换行，UTF-8 中文的字节数也不同于字符数。上限、单位和边界都需要测试。

流式不等于所有后续操作都是常数内存。reader 只负责单行，engine 还保留唯一编号集合及选中耗时，本例通过 max_records 进一步控制范围。

## 13. 验证、筛选与汇总的顺序

本例先校验所有记录，再筛选。未选中的 failed 记录也必须字段合法、编号不重复，且计入输入上限；否则用户换个筛选条件就能隐藏坏文件。

```python
records = [{"status": "passed", "valid": True}, {"status": "failed", "valid": False}]
selected = [row for row in records if row["status"] == "passed"]
print(all(row["valid"] for row in selected))
print(all(row["valid"] for row in records))
```

先过滤再验证会得到不同结论。并非所有工具都必须采用本例策略，但协议要说明验证范围，测试要检查未选数据中的错误是否按约定暴露。

## 14. 唯一编号与重复处理

用字典按编号保存结果会覆盖旧项，不能默认“去重”符合业务。本例要求同一输入内编号唯一，遇到重复报告 InputError 并保留出错行。

```python
rows = [("C-A", "passed"), ("C-A", "failed")]
mapping = dict(rows)
print(len(rows), len(mapping), mapping["C-A"])
```

重复可能是重复导入、不同尝试或不同任务；若未来要支持多次尝试，应新增 attempt 或明确合并规则，而非不加说明保留最后一条。跨次运行使用 run_id 关联，不把它与每条 case_id 混为一谈。

## 15. 输入总数与选中统计

Summary 同时保留 input_total 与 selected_total，counts 和 duration_seconds 只属于选中集合。这样能解释“输入三条、只选一条”而不丢失范围。

```python
statuses = ["passed", "failed", "skipped"]
selected = [value for value in statuses if value == "passed"]
print(len(statuses), len(selected), selected.count("passed"))
```

空输入合法返回零统计，不表示产品已通过测试。过滤后没有 failed 也不能证明被过滤集合正确。本例退出码 0 表示工具完成汇总且选中项无 failed；这个入口语义不能被扩大为总体质量保证。

## 16. 复杂度与明确的资源上限

设实际读到 n 条记录，正常哈希假设下，唯一性检查与汇总通常是 O(n) 时间；编号集合与耗时列表最多 O(n) 空间。本例最多 10000 条，单行也有限，因此不是无上限积压。

math.fsum 改善一组浮点数累加的数值表现，不把浮点变成无限精度实数。若目标规模扩大，可按明确误差要求改累计策略或采用分块存储，不能只把生成器语法贴上去就说内存恒定。

输入字节、解析对象、编号集合、Future 和输出都属于资源分析范围。先测量有代表性的路径，再优化真正的热点。

## 17. 一次性迭代输入与所有权

可迭代对象不保证能重放。核心 summarize 一次遍历，不先 len(records)，也不消费两遍来先计数再求结果。

```python
values = (number for number in [1, 2, 3])
print(sum(values))
print(list(values))
```

第二次消费已耗尽。数据完整性依赖正确的一次处理；需要重试读取文件时重新建立来源，不能重用旧生成器。谁取得文件范围，谁负责结束它；核心处理调用方的迭代器时不应随意关闭任意外部资源，CLI 则显式关闭自身取得的 reader。

## 18. 组合、注入与边界替换

**组合**是把多个职责清楚的组件连接起来；**依赖注入**是由外部提供协作者。本例 main 可注入 reader、writer，核心又可以不经过 main 直接调用。

单元测试可以给固定记录，入口测试可以核对写入目标和报告，真实文件测试补充编码与资源证据。不要把 summarize 本身替换成固定值后声称验证了汇总规则。

接口足够小且确有多种实现时，可以用 Callable 或 Protocol 描述约定。Protocol 是按所需成员表达的结构化接口，不会默认对业务数据做运行时验证；不必为了类型标注先建立万能基类。

## 19. 结构化日志与稳定报告

报告是给使用者读取的稳定结构，日志是过程证据。stdout 一份 JSON，stderr 的事件带 run_id、类别和必要统计，机器可明确区分两种通道。

```python
import json

event = {"event": "summary_finished", "run_id": "R-demo", "selected_total": 1}
print(json.dumps(event, sort_keys=True))
```

每次执行编号可以不同，但字段语义稳定。不能因为日志时间相邻就推断属于同一输入，不能把调试 print 混入结果。示例只保存虚构编号和摘要，不输出完整环境、身份信息或原始业务内容。

## 20. 报告结构版本与发行版本

**schema_version** 表示报告格式的约定版本；发行版本描述发布的软件包版本。两者相关但不同：工具修复内部算法可以不改报告字段，报告语义变化则可能需要专门的格式迁移。

本例报告 schema_version=1，发行版本 0.1.0。新增、删除字段或更改单位时，应说明旧读取者的行为；不能只改版本字符串就声称兼容。

回归测试保留一份明确输入与独立预期结构，同时避免把随机 run_id、真实时间或排版空格当稳定业务规则。序列化顺序也不应成为无约定的隐藏接口。

## 21. 文件提交与旧报告保护

先完全汇总，再生成报告、序列化到内存、同目录写临时文件、关闭并替换目标。**提交点**是正式路径切换到新内容的时刻，之前的错误不应截断旧报告。

第 15 章已经解释 os.replace，本章将它放进独立 report 模块并直接测试。序列化失败没有临时文件，替换失败清理本次临时文件并保留旧目标，清理失败记录证据而不覆盖原提交错误。

它不保证断电持久性、多文件事务或并发写入仲裁。输出路径不得与输入或配置相同；用户明确指定的报告保存失败时，入口也不能宣布本次输出成功。

## 22. 部分失败与证据范围

输入第二条错误时，第一条可能已经在内存累计，但本例不返回半份 Summary，也不提交新文件。旧报告仍存在也不属于本次成功，应对照 run_id。

```python
items = ["valid", "invalid"]
prepared = []
published = None
try:
    for item in items:
        if item == "invalid":
            raise ValueError("bad input")
        prepared.append(item)
    published = tuple(prepared)
except ValueError:
    pass
print(prepared, published)
```

这是“准备与发布分开”的内存示意，不代表数据库事务。若未来允许部分结果，必须把已完成、失败、取消和尚未读取范围分别表示，不能静默丢掉失败项。

## 23. 有限批量组件与在途数量

可选 batch.map_bounded 为有限输入提供线程执行，限制 workers 与 max_in_flight。前者约束运行工作线程，后者限制已提交且尚未交付结果的 Future；Future 表示一项工作的状态与结果。

```python
workers = 2
max_in_flight = 3
submitted_not_yet_consumed = ["F-A", "F-B", "F-C"]
print(len(submitted_not_yet_consumed) <= max_in_flight)
print(workers <= max_in_flight)
```

这只是数量关系，不运行任务。真实组件只有 pending 集合未满才消费和提交输入，按 Future 映射恢复输入序号。错误结果保留 error_type，不把返回列表等同于全部任务成功。

## 24. 完成顺序、取消与时间预算

并发完成顺序不必等于输入顺序，用 index 关联，不依赖偶然调度。协作取消在提交或消费检查点结束，取消未开始项并等待已开始项收尾。

budget 用单调时钟限制继续调度和接受结果，不能强制打断任意线程、阻塞的输入迭代或外部副作用。线程池 shutdown(wait=True) 的收尾可能越过预算，本例文档明确这一限制。

异常发生后也不能只退出主循环留下后台工作。单项限时、整体停止、输出关联和实际资源清理是不同责任；若未来需要强制进程终止，应另设平台相关接口和验证。

## 25. 生成器退出与资源收尾

惰性 API 把资源生命周期延长到消费期间。调用者只取第一项就停止时，应关闭自己取得的批量迭代器；生成器的 finally 才能确定运行。

```python
from contextlib import closing

events = []
def values():
    try:
        yield 1
        yield 2
    finally:
        events.append("closed")

with closing(values()) as source:
    print(next(source))
print(events)
```

batch 退出时还会等待运行项并关闭其取得的输入生成器。不要把 for 循环中的 break 误当自动调用任意迭代器的 close。资源所有权越清楚，提前停止和失败路径越容易验证。

## 26. 核心组件的单元测试

**单元测试**围绕较小边界验证规则，本例直接创建 CaseRecord、调用 parse_line 和 summarize，检查空输入、过滤、类型、边界、重复与一次性消费。

```python
def totals(statuses):
    return {name: statuses.count(name) for name in ("passed", "failed", "skipped")}

assert totals([]) == {"passed": 0, "failed": 0, "skipped": 0}
assert totals(["passed", "failed"]) == {"passed": 1, "failed": 1, "skipped": 0}
```

教学函数只展示独立预期，正式工具支持迭代输入并分离输入与选中统计。测试自己也可能写错；正常实现要通过，故意漏计、忽略未选数据错误或吞异常的实现应被识别。

## 27. 文件、入口与安装测试

**集成测试**验证组件真实协作，例如 UTF-8 文件、物理行号、错误传播与报告替换。CLI 测试再核对命令实参、退出码、两个通道和文件结果。

调用 main 的测试速度快、可注入依赖，但不能证明 console script 正确生成。真实 `python -m` 补一层入口证据；在全新环境运行安装后的命令，再验证分发配置。几层测试互补，不以测试函数数量分类。

本例还检查从其他工作目录运行，避免仓库位置恰好进入 sys.path 造成假成功。测试私有内部实现时也应考虑维护成本，优先稳定外部行为。

## 28. 故障注入与清理错误

**故障注入**在指定边界让依赖失败，检查传播、证据和不应发生的下一步。报告替换器可注入 PermissionError，reader 可在中间抛 InputError，批量 worker 可一项失败而其他项仍有明确结果。

验证不能只看最终字符串：非法配置不读输入，输入失败不调用 writer，报告失败不向 stdout 发布成功，提前取消不继续提交，清理后原错误仍可定位。

同步测试用事件建立明确顺序，而不是靠偶然 sleep 制造并发。需要演示预算时用可控时钟或受控边界，测试本身也必须有防止挂起的限制。

## 29. 回归数据与断言质量

修复一个边界后，保留触发条件与独立预期。代码覆盖率能指出哪些语句或分支没走到，不能证明过滤范围、报告含义和错误优先级都正确。

```python
def broken_count(values):
    return len(values) + 1

actual = broken_count(["A"])
print(actual == actual)
print(actual == 1)
```

第一项检查毫无区分能力。可以用受控错误候选检查测试，或比较输入重排后的关联等性质，但性质也需来自明确约定。不能为让测试通过把 expected 改成当前输出。

## 30. 性能测量的对象与范围

**性能测量**要说明测什么、输入规模、环境和包含哪些开销。本章限于 Python 工具的构造、解析、汇总和内存，不是服务器压力或硬件稳定性测试。

```python
import timeit

elapsed = timeit.timeit("sum(range(1000))", number=20)
print(elapsed >= 0)
```

这个小例子只测所给表达式的重复执行，不能代表整项工具耗时。正式 benchmark_core 同时记录记录数、perf_counter 耗时和 tracemalloc 峰值，并说明包含记录构造与追踪开销、不含文件与安装。

## 31. 热点、峰值内存与优化验证

cProfile 帮助观察调用与累计时间，tracemalloc 追踪 Python 分配，不等于进程全部原生内存。峰值受输入对象、编号集合、临时结果与测量自身影响。

```python
import tracemalloc

tracemalloc.start()
values = [str(number) for number in range(100)]
current, peak = tracemalloc.get_traced_memory()
print(peak >= current >= 0, len(values))
tracemalloc.stop()
```

先用有代表性的规模比较完整路径，再优化热点；优化后重跑正确性、错误和资源测试。不要把小样本时间差当普遍结论，也不要为减少一项分配破坏编号或失败证据。

## 32. 发行包、导入包与项目名

**发行包**是供安装工具管理的软件单元，**导入包**是 Python import 使用的名字。示例发行名 study-results-demo，导入名 study_results，命令名 study-results，三者可以不同。

```text
发行包 study-results-demo
→ 安装 src/study_results 中的导入包
→ 注册 study-results 命令
→ 命令调用 study_results.cli:main
```

项目根目录名也不是导入协议。不要把文件夹重命名当成完整分发配置；包中需要的资源、版本和入口都由构建与安装验证确认。

## 33. 运行依赖、开发依赖与锁文件

运行依赖是工具使用者执行功能必须安装的库，开发依赖用于测试、检查和构建等工作。本例运行依赖为空，pytest 和 Ruff 放开发组；Hatchling 是构建后端，供生成分发产物。

pyproject.toml 记录允许范围与项目元数据，uv.lock 记录解析出的版本。锁文件提高可复现性，不保证跨所有系统永远相同，也不是漏洞或兼容性证明。

`uv sync --frozen --group dev` 使用现有锁而不更新它，适合自动检查；修改依赖范围后，应主动更新锁并验证。不要把某个开发者 .venv 目录复制给其他人当交付。

## 34. 可编辑安装与命令入口

**可编辑安装**使开发环境的导入关联到源码，修改可直接用于开发测试。它很方便，但可能掩盖漏打包文件或工作目录依赖。

本例在示例工具目录执行 uv sync，形成独立环境，不改变前十五章环境。`[project.scripts]` 指定 study_results.cli:main，安装器生成对应命令；__main__.py 支持 `python -m study_results`。

帮助、版本、正常输入、错误输入和从其他目录调用都要检查。打包后的命令入口是否存在，不能由可编辑安装中手工运行某个 .py 文件来证明。

## 35. 构建后端、sdist 与 wheel

**构建后端**根据源码和配置生成分发产物；本例使用 Hatchling，uv 作为调用构建流程的工具。**sdist** 是源码分发包，**wheel** 是便于安装的已构建分发包。

```text
在示例工具目录执行：
uv build

生成：
dist/study_results_demo-0.1.0.tar.gz
dist/study_results_demo-0.1.0-py3-none-any.whl
```

本次构建先生成 sdist，再从它构建 wheel，帮助暴露遗漏源码的情况。py3-none-any 表达构建标签，不等于已在所有 Python 和系统验证。wheel 是 ZIP 格式，但不要靠手工改归档拼一个看似有效的包。

## 36. 干净环境验证构建产物

**干净环境验证**把构建产物安装到新的环境并从仓库之外运行，排除源码路径与开发依赖的偶然帮助。本例 scripts/verify_wheel.py 执行这条路径。

```text
uv run python scripts/verify_wheel.py "dist/*.whl"
```

模式必须恰好匹配一个 wheel，避免旧产物被误测。脚本在外部临时目录建立新环境，只安装该 wheel，移除 PYTHONPATH 等来源干扰，确认导入位置在新环境，核对发行版本、真实命令、模块入口和错误退出。

这不是发布到 PyPI，也不改系统环境。当前本机证据是 CPython 3.12.13；其他系统与最低版本由相应自动检查提供独立证据，不能先写成已经通过。

## 37. 静态检查、测试与构建的分工

**静态检查**分析源代码而不代表业务执行，Ruff 可以发现未使用导入和常见写法问题。pytest 执行行为，构建检查产物生成，干净安装检查交付物可用。

```text
uv run ruff check src tests scripts
uv run pytest -q --junitxml=reports/junit.xml
uv build
uv run python scripts/verify_wheel.py "dist/*.whl"
```

四步不能互相替代：静态通过可能算错，测试通过可能漏文件，能构建可能缺入口，能安装也不能证明测试充分。新增失败时定位对应层，避免把所有检查堆成不知原因的一个绿灯。

## 38. 持续集成与结果保存

**持续集成 CI** 在提交或拉取请求等事件触发后，自动获取代码、准备环境并执行检查。它能缩短重复验证反馈，不会自动设计测试，也不保证线上所有环境。

本仓库的 [第十六章自动检查](../.github/workflows/chapter16.yml) 使用 Windows、Linux 和 Python 3.11、3.12 组合，限定相关路径触发。步骤按锁同步、Ruff、pytest、构建、干净安装安排；报告和产物通过 artifact 保存，artifact 是本轮自动任务可下载的文件集合。

配置存在不等于远端运行已通过。检查实际 job 状态、失败步骤和对应提交，保留 JUnit XML 与构建文件。自动保存结果不需要把真实业务数据、凭证或个人路径写入公共日志。

## 39. 使用文档、兼容性与维护成本

使用者需要知道安装、输入字段、单位、配置来源、退出码、报告版本、失败处理和未实现范围。README 应让人按命令跑通最小例子，而不是只列内部类名。

兼容性包括 Python 版本、平台、调用签名、报告含义与错误分类。新增字段是否兼容、默认变化是否影响旧调用，都要有测试与说明。发行版本和报告 schema_version 分开维护。

工具规模变大时才继续提取适配器、插件或存储接口。维护成本包括依赖更新、失败定位、文档和回归，不只是最初写了多少行。适度抽象保留清楚的数据流。

## 40. 综合练习与后续扩展

先运行示例工具全量与筛选命令，解释每个计数的范围；再在个人副本新增一条规则，补正反测试；最后构建并在干净环境验证，记录命令、版本和证据。

Notebook 包含观察与实现练习，客观检查验证有限行为，公共接口设计、测试理由和兼容策略还需人工复述。没有真实工作经历时，用这些实际学习实验或明确虚构方案说明，不编造项目故事。

前十六章资料建立不等于课程固定结束，更不等于个人学习已完成。后续批量执行、插件扩展与打包交付可按独立 Python 学习目标深入；完整系统和领域课程仍另行组织。

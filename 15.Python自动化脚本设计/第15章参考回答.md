# 第 15 章参考回答：Python 自动化脚本设计

与 45 道面试题逐题对应。先给结论，再解释接口、状态和证据，最后说明限制。不是唯一话术，不用编造工作经历；设计质量与理解仍需人工复述。

## 一、接口与配置

### 第 1 题：脚本的输入输出与副作用约定

**首轮结论：** 先定义输入、输出、前置、失败、退出状态与副作用，才能判断脚本是否满足任务。

例如本地数量检查要说明快照路径、编码、数量类型、就绪状态、预期来源和停止条件。还要说明输入只读、报告写哪里、失败后旧文件是否保持。

异常不会自动撤销此前创建的数据。写清正常与失败约定，比先选一个重试库更能确定测试目标。

**常见误答：** 步骤能跑通就是可靠，或者抛异常后此前操作自动回滚。

**继续追问：** 某次提交超时，应在约定里如何表示结果未知？

**回答边界：** 给出一个有具体失败状态的小任务接口。

### 第 2 题：纯判断与外部操作的分离

**首轮结论：** 规则与外部操作分开，有利于独立测试和定位；普通函数通常足以建立第一层边界。

读取器负责取得实际数量，判断函数依据明确 expected 比较。测试规则时可给固定输入，测试读取时再验证编码与外部接口。失败来自读取还是比较，因此也更清楚。

拆分不以文件或类数量为目标。短脚本先用有责任的函数，复杂复用和状态确有需要时再增加结构。

**常见误答：** 把所有代码放进一个类就自动可测试，或纯函数一定不需要测试。

**继续追问：** 如果判断依赖真实当前时间，应把哪个输入显式提供？

**回答边界：** 说清两类责任与各自测试证据。

### 第 3 题：执行器、时钟与等待的依赖注入

**首轮结论：** 在外部变化明显的边界注入协作者，让测试控制结果、时间和交互。

执行器替身返回受控退出和输出，clock 提供单调测试时间，wait 记录并推进虚构时间。测试能精确触发迟到结果和预算耗尽，不需真实长等待。

依赖注入不证明真实外部接口可用，仍需少量受控集成测试；也不必把所有普通计算都改成难读回调。

**常见误答：** 全部 mock 后就等于完整系统通过，或依赖注入只能用复杂容器实现。

**继续追问：** 默认形参早已绑定旧函数时，patch 为什么可能影响不到？

**回答边界：** 给出一个可控边界与一个真实验证边界。

### 第 4 题：失败阶段与结果类别

**首轮结论：** 阶段和类别保留了不同原因与下一步行动，不能被一个宽泛状态抹平。

配置错误应在外部操作前拒绝；启动与非零退出看进程证据；坏输出看协议；failed 是明确终止状态；ready 后数量不同才是业务检查不通过。

分类应与接口一致，保留稳定字段和必要原因链。未知编程错误不应被自动改成可恢复错误或 passed。

**常见误答：** 所有失败一律重试三次，再返回 None。

**继续追问：** 什么情况下一个流程同时有业务通过和报告保存失败？

**回答边界：** 沿一次失败指出停止阶段和未执行的下一步。

### 第 5 题：main 与进程退出的分工

**首轮结论：** main 连接命令行与核心并返回退出码，帮助函数提供可调用接口，实际入口负责结束进程。

测试向 main 显式传实参列表，避免读取 Notebook 或测试运行器的 sys.argv。导入文件不应立即执行整项外部任务。

帮助函数用返回对象或异常传信息，通常不随意 sys.exit；只有外层脚本把 main 的返回值交给 SystemExit。

**常见误答：** 每一层都可以直接退出进程，这样错误处理最简单。

**继续追问：** 测试 argparse 的非法输入时，怎样避免结束整个内核？

**回答边界：** 说明调用接口与进程边界。

### 第 6 题：命令行转换与范围校验

**首轮结论：** 转换只解决输入形式，业务范围另行校验；文本布尔值不能直接靠 bool 转换。

int 能把负整数字符串转换为整数，但不决定数量允许负值。bool('False') 为真，因为字符串非空；开关通常用 store_true 等明确接口。

CLI 未提供可用 None 区分，错误时检查 SystemExit 或 main 的状态。不要把参数错误伪装成执行了检查且全部通过。

**常见误答：** type=int 自动保证正数，type=bool 自动理解英文真假。

**继续追问：** 预算 NaN 能通过 float 转换时，哪一步负责拒绝？

**回答边界：** 区分形式、类型、范围与有限性。

### 第 7 题：假值与缺失配置

**首轮结论：** 假值不等于未提供，缺失规则应按配置接口定义。

输出为 3 和 0。or 按真值选择，合法零会被默认值覆盖；is None 可以在当前约定下区分缺失与零。

但不能把所有来源的 None 都当未提供。示例 CLI 的 None 是没有选项，文件 null 则是已提供但不合法的时间或数量。

**常见误答：** 所有 0、False、空文本和 None 都可以统一丢弃。

**继续追问：** 未知字段的值是 None 时为什么仍可能需要报错？

**回答边界：** 给出来源明确的缺失标记。

### 第 8 题：配置优先级与逐层校验

**首轮结论：** 优先级和校验时机属于应用约定，本章选择逐层验证，后层不能隐藏已提供的非法值。

默认、文件、指定环境、CLI 按顺序合并，每层先做未知字段、转换和范围检查。这样能暴露过期或误写配置，而不让本次 CLI 偶然掩盖。

其他应用也可规定只验证最终值，但应清楚说明并测试。本章不把一种选择说成所有配置系统的固定规则。

**常见误答：** 所有框架自动提供同一优先级，或只要最终值有效就必然正确。

**继续追问：** 怎样记录某个生效值的来源而不打印完整环境？

**回答边界：** 说明本例选择、理由与替代方案边界。

### 第 9 题：精确整数与有限正数

**首轮结论：** bool 的继承关系和特殊浮点值都可能绕过过宽检查。

输出为 True False，再是 False False。精确整数数量可用 type(value) is int；时间需允许约定的数值类型，同时排除 bool、非有限值和非正值。

单位也必须明确，毫秒和秒即使同为 float 也不能随意混用。校验应在启动外部任务前完成。

**常见误答：** isinstance(value, int) 永远等同精确整数检查，或 value > 0 足以保证有限预算。

**继续追问：** 为什么 NaN 的比较行为容易让负向条件写错？

**回答边界：** 给出类型、有限性、范围和单位四项检查。

### 第 10 题：路径基准与编码边界

**首轮结论：** 每个相对路径都要有基准，文件与进程流是分别处理的编码边界。

区分调用时工作目录、配置文件目录和脚本自身目录。本例 source/report 相对工作目录，辅助程序相对 __file__，避免随启动位置丢失程序。

读取文件和解码 stdout 都明确 UTF-8；存在性预检查不能保证使用时仍存在，实际读取仍需处理错误。

**常见误答：** 所有相对路径都天然相对脚本所在目录，或先 exists 就不会再失败。

**继续追问：** 配置文件中的相对路径该如何写入约定？

**回答边界：** 至少区分三类基准并说明真实读取错误。

## 二、外部调用与结果

### 第 11 题：程序与实参列表

**首轮结论：** 实参列表保持调用边界，避免额外 shell 解释，但目标程序仍有自己的选项与语义。

明确 sys.executable 与每一项输入，可以让子进程按 argv 收到完整文本。把文本拼成 shell 命令会引入另一层解析。

不能把 shell=False 当作任意程序、选项或 Windows 批处理都无额外规则的承诺。本例始终启动明确的本地 Python。

**常见误答：** 用空格拼字符串与传列表永远等价，或 shell=False 能证明全部业务输入安全。

**继续追问：** 为什么当前解释器路径可能比直接写 python 更可复现？

**回答边界：** 说明数据边界和目标解释边界。

### 第 12 题：工作目录与环境副本

**首轮结论：** cwd 和传入的环境作用于子进程，副本修改不改父映射。

cwd 不需要父进程全局 chdir；env 若提供就是子进程环境映射，通常先复制父环境再调整明确字段。单独构造过小环境可能遗漏程序依赖的变量。

子进程普通环境赋值也不会反向改变父进程。并发脚本尤其应避免为每项修改共享全局工作目录或环境，日志仅保留必要键。

**常见误答：** env 自动在父环境上追加所有键，或子进程能通过普通赋值设置父环境。

**继续追问：** 多个线程使用不同输入目录时，为什么应优先传 cwd？

**回答边界：** 指出局部映射、子进程与父进程边界。

### 第 13 题：退出状态与两个输出流

**首轮结论：** 成功含义由目标协议规定，流内容和退出状态分别保留并由明确层解释。

一些程序在 stderr 输出正常诊断；stdout 有内容也可能是在非零失败前留下。执行器可以返回原记录，流程层先判断 returncode，再决定能否解析。

check=True 改为抛 CalledProcessError，仍需有人处理并保留信息。选 False 却不检查结果是遗漏责任，不是更宽容的实现。

**常见误答：** stderr 非空必然失败，stdout 非空必然成功。

**继续追问：** 非零退出但输出也是 JSON 时，如何决定优先级？

**回答边界：** 先声明目标协议，再说明检查者。

### 第 14 题：执行、协议与业务三层结果

**首轮结论：** 命令成功、结构可用和满足预期分别成立或失败，不能互相代替。

三项输出为 True、True、False。程序正常返回，数据也可按当前结构解释，但数量不符合独立预期 2。

另一种错误是退出 0 却输出截断文本，解析都不能成功；再一种是 JSON 为列表或 count 为布尔值。分类应保留实际结束阶段。

**常见误答：** 只要返回 0 就代表功能正确，或 JSON 能解析就可以直接报告通过。

**继续追问：** 哪一层负责把 failed 状态解释成终止失败？

**回答边界：** 分别给三层一个失败反例。

### 第 15 题：结构校验与独立预期

**首轮结论：** 协议规定可接受结构，需求规定判断标准，实际结果不能自己充当独立判据。

解析器检查顶层对象、字段、状态和值域，合法 failed 可以被解析但由流程终止。ready 的数量再与需求给定值比较。允许额外字段与否也应明文规定。

复制实现或实际输出生成 expected，可能只证明两者一致地错。受控参考和不变量可以补充，但要说明适用范围。

**常见误答：** JSON 天然保证业务 schema，或 actual 等于自己就算验证。

**继续追问：** 协议允许新增字段时，严格字段集合检查会产生什么兼容问题？

**回答边界：** 分清协议来源与业务判定依据。

### 第 16 题：单次子进程超时

**首轮结论：** run 处理直接子进程的超时并抛异常，启动、调度和收尾不构成严格实时承诺。

通常会终止或杀死并等待其启动的直接子进程，然后报告 TimeoutExpired；不能据此保证所有后代和远端任务停止。某些平台的进程创建阶段本身不能及时被中断。

有限 timeout 是一项控制，不是对所有副作用、外部操作和墙上时长的统一保证。

**常见误答：** 超时一到所有子孙和外部业务全部回滚。

**继续追问：** 手工使用 Popen 时哪些超时收尾需自己安排？

**回答边界：** 指出直接进程、启动与业务边界。

### 第 17 题：超时部分输出的处理

**首轮结论：** 部分输出是诊断线索，既不保证完整，也不保证在该异常接口中是文本。

TimeoutExpired 的捕获输出可能是 bytes，先按受控方式解码再作为证据；截断的结构或业务尚未提交的内容不能自动用于通过判断。

即使部分输出恰好能解析，也需目标程序明确说明何时输出已经代表完成。超时后最终业务状态通常需要额外确认。

**常见误答：** text=True 后任何异常字段都必然是 str，只要解析成功就忽略超时。

**继续追问：** 诊断解码使用 replace 与协议严格解码为什么目的不同？

**回答边界：** 区分证据保存和最终结果接受。

## 三、预算、状态与重试

### 第 18 题：单调时钟与墙上时间

**首轮结论：** 预算关注经过时长，日志日期关注人类定位，两者口径不同。

单调时钟适合截止和耗时，不因常规系统日期调整倒退；其数值不适合当成日历时间。墙上时间用于跨记录查找，但调整可能影响相减。

记录时注明含义，跨机器时钟也不能只凭相近时间证明严格先后。测试可以注入单调假时钟验证边界。

**常见误答：** 任何 time 函数都可互换，或 monotonic 返回可直接展示的日期。

**继续追问：** 同一流程每进入一层都重新取 started 有什么预算风险？

**回答边界：** 区分时长计算和日期证据。

### 第 19 题：总体预算的向下传递

**首轮结论：** 按当前剩余量与单次上限的较小者传递，不能在每层重置预算。

剩余 1.5 秒，因此本次限为 1.5。若仍传 3，操作可能在总截止点之后才结束；多次重试和间隔也会继续累加。

只建立一次 deadline，启动前计算剩余，返回后再核对时刻，等待也按剩余截断。底层仍须遵守传入上限。

**常见误答：** 每项各自有限时就自动保证整个流程同样有限。

**继续追问：** 执行器内部还有重试时怎样避免获得新的完整预算？

**回答边界：** 算清数值并说明预算所有权。

### 第 20 题：截止点与迟到结果

**首轮结论：** 本例只接受早于截止点的结果，返回后校验拒绝迟到，但不具有强制中断能力。

检查时间边界避免依赖忽略 timeout 后迟到返回仍被报成功。边界使用 < 而非 <= 是本例明确选择，测试应覆盖等于截止点。

该逻辑依赖操作可按限时返回；无法仅靠检查时刻让任意同步阻塞函数停止。应区分决策预算与严格进程总耗时。

**常见误答：** ready 总比时间约束优先，或加一个 if 就能杀死所有超时调用。

**继续追问：** 如果收尾必须额外一秒，应如何说明预算范围？

**回答边界：** 明确边界、协作者与收尾限制。

### 第 21 题：轮询状态与终止行为

**首轮结论：** 按明确状态决定继续、检查或失败，查询同一任务与重复创建是不同操作。

pending 在预算和次数内继续，ready 进入业务判断，failed 立即终止，未知状态按协议错误结束。保留同一任务或输入标识，避免把无关成功响应拼接进结果。

每次查询若会创建任务，就必须重新讨论副作用与幂等性，不能套用只读等待策略。

**常见误答：** 所有非 ready 都继续等，或查状态与重新提交等价。

**继续追问：** 如果合法状态增加 cancelled，应先改哪项约定和测试？

**回答边界：** 给出完整状态决策而非只写 while。

### 第 22 题：尝试上限与等待截断

**首轮结论：** 次数、预算、间隔共同约束流程，结束条件成立后不再增加无意义动作。

max_attempts 包含首次，耗尽时结束且不再等待；wait 不超过当前剩余预算。等待晚返回后，下一轮先查预算，不盲目启动。

时钟不前进的可控实验仍应被次数上限停止。这是两项独立约束，不能用循环写法本身代替。

**常见误答：** 有 sleep 就不会失控，或次数上限只统计失败后的额外调用。

**继续追问：** 怎样检查最后一次后没有多余查询和 wait？

**回答边界：** 说明调用计数与每条退出路径。

### 第 23 题：可恢复错误与异常传播

**首轮结论：** 重试类别由任务策略声明，不能对所有异常自动循环。

本例只读 ReadTimeout 可在预算内继续，配置和协议错误立即结束，明确 failed 状态也不重试。未知 RuntimeError 保留原异常，而不是改成 passed 或吞掉。

其他任务可能有不同可恢复错误，但仍需副作用和停止约定。保留 raise from 原因链有助于定位转换前的错误。

**常见误答：** except Exception 后 continue 足够稳健。

**继续追问：** 原异常对象和 cause 为什么也值得在测试中检查？

**回答边界：** 按明确策略分类，并给一种不能重试的原因。

### 第 24 题：退避与总体停止条件

**首轮结论：** 退避控制重复节奏，预算与次数控制何时结束，责任不同。

间隔逐步增大可减少持续失败时的调用频率，用 ceiling 限制单次等待。但无限次地等待固定上限仍可永远继续。

每次实际等待还要截断到剩余预算，并限制计算溢出和策略复杂度。固定小规则先可测试，再考虑通用策略。

**常见误答：** 有指数退避就自动有限，或上限只需约束 sleep。

**继续追问：** 剩余预算小于下一次退避值时怎样处理？

**回答边界：** 区分节奏与停止，并给出截断关系。

### 第 25 题：随机抖动的可重复测试

**首轮结论：** 抖动减少同步重试，测试应控制随机来源并检查区间和预算。

在约定范围加入随机变化，使调用分散。可注入随机函数或局部种子，检查生成间隔和实际传给 wait 的截断结果。

固定种子只控制对应发生器，不控制真实线程调度、网络或时钟；不以一次真实耗时等于某值作为可靠单测。

**常见误答：** 随机越多越可靠，或固定 seed 会固定全部外部环境。

**继续追问：** 有最大间隔时，抖动是在截断前还是后加入？

**回答边界：** 先规定公式与范围，再说明可控验证。

### 第 26 题：幂等性与重复效果

**首轮结论：** 幂等关注重复业务操作的最终效果，需要接口实际支持相同请求的处理约定。

同一设置重复执行最终状态一致，响应时间或日志可不同。客户端标识只有在服务按它去重、校验请求内容并规定保存期等条件下才有意义。

每次重试都生成新标识，反而可能被当成新任务。不能凭客户端代码独自宣称远端具有幂等保证。

**常见误答：** 返回值相同就是幂等，或 UUID 自动实现一次且仅一次。

**继续追问：** 同一标识对应不同参数时，接口该如何处理？

**回答边界：** 描述业务效果和去重责任。

### 第 27 题：超时后的结果未知

**首轮结论：** 调用可能先完成业务效果再丢失响应，超时与未发生不是同一个结论。

输出为 2。每次都先追加，再抛超时；简单重试使效果重复。真实流程应依据接口查询确认、复用请求标识或进入人工确认等路径。

本例只读查询的有限重试不能直接搬到创建、扣减或发布操作。保存首次失败和请求关联有助于确认。

**常见误答：** 没有收到成功响应就证明服务器没执行。

**继续追问：** 确认接口本身暂时不可用时，应如何报告？

**回答边界：** 保留未知状态，避免扩大结论。

### 第 28 题：部分成功与补偿

**首轮结论：** 按每步提交与资源责任记录部分结果，补偿是另一项需要验证的业务操作。

先确认哪些效果已经发生，哪些仅是暂存；确定负责撤销或保留的人和接口。补偿也可能失败，需保存原失败、补偿尝试和当前状态，而非统一返回已回滚。

with 关闭文件、释放锁只处理资源，不自动撤销业务。查询示例保持只读正是为了限制当前练习的业务背景。

**常见误答：** finally 执行了就代表全部业务恢复原状。

**继续追问：** 补偿失败时应怎样保留原错误和待处理项？

**回答边界：** 分开资源清理、提交点和恢复证据。

## 四、资源、报告与测试

### 第 29 题：资源取得与清理登记

**首轮结论：** 每项取得成功后及时进入清理范围，成功取得部分按依赖逆序退出。

可以用嵌套 with 或 ExitStack，在 A 成功后登记其退出，再取得 B。B 内部未成功交付的部分由 B 自己清理，不让调用者猜它取得到了哪里。

return 和异常都应经过退出逻辑，未知错误不能因 finally 中的新 return 被掩盖。清理失败也要保留诊断，不无条件 pass。

**常见误答：** 局部名字消失就关闭所有资源，或清理都放最后一行即可。

**继续追问：** 先登记假设资源已存在的清理有什么风险？

**回答边界：** 说明取得时点、所有者与退出顺序。

### 第 30 题：管道消费与进程等待

**首轮结论：** 有限缓冲装满时写方会等待消费，父进程只等退出可能形成等待环。

使用 communicate 协调有限输入输出，或为大输出设计文件和受限流式消费。capture_output 会把结果放进内存，不能用于无上限输出而不考虑容量。

手工超时需明确终止直接进程、收取输出和确认退出的责任，不能只抛一个异常就遗留后台进程。

**常见误答：** 输出管道无限大，或 wait 会自动持续读走全部内容。

**继续追问：** stderr 也可能写满时，只读 stdout 是否足够？

**回答边界：** 画出写方与等待方的阻塞关系。

### 第 31 题：直接进程与后代的终止边界

**首轮结论：** 后代进程、远端任务和已提交副作用具有另外的生命周期。

目标程序可再创建子孙，或把请求交给外部系统。直接进程退出不保证这些工作全部结束，平台相关的进程组和远程撤销需要独立约定与测试。

本章真实查询端不创建后代，只证明所测试的直接调用路径。用户中断也应保存未知结果，避免包装成普通业务失败继续重试。

**常见误答：** 父进程退出后任意后代自动全部回滚。

**继续追问：** 怎样给进程树控制定义可验证的平台范围？

**回答边界：** 说明当前证据能覆盖哪些生命周期。

### 第 32 题：报告临时写入与提交点

**首轮结论：** 先准备再替换保护旧目标，提交可见性与持久性、并发和多文件一致性是不同承诺。

先完成序列化，避免类型错误已经截断旧文件；临时文件同目录有利于同文件系统替换，关闭后更适应 Windows 句柄约束。替换失败要清理自身暂存并保留原目标与原因。

仍需另行设计同步、并发写入仲裁和多文件提交，不能把 os.replace 当作通用事务。

**常见误答：** 使用临时文件就保证任意断电后也永久保存，或可以无条件并发覆盖。

**继续追问：** 报告目标与输入相同为何应提前拒绝？

**回答边界：** 指出提交点和至少两项限制。

### 第 33 题：检查通过但报告失败

**首轮结论：** 业务判断与保存步骤分别记录，整项调用按明确完成条件返回失败。

本例保留原 category=passed，在 stdout 追加 report_error，退出 8 表达请求的报告未完成。不能说数量不对，也不能因为业务正确就忽略证据缺失。

旧报告若仍存在，不代表是本次结果；需要版本或运行关联。具体退出码是本脚本约定，外部调用者应同时读取摘要和结构化记录。

**常见误答：** 只要业务 passed 就忽略保存错误，或把保存错误改成业务数量不符。

**继续追问：** 如何避免读取者把旧报告误认成本次产物？

**回答边界：** 同时描述检查事实、保存事实和整体状态。

### 第 34 题：日志、结果通道与关联编号

**首轮结论：** 结果通道保持约定结构，日志用于过程诊断并带必要关联字段。

混入文本会让机器读取 JSON 失败。可把过程诊断放 stderr 或独立日志，但具体输出约定需统一。每条记录带虚构 case_id、attempt 等，完成顺序变化时仍能找回来源。

只保存必要字段与摘要，不把完整环境、身份或真实业务写进公开记录。墙上时间用于定位，单调耗时用于预算。

**常见误答：** 只要人能读懂，机器结果混入任何文本都没问题。

**继续追问：** 日志里出现成功语句是否足以证明输出和状态正确？

**回答边界：** 说明通道、字段与证据边界。

### 第 35 题：函数结果、异常与退出码

**首轮结论：** 三者处于不同调用层，码表由各入口协议定义。

函数对象结果给 Python 调用者，异常中断当前正常路径并向处理者传播，进程退出状态给外部调用程序。核心一般不自己结束整个进程。

本章区分检查、执行、协议、预算和报告失败的码值，仅属于示例。pytest 有独立码表，不能因数字相同就认定同一原因。

**常见误答：** 所有非零都表示产品缺陷，所有工具的码值都统一。

**继续追问：** 命令使用错误时没有执行业务，为什么不能计为已通过？

**回答边界：** 按调用层说明并给一个例子。

### 第 36 题：可控时钟验证边界

**首轮结论：** 把 clock、wait 和查询耗时显式控制，用确定时间推进验证决策。

wait 记录时长并推进测试 now，fetch 可在返回前再推进时间。构造 pending→ready、恰好截止、超时与停止时钟等序列，断言次数和传递预算。

它验证控制逻辑，不证明真实系统的实时性能。少量真实限时子进程再验证适配接口，不能用假时钟代替全部集成证据。

**常见误答：** 测试必须真实等满时间才可信，或假时钟通过说明真实调度必然一致。

**继续追问：** 为什么最大次数也要在时钟不前进时测试？

**回答边界：** 给出状态、时间推进和期望动作。

### 第 37 题：故障注入与不应发生的动作

**首轮结论：** 检查必要交互及未执行的下一步，避免错误类别正确但过程仍有副作用。

无效配置不调用执行器，非零退出不当作正常协议，最后一次不再 wait，未知错误不重试，报告替换失败保护旧目标。检查命令、实参、次数、timeout 和状态。

返回值与交互互补，不机械绑定无关内部细节。用典型错误候选检查测试能否发现遗漏，也要让正确候选通过。

**常见误答：** 只要最后返回 expected 字符串，过程怎样都无所谓。

**继续追问：** 一个总是抛错的测试为何不是有效的区分器？

**回答边界：** 给一项正向结果和一项负向交互断言。

### 第 38 题：脚本边界测试的选择

**首轮结论：** 同时覆盖输入、状态、时间、次数与资源边界，并说明独立预期。

数量考虑零、普通、负值、bool 和字符串；协议考虑截断、顶层、字段与未知状态。时间考虑首次 ready、pending 后 ready、截止前/等于/之后、wait 晚返回、最大次数及可恢复超时。

再补启动、非零退出和报告失败，按风险说明未覆盖内容。不是把所有数值随便随机生成就拥有设计依据。

**常见误答：** 只测一次成功和一次随意错误即可覆盖全部流程。

**继续追问：** 为什么精确截止点的用例比多测几个普通时间更有价值？

**回答边界：** 说明每类边界对应的缺陷风险。

## 五、小批量与程序组织

### 第 39 题：小批量编号与部分结果

**首轮结论：** 输入与结果应可逐项关联，状态完整并先拒绝歧义编号。

记录每项稳定 case_id、执行状态和错误，区分未提交、运行、完成失败和取消。字典按重复编号保存会覆盖旧项，应在启动前验证唯一性。

还需约定空输入、首失败即停或继续汇总，以及已开始工作如何收尾。成功列表长度不能替代逐项证据。

**常见误答：** 没出现在失败列表里就是通过，或字典会替重复编号自动去重且不丢信息。

**继续追问：** 首失败停止时，已开始项和未开始项如何分别报告？

**回答边界：** 给出完整结果关联与状态约定。

### 第 40 题：完成顺序与 Future 关联

**首轮结论：** 按完成顺序消费时，用 Future 到输入标识的映射找回对应关系。

运行时间和调度可能让后提交先完成。预先保存 future→case_id，每次取结果时查映射，最后按需要排序展示或按原顺序重组。

测试应控制关联正确，避免断言偶然完成次序。每项异常也应带回相同编号，不能只汇总成功值。

**常见误答：** 线程池总是按提交顺序完成，所以直接 zip 就行。

**继续追问：** map 的结果顺序与 as_completed 的消费特点有何不同？

**回答边界：** 说明映射与展示顺序的区别。

### 第 41 题：运行并发与提交积压

**首轮结论：** 运行上限不等于排队数量上限，一次性大量提交仍可积压输入和结果。

小批量预提交可以简单清楚，大批量要控制同时在途的任务与结果消费，考虑输入对象、Future 和输出体积。

增加线程不自动提高全部任务吞吐，也不解决共享路径和缓存污染。更完整的有界队列与恢复机制是后续独立主题，不为一个小脚本过度搭平台。

**常见误答：** 线程数有限就天然是全部资源有界。

**继续追问：** 每项输出很大时，仅限制输入数量是否足够？

**回答边界：** 至少区分运行、排队和已完成未消费三个范围。

### 第 42 题：等待超时与取消运行中任务

**首轮结论：** 等待者超时不停止工作，运行中任务通常不能靠 cancel 强制中断，池退出可能仍等待。

cancel 更适合尚未开始项。运行中任务需协作停止、每项底层超时或适合的进程边界，不能把主线程的一秒等待当整体一秒截止。

先定义停止后哪些项可继续、哪些只是不接受结果，再安排收尾与报告。强制终止另有平台和资源风险，不是 Future 接口自动提供的性质。

**常见误答：** result 超时就代表函数结束，或 cancel 一定能杀掉线程。

**继续追问：** 如果任务不理会停止信号，脚本能承诺什么、不能承诺什么？

**回答边界：** 分清等待、取消请求与实际停止。

### 第 43 题：远程调用适配的边界

**首轮结论：** 可保持核心接口，但真实协议、错误、超时与副作用承诺必须重新验证。

适配器把具体传输转换为快照接口，预算与业务判断可复用。仍要确认远端状态、鉴权、去重、取消、响应字段与错误分类，不把本地假设直接推广。

替身提供确定控制逻辑的证据，受控集成验证实际边界。完整网络或设备背景在相应课程补充，本章只建立可替换接口。

**常见误答：** 替换一行库调用就保留全部可靠性，或 mock 通过等于远程端到端通过。

**继续追问：** 某远端 timeout 不包含读取阶段时，如何影响总体预算？

**回答边界：** 说明可复用核心和必须重验的边界。

### 第 44 题：脚本拆分与依赖方向

**首轮结论：** 按真实复用和职责复杂度拆分，保持核心规则不依赖 CLI 与全局环境。

初期函数边界足以测试；接口需要复用、实现替换或职责混杂后再拆。入口连接配置和流程，纯规则不反向读取 sys.argv 或全局环境。

重构后验证原输入、输出、异常与副作用，不只检查导入。第 16 章继续处理公共接口、包结构与交付，而非本章先搭完整框架。

**常见误答：** 预建十层目录就自动可维护，或所有全局状态放配置模块即可解决耦合。

**继续追问：** 哪些共享组件需要独立测试与文档？

**回答边界：** 给一个有具体需求的拆分理由。

### 第 45 题：小流程的完整复盘

**首轮结论：** 用可核对的输入和证据说明整条流程，而不是列出使用过的工具名。

先给快照、预期与编码；说明命令边界、退出校验、字段协议、pending/ready/failed、总体截止与尝试上限。指出只读查询可有限重试，而创建操作需另查幂等与未知结果。

再说明临时文件和报告提交、业务与保存结果的区别，用可控时钟及真实本地子进程分别提供证据。明确未实现的远端撤销、进程树、海量输出、并发写入和持久性范围，不虚构工作经历。

**常见误答：** 只报使用了 subprocess、pytest 和线程池，就等同解释了方案。

**继续追问：** 如果只允许再补一条测试，依据哪项剩余风险选择？

**回答边界：** 沿一次真实学习运行解释原因与限制。

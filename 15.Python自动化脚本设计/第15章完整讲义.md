# 第 15 章完整讲义：Python 自动化脚本设计

第 14 章已经学习怎样组织、运行和诊断测试。本章继续把函数、文件、子进程、异常与时间控制组合成一个可验证的小流程。**自动化脚本**是按明确输入和规则执行一项任务的程序；可靠性来自失败和收尾约定，不能只看正常路径能否运行。

本章以 **CPython 3.12.13、pytest 9.1.1** 验证，使用兼容 Python 3.11 及以上的语法。案例是本地虚构快照的查询，不需要网络、账号或设备。完整示例位于 [示例脚本](./示例脚本/README.md)，用独立本地子进程提供外部调用边界，用替身控制失败与时间。后续第 16 章再组织完整工具的模块、打包与交付。

## 1. 从手工步骤写出脚本约定

假设手工任务是“读取数量，等状态就绪，检查数量是否等于预期，记录结果”。直接把这些动词拼成代码，还不能判断脚本是否正确。需要先写出**接口约定**：允许什么输入、输出表示什么、哪些状态算完成、失败如何报告，以及会修改哪些东西。

本章示例的约定是：输入一个 UTF-8 快照路径；查询输出必须包含 state 和 count；只在 ready 状态比较数量；failed 为终止失败；pending 可以在有限范围继续查询。输入文件只读，报告写到显式指定的其他路径。

**副作用**是返回值以外的可观察变化，例如创建文件、发送请求或启动进程。即使函数最后抛异常，此前的副作用也可能已经发生。因此设计表里不仅写“抛什么异常”，还要写“失败时哪些状态保持、哪些结果未知”。

第一次运行从准备好的快照开始。先在仓库根目录同步已有开发环境，再进入示例目录；以下是终端命令，不是 Python 语句。

```text
uv run --project ../.. python -X utf8 sample_check.py snapshot.json
uv run --project ../.. python -X utf8 sample_check.py snapshot.json --expected-count 3
```

`--project ../..` 明确选中仓库依赖环境，仍在当前目录执行命令；`-X utf8` 启用该 Python 进程的 UTF-8 模式。第一条检查给出通过记录，第二条给出数量不匹配及非零退出状态。实际输出还包含阶段、尝试次数、数量与简要说明。

先跟踪一次调用：main 读取配置，check_file 组织流程，execute 启动查询，parse_snapshot 解析，poll_snapshot 安排等待。不要先研究所有抽象形式，先确认这次执行读了什么、检查了什么、写了什么。

## 3. 把业务判断与外部操作分开

**纯函数**的结果只依赖输入，且不改变外部可观察状态，适合快速覆盖规则。读文件、运行程序属于外部操作；决定“数量是否符合约定”属于业务判断。将两者分开，能让不同失败有明确归属。

```python
def count_matches(actual, expected):
    return actual == expected

def check_once(reader, expected):
    actual = reader()
    return count_matches(actual, expected)

reads = []
def fake_reader():
    reads.append("read")
    return 2

print(check_once(fake_reader, 3), reads)
```

reader 是由调用方提供的协作者，这种方式称为**依赖注入**。测试不必真的读取远端数据，也能验证判断。若把 reader 自己替换掉再只检查它的返回值，则没有验证被测判断；真正需要验证的逻辑仍要保留。

## 4. 用分阶段结果表达失败

“执行失败”太宽泛。至少区分输入配置、启动与运行、输出解析、状态等待、业务判断和报告保存。**阶段**说明正在做哪一步，**结果类别**说明这一步产生了哪种结论。本章的**协议**指调用双方对退出状态、输出字段和类型等内容的约定。

| 现象 | 主要类别 | 接下来查看 |
|---|---|---|
| 预算是负数 | 配置错误 | 字段、来源与校验 |
| 查询程序无法启动或非零退出 | 执行错误 | 程序、退出状态、受控诊断 |
| 输出不是约定 JSON | 协议错误 | 编码、字段与类型 |
| 查询报告 failed | 任务终止失败 | 状态约定与业务证据 |
| ready 但数量不等 | 检查不通过 | 预期来源与实际数量 |
| 超时未取得可接受结果 | 等待失败 | 已执行次数、截止点、未知状态 |

分类不是为了把所有问题压成一个数字，而是保留可采取的下一步。意外的程序错误不应一律转成“重试一下”；未知异常应保留 traceback（异常的调用路径记录），或由明确的最外层记录后上报。

## 5. 命令行入口与可调用核心

**命令行入口**把终端文本转成配置并决定进程退出状态；核心函数处理已明确的输入。常用 `main(argv=None)` 接收可选实参列表，测试显式传列表，实际入口默认读取终端实参。

```python
import argparse

def main(argv=None):
    parser = argparse.ArgumentParser()
    parser.add_argument("--count", type=int, default=2)
    args = parser.parse_args(argv)
    if args.count < 0:
        parser.error("count must be non-negative")
    return 0 if args.count == 2 else 1

print(main(["--count", "2"]), main(["--count", "3"]))
```

`type=int` 做语法转换，范围仍需校验。argparse 的错误通常通过 SystemExit 表达，测试不能让它直接结束 Notebook 内核，应捕获并检查退出状态。普通脚本文件在 `if __name__ == "__main__"` 下使用 `raise SystemExit(main())`，导入核心模块时不启动整项任务。

## 6. 配置覆盖与缺失值

默认值、文件、环境和命令行可以提供同一字段，但优先级必须由应用规定。本章示例采用“默认 → 文件 → 指定环境变量 → 显式命令行”，并验证每层实际提供的值。后层覆盖不能替非法前层悄悄消除错误。

```python
defaults = {"limit": 3, "enabled": True}
provided = {"limit": 0, "enabled": False}
merged = defaults.copy()
for name, value in provided.items():
    if value is not None:
        merged[name] = value
print(merged)
print(provided["limit"] or defaults["limit"])
```

0、False、空字符串与“没有提供”不同。示例把 CLI 的 None 作为未提供；文件中的 null 则不是合法数值。不能不加区分地在所有层都跳过 None。只读取文档明确列出的环境变量，也不要把完整环境写入报告。

## 7. 数值类型、有限值与单位

时间字段不仅需要大于零，还要是有限数值。`float("nan")` 表示非数值，`float("inf")` 表示正无穷；它们不适合直接作为有限预算。bool 是 int 的子类，因此数量接口若要求精确整数，不能只靠 isinstance(value, int)。

```python
import math

values = [1.0, 0.0, float("nan"), float("inf"), True]
valid = [type(value) in (int, float) and math.isfinite(value) and value > 0
         for value in values]
print(valid)
print(isinstance(True, int), type(True) is int)
```

接口还要写单位：秒、毫秒、字符、字节或记录数。单次查询 timeout、总体 budget 和查询间隔 interval 虽然都用秒，责任不同；不能因为类型相同就互换。所有配置应在外部操作之前验证，避免无效输入已经触发部分任务。

## 8. 路径基准与编码约定

相对路径必须相对某个基准。本章 source 和 report 按调用时工作目录解释；辅助查询程序的位置基于 `__file__` 查找。配置文件中的路径若被引入，应另行说明是相对文件本身还是工作目录。

```python
from pathlib import Path
from tempfile import TemporaryDirectory

with TemporaryDirectory() as directory:
    root = Path(directory)
    path = root / "snapshot.json"
    path.write_text('{"count": 2}', encoding="utf-8")
    print(path.read_text(encoding="utf-8"))
    print(path.parent == root)
```

文件编码、子进程输入输出编码是不同边界，要分别声明。路径存在性预检查不能保证稍后读取仍成功，实际操作仍需处理 OSError。不要把检查阶段叫作“保证环境永远不变”。

## 9. 独立执行器的接口

**执行器**封装程序启动、等待、输入输出和直接子进程结果，向上层提供明确记录。示例 execute 返回 argv、returncode、stdout、stderr，并保留非零退出结果让流程层解释。

```text
流程层构造 argv 与本次 timeout
→ 执行器启动并等待
→ 返回退出状态和输出，或抛启动/超时/解码错误
→ 流程层决定能否继续解析
```

这个边界使测试可以注入假的执行器，核对命令、实参、次数和超时值。执行器不应直接决定“业务数量正确”，也不应把所有输出拼成一条无法区分 stdout、stderr 的字符串。

## 10. 程序路径与实参列表

优先把程序与每个实参分别放进列表，保持数据边界。下面的带空格和分号的文本作为一个普通实参传给 Python，不交给 shell 解释。capture_output=True 捕获两个输出流，text=True 按 encoding 将结果作为文本处理；check=False 保留退出状态，后面会说明它的检查责任。

```python
import subprocess
import sys

data = "sample with spaces; literal data"
result = subprocess.run(
    [sys.executable, "-X", "utf8", "-c", "import sys; print(sys.argv[1])", data],
    capture_output=True, text=True, encoding="utf-8", shell=False, check=False, timeout=5,
)
print(result.returncode, result.stdout.strip() == data)
```

`sys.executable` 明确选中当前解释器。shell=False 不等于任意可执行程序和选项都安全；目标程序仍会解释自己的实参。Windows 批处理等目标也有额外规则。本例始终启动明确的 Python 程序，不要求学习完整 shell 语法。

## 11. 工作目录与子进程环境

`cwd` 只改变新进程的工作目录，不把父进程全局 chdir；`env` 若提供，就是交给子进程的环境映射，不是自动追加。通常从 os.environ.copy() 建立局部副本，再修改明确字段。

```python
import os
import subprocess
import sys

environment = os.environ.copy()
environment["CH15_DEMO_MODE"] = "sample"
result = subprocess.run(
    [sys.executable, "-c", "import os; print(os.environ['CH15_DEMO_MODE'])"],
    env=environment, capture_output=True, text=True, encoding="utf-8", check=False, timeout=5,
)
print(result.stdout.strip())
print(os.environ.get("CH15_DEMO_MODE") == environment["CH15_DEMO_MODE"])
```

最后一项是否相等取决于原环境，所以它是观察，不是固定断言。可重复测试应先控制原值。修改副本不修改父映射，子进程也不能靠普通环境赋值反向修改父进程环境。记录必要模式即可，不打印整个 environment。

## 12. 标准输出、标准错误与退出状态

**标准输出 stdout** 常用于结果，**标准错误 stderr** 常用于诊断；是否成功以目标程序协议决定。stderr 非空不自动表示失败，stdout 非空也不代表成功。

```python
import subprocess
import sys

source = "import sys; print('result'); print('diagnostic', file=sys.stderr)"
result = subprocess.run([sys.executable, "-c", source], capture_output=True,
                        text=True, encoding="utf-8", check=False, timeout=5)
print(result.returncode, result.stdout.strip(), result.stderr.strip())
```

`check=True` 会在非零退出时抛 CalledProcessError；`check=False` 把状态留在结果里。两种方式都可以，但必须明确谁负责检查，不能选择 False 后忘记 returncode。示例先处理非零退出，再解释输出，以免错误程序留下的半段 JSON 被当成成功结果。

## 13. 命令成功、解析成功与检查通过

这是三个独立条件：进程按协议结束，输出能解释为约定结构，结构内容满足本次需求。每一层通过，都不足以代替下一层。

```python
import json

returncode = 0
text = '{"count": 1}'
data = json.loads(text)
print(returncode == 0)
print(type(data) is dict and type(data["count"]) is int)
print(data["count"] == 2)
```

反例包括：退出码 0 但输出截断；输出合法 JSON 但顶层是列表；字段都有但 count 是 True；ready 且结构合法但数量不等。本章实验分别触发这些情况，避免用一句“命令执行成功”掩盖全部业务判断。

## 14. 结构化输出与字段校验

优先采用 JSON 等明确结构，而不是从任意一行成功日志推导状态。JSON 能解析，不等于满足协议；还要检查顶层、字段、类型、允许值和取值范围。

```python
import json

for text in ['{"count": 2}', '{"count": true}', '[2]', '{"count": -1}']:
    data = json.loads(text)
    valid = (type(data) is dict and set(data) == {"count"}
             and type(data["count"]) is int and data["count"] >= 0)
    print(valid)
```

示例快照严格要求 state、count 两个字段，拒绝未知状态；这是本例约定，不代表所有协议都应拒绝新增字段。对兼容性需求，应明文说明额外字段、重复键和协议版本的处理。解析器不靠宽泛字符串搜索，例如文本里出现 ready 不能自动证明状态就绪。

## 15. 输出解析与业务断言的分工

解析器回答“得到的是什么”，判断器回答“是否满足本次目标”。本章 parse_snapshot 允许合法的 failed 状态，随后由轮询层把它认定为任务终止失败；count 不匹配则只在 ready 后判断。

这样设计可以分别测试字段错误、状态行为和数量规则。若解析函数把“不是我本次期望的数量”也当成 JSON 错误，报告会误导定位。相反，解析器若直接用 `bool(data["count"])`，又会丢掉零数量和布尔类型的差异。

异常转换应保留 `raise NewError(...) from original` 形成的原因链。对外记录稳定类别，诊断时保留原始类型和调用路径；不要依赖解析错误消息的语言或空格来决定业务分支。

## 16. 单次超时的范围

单次 timeout 限制一次外部操作的等待。subprocess.run 超时会处理它启动的直接子进程并抛 TimeoutExpired，但启动过程、操作系统调度和收尾可能增加实际耗时。它不是严格的实时截止保证。

TimeoutExpired 保存的部分 stdout、stderr 不一定是完整结果，即使开启文本模式也可能是 bytes。可以保留受控诊断，不能把半段输出自动当成可信最终结果。

```python
import subprocess

error = subprocess.TimeoutExpired(["sample"], 1, output=b'{"count":', stderr=b"waiting")
print(type(error.stdout).__name__)
print(error.stdout.decode("utf-8", errors="replace"))
```

此处主动创建异常对象观察接口，不启动慢进程。真实超时会在示例测试的短子进程中验证。任意后代进程是否结束、远端任务是否已提交、文件是否已写入，都不由这个异常自动回答。

## 17. 总体预算与单调时钟

**总体预算**覆盖整个观察流程，包括查询、间隔和重复尝试。每次查询都给相同 timeout，并不能限制多次合起来的时长。使用**单调时钟**计算经过时间，避免系统日期调整影响截止判断。

```python
started = 10.0
budget = 5.0
deadline = started + budget
now = 13.5
remaining = max(0.0, deadline - now)
per_call_limit = 3.0
print(remaining, min(per_call_limit, remaining))
```

真实代码用 time.monotonic()；这与保存日志用的墙上时间不同。把一次计算出的 deadline 传递下去或反复计算剩余量，避免每进入一层都重置完整 budget。本例要求结果必须在 deadline 之前到达，恰在截止点也不接受；其他任务可有不同边界，但必须一致。

## 18. 剩余预算与迟到结果

启动查询之前检查剩余量，把 `min(单次上限, 剩余量)` 传给执行器；返回之后再检查当前时刻。否则一个忽略超时的依赖可能返回迟到的 ready，而流程仍误报成功。

```python
deadline = 5.0
for returned_at in [4.5, 5.0, 5.5]:
    accepted_in_time = returned_at < deadline
    print(returned_at, accepted_in_time)
```

这个检查只能拒绝迟到结果，不能使任意阻塞函数在截止点被强制停止。预算依赖底层协作者遵守时间限制，收尾也可能需要额外时间。因此应区分“决策不接受超时结果”和“整个进程绝不超过某个墙上时长”。

## 19. 轮询状态与终止条件

**轮询**是重复查询同一任务的状态，直至完成或达到边界。本例 pending 表示可以继续观察，ready 表示开始检查数量，failed 表示立即终止；未知状态是协议错误。

```text
检查剩余预算
→ 查询一次并记录尝试编号
→ 解析结构
→ 检查返回时刻
→ ready：交给业务判断
→ failed：立即失败
→ pending：若还有次数与预算，有限等待后再查
```

轮询不等于反复执行创建任务。若每次“查状态”实际又提交一项新任务，副作用和结果关联会完全不同。应保留同一个任务或数据标识，不从多次无关联响应里挑一个成功的就结束。

## 20. 次数上限与等待间隔

总体预算之外，还需要有限的 max_attempts。它能限制查询频率和调用数量，也能在可控时钟不前进的实验里阻止无限循环。总尝试次数包含第一次；“重试三次”若不说明，可能被理解成三次或四次调用。

等待不得超过剩余预算，最后一次失败后不再无意义 sleep。若 wait 比要求晚返回，下一轮先检查截止点，不能继续启动新查询。间隔为零或忙循环会增加压力，是否允许由接口明确；本例要求 interval 为有限正数。

验证时记录每次 fetch 收到的 timeout 和 wait 收到的时长，不能只看最终状态。一次最终成功也可能隐藏中途超预算或多余调用。

## 21. 重试条件与不可恢复错误

**重试**是在一次操作失败后重新尝试该操作。只有明确可恢复的错误才应进入重试，本例只对只读查询的 ReadTimeout 重复观察；非零退出、解析错误和 failed 状态立即结束。

```python
events = []

def operation():
    events.append("call")
    raise ValueError("invalid configuration")

try:
    operation()
except ValueError:
    events.append("stop")
print(events)
```

配置错误不是因为再等一会儿就一定会恢复，程序错误也不应被无限吞掉。异常层次和状态分类表达重试策略，不能只写 `except Exception: continue`。重试前仍要确认重复操作是否可接受。

## 22. 退避、抖动与可测试等待

**退避 backoff** 是失败后逐步增加等待间隔；**抖动 jitter** 是按约定加入一定随机变化，以减少很多调用者同时重试。它们控制节奏，不代替最大次数和总体预算。

```python
def delays(base, ceiling, count):
    value = base
    result = []
    for _ in range(count):
        result.append(min(value, ceiling))
        value = min(value * 2, ceiling)
    return result

print(delays(0.25, 1.0, 5))
```

实际等待还要截断到剩余预算。加入随机抖动时可注入随机函数，并检查取值区间，不要求测试真实 sleep。间隔也可能按状态不同选择，但应先有明确的小规则，再引入通用策略对象，避免为一个脚本堆出复杂调度框架。

## 23. 幂等性、超时与结果未知

**幂等性**描述同一业务操作重复执行的最终效果是否与执行一次一致。它不意味着每次返回值完全相同、日志只写一次，或任意失败都能安全重试。

```python
records = []

def submit():
    records.append("created")
    raise TimeoutError("response lost after commit")

for _ in range(2):
    try:
        submit()
    except TimeoutError:
        pass
print(len(records))
```

调用者超时之前，提交可能已经发生。上面重试产生两项效果，不能因为没有收到成功响应就假定未执行。真实接口可使用稳定请求标识、查询确认或明确补偿，但这些都需要相应服务承诺，不能只在客户端生成一个 UUID 就宣称幂等。

## 24. 部分成功与补偿责任

多步流程“创建记录 → 写文件 → 发布结果”，第三步失败时，前两步可能已经完成。**补偿**是按业务规则执行另一操作，尽量恢复可接受状态；它不等于语言自动回滚，也不保证总能成功。

```python
events = []
try:
    events.append("record created")
    events.append("file prepared")
    raise RuntimeError("publish failed")
except RuntimeError:
    events.append("compensation requested")
print(events)
```

这只是状态记录，不证明补偿真的撤销了业务。方案需要说明每步提交点、谁拥有已创建数据、补偿失败如何保存证据，以及是否需要人工确认。本章查询示例保持只读，避免把未定义的业务回滚当作练习前提。

## 25. 资源取得与提前退出

资源包括文件句柄、临时目录、锁、子进程和连接。每次取得成功后，立即建立相应清理范围；正常返回、异常和用户中断都要经过预期收尾。

```python
from contextlib import ExitStack

events = []
try:
    with ExitStack() as stack:
        events.append("A acquired")
        stack.callback(events.append, "A released")
        events.append("B acquired")
        stack.callback(events.append, "B released")
        raise ValueError("stop early")
except ValueError:
    pass
print(events)
```

ExitStack 按逆序调用已登记动作。第二项取得失败时，第一项也已受到保护；第二项内部尚未交付的资源仍由第二项取得函数负责。与第 14 章 fixture 相同，不能把清理留给“碰巧最后会运行”的另一条语句或另一项测试。

## 26. 子进程管道、等待与后代进程

capture_output 把输出放入内存，适合本例很小的 JSON；海量输出需要文件或受限流式消费。Popen 启动后若只 wait 而不消费已装满的管道，子进程可能等父进程读，父进程又等子进程退出，形成等待环。

`communicate()` 协调输入与输出消费；若使用 Popen，自行超时处理通常要终止或杀死直接进程，再 communicate 收走输出并确认退出。对真正长期运行的程序，要另行设计进程组和平台相关收尾。

本例的查询端不创建后代。不要把 run 的直接进程处理推广为“任何子孙、远端任务和副作用都已经停止”。用户中断也要作为独立控制路径处理，尽量不被广泛 except Exception 转成普通重试。

## 27. 临时文件与报告提交点

打开正式报告并用 w 写入，会先截断旧内容。为保护旧报告，先完成序列化，再在同目录写临时文件，关闭句柄后使用 os.replace 替换。**提交点**是新结果成为正式目标的时刻。

```python
import json
import os
from pathlib import Path
from tempfile import NamedTemporaryFile, TemporaryDirectory

with TemporaryDirectory() as directory:
    destination = Path(directory) / "report.json"
    destination.write_text('{"old": true}', encoding="utf-8")
    payload = json.dumps({"new": True}, allow_nan=False)
    with NamedTemporaryFile("w", encoding="utf-8", dir=directory, delete=False) as stream:
        pending = Path(stream.name)
        stream.write(payload)
    try:
        os.replace(pending, destination)
    finally:
        pending.unlink(missing_ok=True)
    print(json.loads(destination.read_text(encoding="utf-8")))
```

上块只演示正常提交与替换后的收尾，完整失败保护见示例 atomic_write_json。序列化、写入或替换失败要清理自己取得的临时文件，并保留原错误。替换可见性、断电持久性、并发写入者和多文件事务是不同约定，不能一概由“原子写入”四字保证。

## 28. 检查结果与报告保存结果

业务检查通过，但报告写入失败，整个调用是否成功？取决于入口约定。本章若明确请求 --report，保存失败返回 8，同时在 stdout 的检查记录追加 report_error；检查类别仍说明原业务判断，错误退出表达整项请求未完成。

这能避免把“未生成证据”悄悄忽略，也避免把原本通过的业务检查改说成数量错误。报告目标不得与输入快照或配置文件相同，目标父目录必须已存在。

旧报告可能保留，读取者还需要运行标识或版本等关联，才能知道它是否属于本次执行。成功创建一个文件不代表其内容、字段和关联正确，报告本身也要测试。

## 29. 日志、结果通道与关联编号

日志描述过程，结果通道表达程序接口。本例成功启动后的 stdout 输出一条 JSON 结果；stderr 用于简要诊断，CLI 帮助和参数错误仍遵循 argparse 约定。不要把随意 print 的调试文本混进机器读取的 JSON。

**关联编号**把输入、尝试、结果和失败证据连起来，例如虚构 case_id 与 attempt。并发时尤其不能只凭相邻日志推断属于同一项。需要时间信息时，墙上时间便于人定位，单调耗时用于预算，二者分别记录含义。

日志只保存必要字段、受控错误类别和摘要。本章示例不输出完整环境，也不把真实账号、组织、路径或业务内容放入公开材料。实际诊断详情的访问与保留由使用场景安排。

## 30. 返回值、异常与进程退出码

函数返回对象交给 Python 调用者，异常中断当前正常路径，进程退出码交给外部调用者。它们是不同接口，不应让每个帮助函数随意调用 sys.exit。

| 本例退出码 | 入口含义 |
|---:|---|
| 0 / 1 | 检查通过 / 数量不匹配 |
| 2 | 配置或命令使用错误 |
| 3 / 4 | 执行错误 / 协议错误 |
| 5 | 查询报告任务失败 |
| 6 / 7 | 总预算耗尽 / 尝试次数耗尽 |
| 8 | 显式请求的报告未能保存 |
| 130 | 本例接收到用户中断 |

这是本脚本约定，不是 Python 或 pytest 的通用码表。退出码是摘要，结构化结果提供阶段、次数和数量；两者共同解释任务。没有执行任何检查的参数错误，不能伪装成 0。

## 31. 可控时钟与等待函数

测试时间逻辑不必真的等很多秒。传入 clock 与 wait，让测试记录虚构时间，按计划推进；依赖在本地返回状态序列，就能精确触发边界。

```python
class ManualClock:
    def __init__(self):
        self.now = 0.0
        self.sleeps = []
    def clock(self):
        return self.now
    def wait(self, seconds):
        self.sleeps.append(seconds)
        self.now += seconds

timer = ManualClock()
timer.wait(0.25)
timer.wait(0.5)
print(timer.clock(), timer.sleeps)
```

测试查询消耗时间时，fetch 也可推进 timer.now。这样能验证“返回恰好到期”“等待比要求晚”“时钟不前进但次数仍有限”。替身不是证明真实系统实时性，而是验证控制逻辑在明确输入下的决定。

## 32. 流程测试与故障注入

**故障注入**是主动让某个依赖在指定位置失败，观察传播、状态与清理。脚本自身至少需要正常、空值或边界、启动失败、非零退出、坏输出、终止状态、超时与报告失败的测试。

成功测试同时检查输出与必要交互；失败测试检查没有发生不应发生的下一步。例如非零退出后不解析，达到最大次数后不等待，非法配置不调用执行器，报告替换失败后旧文件保持。

用一个正确候选和若干故意错误候选检验自己的测试，能发现“测试总通过”或只检查调用次数等薄弱处。检查器验证有限行为，设计理由、覆盖和可维护性仍需人工评审。

## 33. 小批量输入与唯一编号

单项检查可靠之后，再处理小批量。每个输入有稳定编号，结果保留对应编号；空集合、重复编号和部分失败要有约定。不要从成功结果列表长度反推出其余项“应该也通过”。

```python
inputs = [{"case_id": "C-A", "value": 2}, {"case_id": "C-B", "value": 3}]
results = [{"case_id": row["case_id"], "matched": row["value"] == 2} for row in inputs]
print(results)
print(all(row["matched"] for row in results))
```

重复编号可能使字典覆盖旧项，应在提交前检查。批量还需说明是所有项执行后汇总，还是首项失败就停止，以及已开始项如何收尾。更深入的队列、恢复与结果存储留到独立主题。

## 34. 有限并发与结果关联

独立 I/O 任务可以用小型线程池限制同时执行数量。**Future** 是表示一项已提交工作状态与结果的对象。**并发上限**限制正在运行的任务数量，不自动限制一次性提交的全部 Future 数量；小批量可以预先提交，大批量需要有界生产和消费。下面的 as_completed 按完成顺序提供 Future。

```python
from concurrent.futures import ThreadPoolExecutor, as_completed

def check(value):
    return value * 10

with ThreadPoolExecutor(max_workers=2) as pool:
    pending = {pool.submit(check, value): case_id
               for case_id, value in [("C-A", 2), ("C-B", 1)]}
    collected = {}
    for future in as_completed(pending):
        collected[pending[future]] = future.result()
print(sorted(collected.items()))
```

结果完成顺序未必等于输入顺序，所以按 Future 映射找回编号。本例打印排序后的关联，不预测调度先后。共享可变配置与输出路径仍需隔离，线程池不会自动修复数据竞争。

## 35. 取消与正在运行的工作

Future.result(timeout=...) 只限制调用方这次等待，不自动停止工作。cancel 通常只能取消尚未开始的任务，正在运行的线程需要协作停止条件或底层操作超时。

```python
from concurrent.futures import Future

pending = Future()
running = Future()
running.set_running_or_notify_cancel()
print(pending.cancel(), running.cancel())
running.set_result("finished")
print(running.result())
```

本块直接观察 Future 状态，不启动线程。线程池 with 退出通常仍等待已开始项收尾，因此外层等待超时不等于程序瞬间退出。批量场景应给每项预算、整体停止策略与清理责任，而不是只给主线程加一个 timeout。

## 36. 远程调用适配与最小领域背景

若以后把本地查询替换为远程读取，先保持明确接口，例如 fetch_snapshot(task_id, timeout) 返回约定快照。**适配器**把某种具体调用方式转换为这套接口；状态解析、预算与业务判断仍可复用。

但不同系统的异常、超时、身份和幂等承诺并不相同，不能假设替换一行库调用就保留了全部可靠性。应另设受控集成测试，确认真实协议与适配器一致。本章不要求掌握完整网络、服务器或设备课程。

依赖注入控制测试，不应把全部程序拆成难以理解的一堆回调。先在确有外部变化和测试成本的边界注入执行器、时钟或等待，再按需要扩展。

## 37. 单文件拆分为模块的时机

脚本开始时可以只有一个核心文件与一个本地查询端。配置、执行、解析、流程已经各有函数，就能通过普通导入测试，不必先建多层类层级。

当多处复用、文件职责混杂、接口需要稳定，或替换实现开始困难时，再按配置、执行、解析和入口等职责拆分。依赖方向应让核心规则不反过来依赖 CLI 解析与全局配置。第 16 章继续讲多模块工具、发行入口与交付验证。

改造后验证原有输入、输出、错误和副作用约定，而不是只看导入不报错。抽象是维护选择，不是可靠性的替代证明。

## 38. 示例脚本的完整执行与局限

阅读示例 README，依次运行通过、数量不匹配、输入缺失、非法配置与显式报告。pytest 测试通过替身模拟 pending、超时、坏输出和报告失败，不需要真实等待很久。

示例查询端仅原样输出本地文件，结构由调用方解析。默认最多三次查询，不会把“文件可能会变化”当作无限等待理由。它不提供远程任务撤销、任意进程树控制、海量输出流式处理、跨进程并发写入或断电持久性承诺。

这些限制是当前接口与练习范围。是否增加能力，要先明确需求和验证条件，不能把未测试过的性质写成“脚本可靠”。

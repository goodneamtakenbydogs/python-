# 第 2 章参考回答：内置数据结构与复杂度

本文件与《第 2 章面试题》逐题对应。参考回答展示的是组织思路，不是唯一话术。涉及复杂度时，除非另有说明，`n` 表示容器当前元素数量；字典和集合的结论还依赖哈希分布良好这一通常条件。

## 一、基础概念题

### 第 1 题：复杂度中的平均、摊销与最坏情况

**一句话结论：**复杂度描述输入规模增长时资源消耗的增长趋势；平均、摊销和最坏情况的统计对象不同，不能省略条件后当成同一个概念。

- 平均复杂度是对某种输入分布下多种可能输入取期望，但结论依赖所假设的分布。
- 摊销复杂度研究一串操作的总成本，不要求输入随机；少数昂贵操作可以被大量便宜操作分摊。
- 最坏复杂度给出规模为 `n` 时任何合法输入或状态下的上界。

`list.append()` 在常见实现中通常是 `O(1)`，但单次触发扩容时可能为 `O(n)`；对连续追加序列而言是摊销 `O(1)`。常见错误是把“摊销”解释成运行多次后自动变快，或把一次最坏操作隐藏掉。面试首轮回答到能区分三者并用追加举例已经足够。

### 第 2 题：列表的存储与动态扩容

**一句话结论：**常见 CPython 列表用连续区域保存对象引用，因此下标定位快，开头插入却要移动后续引用；预留额外容量能避免每次追加都重新分配。

下标可以通过起始位置和偏移量直接定位，通常为 `O(1)`。末尾有空余容量时，追加只需写入一个引用；开头插入需要为新位置腾空间，移动约 `n` 个引用，因而是 `O(n)`。容量不足时，CPython 通常按一定策略超额分配，而非只多开一个位置，从而让追加获得摊销 `O(1)`。

Python 语言规定列表的行为和顺序语义，但连续引用数组、具体增长比例和内存布局是 CPython 实现细节，不宜写进依赖跨实现的业务逻辑。常见错误是说列表连续存储的是所有对象本体；通常连续的是对象引用。

### 第 3 题：列表常用操作及复杂度

**一句话结论：**直接定位通常是 `O(1)`；创建或扫描 `k` 或 `n` 个元素需要线性时间；在中间改变长度还要移动后续元素。

- `values[index]`：通常 `O(1)`。
- `values[start:stop]`：创建新列表，时间和额外空间均为 `O(k)`。
- `append(value)`：摊销 `O(1)`，单次扩容最坏 `O(n)`。
- `extend(items)`：若加入 `k` 个元素，通常为 `O(k)`，扩容成本包含在整体摊销分析中。
- `insert(index, value)`：最坏 `O(n)`，因为可能移动后续引用。
- `pop()`：末尾弹出通常 `O(1)`；`pop(index)` 最坏 `O(n)`。
- `remove(value)`：先线性查找，再可能移动元素，最坏 `O(n)`。
- `value in values`：最坏 `O(n)`。
- `reverse()`：原地 `O(n)`。
- `sort()`：通常 `O(n log n)` 时间；辅助空间依数据分布与实现而变，不应草率断言恒为 `O(1)`。

常见错误是只看方法名，不考虑位置和新增数量。可能追问：切片赋值的复杂度如何判断？需要同时考虑被替换区间、插入数量和后续元素移动。

### 第 4 题：`sort()` 与 `sorted()`

**一句话结论：**`list.sort()` 原地排序列表并返回 `None`；`sorted()` 接受任意可迭代对象并返回一个新列表。

两者通常都需要 `O(n log n)` 时间。`sort()` 会改变原列表；`sorted()` 不修改输入容器本身，但会建立结果列表，需要 `O(n)` 级别的结果空间。二者都支持 `key` 和 `reverse`。

```python
numbers = [3, 1, 2]
numbers.sort()
# numbers 已经改变

ordered = sorted(numbers)
# ordered 是新列表
```

写 `numbers = numbers.sort()` 会把名字绑定到返回值 `None`。常见错误是说 `sorted()` 只能接受列表，或声称两者的排序算法必然适用于所有 Python 实现；具体算法属于实现层面。

### 第 5 题：列表与元组

**一句话结论：**列表适合会变化的有序集合，元组适合结构固定的有序记录；元组只有在所有元素都可哈希时才可能可哈希。

在 Python 语言层面，列表支持原地增删和替换元素；元组创建完成后不能改变长度，也不能替换位置中的对象引用。二者都保存对象引用，并支持顺序遍历、索引和切片。

从常见 CPython 实现看，元组可以理解为按创建长度分配固定数量的引用槽位；列表为了支持追加和删除，另外维护当前长度、已分配容量以及可调整的引用数组。这个模型可以解释列表扩容和元组固定结构，但具体 C 字段、容量策略与字节数不是 Python 语言保证。

```python
values = (1, 2)
alias = values
values += (3,)

print(values)  # (1, 2, 3)
print(alias)   # (1, 2)
```

元组的 `+=` 构造结果元组并重新绑定左侧名字，没有修改旧元组。反复拼接越来越长的元组需要反复复制引用，累计成本可能达到 `O(n²)`；持续追加通常应先用列表。

```python
print(hash((1, "A")))  # 通常可行
# hash((1, []))         # TypeError：内部列表不可哈希
```

元组不可变只约束它自身的长度和位置引用，不能保证内部对象不可变。元组哈希需要组合内部元素的哈希，因此包含列表的元组整体不可哈希。

首轮回答到语言层面的不可变性、`+=` 新建结果、固定槽位与动态容量的实现模型，以及可哈希条件即可。常见错误包括把不可变等同于可哈希、声称元组永远更快，或者把 CPython 当前布局说成所有 Python 实现的永久保证。

### 第 6 题：可哈希对象

**一句话结论：**可哈希对象在参与哈希容器期间需要有稳定哈希值，并保持“相等对象必须有相同哈希值”的约束。

字典和集合先使用 `hash()` 缩小查找范围，再用 `==` 相关的相等性协议确认键。最低限度可以理解为：`__hash__()` 相关行为提供稳定哈希值，`__eq__()` 相关行为定义候选对象何时相等。若键加入后其哈希相关状态能改变，容器可能再也找不到原位置，因此普通列表这类可变对象不可哈希。只含可哈希元素的元组能组合出稳定哈希，通常可作为键。

列表也不能在保留现有内容相等规则时简单改用身份哈希：两个不同列表可能按内容相等，但身份哈希不同，这会违反“相等对象必须具有相同哈希值”的约束。

需要注意：不同对象哈希值相同是允许的；反向规则不成立。常见错误是说不可变对象一定可哈希，例如包含列表的元组就是反例。自定义对象的 `__eq__` 与 `__hash__` 细节留到数据模型章节。

### 第 7 题：字典查找与哈希冲突

**一句话结论：**哈希表用 `__hash__()` 相关行为定位少量候选位置，再用 `__eq__()` 相关的相等性协议确认键，因此正常分布下插入、查找和删除平均是 `O(1)`。

哈希值相同只说明发生冲突，不说明键相等。容器会按照其冲突处理机制继续寻找，并对候选键执行相等性判断，所以不同键仍可共存。这里不是简单使用 `is`：类型不同的 `1` 和 `1.0` 也满足 `1 == 1.0`，并具有符合相等性约束的哈希值，可以匹配同一个字典键。若大量键集中到冲突路径，单次操作最坏可能退化为 `O(n)`。

“开放寻址的具体探测方式、装载因子和扩容细节”属于 CPython 实现；“哈希定位、冲突处理、最终确认相等”属于通用原理。常见错误是说字典完全不比较键，或说一次冲突就会覆盖旧键。本章回答到两阶段职责即可；自定义 `__eq__()`、`__hash__()` 与 `NotImplemented` 的完整规则属于第 6 章。

### 第 8 题：字典顺序与视图

**一句话结论：**当前 Python 语言保证字典按插入顺序迭代；更新已有键通常不移动位置，删除后重新插入会把它放到末尾。

`keys()`、`values()` 和 `items()` 返回与原字典关联的动态视图，不是当时内容的独立列表。字典改变后，视图通常能反映新状态；需要快照时应显式转换，例如 `list(mapping.items())`。

字典有插入顺序不等于按键大小排序，也不能依赖内部哈希表槽位顺序。常见错误是把历史上某个 CPython 版本的实现表现说成所有 Python 版本的语言保证；回答时应说明当前 Python 3 语义。

### 第 9 题：字典的读取与更新接口

**一句话结论：**下标读取缺失键会报错，`get()` 可只读地提供默认结果，`setdefault()` 会在缺失时插入默认值，`update()` 批量写入，推导式构造新字典。

```text
mapping[key]                 # 缺失时 KeyError
mapping.get(key, default)    # 不插入缺失键
mapping.setdefault(key, [])  # 缺失时把列表存入字典
mapping.update(other)        # 新增或覆盖多个键
```

调用前，函数实参会先求值，因此 `mapping.get(key, expensive())` 和 `setdefault(key, expensive())` 即使键已存在，也会先构造默认对象。若构造昂贵，应先判断或改用适合的默认工厂方案。常见错误是以为 `get()` 会把默认值存入字典。

### 第 10 题：集合与不可变集合

**一句话结论：**集合保存不重复的可哈希元素，适合成员判断、去重和集合关系运算；`frozenset` 是不可变版本。

- `a & b`：交集。
- `a | b`：并集。
- `a - b`：只在 `a` 中的元素。
- `a ^ b`：只在其中一方出现的元素。

集合成员查询平均 `O(1)`、最坏 `O(n)`；构造包含 `n` 个元素的集合平均需要 `O(n)` 时间和 `O(n)` 空间。`set` 可修改，因而不可哈希；`frozenset` 不可修改且元素本身必须可哈希，可以作为字典键或另一个集合的元素。

常见错误是认为集合自动按大小排序，或认为去重后仍保留输入顺序。输出顺序不应作为普通集合接口契约依赖。

### 第 11 题：`list` 与 `deque`

**一句话结论：**列表适合随机访问和尾部操作，`deque` 适合两端频繁加入与删除。

列表尾部追加和弹出通常为摊销 `O(1)`/`O(1)`，但头部插入或删除为 `O(n)`。`deque.append()`、`appendleft()`、`pop()`、`popleft()` 在两端通常都是 `O(1)`。不过 `deque` 的中间索引和中间插删不是其优势；按下标频繁访问时列表更合适。

这些复杂度是公开接口上可依赖的性能特征；`deque` 的块状存储等属于 CPython 实现细节。常见错误是把 `deque` 当成更快的通用列表。

### 第 12 题：`Counter`、`defaultdict` 与 `namedtuple`

**一句话结论：**`Counter` 表达频数映射，`defaultdict` 用工厂自动生成缺失值，`namedtuple` 给固定位置的元组字段提供名称。

`Counter(iterable)` 适合计数，并提供 `most_common()` 等语义化工具。`defaultdict(list)` 适合分组，但读取缺失键会创建并插入默认值。`namedtuple` 的实例仍具有元组的固定、按位置存储和通常可哈希等特性，同时可用属性名访问字段；复杂行为和可变状态通常更适合普通类或数据类。

常见错误是只因工具短就必然选它。项目还要考虑接口语义、团队熟悉度、序列化形式和是否会误触发默认工厂。

### 第 13 题：最小堆与 Top K

**一句话结论：**`heapq` 默认维护最小堆，只保证堆顶是最小元素；保留最大 `k` 项时，用大小为 `k` 的最小堆把当前门槛放在堆顶。

每来一个候选值，若堆未满就压入；堆满后，只在候选值大于堆顶时替换堆顶。处理 `n` 个元素通常需要 `O(n log k)` 时间和 `O(k)` 额外空间，最终堆内是最大 `k` 项，堆顶是其中最小者，即全体第 `k` 大。

堆内部不是全局有序列表；若要按序输出，还需额外工作。常见错误是维护最大堆保存最大 `k` 项，却无法 `O(1)` 找到其中最小的淘汰门槛。若 `k` 接近 `n` 或必须输出全序，排序可能更简单。

Python 3.14 起，`heapq` 增加了公开最大堆接口；Python 3.11～3.13 的数值最大堆通常用取负模拟。无论接口版本如何，求最大 `k` 项仍使用最小堆维护淘汰边界，不能因为“最大”二字机械改成最大堆。

## 二、代码理解题

### 第 14 题：`append()`、`extend()` 与 `insert()`

**结论：**输出为 `[1, 0, 2, [3, 4], 5, 6]`。

`append([3, 4])` 把整个列表当作一个元素加入；`extend([5, 6])` 逐个加入两个元素；`insert(1, 0)` 在下标 1 前插入，并移动原下标 1 之后的引用。最后一步最坏为 `O(n)`。

常见错误是把 `append()` 和 `extend()` 都说成合并列表。可能追问：`extend()` 加入 `k` 项的复杂度？通常为 `O(k)`，还需接受可能扩容的摊销成本。

### 第 15 题：删除列表元素

**结论：**输出 `20`，然后输出 `[30]`。

末尾 `pop()` 删除并返回最后一个 `20`；`remove(20)` 删除从左侧找到的第一个值为 `20` 的元素；`del values[0]` 按位置删除 `10`。末尾 `pop()` 通常为 `O(1)`；`remove()` 查找加移动最坏 `O(n)`；按位置 `del` 最坏也为 `O(n)`。

若找不到 `20`，`remove(20)` 引发 `ValueError`。常见错误是认为 `remove()` 删除所有相同值，或者混淆 `pop(index)` 的位置与 `remove(value)` 的值。

### 第 16 题：单元素元组与可哈希性

**结论：**三个类型依次为 `int`、`tuple`、`tuple`；`candidate_a` 能加入集合，`candidate_b` 不能。

单元素元组依靠逗号形成，括号本身只用于分组。`candidate_b` 内含不可哈希列表，所以计算整个元组的哈希时会引发 `TypeError`。

常见错误是把 `(10)` 认成元组，或只看最外层不可变就认定可哈希。回答到逗号语法和递归可哈希条件即可。

### 第 17 题：字典的 `get()` 与 `setdefault()`

**结论：**输出 `{'A': 80, 'C': [70]}`，然后输出 `[60]`。

`get("B", [])` 返回新建的默认列表，但不会把它存入 `scores`；修改 `missing` 不影响字典。`setdefault("C", [])` 在键缺失时把列表插入字典并返回同一列表，因此 `stored.append(70)` 改变了字典中保存的值。

常见错误是认为两个方法都会自动插入默认值。可能追问：键已存在时 `setdefault()` 会覆盖吗？不会，它返回已有值。

### 第 18 题：字典视图会随字典变化

**结论：**按插入顺序输出 `['name', 'age']`，随后输出 `True`。

`keys` 是关联字典的动态键视图。创建视图后添加 `age`，视图也反映这个变化。成员查询键视图通常能利用底层字典，平均为 `O(1)`；把视图转换为列表需要 `O(n)` 时间和空间。

常见错误是把视图理解成创建时复制的列表。若要固定快照，应显式写 `list(profile.keys())` 或其他合适副本。

### 第 19 题：集合运算

**结论：**四个集合分别是 `{3}`、`{1, 2, 3, 4}`、`{1, 2}` 和 `{1, 2, 4}`。

`&` 取共同元素，`|` 合并所有不同元素，`-` 只保留左集合独有元素，`^` 保留恰好出现在一方的元素。集合显示次序不属于本题答案。

常见错误是把差集认为具有交换性；`left - right` 和 `right - left` 通常不同。实际复杂度依参与集合大小和具体运算而异，不应把所有集合操作都笼统说成 `O(1)`。

### 第 20 题：`Counter` 的计数语义

**结论：**依次输出 `3`、`0`、`False`。

`banana` 中 `a` 出现三次。`Counter` 对缺失键的下标读取返回零，但这种读取本身不会把 `"x"` 插入映射，因此成员判断仍为假。

常见错误是把它与 `defaultdict(int)` 的缺失读取行为混淆。可能追问：显式执行 `counts["x"] += 1` 后呢？这会存入该键并将计数变成 1。

### 第 21 题：`defaultdict` 的默认工厂

**结论：**输出等价于 `{'A': [1], 'B': []}`，第二行是 `True`。

访问缺失的 `groups["A"]` 时，工厂 `list` 创建列表、存入字典并返回，随后加入 `1`。读取缺失的 `groups["B"]` 同样创建并存入空列表，所以再次访问得到同一对象。

常见错误是认为任何读取都没有副作用。若只想查询而不创建，可以使用成员判断或 `get()`，但要根据接口区分缺失和合法空值。

### 第 22 题：`deque` 的双端操作

**结论：**第一行输出 `1 4`，第二行输出 `[2, 3]`。

`appendleft()` 和 `append()` 分别从左、右加入；`popleft()` 和 `pop()` 分别从左、右删除并返回。对 `deque` 而言，这四个端点操作通常都是 `O(1)`。

常见错误是根据最终值正确就忽略容器选择。用列表也能得到相同结果，但头部插入、删除通常需要 `O(n)`。

### 第 23 题：`heapq` 只保证堆序

**结论：**`smallest` 与 `removed` 都是 `1`；弹出后列表第一个元素是 `2`。

`heapify()` 原地建立最小堆，通常为 `O(n)`。最小堆保证每个父节点不大于孩子，因此根是全局最小值；它没有保证不同子树之间形成完整排序。弹出根后通过下沉恢复堆序，通常为 `O(log n)`。

最后的具体内部排列可能受实现过程影响，不应把整个堆列表作为排序结果使用。常见错误是说 `heapify()` 等价于 `sort()`；若连续弹出所有元素，才会按非降序得到它们，并付出相应成本。

### 第 24 题：容器浅拷贝

**结论：**输出的 `original` 是 `[{"count": 99}, {"count": 2}]`，`copied` 是 `[{"count": 99}, {"count": 2}, {"count": 3}]`。

`.copy()` 建立了独立的外层列表，所以向 `copied` 追加不会改变 `original` 的长度。但是两个外层列表最初保存的是相同内部字典引用，修改第一个字典时两边都能观察到。

常见错误是把浅拷贝说成完全独立，或说它什么都没复制。完整的深拷贝机制放在第 9 章；本题回答到“外层独立、内层共享”已经足够。

## 三、找错与场景题

### 第 25 题：用列表实现高频队列

**一句话结论：**`list.pop(0)` 每次都要移动后续引用，最坏 `O(n)`；高频先进先出队列通常使用 `deque`。

列表末尾 `append()` 是摊销 `O(1)`，但每次从头部删除是 `O(n)`，连续处理 `n` 项可能累计到 `O(n²)`。`deque.append()` 和 `popleft()` 都通常是 `O(1)`，完整处理通常为 `O(n)`。

常见错误是只关注两种代码都能返回正确顺序。可能追问：若只处理几个元素是否必须修改？不一定，工程选型还看规模和可读性，但明确的队列语义用 `deque` 更能表达意图。

### 第 26 题：把列表用作字典键

**一句话结论：**列表可变且不可哈希，不能作为字典键；固定坐标可用 `(10, 20)`。

```python
position = (10, 20)
visited = {position: True}
```

若坐标需要变化，不应修改已经作为键的状态。可以删除旧元组键后用新坐标元组重新插入，或给对象一个与可变坐标无关、稳定且唯一的标识符作为键。

常见错误是建议把列表转成字符串却不定义可靠序列化规则，或尝试让可变状态参与哈希。回答边界是“键的哈希与相等语义在其驻留期间必须稳定”。

### 第 27 题：遍历字典时修改大小

**一句话结论：**遍历字典视图期间删除键改变了字典大小，通常会引发 `RuntimeError`；应遍历快照或分两阶段处理。

一种方式是先复制项目：

```python
scores = {"Ada": 95, "Lin": 0}

for name, score in list(scores.items()):
    if score == 0:
        del scores[name]
```

另一种方式是构造新字典：

```python
scores = {"Ada": 95, "Lin": 0}

scores = {
    name: score
    for name, score in scores.items()
    if score != 0
}
```

还可以先收集待删除键，再统一删除。快照或新字典通常需要 `O(n)` 额外空间；两阶段写法意图清楚。常见错误是认为只删除“当前项”就安全，或把修改值与改变字典大小混为一谈。

### 第 28 题：保留顺序的去重

**一句话结论：**`set` 不承诺按原输入顺序迭代，`list(set(values))` 不能表达“保留第一次出现”；应在扫描时用集合记录已见元素。

```python
values = [3, 1, 3, 2]
seen = set()
result = []

for value in values:
    if value not in seen:
        seen.add(value)
        result.append(value)
```

哈希行为正常时，时间平均为 `O(n)`，额外空间 `O(n)`；最坏时间可能因哈希冲突退化。对于可哈希元素，当前 Python 也可用 `list(dict.fromkeys(values))` 借助字典插入顺序。常见错误是把集合当前一次运行的显示顺序当作保证。

### 第 29 题：频率统计的容器选择

**一句话结论：**三者都能在线性扫描中完成统计；`Counter` 语义最直接，普通字典控制最明确，`defaultdict(int)` 省去显式初始化。

核心思路分别是：

```python
from collections import Counter, defaultdict


words = ["python", "sql", "python"]
word = "python"
counts = {}
counts_default = defaultdict(int)

counts[word] = counts.get(word, 0) + 1
counts_default[word] += 1
counts_counter = Counter(words)
```

处理 `n` 个单词在正常哈希条件下平均都是 `O(n)` 时间、`O(u)` 空间，其中 `u` 是不同单词数。不能脱离数据、版本和后续操作声称某一种永远最快；项目中应看语义清晰度、是否需要 `most_common()`、缺失键行为和团队约定。普通字典也保留键第一次插入的顺序。

### 第 30 题：最大的 `k` 个元素

**一句话结论：**全排序通常为 `O(n log n)`，大小为 `k` 的堆通常为 `O(n log k)` 时间和 `O(k)` 额外空间，适合 `k` 很小或数据流场景。

排序能直接给出全局顺序，实现简单；若后续还要完整有序结果，它可能更合适。固定小堆只保留当前最大 `k` 项，不需要存储并排序所有候选。流式数据每到一个元素即可更新堆，更自然，也不要求一次加载全部数据。

若最终要求最大的 `k` 项按顺序输出，还要对堆中 `k` 项排序，增加 `O(k log k)`。常见错误是写成 `O(n log k)` 后忘记输出顺序成本，或认为堆方法对任何 `k` 都必然更快。

## 四、连续追问题

### 第 31 题：字典的 `O(1)` 到底意味着什么

**一句话结论：**平均 `O(1)` 来自哈希值把键快速映射到少量候选位置，并不代表实现完全没有探测或比较。

1. 查询先计算哈希并定位候选槽位，正常装载和分布下探测次数不随 `n` 线性增长，所以平均 `O(1)`。
2. 冲突后继续探测其他候选位置，并用相等比较确认真正的键。
3. 大量恶意或异常冲突时，单次查询最坏可能达到 `O(n)`。
4. 字符串等类型的哈希随机化让不同进程的哈希布局难以预测，主要降低攻击者构造大量碰撞、导致拒绝服务的风险；这不是加密功能。
5. 哈希、冲突与相等确认是通用哈希表原理；CPython 的开放寻址、具体探测序列、表大小和扩容阈值属于实现细节。

常见错误是说“字典查找绝不遍历所以永远 `O(1)`”，或把随机哈希说成保护字典内容。回答到性能条件、安全动机和语言/实现边界即可。

### 第 32 题：列表追加为什么是摊销 `O(1)`

**一句话结论：**扩容虽然单次最坏 `O(n)`，但容量按比例留余量后不会每次发生，连续 `m` 次追加的总工作量为 `O(m)`，所以每次摊销 `O(1)`。

扩容搬移的规模形成几何级数，例如数量级上可理解为 `1 + 2 + 4 + ... + m`，总和仍是 `O(m)`。这不是假设输入随机后求期望，而是对整串操作给总成本上界，因此准确术语是“摊销”，不是平均输入复杂度。

具体扩容比例由 CPython 版本和实现决定，不应死记；关键是保留额外容量、扩容次数远少于追加次数。常见错误是说每一次追加都为最坏 `O(1)`，或把一次运行耗时平均值当作摊销证明。

### 第 33 题：容器选择综合场景

**一句话结论：**数据结构应围绕最频繁的关键操作和所需语义选择，而不是只比较一个方法的常数。

1. 保持顺序并频繁按下标访问：`list`，索引通常 `O(1)`。
2. 频繁从两端增删：`deque`，端点操作通常 `O(1)`。
3. 只判断用户编号是否出现：`set`，成员判断平均 `O(1)`、最坏 `O(n)`；若还需次数则改用字典或 `Counter`。
4. 固定二维坐标作为键：含两个可哈希值的 `tuple`，如 `(x, y)`。
5. 随时取得最小优先级：用 `heapq` 管理列表，查看堆顶 `O(1)`，加入和弹出通常 `O(log n)`。
6. 统计错误码且保留首次顺序：普通 `dict` 或 `Counter`；当前 Python 字典按首次插入顺序迭代，更新计数不改变原位置，单次更新平均 `O(1)`。

可能改变选择的条件包括是否需要排序、元素能否哈希、是否频繁随机访问、数据是否流式以及是否需要线程间通信。常见错误是把“有顺序”笼统等同于“已排序”。

### 第 34 题：综合复杂度分析

**一句话结论：**原代码最坏为 `O(n²)`，因为外层遍历 `n` 条记录，每次都可能在线性列表中查询；换成集合后，在正常哈希条件下平均降为 `O(n)`。

若元素不可哈希，可根据数据性质考虑排序后双指针、把对象转换成稳定可哈希键，或继续线性比较。排序方案通常为 `O(n log n)`，还要处理是否允许改变顺序及如何保留原结果顺序。常见错误是数循环层数而不分析循环体中的隐藏线性操作。

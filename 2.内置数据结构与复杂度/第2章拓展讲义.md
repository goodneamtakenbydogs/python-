## 2. 哨兵对象：为特殊状态准备的独特标记

### 2.1 `None` 为什么有时不够用

先看两个字典：

```python
with_none = {"font_size": None}
without_key = {}

print(with_none.get("font_size"))
print(without_key.get("font_size"))
```

两次调用都返回 `None`，但实际状态不同：

```text
with_none：键存在，保存的值就是 None
without_key：键不存在，get() 省略默认值时返回 None
```

如果业务允许字典保存 `None`，只检查返回值就无法区分这两种状态。

### 2.2 哨兵对象是什么

**哨兵对象**是专门用来代表某种特殊状态的独特对象。它不是 Python 的特殊语法，而是一种编程模式。

这里可以创建一个只表示“键不存在”的对象：

```python
MISSING = object()
```

`object()` 在这里创建一个普通对象。暂时不需要掌握类的完整机制，只需要知道：每次调用 `object()` 都会得到一个身份不同的新对象。

变量名使用全大写，是在表达“这是一个准备长期复用的特殊标记”，而不是普通业务数据。

### 2.3 使用哨兵区分两种状态

```python
MISSING = object()

settings = {"font_size": None}
result = settings.get("font_size", MISSING)

if result is MISSING:
    print("键不存在")
else:
    print("键存在，保存的值是：", result)
```

这里的 `result` 是 `None`，但它不是 `MISSING`，因此可以判断键确实存在。

换成空字典：

```python
MISSING = object()

settings = {}
result = settings.get("font_size", MISSING)

if result is MISSING:
    print("键不存在")
```

这次 `get()` 返回的正是事先创建的 `MISSING` 对象。

整个判断过程可以概括为：

```text
get() 返回 MISSING
→ 键不存在

get() 返回其他任何对象，包括 None
→ 键存在，该对象就是字典中保存的值
```

`get()` 仍然不会把 `MISSING` 写入字典。它只在键不存在时把传入的默认对象返回给调用者。

### 2.4 为什么使用 `is` 判断

使用哨兵时关心的不是“某个对象的值是否与哨兵相等”，而是“它是否就是事先创建的那个哨兵对象”，所以使用身份判断：

```python
if result is MISSING:
    print("键不存在")
```

这里不使用：

```python
if result == MISSING:
    ...
```

`==` 会进入对象的相等性规则，而这种规则可以由类型自定义；`is` 直接判断两个名字是否指向同一个对象，更符合哨兵的设计目的。

### 2.5 哨兵必须先创建一次，再重复使用

下面的写法不能工作：

```python
settings = {}
result = settings.get("font_size", object())

if result is object():
    print("键不存在")
```

两个 `object()` 分别创建了两个对象：

```text
第一个 object() → 对象 A，作为 get() 的默认值
第二个 object() → 对象 B，用于 is 判断

对象 A is 对象 B → False
```

正确做法是只创建一次：

```python
MISSING = object()
result = settings.get("font_size", MISSING)

if result is MISSING:
    print("键不存在")
```

### 2.6 为什么不用特殊字符串或数字

也许会想到使用一个看起来特殊的字符串：

```python
result = settings.get("font_size", "__MISSING__")
```

但字典可能真的保存这个字符串：

```python
settings = {"font_size": "__MISSING__"}
```

这时又无法区分“键不存在”和“键存在且值恰好是该字符串”。`-1`、`0`、空字符串和空列表也可能是合法业务数据，都存在相同问题。

单独创建且不作为正常数据使用的对象，更适合承担特殊标记的职责。

### 2.7 什么时候直接使用 `in`

如果只想判断键是否存在，成员判断最直接：

```python
if "font_size" in settings:
    print("键存在")
```

如果既要区分键是否存在，又要取得值，也可以写成：

```python
if "font_size" in settings:
    value = settings["font_size"]
else:
    value = 14
```

哨兵方案把“取得值”和“取得缺失标记”合并在一次 `get()` 中：

```python
MISSING = object()
value = settings.get("font_size", MISSING)

if value is MISSING:
    value = 14
```

两种写法都可以。优先选择当前代码中语义最清楚的写法，不必为了少写一次查找而机械使用哨兵。

### 2.8 哨兵还可以区分“未提供实参”和“明确传入 `None`”

哨兵模式不只用于字典。函数有时也需要区分：

```text
调用者没有为该形参提供实参
调用者明确传入了 None
```

例如：

```python
MISSING = object()


def configure(value=MISSING):
    if value is MISSING:
        return "使用原设置"
    if value is None:
        return "明确清空设置"
    return f"改为 {value}"
```

三个调用表达不同意图：

```python
configure()       # 没有提供实参
configure(None)   # 明确传入 None
configure(20)     # 明确传入 20
```

形参默认值以及实参与形参绑定会在第 3 章完整学习。这里的重点仍然是：当 `None` 已经具有正常业务含义时，需要另一个独特对象表示“缺失”。

### 2.9 哨兵对象与 `None`、成员判断的选择

下面几种情况不一定需要哨兵：

- 字典永远不会合法保存 `None`，此时可以直接把 `None` 当作缺失标记。
- 只需要知道键是否存在，此时 `key in mapping` 更直接。
- 业务已经定义了明确且不会与正常数据冲突的状态类型。

使用哨兵之前应先问：当前是否真的需要区分多个看起来相同的返回结果？

### 2.10 哨兵对象的使用规则总结

```text
哨兵对象是什么？
→ 一个专门表示特殊状态的独特对象。

为什么不用 None？
→ None 可能本身就是合法数据。

为什么使用 object()？
→ 可以创建一个与正常业务数据不同的独特对象。

为什么使用 is？
→ 要判断是否就是同一个哨兵对象，而不是比较值是否相等。

最常见错误是什么？
→ 在 get() 和 is 判断处分别调用 object()，实际创建了两个不同对象。
```

## 3. 元组与列表的 CPython 存储模型

### 3.1 元组与列表的存储结构对比

完整讲义已经给出 Python 使用者必须掌握的规则：元组创建完成后不能改变长度，也不能替换位置中的对象引用。本专题继续回答两个实现层问题：

1. CPython 通常怎样保存元组元素？
2. 元组与可以动态扩展的列表在结构上有什么区别？

这里讨论的是 CPython 的常见实现，不是所有 Python 实现必须采用的内存布局。PyPy、MicroPython 或未来 CPython 版本可以使用不同结构，只要继续满足 Python 对外保证的行为。

### 3.2 元组是变长对象，但实例长度固定

“变长对象”与“对象创建后可变”不是一回事。

在 CPython 的 C 层结构中，元组属于创建时可以指定不同元素数量的对象：一个元组可以有两个槽位，另一个可以有一百个槽位。但某个具体元组一旦按长度 `n` 创建完成，它的槽位数量就固定下来。

可以用下面的简化模型理解：

```text
包含 3 个元素的元组实例

┌──────────────────────┐
│ 对象管理信息         │
├──────────────────────┤
│ 长度：3              │
├──────────────────────┤
│ 对象引用槽位 0       │──→ 元素对象 A
├──────────────────────┤
│ 对象引用槽位 1       │──→ 元素对象 B
├──────────────────────┤
│ 对象引用槽位 2       │──→ 元素对象 C
└──────────────────────┘
```

CPython 源码中的结构名称是 `PyTupleObject`。理解源码时可以把其中的元素区域看成随对象一起分配、数量由创建长度决定的一段对象指针槽位。

这些槽位保存的是 `PyObject *`，也就是对 Python 对象的 C 层引用，不是把整数、字符串或列表的全部内容复制进元组。

### 3.3 列表为什么还需要容量信息

列表必须支持：

```python
values.append(item)
values.insert(index, item)
values.pop()
```

如果列表每次追加都只申请恰好一个新槽位，就可能频繁重新分配和复制。因此 CPython 列表通常维护两个不同数字：

```text
当前长度：使用了多少槽位
已分配容量：目前一共准备了多少槽位
```

简化结构是：

```text
PyListObject
├── 对象管理信息
├── 当前长度
├── 已分配容量
└── 指向对象引用数组的指针
```

当容量不足时，列表申请更大的引用数组并搬移已有引用；当容量仍有空余时，末尾追加可以直接使用预留槽位。这是 `append()` 摊销 `O(1)` 的结构基础。

元组不支持追加，不需要为未来元素维护这类预留容量。

### 3.4 “不可变”由类型操作规则落实

下面的代码会失败：

```python
values = (10, 20)
# values[0] = 99
```

Python 执行下标赋值时，会让对象所属类型处理“替换某个下标”这项操作。列表类型实现了可写下标，元组类型没有向普通 Python 代码提供对应的赋值操作。

可以观察公开接口：

```python
print(hasattr(list, "__setitem__"))   # True
print(hasattr(tuple, "__setitem__"))  # False
```

这里的 `__setitem__()` 是下标赋值协议在 Python 层可以观察到的特殊方法。类型协议的完整规则放在第 6 章；当前只需理解，元组不可变是类型主动拒绝修改操作，不是硬件把内存设置成只读。

### 3.5 构造阶段为什么仍然需要写入槽位

如果元组槽位永远不能写，解释器也无法创建元组。CPython 的内部代码会经历类似过程：

```text
按长度 n 申请一个尚未公开的新元组
→ 把各元素引用放入对应槽位
→ 构造完成
→ 把成品交给普通 Python 代码使用
```

CPython C API 提供用于构造新元组的接口，内部宏也能直接填写槽位。这些操作只应按照 API 约束用于尚未与其他代码共享的新对象。任意修改已经公开或共享的元组会破坏不可变性假设，普通 Python 代码也没有这条修改路径。

所以：

```text
构造元组时由解释器填充槽位
```

与：

```text
构造完成后，Python 使用者不能修改槽位
```

并不矛盾。

### 3.6 `+=` 为什么产生新的绑定关系

```python
values = (1, 2)
alias = values
values += (3,)
```

对于元组，这个过程可以理解为：

```text
读取 values 原来绑定的元组
→ 为三个元素分配结果元组
→ 复制原来的两个引用
→ 放入新元素引用
→ 让名字 values 绑定结果元组
```

`alias` 没有参与最后一步，所以仍然绑定旧元组。

不要把所有 `+=` 都理解为同一种底层行为。列表的 `+=` 通常调用原地扩展能力；元组没有这种能力，只能得到新结果并重新绑定左侧名字。

### 3.7 `sys.getsizeof()`：元组与列表的浅层大小

`sys.getsizeof()` 可以返回当前 CPython 环境中一个对象本身的浅层大小：

```python
import sys

tuple_values = tuple(range(10))
list_values = list(range(10))

print(sys.getsizeof(tuple_values))
print(sys.getsizeof(list_values))
```

在常见 CPython 版本中，相同元素数量的元组通常更小，因为列表还需要支持动态容量。但不能背诵某次运行的具体字节数，原因包括：

- Python 版本和构建方式可能不同。
- 列表当时的预留容量可能不同。
- `getsizeof()` 只报告外层对象的浅层大小，不会递归加总元素对象。
- 元组和列表通常引用同一批元素对象，不能把元素大小重复归因于某个外层容器。

这个实验只能帮助观察当前实现，不能把输出数字当成 Python 语言保证。

### 3.8 哈希计算仍要访问内部元素

元组外层固定，不表示可以脱离内部元素直接得到哈希值。元组哈希需要组合各元素的哈希：

```text
元组中的每个元素都可哈希
→ 可以继续组合整个元组的哈希

任一元素不可哈希
→ 整个元组哈希失败
```

当前 CPython 是否缓存某类对象的哈希结果属于实现细节。业务代码只应依赖“可哈希对象在参与哈希容器期间满足稳定性与相等性约束”，不应假设一次 `hash(tuple_value)` 后结果必然被缓存。

### 3.9 元组各项操作的复杂度

固定槽位不会让所有元组操作都变成 `O(1)`：

- 读取长度：对象记录长度，`O(1)`。
- 按下标读取：直接定位引用槽位，`O(1)`。
- 成员查找：最坏逐个比较，`O(n)`。
- 拼接：创建结果并复制两边引用，`O(n + m)`。
- 普通切片：结果含 `k` 个引用时，通常需要 `O(k)` 时间和空间。
- 反复拼接：每次复制越来越长的旧内容，总成本可能达到 `O(n²)`。

因此，元组适合已经确定的固定结构；持续构建数据时，通常先使用列表，完成后再转换为元组。

### 3.10 语言保证与实现细节

```text
可以依赖的 Python 行为：
元组长度和位置引用不能通过普通 Python 操作改变。

用于解释的 CPython 模型：
元组按创建长度分配固定引用槽位；
列表维护可调整的引用数组和容量信息。

不应依赖的细节：
具体 C 字段排列、对象头字节数、扩容比例、
某次 getsizeof() 输出或内部宏行为。
```

源码细节的价值是解释语言行为和复杂度，不是让业务代码绕过不可变性。

# 第 7 章复习卡：异常与资源管理

学完讲义后快速回忆；第一次遇到的机制应回到完整讲义。

## 1. 异常控制流与资源的取得和释放

```text
控制流：在哪一行失败 → 哪层跳过后续代码 → 哪层处理或继续抛出
资源流：何时取得 → 暂停时由谁持有 → 正常或失败时由谁释放
```

已发生的对象修改和外部操作不会因为抛出异常自动撤销。

## 2. 异常层级

```text
BaseException
├── Exception → ValueError、TypeError、LookupError → KeyError 等
├── KeyboardInterrupt
├── SystemExit
└── GeneratorExit
```

`except Exception` 不等于裸 `except:`。多个分支从上到下匹配第一个适用者，具体子类处理通常放在宽泛父类之前。

## 3. 四个 `try` 子句

| 路径 | `except` | `else` | `finally` |
|---|---|---|---|
| `try` 正常走到末尾 | 不运行 | 运行 | 运行 |
| `try` 抛出并被当前层捕获 | 匹配者运行 | 不运行 | 运行 |
| `try` 抛出但本层不匹配 | 不运行 | 不运行 | 清理后继续传播 |
| `try` 提前 `return` | 不运行 | 不运行 | 返回前运行 |

`finally` 中的新 `return` 或新异常可能盖掉旧结果和原异常；清理块尽量不要决定业务返回值。

## 4. 抛出与异常链

- `raise Error(...)`：主动产生异常。
- 活动 `except` 中单独 `raise`：继续抛原异常。
- `raise error`：抛同一对象，但通常增加当前抛出位置；旧失败帧仍在。
- `raise NewError(...) from original`：建立显式 `__cause__`。
- `from None`：抑制旧上下文的默认显示，不保证旧对象被删除。

`str(error)` 主要给消息；traceback 给发生位置和调用路径。自定义异常可保存 `row`、`field` 等结构化信息，不靠解析消息判断分支。

观察 traceback 时，裸重抛可见“包装函数 → 原失败函数”；写出 `raise error` 通常还会多一层包装函数的重新抛出帧。`traceback.format_exc()` 读取当前处理中的异常，`logging.exception()` 在处理块记录消息和 traceback；选一个负责上报的边界即可。

EAFP 是先尝试实际操作并捕获预期错误；LBYL 是先检查再操作。检查结果可能在使用前过时，`try` 也不自动让多步操作变成原子操作。两者按接口和失败成本选择，捕获范围尽量小。

## 5. 资源所有权

```text
取得成功 → 进入负责释放的范围 → 使用 → 正常/异常/提前返回均收尾
```

文件要关闭，锁要释放，事务要明确提交或回滚。局部名字消失不代表资源已按接口约定清理。取得过程若部分成功后失败，取得逻辑自身也要负责已取得的部分。

取得一对资源时，若第一个已取得、第二个失败，负责交付这对资源的一层应先关闭第一个，再把错误交给调用方；第二个取得函数内部的部分资源仍由它自己清理。

## 6. `with` 与上下文管理器

```text
求值 manager
→ __enter__()，其返回值交给 as
→ 执行代码块
→ __exit__(exc_type, exc_value, traceback)
```

正常离开时三个异常参数都是 `None`。异常路径中，`__exit__()` 返回真值会抑制这次异常，假值或 `None` 让它继续传播。当前管理器的 `__enter__()` 自己失败，不会调用自己的 `__exit__()`；多个管理器按进入的逆序退出。

## 7. 生成器式管理器

`@contextmanager` 把 `yield` 前接到进入，`yield` 的值交给 `as`，恢复后完成退出。代码块抛出异常时，异常被送回暂停的 `yield`。清理通常放在 `try/finally`；捕获后不重抛可能导致异常被抑制。

返回持有文件的生成器时，文件可能在首次消费时才打开，并在暂停期间持续打开。提前停止的调用者须按接口负责关闭。

```text
创建生成器：尚未进入 with
第一次 next()：进入 with、取得并产出一行，资源仍打开
显式 close()：生成器内部 finally → 退出 with → 资源关闭
```

## 8. 常见陷阱

1. 把语法错误和运行时异常混在一起。
2. 把父类 `except` 放前面，使具体分支失效。
3. `except Exception: pass` 吞掉真正的编程错误。
4. 裸 `except:` 拦住中断或退出信号。
5. 把 `else` 当作“最终没报错就运行”。
6. 在 `finally` 里返回，盖掉原异常。
7. 转换异常类型却不保留原始原因。
8. `__exit__()` 无条件返回真值，误把失败视为成功。
9. 返回文件生成器但不说明提前停止后的关闭责任。
10. 每一层重复记录同一错误，或把敏感实参写入日志。
11. 先检查条件后仍假设状态不变，忘记实际操作时可能已经变化。

## 9. 一分钟自测

1. `Exception` 为什么不是全部异常类的顶层？
2. 内层抛错后，中层没有处理时哪些语句会跳过？
3. `else` 和 `finally` 的触发条件有何不同？
4. 裸 `raise` 与 `raise NewError(...) from error` 有何不同？
5. `finally` 中返回为什么危险？
6. `__exit__()` 返回真值会怎样？
7. `__enter__()` 自己失败时谁负责清理已取得的部分？
8. 生成器暂停时文件为什么可能仍打开？
9. 一次业务失败又发生清理失败时，如何找到原故障？
10. 为什么 `raise error` 的 traceback 可能比裸 `raise` 多一层？
11. 第一个资源成功、第二个失败时谁关闭第一个？
12. 生成器产出一行后，为什么内部的 `with` 尚未退出？

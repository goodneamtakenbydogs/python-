# 第 7 章完整讲义：异常与资源管理

本章从“失败发生后代码怎样走”开始，而不是先背一张异常名称表。第 1～10 节建立异常对象、传播、捕获与重新抛出的运行模型；第 11～19 节把同一模型用于文件、锁、事务和上下文管理器；最后分析容易掩盖原错误的写法。阅读例子时同时记录两列：**下一步执行哪一行**，以及**已取得的资源是否仍被持有**。

## 1. 语法错误与运行时异常的发生时机

### 1.1 语法错误发生在执行目标代码之前

下面的函数定义少了一个形参位置，Python 无法把它解析为有效程序：

```python
# def broken(:
#     pass
```

**语法错误**表示代码不符合语言的书写规则。对一份含这种错误的源文件，解释器不能正常开始执行那部分程序。你不能在同一段无效源代码的外围写 `try`，指望那段代码先运行再捕获自己造成的语法错误。

但有效程序可以把另一段源代码当作字符串交给 `compile()` 检查，并捕获检查过程抛出的 `SyntaxError`：

```python
try:
    compile("def broken(:\n    pass", "<example>", "exec")
except SyntaxError as error:
    print(type(error).__name__)  # SyntaxError
```

这里运行的是外层有效代码；被检查的字符串没有作为正常函数定义运行。区分这两个层次，才不会把“语法错误”和“运行时异常”混为一谈。

### 1.2 运行时异常发生在代码已经开始执行之后

```python
events = ["started"]

try:
    int("not a number")
except ValueError:
    events.append("conversion failed")

print(events)  # ['started', 'conversion failed']
```

`int()` 已开始执行，它发现文本不能按要求转换，于是抛出 `ValueError`。此前 `events` 的修改已经发生，异常不会自动撤销它。后面的 `except` 选择了另一条控制流。错误类型与业务操作的关系在下一节再展开。

## 2. 异常是对象，也有继承关系

### 2.1 什么叫“抛出异常”

异常对象保存失败类型和相关信息。`raise ValueError("bad input")` 创建或取得异常对象，要求当前正常执行路径中断，并向外寻找能处理它的代码。

```python
error = ValueError("bad input")
print(type(error).__name__)  # ValueError
print(str(error))            # bad input
```

异常不是普通函数的返回值。函数若抛出异常，就不会沿原来的 `return` 路径交还结果；调用者需要捕获、让它继续传播，或由更外层处理。

### 2.2 `BaseException`、`Exception` 与具体类型

Python 的异常类存在继承层级。这里先记住骨架：

```text
BaseException
├── Exception
│   ├── ValueError
│   ├── TypeError
│   ├── LookupError
│   │   ├── KeyError
│   │   └── IndexError
│   └── OSError
├── KeyboardInterrupt
├── SystemExit
└── GeneratorExit
```

图只列本章会用到的部分，不是完整异常树。`KeyError` 是 `LookupError` 的子类，因此一个捕获 `LookupError` 的分支也能捕获 `KeyError`。`OSError` 常用于文件等系统操作失败；`KeyboardInterrupt` 常见于用户主动中断程序，`SystemExit` 表示退出请求，`GeneratorExit` 会在关闭生成器时出现。后三者没有继承 `Exception`，所以普通的 `except Exception` 不会捕获它们；裸 `except:` 的范围则更广，可能挡住用户中断或程序退出请求。

```python
print(issubclass(KeyError, LookupError))          # True
print(issubclass(KeyboardInterrupt, Exception))  # False
print(issubclass(KeyboardInterrupt, BaseException))  # True
```

**异常匹配**按类型及其父类判断，不按错误消息里的中文或英文关键词匹配。不要从“这个错误看起来像类型问题”猜它一定是 `TypeError`；实际抛出的类型由运行的操作决定。

## 3. 异常沿调用栈传播

第 3 章把每次函数调用看成一层栈帧。某层无法处理异常时，这一层尚未执行的普通语句会跳过，异常返回到调用它的那一层继续寻找处理者。

```python
events = []


def inner():
    events.append("inner entered")
    raise ValueError("invalid")
    # events.append("inner after raise")


def middle():
    events.append("middle before inner")
    inner()
    events.append("middle after inner")


try:
    middle()
except ValueError:
    events.append("outer handled")

print(events)
```

结果依次是 `inner entered` 前的 `middle before inner`、`inner entered`、`outer handled`。`inner()` 抛出后，`middle()` 没有自己的处理分支，因此 `middle after inner` 不执行；异常到达外层 `except` 后才转为已处理状态。

```text
调用 middle()
→ middle 调用 inner()
→ inner 抛出 ValueError
→ inner 中断普通路径
→ middle 也没有匹配处理，跳过后续普通语句
→ 外层 except ValueError 处理
```

**traceback** 是异常发生时的调用路径记录。报错显示的多层文件、函数和行号，说明异常从哪里来、经哪些调用传播。它不是“最后一行报错就只检查最后一行”的意思。捕获后若继续抛出，还要尽量保留这条来源链。

## 4. `try` 与 `except` 怎样选择分支

### 4.1 用具体异常类型处理预期错误

```python
def parse_age(text):
    try:
        return int(text)
    except ValueError:
        return None
```

这里的接口明确规定：“文本不是整数时返回 `None`”。`int()` 若因完全不合适的输入类型而产生 `TypeError`，当前分支不会捕获它。这个区别是有意的：函数没有把所有错误都伪装成“文本写错”。如果 `None` 也是有效业务结果，就应选择更明确的结果类型或异常接口，而不是让调用者猜。

### 4.2 多个 `except` 从上到下选择第一个匹配者

```python
try:
    {}["missing"]
except KeyError:
    print("specific")
except LookupError:
    print("general")
```

输出 `specific`。`KeyError` 同时也是 `LookupError`，但第一条已经匹配，第二条不再执行。若把 `except LookupError` 放在前面，后面的 `except KeyError` 对这种异常就永远轮不到；把父类写在子类前面会掩盖具体处理。

`except (KeyError, IndexError):` 可以在确实采取同一种处理时合并两类异常。合并不意味着它们本质相同，只表示当前处理动作相同。

### 4.3 `except Exception` 与裸 `except:`

`except Exception as error` 适合程序边界需要记录普通错误、清理后继续上报的场景，不应成为所有函数的默认写法。只打印一句错误再返回 `None`，会把真正的编程错误与合法空结果混在一起。

裸 `except:` 连 `KeyboardInterrupt`、`SystemExit` 等更高层控制信号也可能拦下，风险更大。即便在需要统一清理的代码里，也应优先用 `finally` 保证清理，再让不认识的异常继续传播。

## 5. `else` 与 `finally` 是两种不同的路径

### 5.1 `try` 正常结束时的 `else` 与 `finally`

```python
events = []

try:
    events.append("try")
except ValueError:
    events.append("except")
else:
    events.append("else")
finally:
    events.append("finally")

print(events)  # ['try', 'else', 'finally']
```

`else` 只在 `try` 代码块正常走到末尾时执行；`finally` 在离开这组结构前执行清理路径。把成功后才应执行的动作放在 `else`，能避免它意外落在被捕获异常的范围里。

### 5.2 异常被捕获后的 `except` 与 `finally`

```python
events = []

try:
    events.append("try")
    raise ValueError("failed")
except ValueError:
    events.append("except")
else:
    events.append("else")
finally:
    events.append("finally")

print(events)  # ['try', 'except', 'finally']
```

异常出现后跳到匹配的 `except`，因此 `else` 不执行。`except` 正常结束后仍经过 `finally`。

### 5.3 未被当前分支捕获时也经过 `finally`

```python
events = []

try:
    try:
        events.append("inner try")
        raise TypeError("unexpected")
    except ValueError:
        events.append("inner handled")
    finally:
        events.append("inner cleanup")
except TypeError:
    events.append("outer handled")

print(events)  # ['inner try', 'inner cleanup', 'outer handled']
```

内层没有匹配的 `except`，但它的 `finally` 先执行；之后异常继续传播到外层。这就是 `finally` 与“捕获所有异常”不同的地方：它能清理，却不必改变错误归属。

### 5.4 `else` 的执行条件与异常传播

若 `try` 中执行 `return`、`break` 或 `continue` 而没有正常走到末尾，`else` 不执行，`finally` 仍会在离开前运行。若 `else` 自己抛出异常，前面的 `except` 不会反过来捕获它，但 `finally` 仍会执行。判断时先看当前离开的原因，再看清理，而不是只背四个词的固定顺序。

```python
events = []
try:
    try:
        events.append("try")
    except ValueError:
        events.append("inner except")
    else:
        events.append("else")
        raise ValueError("from else")
    finally:
        events.append("finally")
except ValueError:
    events.append("outer caught")

print(events)  # ['try', 'else', 'finally', 'outer caught']
```

内层的 `except` 只保护前面的 `try` 代码块，不会回头接住同级 `else` 中产生的新异常。外层处理者才有机会捕获它。

## 6. `finally` 可以清理，也能意外覆盖结果

### 6.1 `return` 前仍运行 `finally`

```python
events = []


def calculate():
    try:
        events.append("body")
        return 10
    finally:
        events.append("cleanup")


result = calculate()
print(result, events)  # 10 ['body', 'cleanup']
```

函数准备返回 `10` 时，会先执行 `finally`，然后把结果交给调用者。这里清理只记录事件，不改变返回值。

### 6.2 `finally` 里的新 `return` 会盖掉旧控制流

```python
def masked_result():
    try:
        raise ValueError("important failure")
    finally:
        return "looks successful"


print(masked_result())  # looks successful
```

原本的异常被 `finally` 中的 `return` 掩盖，调用者看见一个貌似成功的结果。若 `try` 已准备返回旧值，`finally` 的新 `return` 也会取而代之；`break`、`continue` 或在 `finally` 新抛出的异常同样可能改变原控制流。把 `finally` 用于释放资源，尽量不要在其中决定业务返回结果。

“`finally` 总会执行”也不是不带条件的保证：进程被强制终止、解释器崩溃等情况不属于正常的 Python 控制流。资源设计应保证常见返回和异常路径正确，不应声称能抵御一切外部终止。

### 6.3 `break`、`continue` 退出 `try` 时的清理

`return` 不是唯一提前离开的方式。循环中的 `continue` 要去下一轮，`break` 要退出循环；只要离开当前 `try`，就先执行它的 `finally`：

```python
events = []

for number in range(2):
    try:
        events.append(("body", number))
        if number == 0:
            continue
        break
    finally:
        events.append(("cleanup", number))

print(events)
# [('body', 0), ('cleanup', 0), ('body', 1), ('cleanup', 1)]
```

第一轮 `continue` 前清理，第二轮 `break` 前也清理。这个例子说的是语言控制流，不代表可以在 `finally` 中随意再写新的 `break` 或 `continue`；后者可能覆盖正在传播的异常，和 `finally` 中 `return` 的风险相同。

## 7. `raise`、重新抛出与调用方责任

### 7.1 主动拒绝无效输入

```python
def require_positive(number):
    if number <= 0:
        raise ValueError("number must be positive")
    return number
```

调用者传入 `0` 时，函数没有可返回的合法正数；它用异常明确表明接口前提未满足。错误消息给人阅读，程序分支主要依据异常类型，而不是解析消息文本。

### 7.2 捕获后只记录，再用裸 `raise` 继续传播

```python
events = []


def convert(text):
    try:
        return int(text)
    except ValueError:
        events.append("conversion failed")
        raise


try:
    convert("bad")
except ValueError:
    events.append("caller knows")

print(events)  # ['conversion failed', 'caller knows']
```

单独的 `raise` 在当前正在处理的异常上下文中重新抛出原异常，保留原始失败位置供外层判断。`raise error` 也会抛出同一个异常对象，但通常会把当前重新抛出的行加入 traceback；它并非“完全丢掉旧 traceback”，只是记录路径不同。离开异常处理上下文后，不能随处写一个没有目标的裸 `raise`。

### 7.3 裸 `raise` 与 `raise error` 的 traceback 对比

先让两个包装函数都调用同一个失败源。标准库 `traceback.extract_tb()` 把异常对象保存的 traceback 拆成帧；这里只取函数名，不依赖编辑器中的行号：

```python
import traceback


def fail():
    raise ValueError("bad")


def reraised_bare():
    try:
        fail()
    except ValueError:
        raise


def reraised_named():
    try:
        fail()
    except ValueError as error:
        raise error


for function in (reraised_bare, reraised_named):
    try:
        function()
    except ValueError as error:
        names = [frame.name for frame in traceback.extract_tb(error.__traceback__)]
        relevant = [name for name in names if name in ("reraised_bare", "reraised_named", "fail")]
        print(function.__name__, relevant)
```

结果中，裸重抛路径的相关帧是 `['reraised_bare', 'fail']`；显式写出异常对象的路径是 `['reraised_named', 'reraised_named', 'fail']`。多出的同名帧对应 `raise error` 所在的重新抛出位置，最初的 `fail` 帧并没有消失。面试中说“裸 `raise` 更直接保留原失败路径”即可；排查时真正需要看的仍是 traceback 中最早的失败处和沿途的调用。

## 8. 异常链：保留新旧错误的关系

### 8.1 转换异常类型时说明原因

一个底层库抛出 `ValueError`，对外接口可能想提供更贴近业务的异常。若直接改抛新错误而不说明关系，调用方难以找到根因。

```python
class ConfigurationError(Exception):
    pass


def read_port(text):
    try:
        return int(text)
    except ValueError as original:
        raise ConfigurationError("port must be an integer") from original


try:
    read_port("bad")
except ConfigurationError as error:
    print(type(error.__cause__).__name__)  # ValueError
```

`raise new from original` 建立显式原因，`error.__cause__` 指向原异常对象；traceback 展示时会把两层错误联系起来。调用者可以只按新的业务异常类型处理，同时排查时仍保留底层原因。

### 8.2 隐式上下文与 `from None`

在 `except` 中直接抛一个新异常，Python 仍会把正在处理的旧异常放入新异常的 `__context__`。显式 `from` 使因果意图更清楚；`from None` 会抑制旧上下文在默认 traceback 中的显示，但旧对象通常仍可从 `__context__` 观察到。它不是删除错误，也不应成为掩盖问题的常规办法。

```python
try:
    try:
        int("bad")
    except ValueError:
        raise RuntimeError("public failure") from None
except RuntimeError as error:
    print(error.__cause__ is None)                  # True
    print(isinstance(error.__context__, ValueError))  # True
    print(error.__suppress_context__)              # True
```

`from None` 改变的是默认展示哪段链，不代表旧异常对象从运行状态中彻底消失。

### 8.3 `NotImplemented` 与 `NotImplementedError` 的区别

第 6 章的 `NotImplemented` 是比较特殊方法返回的单例值；`NotImplementedError` 是一种异常，表示某个操作尚未实现。两者名称相似，却在控制流中承担完全不同的角色。

## 9. 自定义异常与错误信息

自定义异常通常继承 `Exception` 或更具体的异常类，用来让调用者按语义捕获，而不是解析错误字符串：

```python
class InvalidFieldError(Exception):
    def __init__(self, field, message):
        self.field = field
        super().__init__(message)


try:
    raise InvalidFieldError("age", "must be non-negative")
except InvalidFieldError as error:
    print(error.field, str(error))  # age must be non-negative
```

继承 `Exception` 让普通应用错误处理能接住它，却不冒充程序退出或键盘中断。字段 `field` 供程序定位输入项，消息供人阅读。错误类型要表达调用者能够区别处理的情况；只为给每个报错句子起一个新类名，会让接口变得难用。

## 10. 使用 traceback 和日志定位异常

异常对象保留类型、消息和 traceback。调试时优先查看“最初哪里失败”和“之后怎样传播”。标准库 `traceback` 可以把当前错误格式化为文本，`logging.exception()` 在异常处理块中记录错误及 traceback。这里不要求记忆日志配置，但要知道 `print(error)` 只显示消息，通常不足以解释调用链。

### 10.1 traceback 是从异常对象到调用位置的记录

在下例里，`read_count()` 的源代码本身没有写错转换规则，它只是调用了更内层的 `parse_count()`；但排查者仍要知道是谁把坏文本交了进去：

```python
import traceback


def parse_count(text):
    return int(text)


def read_count():
    return parse_count("bad")


try:
    read_count()
except ValueError as error:
    frames = traceback.extract_tb(error.__traceback__)
    print([frame.name for frame in frames[-2:]])  # ['read_count', 'parse_count']
```

`error.__traceback__` 关联这次异常的路径；`extract_tb()` 给出可阅读的帧摘要，包括函数名、文件和行号。这里从外到内能看见 `read_count → parse_count`，说明“坏文本进入转换”的调用链；真正失败的表达式仍要到 `parse_count` 中找。显示内容也可能包含文件路径等信息，不能不加选择地公开给终端用户。

### 10.2 当前异常与已保存异常怎样格式化

```python
import traceback

try:
    int("bad")
except ValueError:
    text = traceback.format_exc()
    print("ValueError" in text)  # True
```

`traceback.format_exc()` 读取当前正在处理的异常，因此通常放在 `except` 中。若已经把异常对象保存下来，之后可以用 `traceback.format_exception(error)` 格式化该对象及其链；它能包含显式原因或隐式上下文。`str(error)` 则主要得到消息文本，不会替你列出多层调用。

### 10.3 异常日志的记录位置与敏感信息处理

`logging.exception()` 的用途是在当前异常处理块中记录消息和异常追踪。下面的函数接收一个已由应用配置的 `logger`；此处只定义函数，不向外部日志系统发送内容：

```python
def convert_with_logging(text, logger):
    try:
        return int(text)
    except ValueError:
        logger.exception("conversion failed")
        raise
```

`logger.exception()` 会附带当前异常信息；普通 `logger.error("conversion failed")` 默认只记录这句文本，不能直接代替前者。这里仍裸重抛，让调用方按接口处理失败。通常由负责处理或统一上报的一层记录一次，避免同一异常跨四层重复记录四次。

把错误记录到日志前，仍要考虑密码、令牌等敏感实参不能原样写入；也不应把日志替代为“捕获后什么都不做”。对于预期输入错误，可给调用者简洁提示；对于意外程序错误，应保留足够上下文并在合适边界上报。

## 11. EAFP 与 LBYL：检查时机的选择

**LBYL**（Look Before You Leap）先检查条件，再执行操作；**EAFP**（Easier to Ask Forgiveness than Permission）先尝试操作，再捕获明确预期的异常。

```python
settings = {"timeout": 5}

if "timeout" in settings:  # LBYL
    first = settings["timeout"]

try:  # EAFP
    second = settings["timeout"]
except KeyError:
    second = 10
```

两种写法都可能合理。EAFP 能把“取得值”与“缺失时处理”写在一起，也避免在某些并发或外部状态场景中“刚检查完，实际执行前条件已变”的时间窗口。这个窗口常称为**检查与使用之间的竞态**；它不表示 `try` 自动解决所有并发问题。LBYL 在检查成本低、失败代价高或预期条件需要清楚展示时更自然。

不用真的启动两个线程，也能模拟“检查后数据变了”的问题：

```python
settings = {"timeout": 5}
was_present = "timeout" in settings
settings.pop("timeout")  # 模拟检查与使用之间的其他修改

try:
    value = settings["timeout"]
except KeyError:
    value = "missing at use"

print(was_present, value)  # True missing at use
```

`was_present` 描述的是过去那次检查，并不能保证现在还能读取到值。EAFP 把实际读取放在 `try` 中，可以按这次操作真正发生的结果处理；若一次操作本身跨多个外部步骤，它依然不保证整体原子性，需要锁、事务或接口自身的保证。反过来，预期失败很频繁、异常创建较昂贵或显式检查更能表达规则时，LBYL 也可能更合适；不能把两种风格简化成“Python 永远推荐其中一种”。

捕获范围要小：只把可能产生预期 `KeyError` 的读取放进 `try`。若把整段业务代码包起来，后面另一处真正的错误也可能被误认为“这个键不存在”。异常处理风格应服务具体接口，不是需要站队的语言口号。

例如下面这段代码要给配置提供默认超时，但调用 `send_request()` 也可能因为内部字典拼写错误抛出 `KeyError`。若把两行都放进同一个 `try`，`except KeyError` 就无法分辨“配置缺失”和“发送逻辑有缺陷”：

```python
settings = {}


def send_request(timeout):
    headers = {}
    return headers["Authorization"]  # 模拟发送逻辑内部的编程错误


try:
    timeout = settings["timeout"]
except KeyError:
    timeout = 10

try:
    send_request(timeout)
except KeyError:
    print("request error reached caller")
```

第一个 `try` 只处理配置缺少 `timeout`，于是使用默认值 `10`。`send_request()` 放在这个捕获范围之外，它内部产生的另一个 `KeyError` 会到达调用方，并显示 `request error reached caller`，不会被误认成配置缺失。外层第二个 `try` 只是为了让教学示例继续运行；真实调用方应根据请求接口决定记录、转换还是继续传播该错误。

## 12. 资源的取得、使用、释放与所有权

文件句柄、锁和数据库连接都属于需要明确**取得和释放**的资源。文件句柄让程序继续读写文件；锁让一段共享状态暂时只能由符合约定的一方使用；数据库事务把一组写入视作需要一起确认或回滚的操作。它们的具体协议不同，但生命周期问题相同：

```text
取得资源
→ 在有限范围内使用
→ 不论正常结束还是抛出异常，都明确结束这次使用
```

只让保存资源的局部名字离开函数，不等于已经按约定释放资源。其他对象可能还引用它，解释器回收时机也不应成为业务上的清理策略。先明确**所有权**：由哪个函数或代码块取得资源、由谁负责关闭、是否允许把它交给外层长期持有。

先假设接口明确约定：调用方把资源的关闭责任交给 `unsafe_read()`。即使有这个约定，下面的结构仍会出错：

```python
def unsafe_read(resource):
    data = resource.read()
    resource.close()
    return data
```

用一个会读取失败的对象观察状态：

```python
def unsafe_read(resource):
    data = resource.read()
    resource.close()
    return data


class FailingReader:
    def __init__(self):
        self.closed = False

    def read(self):
        raise OSError("read failed")

    def close(self):
        self.closed = True


resource = FailingReader()
try:
    unsafe_read(resource)
except OSError:
    pass

print(resource.closed)  # False
```

`read()` 抛出异常后，后面的 `close()` 没有执行。即使大多数测试走正常路径，这个资源接口仍不完整。如果调用方没有转交关闭责任，函数本来就不应擅自关闭传入资源；无论选择哪种接口，都必须先把所有权写清楚。

## 13. `try/finally` 负责正常与失败两条路径

### 13.1 使用 `StringIO` 练习资源关闭

标准库 `io.StringIO` 提供在内存中读写文本的对象，也有 `close()` 和 `closed` 状态。它适合练习清理，不需要创建真实文件：

```python
from io import StringIO


buffer = StringIO("hello")
try:
    content = buffer.read()
finally:
    buffer.close()

print(content, buffer.closed)  # hello True
```

改成在 `try` 中故意抛错时，`finally` 仍会执行 `close()`，然后异常继续向外传播。`finally` 负责资源，不需要假装自己知道怎样修复每种业务失败。

### 13.2 取得资源的时点决定谁能清理

```python
from io import StringIO


def acquire_resource():
    return StringIO("data")


def use_resource(resource):
    return resource.read()


resource = acquire_resource()
try:
    use_resource(resource)
finally:
    resource.close()
```

这里用内存文本对象模拟取得和使用资源。如果取得资源本身失败，程序尚未进入 `try`，也就没有成功取得、需要由这段代码关闭的资源。成功取得后才进入负责它生命周期的范围。若取得过程可能部分成功后再失败，取得函数本身还要负责清理它已取得的部分。

### 13.3 多个资源部分取得失败时的清理

先取得第一个，再尝试第二个。如果第二次失败，第一个已经存在，不能因为还没进入“正式使用”阶段就忘记它：

```python
from io import StringIO


events = []


def acquire_pair():
    first = StringIO("first")
    events.append("first acquired")
    try:
        events.append("second attempted")
        raise ValueError("cannot acquire second")
    except ValueError:
        first.close()
        events.append("first closed")
        raise


try:
    acquire_pair()
except ValueError:
    events.append("caller caught")

print(events)
# ['first acquired', 'second attempted', 'first closed', 'caller caught']
```

这个教学例子明确让第二步只抛出 `ValueError`，所以捕获这个具体类型，关闭 `first` 后立即裸重抛。`acquire_pair()` 是取得过程的所有者：它已经拿到 `first`，在向调用者成功交付完整结果前必须自己关闭它。

真实的第二步若可能以多种方式失败，不能随意把 `except Exception` 当作万能清理，因为它不覆盖 `KeyboardInterrupt`、`SystemExit` 等 `BaseException` 分支。更稳妥的设计是让每个取得函数负责自身的部分资源，并使用嵌套 `with` 或 `ExitStack` 登记已经成功取得资源的退出动作。只有成功交付后，调用方才能接过完整资源的关闭责任；所有权问题仍要先想清楚。

### 13.4 提前 `return` 也需要清理

```python
from io import StringIO


def first_character(buffer):
    try:
        return buffer.read(1)
    finally:
        buffer.close()


buffer = StringIO("abc")
print(first_character(buffer), buffer.closed)  # a True
```

`return` 准备交出字符，但函数必须先离开 `try` 范围，于是运行 `finally` 关闭资源，再把字符交给调用者。若清理本身抛出异常，原本准备好的返回值可能无法交付；清理错误也需要被认真对待。

## 14. `with` 是把取得与清理封装成协议

每次手写 `try/finally` 容易漏掉某条路径。**上下文管理器**是实现进入和退出协议的对象；`with` 让调用方用统一写法管理一个范围。

```python
from io import StringIO


buffer = StringIO("abc")
with buffer as active:
    print(active.read(1))  # a
print(buffer.closed)       # True
```

第 6 章认识了 `__enter__()` 与 `__exit__()`。这里把 `with manager as value:` 按可观察行为近似展开：

```text
求值 manager 表达式，得到上下文管理器
→ 调用 __enter__() 取得交给 as 的对象
→ 执行 with 内的代码块
→ 离开时调用 __exit__(异常类型, 异常对象, traceback)
```

正常离开时，传给 `__exit__()` 的异常相关参数是 `None`；代码块抛出异常时，三个参数描述正在传播的异常。`__exit__()` 返回假值或 `None`，异常继续传播；返回真值则表示管理器已处理它，外层不会再收到这一异常。

这只是控制流模型，不是说所有上下文管理器都在 `__enter__()` 中创建资源。文件对象通常在调用 `open()` 时已经得到，`__enter__()` 再建立受管理的使用范围。要判断具体资源何时产生，仍要看创建它的表达式。

## 15. 类式上下文管理器逐步执行

### 15.1 正常路径和异常路径

```python
class TracedScope:
    def __init__(self, events, suppress=False):
        self.events = events
        self.suppress = suppress

    def __enter__(self):
        self.events.append("enter")
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        self.events.append("exit:" + (exc_type.__name__ if exc_type else "none"))
        return self.suppress


events = []
with TracedScope(events) as scope:
    events.append("body")
print(events)  # ['enter', 'body', 'exit:none']
```

`scope` 绑定到 `__enter__()` 返回的对象；它不一定必须是管理器自身，只是这里选择返回 `self`。正常路径传给 `__exit__()` 的三个异常参数都是 `None`，其返回值在没有异常时没有“抑制异常”的对象可作用。

再让代码块失败，但不抑制：

```python
class TracedScope:
    def __init__(self, events, suppress=False):
        self.events = events
        self.suppress = suppress

    def __enter__(self):
        self.events.append("enter")
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        self.events.append("exit:" + (exc_type.__name__ if exc_type else "none"))
        return self.suppress


events = []
try:
    with TracedScope(events):
        events.append("body")
        raise ValueError("bad")
except ValueError:
    events.append("outer caught")

print(events)  # ['enter', 'body', 'exit:ValueError', 'outer caught']
```

`__exit__()` 先看见异常，返回假值后异常到外层 `except`。如果这里返回真值，外层处理分支就不会收到这次异常。只应在管理器确实完成约定的错误处理时抑制，不能为了让程序“看起来没报错”无条件返回 `True`。

### 15.2 `__enter__()` 自己失败的边界

如果当前管理器的 `__enter__()` 抛出异常，`with` 代码块尚未开始，该管理器的 `__exit__()` 不会被调用。管理器必须在 `__enter__()` 内处理已经取得的部分资源；外层已经成功进入的其他管理器仍会按自己的规则退出。

## 16. 多个上下文管理器的退出顺序

```python
events = []


class Marker:
    def __init__(self, name):
        self.name = name

    def __enter__(self):
        events.append("enter " + self.name)
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        events.append("exit " + self.name)
        return False


with Marker("outer"), Marker("inner"):
    events.append("body")

print(events)
```

进入顺序是 `outer → inner`，退出顺序是 `inner → outer`，与调用栈逐层返回相似。若内层抛出异常，内层 `__exit__()` 先处理；若未抑制，外层的 `__exit__()` 随后也能看到它。需要管理运行时才知道数量的多个资源时，标准库 `contextlib.ExitStack` 可以把退出动作集中登记并逆序执行；先掌握固定两个管理器的顺序，再学习这种工具。

如果第二个管理器还没成功进入，就不会调用它自己的 `__exit__()`；第一个已经进入，仍需要退出：

```python
class Marker:
    def __init__(self, name):
        self.name = name

    def __enter__(self):
        events.append("enter " + self.name)
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        events.append("exit " + self.name)
        return False


class FailingEntry:
    def __enter__(self):
        events.append("enter inner")
        raise ValueError("cannot enter")

    def __exit__(self, exc_type, exc_value, traceback):
        events.append("exit inner")


events = []
try:
    with Marker("outer"), FailingEntry():
        events.append("body")
except ValueError:
    events.append("outer caught")

print(events)  # ['enter outer', 'enter inner', 'exit outer', 'outer caught']
```

`body` 与 `exit inner` 都不会出现。若 `FailingEntry.__enter__()` 在抛错前已取得部分资源，它自己就要清理那部分；外层的退出不能替内层猜资源状态。

## 17. `@contextmanager`：用生成器写进入和退出

第 5 章学过 `yield` 会暂停。标准库 `contextlib.contextmanager` 用一个生成器函数把 `yield` 前、`yield` 处、`yield` 后分别接到上下文管理器的进入、交付与退出：

```python
from contextlib import contextmanager


@contextmanager
def tracked_value(events):
    events.append("acquire")
    try:
        yield "ready"
    finally:
        events.append("release")


events = []
with tracked_value(events) as value:
    events.append(value)
print(events)  # ['acquire', 'ready', 'release']
```

调用 `tracked_value(events)` 先得到一个上下文管理器；进入 `with` 时才推动内部生成器运行到 `yield`。`yield` 的值交给 `as value`，代码块完成后生成器从暂停处恢复，执行 `finally`。若代码块抛出异常，装饰器会在暂停的 `yield` 位置把异常送回生成器；`finally` 仍会运行，然后异常通常继续传播。

生成器式上下文管理器必须恰好向 `with` 交付一次。若在 `yield` 附近捕获异常却不重新抛出，异常可能被视为已处理；因此清理代码通常采用 `try/finally`，不要随意吞掉代码块里的错误。类式更适合具有多项状态和多种方法的管理器；生成器式适合一次进入、一次退出的短流程。

下面专门展示“处理后不重抛”的效果，只适合接口明确允许抑制这种异常的场景：

```python
from contextlib import contextmanager


@contextmanager
def swallow_value_error(events):
    try:
        yield
    except ValueError:
        events.append("handled")


events = []
with swallow_value_error(events):
    raise ValueError("known failure")
events.append("continued")
print(events)  # ['handled', 'continued']
```

代码块的异常在暂停的 `yield` 处被捕获，生成器正常结束，外层因此继续。若目的只是释放文件或锁，就不应采用这种吞错写法。

## 18. 文件、锁与事务各有什么责任

### 18.1 文件：谁打开，谁保证关闭

```python
def read_first_line(path):
    with open(path, encoding="utf-8") as file:
        return file.readline()
```

这个函数只定义了接口，不会在阅读示例时访问某个不存在的文件。调用时即使 `readline()` 抛出异常，已经进入的文件上下文仍会退出并关闭文件；若 `open()` 本身失败，就没有取得可供这个 `with` 关闭的文件对象。调用者得到的是读出的字符串，不是仍需自行关闭的文件。

不要把已经离开 `with` 的文件对象交给外层继续使用：

```python
def closed_reader(path):
    with open(path, encoding="utf-8") as file:
        return file


# reader = closed_reader("events.log")
# reader.readline()  # 文件已随 with 退出而关闭
```

第 5 章还见过返回生成器的情况：若 `with open(...)` 位于生成器函数内部，文件从首次消费开始保持打开，直到生成器正常耗尽或被明确关闭。调用方若提前停止，就必须考虑谁来关闭生成器，不能只看函数定义处有没有 `with`。

### 18.2 锁：保护范围结束时释放

线程锁用于保护某段共享状态，避免多个线程同时进入需要互斥的代码。标准库的锁对象支持 `with`，这样即使受保护代码抛出异常，也会按协议释放锁：

```python
from threading import Lock


lock = Lock()
with lock:
    print(lock.locked())  # True

print(lock.locked())      # False
```

进入代码块时锁已被持有，退出时上下文管理协议释放它，因此两次分别显示 `True`、`False`。这不能自动让整个程序线程安全。需要保护哪些共享操作、锁的粒度及死锁风险在第 10 章讨论；本章只关心“进入后最终释放”的生命周期。

### 18.3 事务：成功提交、失败回滚

数据库事务可以把一组写入看作一项整体操作。常见接口在正常离开时提交，出现异常时回滚，再把错误交给上层。下面只模拟事件，不连接真实数据库：

```python
class UnitOfWork:
    def __init__(self, events):
        self.events = events

    def __enter__(self):
        self.events.append("begin")
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        self.events.append("rollback" if exc_type else "commit")
        return False


events = []
with UnitOfWork(events):
    events.append("write")
print(events)  # ['begin', 'write', 'commit']
```

失败时同一个管理器走另一条路径：

```python
class UnitOfWork:
    def __init__(self, events):
        self.events = events

    def __enter__(self):
        self.events.append("begin")
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        self.events.append("rollback" if exc_type else "commit")
        return False


events = []
try:
    with UnitOfWork(events):
        events.append("write")
        raise ValueError("write failed")
except ValueError:
    events.append("caller handled")

print(events)  # ['begin', 'write', 'rollback', 'caller handled']
```

实际数据库驱动的事务接口可能不同，是否自动提交必须看具体库的约定；不要把这个教学模型说成所有数据库连接的默认行为。当前重要的是错误路径也要有明确动作，且 `False` 不吞掉原业务异常。

## 19. 清理异常对原始异常的影响

清理代码也可能抛出异常。如果正在传播 `ValueError`，`finally` 中又抛出 `RuntimeError`，调用方最终首先看到后者；前者通常保留为新异常的上下文。这个现象不能靠一句“`finally` 总执行”解释完。

```python
try:
    try:
        raise ValueError("work failed")
    finally:
        raise RuntimeError("cleanup failed")
except RuntimeError as error:
    print(type(error.__context__).__name__)  # ValueError
```

清理函数的接口应尽量可靠；确实失败时，至少要在合适边界保留两层错误信息，而不是无条件忽略清理异常或让原始错误完全失踪。文件关闭、事务回滚和锁释放各有不同的失败语义，不能用一个空 `except` 统一掩盖。

## 20. 异常应该在哪一层处理

调用栈中不是每一层都应该写 `except`。可以把职责分成三类：

1. **本层可以恢复**：例如用户输入无法转整数，本层能要求重填或按约定返回失败结果。
2. **本层只负责清理**：使用 `finally` 或 `with`，让异常继续到能决定业务含义的上层。
3. **本层需要翻译接口**：把底层异常转换成明确的业务异常，并用 `raise ... from ...` 保留原因。

一个底层文件函数如果抓住 `OSError` 后无条件返回空字符串，调用者就无法区分“文件确实为空”和“根本没读到文件”。反过来，应用最外层若直接把完整 traceback 当用户提示，也可能泄露路径、配置或敏感数据。合理边界通常是：靠近发生处保留技术原因，在能够决定业务响应的位置选择重试、提示或终止。

日志也要有边界。若每一层都捕获同一异常、打印一次、再重新抛出，最后一条失败会被记录多次，而调用栈信息却没有更清楚。通常在负责处理或统一上报的层记录一次，并让底层保持异常链。

## 21. 上下文管理器的异常抑制与传播

沿用第 15 节的 `TracedScope`，观察 `__exit__()` 返回真值的路径：

```python
class TracedScope:
    def __init__(self, events, suppress=False):
        self.events = events
        self.suppress = suppress

    def __enter__(self):
        self.events.append("enter")
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        self.events.append("exit:" + (exc_type.__name__ if exc_type else "none"))
        return self.suppress


events = []
with TracedScope(events, suppress=True):
    events.append("body")
    raise ValueError("handled here")
events.append("continued")
print(events)  # ['enter', 'body', 'exit:ValueError', 'continued']
```

外层继续执行是因为管理器明确返回真值，并非 Python “自动忽略了错误”。这种接口适合确实知道怎样处理某类异常的管理器；若让所有异常都被抑制，程序可能把事务失败当成提交成功。

生成器式上下文管理器也有类似边界：代码块的异常会被送回暂停的 `yield`。若管理器捕获它后正常结束而不重新抛出，包装器可能视为已经处理。想只做清理，应使用 `try/finally`；想有条件地处理，应明确写出允许处理的异常类型与返回约定。

## 22. 返回生成器时，清理责任会延后

第 5 章说明生成器函数调用后函数体不会立刻执行。这个事实会改变资源开始和结束的时刻：

```python
def iter_file_lines(path):
    with open(path, encoding="utf-8") as file:
        for line in file:
            yield line
```

调用 `iter_file_lines(path)` 时只是创建生成器；首次消费才进入 `with` 并打开文件。每次 `yield` 后文件仍被这次生成器执行持有。如果调用方只读一行就长期保存生成器，文件也可能长期保持打开。生成器耗尽、显式 `close()` 或最终被清理时会离开 `with`；回收发生的具体时点不应作为调用方的资源管理保证。仅有“函数代码里写了 `with`”不足以证明调用方可以忽略生命周期。

不用创建磁盘文件，也能观察这三个时刻。`StringIO` 在这里模拟文件，`streams` 只用于实验时观察关闭状态：

```python
from io import StringIO


events = []
streams = []


def iter_memory_lines():
    with StringIO("A\nB\n") as stream:
        streams.append(stream)
        events.append("entered")
        try:
            for line in stream:
                yield line.rstrip("\n")
        finally:
            events.append("leaving with")


source = iter_memory_lines()
print(events)  # []，还没有进入 with
print(next(source), events, streams[0].closed)  # A ['entered'] False
source.close()
print(events, streams[0].closed)  # ['entered', 'leaving with'] True
```

`close()` 在暂停点请求生成器结束，控制流先经过生成器内部的 `finally`，然后离开 `with`，由 `StringIO.__exit__()` 关闭资源。这条时间线说明：写了 `with` 是正确的清理机制，但返回生成器后，**何时触发退出**仍取决于消费和关闭责任。

若只需要在函数内部读完并返回统计值，把整个消费放在函数内部会更容易确定关闭时刻。必须返回流时，则要在接口中写明调用方负责关闭或提供能包住消费过程的上下文管理器。`async with` 面向异步上下文管理协议，完整协程与异步生命周期留到第 10 章；不能把普通同步管理器无条件套用到异步资源上。

## 23. 综合案例：解析数据时既保留原因又关闭资源

把异常链、生成器式上下文管理器和清理顺序放到同一个可运行例子中。这里只用内存文本模拟文件，避免依赖外部路径：

```python
from contextlib import contextmanager
from io import StringIO


class RowError(Exception):
    def __init__(self, row):
        self.row = row
        super().__init__(f"invalid row {row}")


@contextmanager
def readable(text, events):
    resource = StringIO(text)
    events.append("opened")
    try:
        yield resource
    finally:
        resource.close()
        events.append("closed")


def sum_rows(text, events):
    with readable(text, events) as resource:
        total = 0
        for row, line in enumerate(resource, start=1):
            try:
                total += int(line.strip())
            except ValueError as original:
                raise RowError(row) from original
        return total
```

先走正常路径：

```python
from contextlib import contextmanager
from io import StringIO


class RowError(Exception):
    def __init__(self, row):
        self.row = row
        super().__init__(f"invalid row {row}")


@contextmanager
def readable(text, events):
    resource = StringIO(text)
    events.append("opened")
    try:
        yield resource
    finally:
        resource.close()
        events.append("closed")


def sum_rows(text, events):
    with readable(text, events) as resource:
        total = 0
        for row, line in enumerate(resource, start=1):
            try:
                total += int(line.strip())
            except ValueError as original:
                raise RowError(row) from original
        return total


events = []
try:
    sum_rows("2\nbad\n4\n", events)
except RowError as error:
    print(error.row, events, type(error.__cause__).__name__)
    # 2 ['opened', 'closed'] ValueError
```

`int("bad")` 在第二行抛出 `ValueError`；本层把它翻译成带行号的 `RowError`，同时保留原异常。`with` 先让 `readable()` 的 `finally` 关闭资源，然后外层才收到 `RowError`。第三行没有被处理；在失败路径上函数也没有返回部分总和。这里的资源和错误接口都由明确的一层负责，而不是让每层做一半。

## 24. 常见错误如何形成

- `except Exception: pass`：把编程错误和业务失败都当成“什么都没发生”。
- `except:`：还可能挡住用户中断和退出信号。
- 把宽泛父类写在具体异常之前：具体分支失去机会。
- 认为 `else` 是“只要最后没报错就会执行”：`try` 中提前返回时它不会运行。
- 在 `finally` 里 `return`：掩盖原异常或原返回值。
- 捕获后 `raise NewError(...)` 却不保留原因：技术根因难找。
- 在 `__exit__()` 中无条件返回 `True`：把失败伪装成成功。
- `with` 退出后继续使用文件，或返回未完成消费的生成器却不说明关闭责任。
- 为全部异常打印完整实参或 traceback：可能泄露敏感信息。

分析错误时先指出是哪一步改变了控制流，再指出哪份状态已经改变、哪份资源仍被持有，最后决定由哪一层恢复、翻译或继续传播。

## 25. 面试中怎样组织回答

对控制流代码题，按下面顺序：

```text
进入 try
→ 哪一行第一次抛出什么异常
→ 该层哪些普通语句被跳过
→ 哪个 except 匹配，或继续向哪层传播
→ else 是否因正常完成而执行
→ finally 或 __exit__() 如何清理
→ 调用者最终拿到返回值还是异常
```

对资源设计题，先说资源的所有权，再说正常退出、异常退出和提前停止分别怎样释放。不要只回答“用 `with` 更好”；要能解释 `with` 在对象协议上调用谁、异常是否被抑制、资源从哪个时刻开始持有。

## 26. 本章总结

1. 语法错误与运行时异常发生在不同阶段；异常是有类型和信息的对象。
2. 异常沿调用栈向外传播，未被处理的层会跳过剩余普通语句。
3. `except` 从上到下按类型及继承关系匹配，应捕获能够处理的具体错误。
4. `else` 只在 `try` 正常结束时运行；`finally` 在离开时执行清理，但其中的新控制流可能掩盖旧错误。
5. 裸 `raise` 重新抛出当前异常；`raise ... from ...` 明确保留新旧错误的因果关系。
6. 文件、锁、事务等资源需要清楚的取得、使用和释放责任。
7. `with` 依赖上下文管理器的 `__enter__()`、`__exit__()`；真值返回可抑制异常。
8. `@contextmanager` 用生成器表达一次进入和退出，但仍须避免吞掉原异常。
9. 返回持有资源的生成器会延后资源生命周期，调用方必须知道何时关闭。

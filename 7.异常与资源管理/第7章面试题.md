# 第 7 章面试题：异常与资源管理

先闭卷回答，再查看 `第7章参考回答.md`。代码题需要给出完整事件顺序，并说明异常与资源分别由哪一层处理。

## 一、基础概念题

### 第 1 题：语法错误与运行时异常

两者分别在什么阶段出现？为什么不能在一段语法无效的源码外简单加一个同文件 `try`，就指望代码开始执行后捕获自己的语法问题？有效程序调用 `compile()` 检查另一段字符串时又为何能捕获 `SyntaxError`？

### 第 2 题：异常也是对象

异常对象携带哪些信息？`raise ValueError("bad")` 与 `return ValueError("bad")` 对调用方控制流有什么根本区别？

### 第 3 题：异常类层级

`BaseException`、`Exception`、`KeyError`、`LookupError` 和 `KeyboardInterrupt` 之间有哪些关键继承关系？为什么 `except Exception` 与裸 `except:` 的捕获范围不同？

### 第 4 题：异常传播

内层函数抛出异常、自己没有匹配处理时，内层和调用它的函数中尚未执行的普通语句会怎样？异常何时停止向外传播？traceback 为什么会列出多层函数？

### 第 5 题：多个 `except` 的顺序

为什么捕获 `KeyError` 的分支通常要放在捕获其父类 `LookupError` 的分支前面？`except (KeyError, IndexError)` 又表示什么？

### 第 6 题：`else` 的条件

`try` 后的 `else` 在什么情况下执行？`try` 内提前 `return`，或 `else` 自己抛出异常时，前面的 `except` 和后面的 `finally` 分别会怎样？

### 第 7 题：`finally` 的职责

正常走完、已捕获异常、未捕获异常以及提前 `return` 时，`finally` 分别怎样参与？“`finally` 总会执行”为什么也需要说明适用范围？

### 第 8 题：`finally` 中的 `return`

为什么在 `finally` 中写 `return` 可能掩盖原本的异常或返回值？清理代码应怎样安排业务结果？

### 第 9 题：`raise` 与重新抛出

主动 `raise SomeError(...)`、处理异常时单独写 `raise`、在同一位置写 `raise error` 各表示什么？若两者都由 `fail()` 抛出后经 `wrapper()` 重抛，traceback 中的相关函数帧可能有什么差异？

### 第 10 题：异常链

`raise NewError(...) from original` 建立什么关系？`__cause__` 与隐式 `__context__` 有什么用途？`from None` 是彻底删除旧异常对象吗？

### 第 11 题：自定义异常

自定义业务异常通常继承什么基类？除了消息，什么时候值得在异常对象上保存字段？为什么调用方不应靠截取错误消息来判断分支？

### 第 12 题：traceback 与日志

`str(error)` 和 traceback 提供的信息有何区别？`traceback.format_exc()` 为什么通常放在 `except` 内，已保存的异常怎样在之后格式化？什么情况下使用 `logging.exception()`，又为什么不应每层都记录一次？

### 第 13 题：EAFP 与 LBYL

两种风格分别怎样处理“可能没有这个键”的操作？假设检查发现键存在，但读取前另一处代码删除了它，哪次判断已经过时？把实际读取放在窄范围的 `try` 中解决了什么、又没有解决什么？是否应该规定全项目只用其中一种？

### 第 14 题：资源所有权

文件、锁和数据库事务为什么不能只等局部变量离开作用域后让解释器自行处理？一个接口应怎样说清谁取得、谁释放以及提前退出时怎么办？

### 第 15 题：`try/finally` 与取得资源的时点

`resource = acquire()` 放在 `try` 前，与把 `acquire()` 放在 `try` 内有什么责任差别？若准备取得一对资源，第一个已经取得、第二个失败，在向调用方交付完整结果前由谁关闭第一个？第二个取得函数自身部分成功后失败又由谁清理？

### 第 16 题：`with` 协议

`with manager as value:` 大致会依次调用什么？正常离开与代码块异常时，`__exit__()` 的三个异常参数各是什么？它返回真值或假值分别有什么影响？

### 第 17 题：`__enter__()` 失败与多个管理器

某管理器的 `__enter__()` 自己抛出异常，它的 `__exit__()` 是否会调用？`with A(), B():` 的进入和退出顺序如何？若 B 进入失败，已经进入的 A 怎样处理？

### 第 18 题：生成器式上下文管理器

`@contextmanager` 把生成器中 `yield` 前、`yield` 处和 `yield` 后分别映射到什么阶段？代码块抛异常时它怎样回到生成器？为什么清理通常使用 `try/finally`？

### 第 22 题：四个子句的执行路径

分别写出两个调用的输出：

```python
def flow(fail):
    events = []
    try:
        events.append("try")
        if fail:
            raise ValueError("failed")
    except ValueError:
        events.append("except")
    else:
        events.append("else")
    finally:
        events.append("finally")
    return events


print(flow(False))
print(flow(True))
```

### 第 26 题：显式异常原因

写出输出，并说明新异常怎样保留旧异常：

```python
original = None
try:
    try:
        int("bad")
    except ValueError as caught:
        original = caught
        raise RuntimeError("converted") from caught
except RuntimeError as error:

    print(error.__context__ is original)
```

### 第 27 题：`with` 的正常路径

写出列表内容与布尔结果：

```python
events = []


class Scope:
    def __enter__(self):
        events.append("enter")
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        events.append("exit")
        return False


manager = Scope()
with manager as active:
    events.append("body")
print(events, active is manager)
```

### 第 28 题：`__exit__()` 返回真值

写出事件顺序，说明为什么外层没有异常：

```python
events = []


class Suppress:
    def __enter__(self):
        events.append("enter")
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        events.append(exc_type.__name__)
        return True


with Suppress():
    events.append("body")
    raise ValueError("bad")
events.append("after")
print(events)
```

### 第 29 题：嵌套 `with` 的顺序

写出输出：

```python
events = []


class Marker:
    def __init__(self, name):
        self.name = name

    def __enter__(self):
        events.append("enter " + self.name)
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        events.append("exit " + self.name)
        return False


with Marker("A"), Marker("B"):
```

### 第 30 题：生成器式管理器

写出两条路径的完整事件列表：

```python
from contextlib import contextmanager


@contextmanager
def managed(events):
    events.append("acquire")
    try:
        yield
    finally:
        events.append("release")


success = []
with managed(success):
    success.append("body")

failure = []
try:
    with managed(failure):
        failure.append("body")
        raise ValueError("bad")
except ValueError:
    failure.append("outer")

print(success)
print(failure)
```

## 三、实现与场景题

### 第 31 题：转换输入并保留原因

设计 `parse_positive_int(text)`：可转换的正整数返回 `int`；无法转换或结果非正时抛出业务异常。两种失败是否都应设置 `ValueError` 为显式原因？怎样让调用者既能捕获业务异常，又能调查转换根因？

### 第 32 题：返回文件生成器

一个函数内部写了 `with open(path) as file`，在循环中逐行 `yield`。调用者只取第一行后长期保存生成器。文件从哪个时刻开始打开，为什么第一行产出后仍打开？显式 `generator.close()` 会经过哪些清理路径，关闭责任应如何写进接口？

### 第 33 题：锁的保护范围

某线程持锁后执行业务代码。若业务抛出异常，怎样保证锁释放？为什么“使用 `with lock:`”仍不能证明整个共享状态处理一定线程安全？

### 第 34 题：模拟事务

设计一个只记录事件的上下文管理器：进入记录 `begin`，正常退出记录 `commit`，异常退出记录 `rollback` 并继续传播原异常。`__exit__()` 应检查什么、返回什么？这个模型能否直接当作所有数据库驱动的事务语义？

### 第 35 题：清理失败与原始异常

业务处理抛出 `ValueError`，清理代码随后抛出 `RuntimeError`。调用者首先收到哪一个？另一个是否一定完全消失？怎样设计或记录才能保留有用的失败信息？

### 第 36 题：过宽捕获与重复日志

四层函数都使用 `except Exception as error: print(error); raise`。这会造成什么观察与维护问题？若最底层还有敏感实参，应怎样选统一记录边界？

# 第 8 章完整讲义：模块、包与依赖管理

本章需要同时分清三个层次：Python 运行时怎样导入模块，项目怎样组织为可安装的包，以及工具怎样为某个解释器安装依赖。第 1～14 节讲导入对象、执行和缓存；第 15～20 节讲包、入口、循环依赖与项目结构；第 21～29 节讲虚拟环境、依赖声明、解析、锁定和排查。遇到命令时先问“哪个解释器执行”，遇到导入时先问“导入名解析到哪个文件或包”。

## 1. 为什么把代码拆成模块

一个文件写几千行代码，会混合无关职责、增加名字冲突，也让测试和复用困难。Python 用**模块**组织一组相关名字。最常见的模块来源是一个 `.py` 文件，但模块本质上是运行时对象，不应简单等同于磁盘文件。

假设目录中有：

```text
project/
├── main.py
└── pricing.py
```

`pricing.py`：

```python
TAX_RATE = 0.13


def with_tax(price):
    return price * (1 + TAX_RATE)
```

`main.py` 可以导入它：

```text
import pricing

print(pricing.with_tax(100))
```

执行 `import pricing` 后，当前模块中的名字 `pricing` 指向一个模块对象；函数和常量位于该模块自己的命名空间，通过属性访问取得：

```text
main 模块名字 pricing ──→ pricing 模块对象
                         ├── TAX_RATE
                         └── with_tax
```

模块带来的不是“文件变多”本身，而是命名空间与职责边界。模块内部的全局名字属于该模块，不是所有文件共享的万能全局。

## 2. 源文件、模块对象与导入名

这三个概念经常被一句“导入文件”混在一起：

- **源文件**：磁盘上的代码文本，例如 `pricing.py`。
- **导入名**：导入语句使用的名称，例如 `pricing` 或 `shop.pricing`。
- **模块对象**：当前 Python 进程内创建并保存名字空间的运行时对象。

可以直接观察标准库模块对象：

```python
import math
import types

print(isinstance(math, types.ModuleType))  # True
print(math.__name__)                       # math
print(hasattr(math, "sqrt"))              # True
```

模块对象也有属性。`math.sqrt` 是在 `math` 模块命名空间中找到的函数对象。导入名与文件路径常有关联，但并非一一等同：有些模块由 C 扩展或解释器提供，有些包跨多个目录组成，导入钩子还可以从其他来源加载。

## 3. 第一次导入大致经历什么

以 `import shop.pricing` 为例，可以先用六步模型理解：

```text
1. 解析导入名 shop.pricing
2. 检查 sys.modules 是否已有对应模块对象
3. 没有缓存时，查找能加载该名称的模块规格
4. 创建模块对象，并在执行前放入 sys.modules
5. 执行模块代码，填充模块命名空间
6. 按 import 语句形式，在当前命名空间绑定名字
```

这里的**模块规格**常由 `ModuleSpec` 对象表示，描述名称、加载器、来源和包信息。初学者不用手写加载器，但要理解“查找”和“执行”是两个阶段。

为什么第 4 步在代码执行前就放入缓存？一方面可让模块代码在递归导入过程中找到当前对象，另一方面也造成循环导入时的关键现象：另一方可能拿到一个**尚未执行完成**的模块。

如果执行失败，导入系统通常会清理这次失败导入加入的缓存项，但已经成功导入的其他模块以及执行过的外部副作用不会自动回滚。不要把导入想成数据库事务。

## 4. 导入会执行模块顶层代码

模块文件中的函数体要等调用才运行，但顶层赋值、函数定义、类定义和函数调用会在首次加载时执行。用内存创建模块对象可以观察这件事：

```python
import types

module = types.ModuleType("study_module")
events = []
source = """
events.append("module body")

def work():
    events.append("function body")
"""
module.__dict__["events"] = events
exec(source, module.__dict__)
print(events)  # ['module body']
module.work()
print(events)  # ['module body', 'function body']
```

真实导入同样会执行模块顶层。导入时连接数据库、发网络请求、启动线程或做长时间计算，会让任何导入者承担这些副作用。模块顶层通常只保留定义、轻量常量和明确的注册行为；真正动作放到函数或应用入口。

## 5. 三种导入写法绑定了什么

### 5.1 `import module`

```python
import math

result = math.sqrt(9)
```

当前命名空间绑定名字 `math`，它指向模块对象。使用成员时写出模块前缀，来源清楚。

对带点名称还有一个绑定细节：普通写 `import shop.pricing` 时，当前命名空间默认绑定顶层名字 `shop`，随后通过 `shop.pricing` 访问子模块；写 `import shop.pricing as pricing` 才把当前别名 `pricing` 直接绑定到子模块对象。导入系统仍会在 `sys.modules` 保存完整名称 `shop.pricing`。

### 5.2 `from module import name`

```python
from math import sqrt

result = sqrt(9)
```

当前命名空间直接绑定名字 `sqrt`，它指向导入当时从模块属性取得的对象。当前模块没有自动获得名字 `math`。

### 5.3 `as` 只改变当前绑定名称

```python
import math as mathematics
from math import sqrt as square_root

print(mathematics.__name__)  # math
print(square_root(16))       # 4.0
```

别名没有复制或重命名模块对象；`mathematics.__name__` 仍是 `math`。别名适合解决当前命名冲突或使用约定简称，不应为了省几个字符制造难懂名称。

## 6. `from ... import ...` 后的名字绑定与模块属性更新

导入语句依然遵守名字绑定。用一个人工模块可稳定观察重新绑定：

```python
import types

settings_module = types.ModuleType("settings_demo")
settings_module.mode = "dev"

module_reference = settings_module
copied_binding = settings_module.mode

settings_module.mode = "prod"
print(module_reference.mode)  # prod
print(copied_binding)         # dev
```

`import settings` 风格保留模块对象引用，之后读取 `settings.mode` 会看到模块当前属性。`from settings import mode` 风格让当前名字直接绑定到导入时那个字符串对象；模块属性后来重新绑定，不会自动重绑当前名字。

若导入的是同一个可变对象，双方仍可能通过各自的名字观察对象内容修改：

```python
import types


settings_module = types.ModuleType("settings_demo")
settings_module.items = []
imported_items = settings_module.items
settings_module.items.append("A")
print(imported_items)  # ['A']
```

区别仍是“修改共享对象”与“重新绑定某个命名空间中的属性”，不是两种导入语句神秘地复制或同步数据。

## 7. `sys.modules`：进程内的模块缓存

`sys.modules` 是导入名到模块对象的字典。成功导入后，重复导入通常直接复用同一对象，不重新执行模块顶层：

```python
import math
import sys

first = math
second = __import__("math")
print(first is second)              # True
print(sys.modules["math"] is math) # True
```

缓存是**当前进程内**的。启动另一个 Python 进程会有自己的 `sys.modules`，模块顶层可能重新执行。缓存也不意味着模块文件永远不能更新；它只是普通导入优先复用当前进程已加载对象。

不要在业务代码中随意删除 `sys.modules` 项来“重置一切”。其他模块可能仍保留旧模块对象或其中成员的引用，导致同一进程里同时存在新旧对象。

## 8. 重复导入、模块状态和测试污染

模块对象可以保存可变全局状态：

```python
import types

registry_module = types.ModuleType("registry_demo")
registry_module.items = []

first_importer = registry_module
second_importer = registry_module
first_importer.items.append("plugin")
print(second_importer.items)  # ['plugin']
```

同一进程中的导入者通常共享同一个模块对象，因此共享它的全局列表、缓存和单例。模块缓存不是错误，但测试如果修改模块全局而不恢复，后续测试会看到污染状态。更清楚的设计是把状态交给显式对象或函数参数；确需模块级注册表时，测试要有明确重置接口。

## 9. `importlib.reload()` 的作用与限制

`importlib.reload(module)` 会使用模块规格重新执行代码，通常复用现有模块对象。它不是“全进程所有引用自动升级”。考虑这组关系：

```text
consumer.module_name → 模块对象
consumer.old_class   → 第一次执行时创建的类对象
模块重新加载         → 同一模块对象中的 class 属性改指向新类对象
consumer.old_class   → 仍指向旧类对象
```

重新加载还会保留模块字典中没有被新代码覆盖的一些旧名字，并再次执行顶层副作用。已有实例仍属于旧类，`from module import name` 得到的旧绑定也不会自动变化。它适合交互式开发中的有限场景，不是生产热更新的通用保证；测试更应倾向启动干净进程或明确重建状态。

## 10. `__name__` 与程序入口

模块被普通导入时，`__name__` 通常等于其导入名；被作为顶层入口执行时，`__name__` 等于 `"__main__"`。

```python
def main():
    print("run application")


if __name__ == "__main__":
    main()
```

这道判断只决定是否调用 `main()`；函数和类定义仍会在加载模块时建立。把主要行为放进 `main()`，可以让导入者复用定义而不自动运行应用流程。

同一源码文件若先作为脚本运行、之后又按正式名称导入，可能在一个进程中形成 `__main__` 与正式导入名对应的两个模块对象，各自执行顶层并保存状态。不要依赖“同一文件路径一定只有一个模块对象”。

## 11. 按文件运行与 `python -m` 运行

假设项目结构：

```text
project/
└── shop/
    ├── __init__.py
    ├── pricing.py
    └── cli.py
```

`cli.py` 使用相对导入：

```text
from .pricing import with_tax
```

在项目目录运行：

```text
python -m shop.cli
```

Python 按模块名找到 `shop.cli`，将它作为顶层执行代码，但保留包上下文 `shop`，因此 `.pricing` 有明确起点。直接执行：

```text
python shop/cli.py
```

该文件成为 `__main__`，通常没有同样的包上下文，相对导入可能报“没有已知父包”。修复方向是从项目入口按模块运行或把项目安装进环境，而不是在代码中临时修改 `sys.path`。

## 12. `__package__` 与 `__spec__` 提供导入上下文

- `__name__`：模块当前名称；入口模块常为 `__main__`。
- `__package__`：相对导入用于确定父包的名称。
- `__spec__`：模块规格，记录导入名称、加载器、来源和包信息等。

```python
import importlib.util

spec = importlib.util.find_spec("json")
print(spec is not None)       # True
print(spec.name)              # json
print(spec.loader is not None) # True
```

`find_spec()` 可以只查找规格而不按普通方式执行模块代码，适合诊断“能否找到”和“会从哪里加载”。某些已导入模块、命名空间包或自定义加载器的 `origin` 表现不同，不能假设每个规格都对应一个普通 `.py` 文件。

## 13. `sys.path` 是模块查找位置列表

`sys.path` 是当前进程用于顶层模块查找的一组字符串路径。来源可能包括：

- 启动脚本所在目录或当前工作目录的表示。
- 标准库路径。
- 当前环境的 `site-packages`。
- 环境配置、`.pth` 文件或启动参数加入的路径。

```python
import sys

print(isinstance(sys.path, list))  # True
print(all(isinstance(path, str) for path in sys.path))  # True
```

它不是递归扫描整个磁盘，也不是“项目根目录”的固定同义词。运行入口、虚拟环境和安装状态变化时，`sys.path` 可能不同。这就是同一代码在 IDE、终端、Notebook 或测试工具中导入结果不同的常见原因。

临时执行 `sys.path.insert(0, some_path)` 会改变当前进程的查找优先级，但容易隐藏项目没有正确安装、运行目录不对或包结构错误。诊断时可以观察路径，长期项目应通过可安装结构和明确入口解决。

## 14. 本地同名文件对标准库和第三方模块的遮蔽

若当前目录有 `json.py`，执行 `import json` 可能先找到本地文件，而不是标准库包。若有 `requests.py`，则可能遮蔽第三方发行包中的 `requests` 导入包。

诊断时检查：

```python
import json

print(json.__name__)
print(json.__file__)
print(json.__spec__.origin)
```

`__file__` 并非所有模块都有，但普通文件模块通常可用。若来源落在意外的当前目录，重命名冲突文件并清理生成的缓存文件，再从干净进程重试。不要看到 `ModuleNotFoundError` 就立即安装一个同名发行包；也可能是模块被错误文件遮蔽后，在其内部继续导入失败。

## 15. 包是组织子模块的模块

最常见的普通包是一个包含 `__init__.py` 的目录：

```text
shop/
├── __init__.py
├── pricing.py
└── reports/
    ├── __init__.py
    └── daily.py
```

导入名形成层级：`shop`、`shop.pricing`、`shop.reports.daily`。包对象仍然是模块对象，只是它拥有可供继续查找子模块的包路径。首次 `import shop.pricing` 时通常先加载 `shop` 的 `__init__.py`，再加载子模块。

`__init__.py` 可以为空，也可以设置包版本、导出稳定接口或做轻量注册。把大量业务计算放在里面会使任何子模块导入都先承担这些成本，也容易加剧循环导入。

导入子模块后，父包通常会获得同名属性：

```text
sys.modules['shop.pricing'] → 子模块对象
shop.pricing                → 同一个子模块对象
```

不能因为磁盘上有 `pricing.py` 就假定只执行 `import shop` 后一定已有 `shop.pricing`；它需要被显式导入，或者由 `shop/__init__.py` 主动导出。

## 16. 绝对导入与相对导入

在 `shop/reports/daily.py` 中：

```text
from shop.pricing import with_tax  # 绝对导入
from ..pricing import with_tax     # 相对导入
```

绝对导入从顶层导入名 `shop` 开始，调用处清楚看到依赖的完整包路径。相对导入根据当前模块的 `__package__` 解释：一个点表示当前包，两个点表示上一级包。点不是相对于当前工作目录，也不是相对于文件系统字符串路径。

相对导入适合包内部结构明确、包顶层名称可能改变的情况；绝对导入通常更易搜索和阅读。二者都依赖包以正确方式被发现和运行。不要为了让直接脚本执行成功，在同一个文件里交替尝试各种导入写法。

相对导入不能越过顶层包。若需要跨两个独立包共享代码，应把公共部分放进双方都能依赖的第三个模块或包，而不是不断增加点号逃出结构。

## 17. `__init__.py` 与稳定公开接口

调用者可以直接导入实现模块：

```text
from shop.pricing import with_tax
```

包也可以在 `shop/__init__.py` 中重新导出稳定入口：

```text
from .pricing import with_tax

__all__ = ["with_tax"]
```

调用者于是写：

```text
from shop import with_tax
```

这让包内部以后有机会移动实现文件而保持外部入口。但每次导入 `shop` 都会导入 `pricing`，也可能造成启动成本和循环依赖。公开接口应有意选择，不应把所有内部名字都塞进 `__init__.py`。

## 18. `__all__` 控制什么

`__all__` 主要控制 `from module import *` 默认导入哪些名字，也能作为工具和读者识别公开接口的信号。它不阻止调用者显式导入或访问未列出的名字：

```python
import types

api_module = types.ModuleType("api_demo")
api_module.public = 1
api_module._internal = 2
api_module.__all__ = ["public"]

print(api_module.public)     # 1
print(api_module._internal)  # 2，仍能显式访问
```

没有 `__all__` 时，星号导入通常跳过以下划线开头的名字；有 `__all__` 时按列表指定。星号导入让名字来源不清楚、容易覆盖当前绑定，业务代码通常使用明确导入。`__all__` 不是权限系统，也不是安全隔离。

## 19. 命名空间包为什么没有单一 `__init__.py`

Python 支持一种**命名空间包**：同一个顶层包的不同子包可以分布在多个目录或发行包中，目录不必含传统 `__init__.py`。例如两个安装来源都向 `company` 命名空间贡献内容：

```text
location_a/company/auth/
location_b/company/reports/
```

只要这些位置都可被导入系统发现，`company.__path__` 可以包含多个目录，分别找到 `company.auth` 和 `company.reports`。它适合大型组织拆分发行包，不等于忘记创建 `__init__.py` 的普通包。

命名空间包没有一个统一的 `company/__init__.py` 可以可靠执行初始化代码；需要公共入口时应选择普通包或在具体子包中定义。排查时不能只看某一个目录，要查看包的 `__path__` 和各子模块的规格来源。

## 20. 循环导入拿到的是部分初始化模块

假设：

```text
a.py 导入 b
b.py 又导入 a，并立刻读取 a.ready
a.py 尚未执行到 ready = True
```

过程是：

```text
开始 import a
→ 创建 a 模块并提前放入 sys.modules
→ a 执行 import b
→ 创建 b 并放入 sys.modules
→ b 执行 import a，命中缓存中的 a
→ 此时 a 只执行了一部分，还没有 ready
→ b 读取 a.ready 失败
```

所以循环导入不是简单的“Python 禁止两个模块互相导入”。有些循环碰巧成功，因为双方只在函数调用时才读取彼此的名字；有些在模块顶层立即读取尚未建立的属性，就出现“partially initialized module”或无法导入名称。

## 21. 怎样处理循环导入

优先处理依赖结构，而不是随意把导入挪来挪去：

1. **提取共同依赖**：若 `orders` 与 `payments` 都依赖同一数据结构，把它放到 `models` 或更低层模块。
2. **反转依赖**：上层通过参数或协议接收协作者，而不是底层反向导入上层具体实现。
3. **减少 `__init__.py` 重导出**：包初始化中一次导入全部子模块，容易形成隐式环。
4. **局部导入**：若依赖只在函数调用时需要，把导入放进函数可以延后读取，但应说明这是合理的运行时依赖，不是掩盖坏结构的万能办法。
5. **仅类型检查时导入**：第 11 章会用 `TYPE_CHECKING` 与前向引用避免某些只为注解产生的运行时环。

循环依赖往往说明两个模块的职责边界不清。局部导入能解除执行时点问题，但若两边业务仍紧密纠缠，维护成本没有消失。

## 22. `ModuleNotFoundError`、`ImportError` 与部分初始化错误

- `ModuleNotFoundError: No module named 'shop'`：顶层导入名没有在当前查找环境中找到，或包内部某个依赖缺失。
- `ImportError: cannot import name ...`：模块被找到并开始加载，但所需名字不存在、尚未建立或导入过程失败。
- `AttributeError: partially initialized module ...`：常见于循环导入中读取未建立属性，也可能是模块遮蔽造成自导入。
- 导入成功但行为错误：可能找到了同名错误模块、环境中版本不同，或旧模块对象仍被缓存。

排查顺序：先确认 `sys.executable`，再看 `module.__file__` / `__spec__.origin`，检查 `sys.path` 与 `sys.modules`，然后分析模块顶层执行和循环关系。不要一看到错误就反复安装包。

## 23. `PYTHONPATH` 的作用与风险

`PYTHONPATH` 是启动 Python 时可用于增加模块搜索位置的环境变量。它影响由该环境变量启动的进程，不是把项目安装成发行包，也不会写入项目的依赖元数据。

临时实验或特殊部署可能使用它，但团队项目若依赖每个人手工设置不同的 `PYTHONPATH`，通常难以复现。路径顺序还可能让同名模块优先级变化。优先把项目建立为可安装包，在虚拟环境中安装；诊断时显式记录额外路径来源。

## 24. 导入包与发行包的区别

日常交流里的“安装一个包”与 `import` 的包不是同一命名层次：

- **导入包（import package）**：Python 运行时通过导入名访问的包，例如 `PIL`。
- **发行包（distribution package）**：安装工具和包索引管理的可发布单元，例如发行名 `Pillow`。

一个发行包可以提供多个导入包，发行名也可以与导入名不同。不能看到 `import yaml` 失败，就武断执行 `pip install yaml`；常见发行名其实是 `PyYAML`。应查项目文档或包元数据，而不是猜同名安装命令。

“项目”“仓库”“发行包”“导入包”“模块”可以关联，却不必一一对应：一个仓库可构建多个发行包，一个发行包可装入多个顶层导入包，一个包又包含多个模块。

## 25. 为什么推荐可安装项目结构

小脚本可直接放在目录里运行；多人项目需要明确源码、测试和项目元数据。常见 `src` 布局：

```text
my-project/
├── pyproject.toml
├── README.md
├── src/
│   └── my_app/
│       ├── __init__.py
│       ├── cli.py
│       └── service.py
└── tests/
    └── test_service.py
```

`src/my_app` 是导入包源码；`my-project` 是项目目录，名称可以不同。将项目安装到虚拟环境后，解释器通过安装元数据找到 `my_app`。

如果把包直接放在仓库根目录，测试从根目录运行时可能因为当前目录恰好在 `sys.path` 而导入未安装源码，即使构建配置漏掉包也看不出来。`src` 布局迫使开发环境更接近真实安装：没有正确安装项目，导入就失败，从而更早暴露打包错误。

`src` 布局不是每个单文件脚本的强制规则。它解决的是项目安装与路径错觉，不会自动修复糟糕的模块边界。

## 26. `pyproject.toml` 的角色

`pyproject.toml` 是 Python 项目的标准配置入口，可声明构建系统、项目元数据、运行依赖、可选依赖以及各种工具配置。当前 `python八股` 项目包含：

```toml
[project]
name = "python-interview-study"
version = "0.1.0"
description = "Python interview knowledge and practice materials"
requires-python = ">=3.11"
dependencies = []

[dependency-groups]
dev = [
    "ipykernel>=7.3.0",
    "jupyterlab>=4.6.2",
    "notebook>=7.6.1",
    "pytest>=9.1.1",
    "ruff>=0.16.1",
]
```

`[project]` 描述发行项目：名称、版本、支持的 Python 范围和运行依赖。这里 `dependencies = []` 表示学习资料本身没有声明运行时第三方依赖；Notebook、测试和格式工具在开发依赖组里。开发工具不应无缘无故成为最终应用的运行依赖。

`pyproject.toml` 不保证环境已经按声明安装，也不记录所有传递依赖的唯一固定版本。它首先表达项目允许和需要什么；解析器再根据这些约束选择一组实际版本。

## 27. 虚拟环境隔离的是什么

虚拟环境为某个项目提供独立的解释器入口和安装目录，避免项目 A 安装的第三方版本直接覆盖项目 B 的环境。可以观察：

```python
import sys

print(sys.executable)   # 当前运行的 Python 可执行文件
print(sys.prefix)       # 当前环境前缀
print(sys.base_prefix)  # 创建虚拟环境所用基础 Python 的前缀
print(sys.prefix != sys.base_prefix)  # 常用于判断是否位于普通 venv
```

本项目解释器位于 `python八股/.venv`，`sys.prefix` 与基础解释器前缀不同。虚拟环境通常隔离第三方安装位置和命令入口，但不会：

- 自动隔离网络、进程、数据库或操作系统用户权限。
- 自动锁定第三方包版本。
- 自动让未声明依赖在其他机器出现。
- 自动选择正确的 IDE / Notebook 内核。

激活虚拟环境主要是调整当前终端的 `PATH`，使输入 `python`、`pip` 时优先找到环境内命令。即使不激活，也可用明确路径调用 `.venv/Scripts/python.exe`（Windows）或 `.venv/bin/python`（POSIX）。

## 28. `python -m pip` 为什么更容易确认解释器

命令行中的 `pip` 是一个可执行入口，它可能来自另一个 Python 安装。下面的形式明确让当前这个 `python` 运行它环境内可用的 `pip` 模块：

```text
python -m pip --version
python -m pip install some-distribution
```

如果终端的 `python` 本身选错，`python -m pip` 仍会作用于那个错误解释器；所以先查看：

```text
python -c "import sys; print(sys.executable)"
python -m pip --version
```

`pip install` 改变当前目标环境，不会自动修改项目的 `pyproject.toml` 或生成可靠锁文件。工具如 `uv add` 可同时更新项目声明和锁定结果，但要理解这是一套工具工作流，不是 `import` 的一部分。

## 29. 直接依赖、传递依赖和依赖图

项目代码直接使用并声明的第三方发行包是**直接依赖**。某个直接依赖为了自身运行还要求其他发行包，这些是**传递依赖**。

```text
你的项目
├── package-a >= 2
│   └── shared-lib >= 3
└── package-b >= 5
    └── shared-lib < 4
```

解析器需要找到同时满足全部约束的 `shared-lib` 版本。若 `package-b` 要求 `<3`，而 `package-a` 要求 `>=3`，交集为空，便产生依赖冲突。解决不是随便强装一个版本，而是找出提出矛盾约束的路径：升级或替换直接依赖、调整项目自身约束，或等待上游支持。

不要把所有传递依赖都手工复制成项目直接依赖。只有项目代码直接使用、或需要明确覆盖某项兼容边界时，才有理由直接声明；否则会增加无谓耦合。

## 30. 版本约束表达允许范围

常见说明：

```text
library>=2.1          至少 2.1，没有给出上限
library>=2.1,<3       允许 2.x 中满足下限的版本
library==2.4.1        只允许这一版本
library~=2.4          兼容发行约束，通常允许 >=2.4 且 <3.0
library>=2; python_version >= "3.12"  环境标记
```

项目依赖声明通常给出经过测试的兼容范围，让不同环境可选择合适构建；应用部署的锁文件则记录一次解析的具体版本。库项目若把所有依赖永久精确钉死，可能与使用者的其他库冲突；应用若完全没有上限或锁定，又可能在未来安装到未经测试的不兼容版本。选择与交付类型有关。

Python 生态采用 PEP 440 版本规则，预发布、开发版、本地版本与兼容约束还有更多细节。本章要求能读常见范围、判断是否有交集，不要求背完整规范。

## 31. 运行、开发与可选依赖

- **运行依赖**：使用项目核心功能就需要，例如 Web 应用运行所需框架。
- **开发依赖**：测试、格式、文档和 Notebook 工具，只为开发流程服务。
- **可选依赖**：只有启用特定额外功能时需要，例如 `project[postgres]`。

分类影响安装体积、安全更新和使用者冲突。把 `pytest` 放进库的核心运行依赖会让所有使用者安装测试工具；反过来，把运行必需的数据库驱动只放在个人开发组里，部署环境会缺失。

当前项目把 Jupyter、pytest 和 Ruff 放在 `dependency-groups.dev`，表达它们服务资料开发。不同工具对开发依赖组和标准可选依赖的支持方式不同；发布给外部使用者的可选功能通常放 `[project.optional-dependencies]`，本地开发组则可用工具支持的依赖组。

## 32. `requirements.txt` 与 `pyproject.toml` 的用途对比

`requirements.txt` 是 pip 可安装的需求列表格式，常用于某个环境安装输入：

```text
requests==2.32.5
urllib3==2.5.0
```

它可以精确固定，也可以使用范围，还支持引用其他文件和索引选项；仅凭文件名无法判断它是顶层抽象需求还是完整冻结结果。团队必须约定生成方式和用途。

`pyproject.toml` 还包含项目名称、Python 范围、构建后端、可选依赖和工具配置，是项目元数据入口。二者可以共存：例如可发布库在 `pyproject.toml` 声明兼容范围，部署流程从锁定结果导出固定 requirements。不要机械地把同一组依赖手工维护在多个文件而不设同步来源。

## 33. 锁文件记录一次完整解析结果

锁文件通常记录直接和传递依赖的具体版本，并可能包含文件哈希、环境标记及多个平台候选，使相同工具可以重建已解析环境。当前项目的 `uv.lock` 与 `pyproject.toml` 配合：声明改变后重新解析，锁文件随之更新；`uv sync` 按声明和锁定结果同步环境。

锁文件不是万能字节级复制：操作系统、CPU、Python 版本和可用构建产物仍可能让安装结果不同。它也不会替代源代码兼容测试和安全更新。锁住旧漏洞版本能复现，却不等于安全；升级依赖时应更新锁并运行测试。

是否提交锁文件取决于项目类型和团队策略。应用通常应提交以复现部署；库也可锁开发测试环境，但发布元数据仍需给使用者合理兼容范围。关键是明确锁文件服务哪个环境，不是背“永远提交”或“永远不提交”。

## 34. 当前项目的 `uv` 工作流怎样理解

当前目录中的关系：

```text
.python-version  → 项目偏好的 Python 3.12
pyproject.toml   → 项目元数据与依赖约束
uv.lock          → uv 解析出的完整锁定结果
.venv/           → 当前机器实际创建的虚拟环境
```

典型命令：

```text
uv sync                 根据项目与锁文件同步环境
uv add package-name     增加运行依赖并更新声明和锁
uv add --dev tool-name  增加开发依赖
uv run python ...       在项目环境中运行 Python
uv lock                 重新解析并更新锁文件
```

命令选项可能随工具版本发展，真实操作以项目当前 `uv --version` 和帮助为准。通用原理是“选择解释器 → 读取约束 → 解析完整图 → 锁定 → 同步环境”，不是必须使用 uv 才成立。`pip`、Poetry、PDM 等工具也在处理这些层次，只是文件和命令工作流不同。

## 35. 可编辑安装的原理与适用场景

开发本地包时：

```text
python -m pip install -e .
```

可编辑安装让当前环境中的发行元数据和导入机制指向工作区源码。修改 Python 源文件后，通常无需重新安装即可在新进程看到变化；新增构建元数据、入口点或编译扩展时仍可能需要重新安装或构建。

可编辑安装的价值是让测试和脚本按“已安装项目”导入，同时编辑真实源码。它不是把任意当前目录永久加进所有解释器，也不是部署方式。部署通常构建并安装不可编辑的 wheel，验证真正交付物包含了需要的包和数据文件。

## 36. 构建后端、wheel 与安装流程

`pyproject.toml` 可通过 `[build-system]` 指定构建后端。后端读取源码和配置，构建 **wheel** 或源码发行包；wheel 是面向安装的归档格式，包含代码、元数据和文件清单。安装工具把 wheel 内容放进目标环境，并创建命令入口等元数据。

```text
源码仓库
→ 构建后端
→ wheel / 源码发行包
→ 安装工具
→ 目标虚拟环境
→ import 按安装结果找到包
```

“我在仓库根目录能 import”不能证明 wheel 包含正确内容。发布前应在干净环境安装构建产物并测试。第 16 章会把构建产物验证用于测试工具交付与持续集成；本章先建立导入与安装之间的连接。

## 37. Notebook 和 IDE 为什么常用错解释器

激活终端环境不保证已经打开的 Notebook 自动切换内核。Notebook 单元格真正使用的是所选内核对应的 `sys.executable`。排查时在 Notebook 内运行：

```python
import sys

print(sys.executable)
print(sys.prefix)
```

若终端安装成功而 Notebook 仍 `ModuleNotFoundError`，常见原因是内核指向另一个环境。应为目标环境安装或注册内核并在界面中选择它，而不是在多个环境里反复安装直到碰巧成功。

IDE 的运行配置、测试发现器和终端也可能各选不同解释器。把“编辑器显示已选择环境”和程序打印的 `sys.executable` 对照，证据比界面印象可靠。

## 38. 一套可复用的导入排查顺序

遇到“本机可以、别人不行”或“终端可以、Notebook 不行”：

1. 打印 `sys.executable`、`sys.prefix`、Python 版本。
2. 确认项目是否在该环境安装，发行包版本是什么。
3. 用 `importlib.util.find_spec(name)` 查看导入名能否找到及来源。
4. 导入成功后看 `module.__file__`、`module.__spec__.origin`。
5. 检查 `sys.path` 是否因运行目录、IDE 或 `PYTHONPATH` 不同。
6. 检查工作区是否有同名 `.py` 文件或目录遮蔽正确包。
7. 若报部分初始化，画模块顶层导入图，寻找循环依赖。
8. 若环境安装不同，比较声明、锁文件和同步步骤。

每一步都回答具体问题，不要把删除缓存、重装全部依赖或修改 `sys.path` 当作首选仪式。

## 39. 依赖版本锁定、安全更新与兼容性测试

锁定版本提高可复现性，但可能长期固定已知漏洞；自动升级获得补丁，却可能引入兼容变化。合理流程包括：定期检查更新和安全公告，在分支中更新锁文件，运行测试，再发布或部署。

安装来源也属于信任边界。发行名相似可能导致安装错误项目；生产环境应使用受信任索引、核对项目来源，并保留锁文件中的哈希或其他完整性信息。不要把代码中的导入名直接当成包索引上的可信发行名。

## 40. 综合案例：从源码到可复现运行

假设构建命令行应用 `report-tool`：

```text
report-tool/
├── pyproject.toml
├── uv.lock
├── src/report_tool/
│   ├── __init__.py
│   ├── cli.py
│   └── reports.py
└── tests/
```

设计过程：

1. `reports.py` 提供纯业务函数，`cli.py` 负责解析输入和调用业务。
2. 包内使用清楚的绝对或相对导入，运行入口使用已安装命令或 `python -m report_tool.cli`。
3. `pyproject.toml` 声明 Python 范围、运行依赖与命令入口；测试工具放开发组。
4. 解析器生成锁文件，团队提交它并用相同工作流同步环境。
5. 开发时可编辑安装；发布前构建 wheel，在干净环境安装并运行测试。
6. 出现导入错误时先确认解释器和模块来源，再检查路径、安装与循环关系。

这条链把“代码在哪”“Python 怎样找到它”“第三方依赖装到哪里”“另一台机器怎样复现”连接起来。少任何一段，都可能出现只在开发者电脑上工作的项目。

## 41. 本章总结

1. 模块是运行时对象；源文件、导入名和模块对象不是一个概念。
2. 首次导入涉及缓存检查、规格查找、模块创建、顶层执行和当前名字绑定。
3. `import module` 保留模块引用；`from module import name` 绑定导入当时取得的对象。
4. `sys.modules` 是进程内缓存，重复导入通常复用对象；重新加载不会更新所有旧引用。
5. 包提供子模块命名空间；相对导入依赖 `__package__`，`python -m` 能保留包上下文。
6. `sys.path`、运行入口和环境共同决定查找位置；本地同名文件可能遮蔽正确模块。
7. 循环导入的问题来自读取部分初始化模块，应优先调整依赖结构。
8. 导入包名与发行包名可能不同，安装前应查元数据而非猜名称。
9. 虚拟环境隔离安装位置，项目声明兼容范围，锁文件记录一次完整解析结果。
10. 可编辑安装服务本地开发，真正交付应验证构建产物和干净环境。

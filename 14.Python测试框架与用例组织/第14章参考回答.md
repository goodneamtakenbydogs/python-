# 第 14 章参考回答：Python 测试框架与用例组织

与面试题 45 题逐题对应。先给结论，再解释依赖、状态与证据，最后说明边界。参考回答帮助组织自己的表达，不是唯一话术；通过检查器不代替设计评审。

## 一、工程运行与断言

### 第 1 题：测试框架与被测程序的职责

**首轮结论：** 框架安排执行与结果，用例表达输入和预期，被测函数实现行为；覆盖与断言质量仍靠设计。

报告函数生成文本，用例依据需求核对标题和行，pytest 负责找到测试、取得 fixture 并记录结果。把三种责任分开，失败时才能判断是需求、业务实现、测试代码还是环境问题。

框架能提供参数化、捕获和诊断，却不能替人确认标题规则是否合理。全部通过必须说明具体版本、选择范围和实际检查内容。

**常见误答：** 使用了成熟框架就等于测试完整，或者所有红色结果都来自产品缺陷。

**继续追问：** 用例自身 expected 写错时，框架能否自动知道？

**回答边界：** 给出一条需求、一个断言和一项框架责任。

### 第 2 题：阅读已有测试工程的顺序

**首轮结论：** 先找运行命令和环境，再沿一条测试的输入、fixture、调用、断言与输出建立关系。

先读 README 和依赖声明，确认解释器；查看 pytest 配置中的搜索范围、标记和默认选项；选一个小测试，找到其数据来源、fixture 依赖和被测接口。最后实际运行节点，核对收集数量和失败阶段。

不需要先读完全部工具源码，但应确认 conftest 或插件有没有增加隐含准备、筛选与报告行为。

**常见误答：** 直接搜索所有 assert，或者只要找到一个 test 文件就认为知道执行入口。

**继续追问：** 配置、入口和应用自身配置为什么不能混成同一层？

**回答边界：** 能画出一条实际用例的依赖路径。

### 第 3 题：解释器与 python -m pytest

**首轮结论：** -m 让选中的解释器执行模块；首先确认不同入口实际使用的 Python 是否一致。

查看 sys.executable、Python 版本和安装环境，再核对 pytest 是否在该环境。虚拟环境隔离安装位置，锁文件固定解析结果，Notebook 内核仍需单独选对。

python -m pytest 比不明来源的 pytest 可执行命令更容易确认解释器，但前提是 python 本身已选对。不要先通过修改 sys.path 掩盖环境或安装问题。

**常见误答：** 所有 Python 命令都自动使用项目虚拟环境，或装一次包所有内核都能用。

**继续追问：** 为什么源码目录在 sys.path 中也不等于发行包安装验证完成？

**回答边界：** 指出解释器、依赖与内核三个检查点。

### 第 4 题：默认命名与显式收集

**首轮结论：** 默认有文件、函数和类命名规则，且普通测试类不应通过自定义构造器建立条件。

默认搜索 test_*.py、*_test.py，收集 test_ 函数和符合规则的 Test 类中的测试方法。helper 只有被调用时才参与行为，不因与测试同文件就成为独立项；命名规则还可能被配置修改。

显式指定文件可改变搜索入口。实际以 collect-only 的节点列表核对，不能只按文件数量推算测试数。

**常见误答：** 所有 .py 文件都会执行所有函数，或者类名以 Test 开头就没有其他限制。

**继续追问：** 为何参数化使一个函数对应多个节点？

**回答边界：** 说明默认规则、配置边界与实际核对方法。

### 第 5 题：只收集时的导入副作用

**首轮结论：** 收集需要导入定义和执行相关收集逻辑，模块顶层副作用仍可能发生。

模块顶层写文件、加载数据或创建连接，都可能先于 test 函数运行。collect-only 仅表示不按常规执行测试体，不能保证整个过程没有副作用。

资源取得应放在明确生命周期中；必须参与生成测试项的静态数据可在收集时加载，但需接受解析失败属于收集问题这一结果。

**常见误答：** 只收集等于完全不执行任何 Python 代码。

**继续追问：** JSON 顶层加载与 fixture 中加载，失败阶段怎样变化？

**回答边界：** 按导入、收集、测试体三个时点解释。

### 第 6 题：节点标识与单项复现

**首轮结论：** 节点由路径、定义名与参数案例编号定位，用于精确选择和复现。

可指定结构如下，放在引号中避免终端处理方括号。它是命令实参示意：

```text
python -m pytest "tests/test_text.py::test_render[upper]" -v
```

编号变化会影响已有复现命令、结果关联或选择脚本，不应无理由随数据位置漂移。node ID 也不能自动替代稳定需求编号。

**常见误答：** 只写 upper 就能在所有工程唯一找到同一需求。

**继续追问：** 类中方法的节点还会增加哪一层？

**回答边界：** 给出完整选择结构及稳定命名理由。

### 第 7 题：关键字与标记筛选

**首轮结论：** -k 匹配名称等关键词，-m 匹配标记表达式，二者不是同一种筛选。

关键字可匹配测试或父级名称、标记等信息；标记由 pytest.mark 等机制附加，名字里出现 slow 不会自动登记一个同名标记。两种表达式都可组合条件，但含义要按对象区分。

用 collect-only 配合相同选择实参核对目标集合，再实际执行。被筛掉是 deselected，不是 skipped 或 passed。

**常见误答：** -k 与 -m 完全等价，只是写法不同。

**继续追问：** marker 已注册是否就会自动附加给全部同名函数？

**回答边界：** 能用一个名称和一个标记作对照。

### 第 8 题：严格标记与标记维护

**首轮结论：** 严格标记帮助暴露拼写错误，标记代表的测试范围仍由明确规则和风险选择。

在 pytest 配置注册自定义标记并开启 --strict-markers，未声明标记会更早暴露；否则可能只有警告或筛选范围悄悄偏离预期。

smoke 不是框架内置的质量保证标签，需要说明目标、纳入条件和维护方式。配置声明不自动标记测试，也不证明范围足够。

**常见误答：** 只要名字叫 smoke，就一定覆盖所有关键业务。

**继续追问：** 新增一条关键路径后怎样检查标记集合是否仍合理？

**回答边界：** 区分技术校验与范围设计。

### 第 9 题：断言真值与业务结构

**首轮结论：** 非空结构的真值不代表内部业务内容符合预期。

输出依次为 True、False。字典非空，因此 bool(actual) 为真；但 rows 与明确预期不同。只写 assert actual 会放过错误内容。

应分别或整体核对需求要求的字段、类型与状态。断言消息保留案例编号和字段即可，不默认输出所有真实实参和环境。

**常见误答：** 返回了非空对象，说明业务处理成功。

**继续追问：** 结构整体相等与逐字段断言分别适合哪些定位需求？

**回答边界：** 解释真值规则，并给出具体业务检查对象。

### 第 10 题：异常范围与拒绝后的状态

**首轮结论：** raises 应尽量只包预期失败的目标动作，状态断言在退出后单独执行。

准备阶段也抛 ValueError 时，可能误满足异常预期；目标抛错后 with 内后续语句不会继续执行，因此把状态检查放在后面会被跳过。pytest.raises 在没有匹配异常时会使测试失败，避免空 try/except 的漏洞。

match 用正则匹配消息，通常也接受期望异常的子类。接口要求精确类型或结构化字段时，再检查异常对象。

**常见误答：** 捕获任意异常都算通过，或者把所有断言写在同一个 raises 块里最安全。

**继续追问：** 消息包含特殊正则字符时应如何处理？

**回答边界：** 说明范围、无异常出口、类型和状态责任。

## 二、参数化与 fixture

### 第 11 题：参数化与测试内循环

**首轮结论：** 参数化通常形成五个独立测试项，循环通常仍是一项并可能中途停止。

循环中的一次断言失败会跳出当前函数，后面的输入可能尚未执行。参数化让每组有独立节点、准备与结果，可单独选择，也便于失败案例定位。

需要验证一个连续状态过程时，一个测试内多步仍可能合理。选择依据是目标和状态联系，不能机械把所有步骤拆成独立参数。

**常见误答：** 两种写法只是行数不同，报告和生命周期完全相同。

**继续追问：** 参数化用例是否自动共享同一 fixture 结果？

**回答边界：** 说明独立节点、失败传播和生命周期。

### 第 12 题：案例编号与组合数量

**首轮结论：** 独立维度形成六种组合，范围应受可行性、目标与成本约束。

笛卡尔积把每个维度全部配对；维度增加时项数相乘。需要剔除不可能组合、控制成本或检查特定交互时，可以显式列行，并说明选择依据。

案例编号表达边界或目标，避免敏感数据和不稳定对象表示进入日志。编号清楚帮助定位，但不替代独立预期或需求覆盖。

**常见误答：** 更多组合总是更好，或者两两覆盖就是完整组合。

**继续追问：** 一个高阶条件错误为什么可能被两两覆盖遗漏？

**回答边界：** 算清数量，说明约束与稳定标识。

### 第 13 题：参数对象的共享引用

**首轮结论：** 参数保存对象引用，pytest 不自动为每次使用深拷贝。

输出为 ['A'] 与 True。两个位置引用同一字典，内部列表也是同一个对象。修改对象内容，不是重新绑定某个测试自己的独立参数。

可以用不可变描述配合 function fixture 创建状态，或明确复制边界。浅拷贝外层不足以分开嵌套列表，资源对象则需要创建与重置接口。

**常见误答：** 参数化的每一行天然是一份递归独立副本。

**继续追问：** 只复制 rows 外层是否能修复内部共享？

**回答边界：** 画出共享字典和内部列表的引用。

### 第 14 题：fixture 请求与普通调用

**首轮结论：** pytest 按形参名解析 fixture 依赖，并管理准备、缓存和退出。

测试形参声明所需条件，框架把相应 fixture 的返回或 yield 值传入；fixture 自己也可通过形参请求依赖。手动调用绕过这套生命周期语义，也不符合 pytest 对 fixture 的使用约定。

普通可复用计算放帮助函数，fixture 负责把它接入测试准备。这样其他代码也能独立调用帮助函数，而不依赖测试框架环境。

**常见误答：** fixture 只是函数别名，直接调用和框架请求完全一样。

**继续追问：** 一个帮助函数什么时候值得包装成 fixture？

**回答边界：** 区分普通函数与受框架管理的条件。

### 第 15 题：单项测试内的 fixture 缓存

**首轮结论：** 同一测试的同一 fixture 实例通常缓存复用，两个请求路径可能取得同一对象。

pytest 为依赖解析复用当前有效结果，而不是每遇到一个形参名就调用一次。child 若返回或修改 base，测试请求 base 时看到的是同一对象当前状态。

function 隔离的是不同测试项的创建范围，不保证同一项内的每个使用者都有副本。具体还要考虑参数化和覆盖关系。

**常见误答：** 有两个形参就必然有两次初始化。

**继续追问：** 需要同项内多份资源时为什么常返回工厂？

**回答边界：** 说明缓存范围和对象身份。

### 第 16 题：fixture 作用域与生命周期成本

**首轮结论：** scope 决定复用范围，应按成本和状态责任选择，不是绝对创建次数承诺。

独立可变数据通常放 function；高成本且可安全共享的基础可放更大作用域。session 结果仍可能被测试修改，生命周期变长会扩大污染影响。

参数实例切换等执行安排可能触发重建与清理，pytest 的缓存不等于同一作用域内保存无限多个参数实例。说明目标版本与实际依赖比背“一次”更准确。

**常见误答：** 全部 session 最快也最安全，或 scope=session 永远精确一次。

**继续追问：** 共享连接需要怎样的每项状态恢复约定？

**回答边界：** 说清成本、可变性与缓存边界。

### 第 17 题：ScopeMismatch 的原因

**首轮结论：** 较长生命周期的 fixture 不能直接持有较短生命周期请求所提供的结果。

session 的共享对象需要跨多项存在，function 的 tmp_path 只按当前测试项安排，两者生命周期不匹配。pytest 会报告 ScopeMismatch，不能靠函数形参重排修复。

可使用适合更大作用域的 tmp_path_factory 建立基础目录，再在每项划分独立路径；或缩小消费者作用域。不要为了消除报错就把所有状态扩大为 session。

**常见误答：** 调整 fixture 在文件中的位置就能解决作用域问题。

**继续追问：** 大目录共享后，哪些文件仍需每项独立？

**回答边界：** 说明生命期冲突并提出两种适当调整。

### 第 18 题：依赖顺序与 autouse

**首轮结论：** 作用域、依赖和 autouse 等规则决定安排，需要先后关系时应表达真实依赖。

A 是 B 的依赖时，应先准备 A 再准备 B，退出时成功进入部分逆序收尾。独立同级 fixture 的偶然排列不适合当接口约定。

autouse 在适用范围自动生效，能统一少量必要条件，也会增加隐含依赖。使用 --setup-show 观察，然后回到依赖图解释，不能把观察到的巧合顺序当保证。

**常见误答：** 名字按字母排序，或把形参放前面就必定先初始化。

**继续追问：** 过多 autouse 会如何增加读用例的成本？

**回答边界：** 画一个有依赖的准备与逆序退出图。

### 第 19 题：yield fixture 与测试体失败

**首轮结论：** 正常框架控制流中，已交付资源的 fixture 仍应收尾；强制终止进程等不受同样保证。

yield 产出资源并暂停，pytest 在退出阶段恢复生成器。需要可靠清理时用 try/finally，避免把普通尾部语句误当能抵御任意退出。测试失败与清理失败应分别记录。

资源关闭也不自动撤销业务写入；要按接口另外检查回滚或状态保持。不能依赖 Python 垃圾回收替代外部资源的确定关闭。

**常见误答：** 只要测试失败就不会执行任何清理，或 yield fixture 能处理断电和任意杀进程。

**继续追问：** 清理本身失败时应如何保留原失败证据？

**回答边界：** 说明框架退出路径与外部终止边界。

### 第 20 题：yield 前部分初始化失败

**首轮结论：** 尚未到 yield，靠后的普通退出段不会自动接管已取得的部分。

应在 A 成功后立即建立清理责任，例如 with ExitStack 登记 A 的退出动作，再取得 B；也可拆分为每个 fixture 一项取得与收尾，让依赖组合。

request.addfinalizer 也是选择，但应在资源真正取得成功后登记。取得函数内部若自己部分成功，它仍要负责未能交付的部分，不能一律推给调用方。

**常见误答：** pytest 会看到局部变量并自动关闭一切资源。

**继续追问：** 为什么不能在取得 A 之前登记一个假定 A 已存在的释放？

**回答边界：** 明确每层已取得资源的所有者和失败路径。

### 第 21 题：工厂 fixture 与多份资源

**首轮结论：** fixture 返回创建入口，每次调用新建结果，资源记录与收尾仍由明确的生命周期负责。

缓存的是工厂函数，不是它的全部调用结果。工厂可为每次创建分配新对象或唯一文件名，把成功取得资源登记在闭包列表或 ExitStack 中，最后逆序清理。

如果每次都返回同一个字典或固定外部路径，工厂名称不会带来隔离。临时目录保留策略与立即删除责任也要区分。

**常见误答：** fixture 工厂天然使每次调用的所有外部资源独立。

**继续追问：** 第三次创建失败时，前两份怎样释放？

**回答边界：** 说明工厂缓存、每次创建和收尾登记。

### 第 22 题：conftest 可见范围与局部覆盖

**首轮结论：** conftest 由 pytest 按目录作用范围加载，测试通过请求名使用并可局部覆盖。

父目录定义通常供后代目录使用，子目录可对同名 fixture 作局部覆盖；同级目录不会天然共享彼此的 conftest。手动导入会混淆普通模块导入与框架的依赖查找。

通用帮助逻辑放普通模块，conftest 负责接入 pytest。覆盖后用 fixtures 或 setup-show 确认实际依赖，避免以为修改了根 fixture 就影响所有局部替代。

**常见误答：** 所有 conftest 自动合并成没有作用域的全局仓库。

**继续追问：** 公共组件的实现为什么不都堆在根 conftest？

**回答边界：** 给出父子目录可见关系与职责。

### 第 23 题：indirect 参数化的使用时机

**首轮结论：** 普通数据直接交测试，indirect 数据先交 fixture 以便在准备阶段建立条件。

例如参数行给出 small，fixture 读 request.param 后创建独立记录，测试收到记录对象。indirect 可只指定部分形参，其他预期仍直接传入测试。

它适合将轻量描述与资源取得分开，但不自动复制对象或保证资源昂贵操作不会出现在收集阶段；代码本身必须按责任组织。简单整数输入直接参数化通常更清楚。

**常见误答：** request.param 总在所有 fixture 中都有，或所有数据驱动都应 indirect。

**继续追问：** 为什么收集阶段不适合建立全部真实连接？

**回答边界：** 沿参数描述、fixture、测试值说明流向。

### 第 24 题：共享模板与独立可变状态

**首轮结论：** 新外层不等于嵌套状态独立，复制边界应与修改边界对应。

输出为 ['base', 'local'] 和 False。浅拷贝得到新字典，内部 tags 仍指向原列表。可以深拷贝普通模板或按字段新建可变部分，再保留真正只读的共享基础。

连接、文件和锁不适合机械深拷贝，要通过资源接口取得、重置和关闭。共享成本与每项隔离应分层安排。

**常见误答：** 只要 case is not base，任意内部修改就不会污染基础。

**继续追问：** 如何测试每项 fixture 同时保持缓存与跨项隔离？

**回答边界：** 解释两层引用，说明数据与资源处理差异。

## 三、替身、隔离与配置

### 第 25 题：skip、xfail 与严格 XPASS

**首轮结论：** skip 通常不执行测试体，xfail 默认执行并期望失败，严格意外通过使会话失败。

xfail(run=False) 是不运行的特例，应明确标注。默认 xfail 的意外通过可记为 XPASS，strict 配置则提醒维护者确认是否已修复，通常计入 failed。

原因、适用条件和关联公开问题应可维护。xfail 可用 raises 限定错误类型，避免无关异常也被当已知问题；skip 和 xfail 都不能算成业务已经通过。

**常见误答：** xfail 永远不运行，或严格 XPASS 应计入普通 passed。

**继续追问：** 为什么给所有不稳定失败加 xfail 会掩盖风险？

**回答边界：** 说明默认行为、特例、严格模式和维护责任。

### 第 26 题：Mock 交互断言与独立业务预期

**首轮结论：** 交互正确不等于业务转换正确，两类断言应对应各自契约。

读取函数被调用一次且编号正确，使用者仍可能丢字段、错误大小写或返回固定值。业务 expected 要来自规则，例如输入标签 demo 应显示 DEMO，而非只验证替身配置与自身一致。

替身还可能与真实接口漂移，因此需要约束签名和必要的真实集成验证。不要把被测函数本身替换掉，再声称验证了其实现。

**常见误答：** mock 有调用记录就证明全部逻辑正确。

**继续追问：** 哪些交互属于必须约定，哪些只是容易让测试脆弱的内部细节？

**回答边界：** 各给一项业务断言与交互断言。

### 第 27 题：autospec 与返回契约

**首轮结论：** 这些工具限制接口使用，不能自动证明响应语义或真实集成。

autospec 根据原对象签名约束调用，spec_set 可限制未声明属性，帮助发现拼错方法或错误调用方式。返回值仍由测试配置，字典缺字段或真实协议变化不一定被自动发现。

应为响应结构建立明确约定并保留受控集成证据。类型标注、替身签名限制与业务测试提供不同层次的信息。

**常见误答：** autospec 会调用真实接口并自动验证所有返回值。

**继续追问：** 被测函数改为额外关键字实参后，哪些测试能更早发现漂移？

**回答边界：** 给出可发现与不可发现的各一种问题。

### 第 28 题：patch 定义位置与使用位置

**首轮结论：** 替换一个属性不会自动重绑另一个已保存的引用，应作用于调用时实际查找的位置。

输出依次是 new、old、old。consumer.read 在建立时就保存旧函数，替换 provider.read 只改 provider 的属性；退出上下文后 provider 的属性恢复。

若真实 consumer 用 from provider import read，通常 patch consumer.read；若它运行时调用 provider.read，则替换那个实际属性。默认形参或闭包早先保存的协作者还需另看绑定时机。

**常见误答：** 依赖在哪里定义，就永远在哪里 patch。

**继续追问：** 函数默认值绑定旧 reader 后，改模块 reader 为什么可能无效？

**回答边界：** 按实际查找路径和旧引用解释。

### 第 29 题：monkeypatch 的恢复边界

**首轮结论：** 局部上下文缩短替换范围，恢复只覆盖已登记操作，不是通用事务回滚。

一个测试需要先观察旧环境、局部换值、再观察恢复，可以用 context。setenv 等修改在范围退出时恢复，测试间不应依赖手工设回恰好记住的值。

若取得某字典后 append 内部列表，或向远端创建记录，这些动作并不会因为恢复某属性而自动撤销。共享线程读取临时替换也可能受影响，需明确并发边界。

**常见误答：** monkeypatch 会回滚测试做过的一切修改。

**继续追问：** 后台任务尚未完成时就退出 patch 范围会怎样？

**回答边界：** 指出登记的操作与其他副作用的区别。

### 第 30 题：side_effect 与失败调用次数

**首轮结论：** 调用记录包含失败调用，序列型 side_effect 按次消费，耗尽可能产生新的异常。

第一次取得配置结果，第二次抛指定 TimeoutError，但调用动作已经发生，call_count 会累计。第三次若序列已耗尽，可能抛 StopIteration，不能把它误当原接口的正常失败。

用这种替身控制故障点，再检查调用次数、实参、结果和状态。框架不会因为设置 side_effect 就自动重试，业务重试另有责任。

**常见误答：** 只有成功返回才算调用，或 side_effect 耗尽会一直复用最后一个值。

**继续追问：** 怎样用交互断言发现业务意外多读一次？

**回答边界：** 说明逐次消费与失败记录。

### 第 31 题：AsyncMock 的调用与等待

**首轮结论：** 创建可等待结果与实际等待是两个事件，异步测试运行支持需要明确安排。

调用会增加 call_count，只有实际等待才增加 await_count，应按接口使用 assert_awaited_once_with 等检查。只创建协程而不等待，业务可能根本没完成。

普通 pytest 不原生执行 async 测试体；可显式采用合适插件并说明循环生命周期，或在普通同步测试中用标准库驱动一个小异步过程。已有循环的 Notebook 不能再直接嵌套 asyncio.run。

**常见误答：** AsyncMock 调用一次就是已完成一次异步执行，或者 pytest 不需任何设置就运行所有 async 测试。

**继续追问：** 异步后台任务退出前还需要确认哪些资源？

**回答边界：** 区分调用、等待与运行器前提。

### 第 32 题：时间与随机数的可重复控制

**首轮结论：** 固定种子只控制对应随机序列，其他外部输入需要各自可控边界。

注入时钟测试到期边界，使用局部 Random 实例避免全局污染；环境通过 monkeypatch，文件通过临时目录，网络通过明确读取接口和替身。保留实际生成输入和种子便于复现。

不应以长 sleep 代替状态约定，也不能把真实调度顺序或跨版本随机细节都当作已固定。轮询预算与重试属于后续脚本流程的独立设计。

**常见误答：** 固定 seed 后真实时间、线程顺序和外部系统也固定。

**继续追问：** 到期判断应测等于边界的哪一侧，依据从哪里来？

**回答边界：** 给出每类输入各自的控制方式。

### 第 33 题：tmp_path 与临时结果保留

**首轮结论：** 每项的目录隔离可使同名文件独立，删除与保留遵循临时目录策略。

应将文件写在各自 tmp_path 下，而非当前工作目录固定路径。tmp_path_factory 提供更大作用域的目录创建能力，共享目录内部仍要划分用例路径。

pytest 可能为诊断保留临时结果，不能依赖马上消失；需长期留存的证据应明确复制到受管理的报告位置。路径独立也不隔离端口、缓存键或外部账号。

**常见误答：** 用了 tmp_path 就隔离了所有资源，或者退出测试立即删除一切。

**继续追问：** 失败附件为什么可能要在某个清理动作之前保存？

**回答边界：** 说明路径边界与保留策略。

### 第 34 题：配置层次与无效值校验

**首轮结论：** 应用覆盖语义必须明文定义，缺失与假值应按接口区分。

若 0 是有效预算或 False 是关闭开关，value or default 会误覆盖。应先判断是否提供，再转换、校验并记录来源；空字符串是否有效同样由约定决定。

pytest 自身有配置选择和选项规则，不自动定义应用的优先级。不同位置的配置也不是一律递归合并，先确认所选配置文件和版本。

**常见误答：** 所有配置系统都固定使用同一优先级，所有假值都代表没填。

**继续追问：** 为什么全局无效选项不应只在个别 fixture 中验证？

**回答边界：** 说明来源、覆盖、转换与校验阶段。

### 第 35 题：数据文件与收集时机

**首轮结论：** 数据与逻辑分离可便于维护，但结构、编号、预期来源和加载时机都要明确。

读取路径优先基于测试文件位置而非偶然工作目录，检查字段、类型和重复案例编号。为生成参数项在模块顶层加载，错误会在收集阶段暴露；fixture 加载则在准备阶段。

简单几行参数直接写代码可能更清楚。数据驱动不应把复杂控制逻辑藏进 JSON，更不能直接从 actual 导出 expected 作为独立判据。

**常见误答：** 只要外置 JSON 就不需要检查其结构和预期正确性。

**继续追问：** 修改数据顺序后案例编号是否应变化？

**回答边界：** 说明路径、加载阶段、数据质量与取舍。

## 四、结果、诊断与扩展

### 第 36 题：capsys 的分段读取

**首轮结论：** readouterr 取当前缓冲并开始下一段，捕获层次应按输出来源选择。

第一次通常读到 alpha 换行，第二次读到 beta 换行，而非两段累计。capsys 主要捕获 Python sys 层，capfd 面向文件描述符层，两者覆盖范围与子进程行为不能简单等同。

调试选项 -s 等影响呈现，不代替自动断言；对关键输出应说明检查内容和编码。

**常见误答：** 每次读取都包含从会话开始的全部输出，所有捕获工具行为完全一样。

**继续追问：** 一项测试自己读掉缓冲后，后续断言怎样组织？

**回答边界：** 解释读取边界与输出层次。

### 第 37 题：caplog 与日志断言

**首轮结论：** 先检查日志是否产生、有效级别、传播和处理器，再对稳定记录字段断言。

用 at_level 在小范围调节目标 logger 级别，过滤相关 logger，检查 levelname、getMessage 与虚构关联字段。代码重配处理器或关闭传播可能影响捕获，不要不加分析就覆盖全局 logging 配置。

时间戳与格式器空格通常不是业务契约，完整文本比较容易脆弱。日志只提供事件证据，仍需检查业务结果。

**常见误答：** caplog 默认能收到任意配置下的一切日志，成功日志就等于业务成功。

**继续追问：** 额外字段丢失与消息内容错误分别怎样检查？

**回答边界：** 沿产生、过滤、传播、捕获解释。

### 第 38 题：执行阶段与清理错误

**首轮结论：** 阶段结果可来自同一节点，测试体通过不等于完整执行成功。

setup 准备条件，call 执行测试体，teardown 清理恢复；同一个节点可在 call 通过、teardown 抛错。应报告业务断言完成但收尾失败，保留节点与阶段证据。

setup 失败时测试体可能未执行，收集失败则更早。不能把阶段计数简单相加作为独立用例数，也不能丢弃清理错误只看 passed。

**常见误答：** 只要出现 passed 就可以忽略之后的 error。

**继续追问：** 怎样保证一个清理失败不遮住其他资源和原失败？

**回答边界：** 明确节点与阶段这两个统计维度。

### 第 39 题：退出码与空收集

**首轮结论：** 退出码区分执行成功、测试失败及运行问题，零测试不等于已验证目标。

常见为 0 成功、1 测试失败、2 中断、3 内部错误、4 使用错误、5 无测试。常规收集错误可能沿中断路径导致 2，不能只凭数字猜某项业务失败。

结合命令、节点列表、收集数量、阶段和具体消息核对本轮范围。即使某个定制系统覆盖了空收集退出规则，也要在报告中明确说明没有验证任何项。

**常见误答：** 所有非零都是业务缺陷，或者零测试的通过率应算 100%。

**继续追问：** -k 筛到零项时应先检查什么？

**回答边界：** 给出主要码值及范围核对原则。

### 第 40 题：报告、失败附件与信息范围

**首轮结论：** 结构化报告提供结果交换，必要日志和附件仍需明确关联、保存和保留策略。

记录版本、运行选择、案例编号和阶段；将最小输入、关键输出或受控日志与失败节点关联。并非所有附件、截图或日志都会自动进入 XML。

清理前保存必要内容，避免固定文件名被重跑覆盖，公开记录仅用虚构内容。不能只保留最后一次绿色结果而删掉首次失败。

**常见误答：** 有 JUnit XML 就自动拥有所有完整现场。

**继续追问：** 不同 worker 同写一个报告路径会怎样？

**回答边界：** 说明关联、保存时点与内容边界。

### 第 41 题：单独通过与整组失败

**首轮结论：** 先保留证据并缩小污染组合，检查共享状态和准备责任，而非先固定顺序。

分别运行目标节点、疑似前置项、最小组合并交换顺序，查看模块全局、session fixture、嵌套参数、环境、工作目录、缓存和固定文件。找出哪项改变了另一项的前置。

每项通过自己的 fixture 准备条件；真正测试一段状态流程时可组织为同一明确场景。强制先创建后读取只是隐藏测试间依赖，不提供独立执行能力。

**常见误答：** 把测试按名字排序就一定修好了隔离。

**继续追问：** 污染来自共享只读模板的嵌套列表时，怎样补回归？

**回答边界：** 提出最小复现与一个状态隔离修复。

### 第 42 题：不稳定用例与重试边界

**首轮结论：** 重试不能抹去首次失败，应先控制未受管理的输入和状态。

保留第一次失败、运行次数、触发输入与阶段，再分析时钟、调度、外部依赖和共享状态。可用可控时钟、替身和同步条件缩小。重试插件与次数也要显式声明。

测试重跑重新执行场景，业务内部重试可能已部分成功并产生副作用，两者不能混用。最终一次通过不证明根因消失。

**常见误答：** 重试到绿说明没有问题，或 pytest 默认自动重试所有失败。

**继续追问：** 重跑前的数据准备与清理怎样避免重复副作用？

**回答边界：** 说明证据、根因与两层重试责任。

### 第 43 题：并行 worker 与共享资源

**首轮结论：** session 通常属于每个 worker 的会话，跨进程资源需要额外隔离与协调。

不同进程的模块与缓存分开，固定文件路径、端口、远端数据和报告目录却可能共享。采用运行与 worker 标识划分资源，明确跨进程协调与清理；线程锁不能管另一进程。

先声明插件依赖与分发方式，再验证独立运行与并行范围。本章默认无需安装并行插件，不能把概念讲解冒充已验证某种分布式执行。

**常见误答：** 不同进程完全没有共享资源，session 在所有 worker 间天然唯一。

**继续追问：** 独立 tmp_path 为什么仍可能使用同一个远端账号？

**回答边界：** 分别说明 Python 内存和外部资源边界。

### 第 44 题：公开 hook 与早期配置校验

**首轮结论：** hook 接入框架阶段，全局配置错误应在执行测试体前验证，不能依赖某项恰好请求 fixture。

pytest_addoption 注册语法与帮助，pytest_configure 等合适阶段验证语义，fixture 向测试提供已验证的值。只在 fixture 中检查，会让不请求它的用例绕过无效全局配置。

使用 pytest.UsageError 表达选项错误，保留清楚的字段名与退出结果。hook 由框架按约定调用，不按 test 命名被当作业务测试，也不应在收集时执行真实业务副作用。

**常见误答：** 所有配置错误都等到第一条业务断言再处理。

**继续追问：** 语法上是整数但超出范围时，由哪一步负责拒绝？

**回答边界：** 说明注册、转换、语义校验与提供值的阶段。

### 第 45 题：公共组件与简单插件的自身测试

**首轮结论：** 按职责抽取并保留可见依赖，简单扩展也要测试正常、覆盖和配置失败。

重复计算用帮助函数，生命周期用 fixture，重复业务检查用断言组件；确有共同测试契约才考虑基类。不要用万能基类隐藏状态，也不要把全部实现堆进 conftest。

选项通过公开 hook 注册、早期转换与范围校验，再由 fixture 提供有效值。用临时小工程和独立 pytest 进程测试默认值、上下界、覆盖、非法文本和越界，并检查不请求 fixture 的用例也不能绕过非法全局配置。多工程确需复用时再提取插件，文档与版本兼容也属维护责任。

**常见误答：** 抽成插件就不再需要测试，或只验证某个使用该选项的成功用例。

**继续追问：** 为什么插件验收优先独立进程，而非在同一 Notebook 反复 pytest.main？

**回答边界：** 用责任、一个最小扩展接口和可重复验收说明。

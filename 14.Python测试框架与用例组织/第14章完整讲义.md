# 第 14 章完整讲义：Python 测试框架与用例组织

第 13 章解决“测什么、预期从哪里来”；本章把这些约定变成能独立运行、失败可定位、资源能收尾的 Python 用例。学习路线是：先运行一条已有用例，再修改输入和断言，随后组织数据、fixture（框架按依赖提供的测试条件）和替身（测试中代替协作者的对象），最后接触简单扩展。

本章以 **CPython 3.12.13、pytest 9.1.1** 验证，使用兼容 Python 3.11 及以上的语法。pytest 的收集、fixture 和 hook（特定阶段调用的扩展函数）是框架规则，不是 Python 语言规则。示例全部使用公开工具与虚构数据，不连接真实服务。配套的 [示例工程](./示例工程/README.md) 可以直接运行；代码实验在临时工程的独立子进程中启动 pytest。

## 1. 测试框架负责哪些工作

**测试框架**组织测试的查找、准备、执行、断言诊断、清理和结果输出。被测函数负责业务行为，测试用例负责表达输入与预期，框架负责安排用例怎样运行。框架不会替人决定需求是否正确或测试是否充分。

例如“空报告也有标题”是需求；调用渲染函数后比较文本是测试；找到这项测试并统计结果是 pytest 的责任。仅仅看到命令退出成功，还应确认运行了哪些用例、检查了哪些性质。

本章选用 pytest，因为普通函数即可表达测试，便于逐步观察。标准库 unittest 使用 TestCase、setUp 和断言方法表达类似责任；第 11 章已经建立最小使用能力。学会迁移这些责任，比记住某个框架的全部接口更有价值。

## 2. 阅读测试工程的目录与入口

先打开示例工程，不要从每个文件的第一行机械读起。目录职责如下：

```text
示例工程/
├── pyproject.toml          pytest 配置与标记声明
├── sample_report/
│   ├── __init__.py
│   ├── core.py             被测报告逻辑
│   └── source.py           可替换的数据读取接口
└── tests/
    ├── conftest.py         共享 fixture 与简单选项
    ├── data/cases.json     虚构输入和独立预期
    ├── test_report.py      渲染规则与文件结果
    └── test_dependencies.py 依赖、日志和选项
```

**入口**是启动测试的命令及其所选择的目录或节点；**配置**决定默认搜索范围等规则；**测试数据**描述具体输入与预期；**报告**记录某次执行。配置文件不等于执行入口，报告也不应覆盖静态测试数据。

阅读顺序可以是 README 的运行命令、配置、一个 test 函数、它请求的 fixture、被测函数，最后查看结果输出。记录“一条用例如何获得输入、调用谁、检查什么、由谁清理”，即可建立第一张执行图。

## 3. 使用正确的 Python 环境运行一条测试

先在仓库根目录完成已有环境同步，再进入示例工程。下面是终端命令，`uv run --project ../..` 明确选中上两级仓库的开发环境；引号包住目录名，命令不是 Python 语句。

```text
uv sync --group dev
cd "14.Python测试框架与用例组织/示例工程"
uv run --project ../.. python -m pytest tests/test_report.py::test_empty_report -v
```

`--project ../..` 选择依赖工程，但仍在当前示例目录执行命令，pytest 因而读取本地测试配置。示例自身的 pyproject.toml 仅提供 pytest 配置；省略工程选择，uv 可能把它当成另一个工程并建立缺少 pytest 的环境。`python -m pytest` 让选中的解释器执行 pytest 模块，`-v` 显示更具体的测试项名称。若不用 uv，可在同一已安装 pytest 的环境里运行相同的 `python -m pytest` 命令。不要默认终端、IDE 和 Notebook 选中了同一个解释器；第 8 章的 `sys.executable` 是排查起点。

**节点标识 node ID** 是 pytest 用来定位测试项的字符串。此例由文件路径与函数名通过 `::` 连接；参数化（同一测试逻辑配多组输入）后还会带方括号案例编号。它用于选择和复现，不能替代长期维护的需求编号。

## 4. 测试发现、收集与导入副作用

默认情况下，pytest 在搜索位置查找 `test_*.py` 或 `*_test.py` 文件，收集其中 `test_` 开头的函数，以及没有自定义构造器的 `Test` 开头类中的测试方法。规则可配置，阅读已有工程时应先查配置。

**收集**是把源码中的定义变成可执行的测试项。pytest 为发现定义会导入相关模块，所以模块顶层的文件写入、连接建立等动作可能在执行测试体之前就发生。`--collect-only` 不运行普通用例体，却仍可能执行导入和收集相关代码。下面的 `-q` 减少常规输出，便于查看节点列表。

```text
uv run --project ../.. python -m pytest --collect-only -q
```

导入失败属于收集问题，不能理解成“某个业务断言失败”。把资源取得放在明确的 fixture 或调用接口里，避免导入模块就连接外部环境。框架配置中的 `rootdir` 用于配置、节点和缓存等定位，不等于自动安装源码包或修好 `sys.path`。

## 5. 按节点、关键字和标记选择用例

**关键字筛选**使用 `-k` 对节点名称、父级名称和标记等关键词作匹配；**标记 marker** 是给测试附加的命名元信息，`-m` 按标记表达式选择。二者都支持 `and`、`or`、`not` 等表达式，但匹配对象不同。

```text
uv run --project ../.. python -m pytest tests/test_report.py::test_empty_report -q
uv run --project ../.. python -m pytest -k "empty or upper" -q
uv run --project ../.. python -m pytest -m "smoke and not extra" -q
```

`smoke` 表达本工程选择的冒烟集合，不会因为用了这个名字就自动拥有合理覆盖。标记在 `pyproject.toml` 注册，开启 `--strict-markers` 可以让拼错标记直接暴露。被筛掉的项是 deselected，按条件跳过是 skipped，二者都不是通过。

## 6. 从已有用例补充一条边界

示例工程规定报告最多包含三条标签，空输入也输出标题。先运行 `test_empty_report`，读懂它比较的具体文本，再运行参数化的 `test_render_rows`。然后复制一条数据到个人练习副本，改变一项输入并写下独立预期。

修改时沿着四步走：确认需求、预测结果、运行目标节点、解释差异。不要看到失败就把 expected 改成当前输出。若需求是三条仍可接受，应检查三条内容；只断言返回值非空，无法发现第三条被丢弃。

先小范围运行能缩短定位路径，随后运行相关整组可以发现共享状态。若修改了所有用例共用的 fixture，就应验证它的使用者，而非只运行眼前一个节点。

## 7. 断言表达业务预期

`assert condition, message` 要求某项关系成立。pytest 会对测试模块中的断言做**重写**：在导入时转换相关代码，以便失败时显示参与比较的值。它是诊断能力，不会补出缺失的业务断言。

下面可独立运行，比较完整结构与只检查真值的差异：

```python
actual = {"title": "Demo", "rows": []}
print(bool(actual))
print(actual == {"title": "Demo", "rows": ["A"]})
```

非空字典为真，不能说明 rows 正确。断言应对应当前需求中的内容、类型和必要状态。错误消息可以带用例编号、字段和受控输入，避免把完整环境变量、令牌或真实业务数据写进输出。

帮助函数所在模块未必自动参与断言重写；必要时可了解 `pytest.register_assert_rewrite()`，它必须在相关模块导入前登记。不要因此把所有断言都塞入 conftest。业务输入校验仍用 `if` 与 `raise`，不能依赖可能被普通 Python 优化移除的 assert。

## 8. 用 raises 验证异常与失败后的状态

`pytest.raises(ExpectedError)` 是验证异常的上下文管理器。若范围内没有相应异常，它会让测试失败；匹配类型通常包括子类。需要精确类型时可以再检查 `type(info.value)`。

```python
import pytest

records = ["kept"]

def reject(value):
    if value < 0:
        raise ValueError("quantity must be non-negative")
    records.append(value)

with pytest.raises(ValueError, match="non-negative") as info:
    reject(-1)
assert type(info.value) is ValueError
assert records == ["kept"]
```

`as info` 保存异常信息，`info.value` 是实际异常对象；`match` 是正则模式匹配，不是固定文本相等。只把目标操作放进 raises 的范围；若把准备数据也放进去，准备阶段的同类错误可能让测试误通过。

异常验证与状态验证是两件事。接口要求拒绝后旧记录不变，就还需要比较旧记录。用 `except Exception: pass` 代替这两项检查，会同时放过未抛错和抛错类型不对等问题。

## 9. 参数化与独立测试项

**参数化**将一项测试逻辑与多组输入、预期配对，让每组成为独立测试项。`@pytest.mark.parametrize("value, expected", rows)` 中字符串列出测试函数的形参名，每一行按位置提供值。第 4 章的装饰器机制解释了这种语法；这里的测试项生成由 pytest 完成。

在示例工程中，`test_render_rows` 通过 `pytest.param(..., id="upper")` 为上界案例提供编号。可以单独运行：

```text
uv run --project ../.. python -m pytest "tests/test_report.py::test_render_rows[upper]" -q
```

在一个 test 函数内部循环，若中间断言失败，剩余循环通常不再执行，也只对应一个测试项。参数化保留各组独立结果。它并不保证测试完整；输入和 expected 仍应由第 13 章的方法选择。

## 10. 案例编号、组合数量与共享参数

案例编号应能帮助定位，例如 `empty`、`upper`、`invalid-type`，避免使用可能含隐私的大对象 repr 作为报告名称。编号不决定逻辑结果，也不应随着数据遍历顺序随意变化。

多个 parametrize 装饰器通常形成笛卡尔积：每个维度的每种值与其他维度全部组合。两种模式、三种数量就是六项；三个十值维度会扩成一千项。先确认可行组合和覆盖目标，需要时明确列出组合或在单行参数上标记。

pytest 不为参数对象自动深拷贝。下面的对象共享关系与是否使用 pytest 无关：

```python
shared = {"tags": []}
rows = [("first", shared), ("second", shared)]
rows[0][1]["tags"].append("changed")
print(rows[1][1]["tags"])
```

参数只保存引用；修改同一个列表会影响另一行。把不可变描述交给 fixture 创建独立状态，或按明确边界复制，比依赖测试顺序更可靠。

## 11. fixture 按依赖提供准备条件

**fixture** 是 pytest 管理的准备条件或资源提供者，用 `@pytest.fixture` 登记。测试函数形参请求同名 fixture，pytest 解析依赖并把其结果作为实参传入。这个形参名不是普通业务输入，也不是要求你手动调用 fixture 函数。

例如示例工程的 `report_path(tmp_path)` 请求内置临时目录，再向测试提供一个报告文件路径。测试请求 report_path，即可间接获得 tmp_path。依赖关系示意如下，图中箭头表示“请求”：

```text
test_write_report → report_path → tmp_path
```

在一次测试内，多个请求路径使用同一个 fixture，通常复用当前作用域中缓存的结果及状态。fixture 名字出现两次，不代表创建两份资源。依赖是否共享必须结合作用域和参数化判断。

## 12. fixture 的作用域与缓存范围

**作用域 scope** 决定一份 fixture 结果可被复用到多大的范围。常见值为 `function`、`class`、`module`、`package`、`session`；默认 function。session 指当前 pytest 会话，不是整台机器永久共享。

| 选择 | 适合的条件 | 常见代价 |
|---|---|---|
| function | 每项需要独立的可变数据 | 重复准备成本 |
| module 或 session | 创建昂贵且适合共享的资源或只读基础 | 状态污染、生命周期变长 |

作用域限制共享上界，不承诺参数化 fixture 一整场永远只建立一次。切换参数实例、执行组织等都可能影响创建与清理。较大作用域不能直接依赖较小作用域的 fixture，例如 session 请求 function，会出现 ScopeMismatch；因为被依赖值不能活得比需要它的共享对象还短。

缓存只表示结果被保留，不表示结果不可变。session 返回字典、测试向内部列表 append，后续测试仍能看见。第 9 章的对象图适用于 fixture 缓存。

## 13. fixture 的准备与清理顺序

对存在依赖的 fixture，先准备被依赖者，再准备依赖者；退出时按已成功进入部分的逆序收尾。pytest 同时考虑作用域、依赖和 autouse 等规则，不应通过函数定义顺序、形参排列顺序或名字字母序安排独立 fixture。

**autouse fixture** 无需测试显式请求，也会在适用范围自动生效。它适合少量必须统一建立的条件，例如禁止误调用某类外部接口；使用过多会让用例的隐含依赖难以阅读。明确要求 A 在 B 前准备时，让 B 请求 A。

```text
base 准备 → child(base) 准备 → 测试体 → child 清理 → base 清理
```

可以用 `--setup-show` 查看真实安排，再回到依赖关系解释原因。这个选项是观察工具，不是固定所有独立 fixture 顺序的契约。

## 14. yield fixture 与测试失败后的收尾

在生成器式 fixture 中，`yield resource` 之前准备并交付资源，pytest 在测试使用完后恢复生成器执行清理。第 5 章的“产出并暂停”在这里由框架驱动。

```python
from contextlib import contextmanager

events = []

@contextmanager
def resource():
    events.append("open")
    try:
        yield {"value": 1}
    finally:
        events.append("close")

try:
    with resource() as item:
        events.append("use")
        raise ValueError("example failure")
except ValueError:
    pass
print(events)
```

这段是可独立运行的上下文管理器对照，不是 pytest 调度器实现。fixture 中同样应把需要保证的清理放进 `try/finally`。测试体断言失败，已成功交付的 fixture 仍会按正常框架退出路径收尾。进程被强制终止不在此保证范围内。

## 15. yield 之前失败时的资源责任

若 fixture 先取得 A，随后取得 B 失败，还没执行到 yield，不能指望写在 yield 之后的普通语句自动释放 A。取得逻辑必须及时建立清理责任。

```python
from contextlib import ExitStack

events = []
try:
    with ExitStack() as stack:
        events.append("A acquired")
        stack.callback(events.append, "A released")
        raise RuntimeError("B acquisition failed")
        # 在 fixture 中，全部准备完成后才在这个 with 内 yield。
except RuntimeError:
    pass
print(events)
```

`ExitStack.callback()` 登记退出动作，`with` 退出时逆序调用。另一种方式是每个 fixture 只负责一项取得与清理，再由依赖组合；也可用 `request.addfinalizer()` 在取得成功后登记动作。**finalizer** 就是框架在退出阶段调用的收尾函数；不要在资源尚未取得时登记一个假设它已存在的清理。

清理函数自己出错也要报告。不要用 `except Exception: pass` 隐藏它，更不要让一个资源清理失败阻止其他已登记清理。清理成功不自动等于业务回滚成功，两者按各自约定检查。

## 16. fixture 工厂与多份独立数据

**工厂 fixture** 返回一个可调用对象，让同一测试按需创建多份资源或数据。fixture 结果是工厂本身，测试调用工厂才得到每份对象。

```python
def make_factory():
    created = []
    def create(label):
        record = {"label": label, "tags": []}
        created.append(record)
        return record
    return create, created

create, created = make_factory()
first = create("A")
second = create("B")
first["tags"].append("checked")
print(first is second, second["tags"], len(created))
```

示例工程的 report_factory 在 tmp_path 下为每次调用分配独立文件名；真实资源可在 fixture 中记录取得结果，退出时逆序清理。只把所有调用都写到 `report.txt`，不会因为函数名含 factory 就自动隔离。

## 17. conftest 的可见范围与覆盖

`conftest.py` 是 pytest 按目录发现的本地配置与扩展文件。测试通常直接请求其中 fixture，不写 `from conftest import fixture_name`。在父目录定义的 fixture 可以供子目录使用，子目录定义可在局部覆盖同名 fixture；同级其他目录的 fixture 不会天然互相可见。

把某个子领域专用准备放在相应子目录，减少全部测试的隐含影响。通用解析函数放普通模块，让依赖方向明确；conftest 用于把组件接入 pytest，而非存放所有业务实现。

同名 fixture 覆盖属于框架查找规则。修改覆盖关系时，要检查使用者实际取得的是哪一份，可以通过 `--fixtures`、`--setup-show` 和局部最小用例定位。

## 18. indirect 参数化与准备阶段的分工

普通参数化把数据直接交给测试函数；`indirect=True` 让参数先交给同名 fixture，通过 `request.param` 读取，由 fixture 建立结果再交给测试。`request` 是 pytest 提供的当前请求信息对象。

结构示意如下，完整运行见实验 15：

```text
参数行 "small"
→ fixture 读取 request.param
→ 根据描述创建当前测试的数据
→ test 函数收到创建结果
```

适合把轻量数据描述留在收集阶段，把实际取得资源留到运行准备阶段。它不等于所有数据驱动都必须使用 indirect，也不保证参数对象被复制。只需替换整数输入时，普通参数化往往更清楚。

## 19. 共享高成本资源与隔离可变状态

把创建昂贵的只读基础共享，把每项会修改的状态单独建立，可以同时控制成本和污染。例如 session 加载一份模板，function fixture 依据模板创建当前用例的独立嵌套记录。

```python
import copy

base = {"limit": 3, "tags": ["template"]}
case = copy.deepcopy(base)
case["tags"].append("local")
print(base, case)
```

浅拷贝只分开外层，内部列表仍共享。也不能对文件、锁和连接一律 deepcopy；资源需要明确的创建、重置或事务接口。若必须共享可变资源，应证明用例前后如何恢复，并验证失败路径；不能只要求“大家记得清理”。

## 20. skip、xfail 与维护责任

**skip** 表示按已知条件不执行测试体，需记录原因。**xfail** 表示已知问题下预期测试会失败；默认仍运行，符合预期的失败记为 XFAIL，意外通过记为 XPASS。`xfail(run=False)` 是不执行的特例，要明确说明。

`strict=True` 或配置 `xfail_strict=true` 可让意外通过影响会话失败，提醒维护者确认是否已修复。strict XPASS 在会话汇总通常计入 failed，不能把所有 XPASS 都当作单独的成功类别。

标记应带公开可说明的原因和维护条件。xfail 的 `raises` 可限定预期错误类型，避免无关异常也被当作已知失败；给任意失败加 xfail 会掩盖新问题。环境不满足、产品缺陷和用例自身错误应分别定位。

## 21. 测试替身、交互断言与接口约束

**替身**在测试中代替协作者，固定输入、输出或故障；**交互断言**检查调用对象、实参、次数等协作约定。它们服务于业务断言，不应把“调用过”当成业务结果正确。

```python
from unittest.mock import create_autospec

def read_record(case_id, *, timeout=1):
    raise RuntimeError("real implementation not used")

def title(reader, case_id):
    return reader(case_id, timeout=2)["title"].upper()

reader = create_autospec(read_record, return_value={"title": "demo"})
assert title(reader, "C-demo") == "DEMO"
reader.assert_called_once_with("C-demo", timeout=2)
```

`create_autospec` 根据原接口约束调用签名；`spec_set` 可限制未声明属性。它们不会自动证明返回内容合法，也不能证明真实协作方与替身一致。保留必要的受控集成测试，检验接口契约。

## 22. patch 应替换代码实际查找的名字

第 8 章的导入绑定解释了 patch 的关键。如果 core 模块写 `from source import read_label`，运行时查找的是 core 自己的 read_label，替换 source.read_label 不会自动更新旧绑定。

```python
from types import SimpleNamespace
from unittest.mock import Mock, patch

source = SimpleNamespace(read=lambda: "original")
consumer = SimpleNamespace(read=source.read)
with patch.object(source, "read", Mock(return_value="changed")):
    print(source.read(), consumer.read())
with patch.object(consumer, "read", Mock(return_value="local")):
    print(consumer.read())
print(consumer.read())
```

此例用两个命名空间模拟两个模块属性的绑定，避免隐藏跨文件前提。退出 with 后恢复对应绑定。示例工程则真实导入 core，并在 `core.read_label` 处 monkeypatch。函数默认实参若早已绑定旧协作者，仅替换模块属性也可能无效；此时检查默认值的计算时机，或使用显式注入接口。

## 23. monkeypatch 的恢复范围

pytest 的 monkeypatch fixture 提供 `setattr`、`setenv`、`delenv`、`chdir` 等操作，并在所属作用域退出时恢复登记的修改。`monkeypatch.context()` 还能在单个测试内建立更短的恢复范围。

```python
from types import SimpleNamespace
import pytest

settings = SimpleNamespace(mode="outer")
with pytest.MonkeyPatch.context() as patcher:
    patcher.setattr(settings, "mode", "inner")
    print(settings.mode)
print(settings.mode)
```

恢复登记的属性绑定，不等于撤销任意内部对象修改、删除外部创建数据或还原远端状态。patch 范围越大，越容易影响框架自身或其他线程；优先替换清楚的小边界。局部上下文结束前，也要让依赖它的后台任务按约定完成。

## 24. side_effect、故障注入与异步替身

`Mock.side_effect` 可配置抛错、根据实参响应，或每次调用消费序列下一项。它用于控制失败位置，不代表框架会自动重试；序列耗尽可能抛出 StopIteration，应检查调用次数是否符合约定。

```python
from unittest.mock import Mock

reader = Mock(side_effect=[{"state": "ready"}, TimeoutError("sample timeout")])
print(reader("C-1")["state"])
try:
    reader("C-2")
except TimeoutError:
    print("dependency failed")
print(reader.call_count)
```

异步协作者使用 AsyncMock 时，调用和等待是不同事件：

```python
import asyncio
from unittest.mock import AsyncMock

async def main():
    reader = AsyncMock(return_value="ready")
    pending = reader("C-1")
    print(reader.call_count, reader.await_count)
    assert await pending == "ready"
    reader.assert_awaited_once_with("C-1")
    print(reader.call_count, reader.await_count)

asyncio.run(main())
```

本块在普通 Python 进程独立运行；已有事件循环的 Notebook 中用 `await main()`，不再嵌套 asyncio.run。pytest 原生不直接执行 async def 测试体；若采用异步测试插件，应单独声明并说明事件循环生命周期。本章异步对照使用标准库驱动，不把安装插件当成隐藏前提。

## 25. 时间、随机数与外部依赖的可重复性

可重复测试应控制实际读取的输入。时间可以注入 clock，随机行为可以使用局部 Random 实例，环境用 monkeypatch，文件用临时目录，网络用受控读取接口。固定随机种子只控制对应发生器序列，不会固定真实时钟、调度或外部服务。

```python
import random

def expired(start, budget, clock):
    return clock() - start >= budget

assert expired(10, 3, lambda: 13)
first = random.Random(7)
second = random.Random(7)
print([first.randrange(100) for _ in range(3)] ==
      [second.randrange(100) for _ in range(3)])
```

时间边界应按需求选择；不能用大量 sleep 等待一个“应该已经结束”的状态。轮询、重试与总体预算在第 15 章组织为完整流程，本章先学会用可控依赖验证调用条件。

## 26. tmp_path、测试数据编号与文件隔离

内置 fixture tmp_path 为每个测试项提供独立 pathlib.Path 目录。即使都写 `report.txt`，只要位于各自 tmp_path 下，通常不会写同一文件。`tmp_path_factory` 支持更大作用域创建目录，但共享目录内仍需划分每项文件。

临时目录不等于测试结束立刻消失。pytest 可按保留策略留存临时结果供诊断，不应把“立即删除”写成接口保证。输出文件位于谁的目录、是否需要长期保存，要分开说明。

内部数据标识可用固定案例编号加当前运行或 worker 的唯一前缀。记录实际使用的标识，避免只生成随机字符串而无法复现。文件隔离不能自动隔离数据库记录、端口、缓存键或外部账号。

## 27. 配置来源、覆盖规则与校验时机

先分清 pytest 自身配置和被测程序配置。pytest 读取的配置文件、`-o` 覆盖和命令行选项有框架规则；应用默认值、环境与文件的优先级必须由应用明文定义，pytest 不会自动发明一套通用优先级。

例如约定“默认值 → JSON 文件 → 环境变量 → 显式命令行”，后者只在确实提供时覆盖。空字符串、0、False 是否有效由接口决定，不要用 `value or default` 把它们全部当成缺失。先转换，再校验范围；错误信息应指明字段与来源。

示例工程把 pytest 配置集中在一个 pyproject.toml，使用兼容的 `[tool.pytest.ini_options]`。本章不要求所有 pytest 版本支持所有新配置格式；阅读已有工程时先确认版本和实际选中的 configfile。不同位置的配置文件也不是自动逐层全部合并。

## 28. 数据文件与用例逻辑分离

数据文件适合保存明确的输入和预期，函数负责执行和断言。示例工程用 tests/data/cases.json 保存虚构报告案例，读取路径基于 `Path(__file__).parent`，避免依赖命令启动时碰巧位于某目录。

数据加载时检查结构、字段和重复编号。若模块顶层加载 JSON，解析错误会在收集阶段暴露；若在 fixture 中加载，失败发生在准备阶段。选择时机应看是否参与生成测试项、是否需要外部资源，不是越晚越好。

外部化数据不能替代可读性。三行简单输入直接写在 parametrize 可能更清楚；大量嵌套 JSON 若含复杂条件，可能把代码逻辑藏进数据。更不能从被测函数输出自动生成 expected，再把它当独立依据。

## 29. capsys 与标准输出捕获

pytest 默认捕获运行输出，失败时展示相关内容。`capsys` 主要捕获 Python 层的标准输出和标准错误，`readouterr()` 读取当前已捕获内容，并开始下一段缓冲。

如果第一次读取后再次读取，第二次得到的是后续新增内容，不能假设每次都返回完整历史。需要文件描述符层面的输出可了解 capfd；是否覆盖子进程输出取决于捕获方式，不能把所有捕获工具说成相同。

调试时 `-s` 关闭常规捕获，`--capture=tee-sys` 可同时显示与捕获部分 Python 输出。它们改变证据呈现，不应改变业务断言。给需要验证的输出单独写测试，不靠人看一眼终端就宣布通过。

## 30. caplog 与日志字段

`caplog` 收集日志记录。`caplog.at_level(logging.INFO, logger="sample")` 在指定范围调整相关日志级别，读取 records 或 messages 可避免断言依赖格式器的时间和空格。

检查日志时，先确认事件是否产生、级别是否允许、记录是否传播到捕获处理器。被测代码若重配 root handler 或关闭 propagate，可能影响捕获，不要先通过全局 basicConfig 强行覆盖整个会话。

示例工程检查 `case_id` 这一虚构关联字段，并同时检查业务返回值。日志通常提供失败证据和定位线索；“出现成功日志”本身并不证明输出文件和数据状态正确。

## 31. setup、call、teardown 与结果解释

pytest 对普通测试执行区分准备 setup、测试体 call、退出 teardown。准备失败时测试体可能根本没运行；测试体失败后通常仍执行已进入 fixture 的收尾；收尾失败也应报告。

| 现象 | 首先检查 | 不能直接推出 |
|---|---|---|
| 收集失败 | 导入、语法、数据解析、配置 | 业务断言已经执行 |
| setup ERROR | fixture 取得与依赖 | 测试体已检查业务 |
| call FAILED | 断言、目标异常、测试实现 | 一定是产品缺陷 |
| teardown ERROR | 释放、恢复、清理接口 | 整个用例完整成功 |

同一个测试可能测试体通过，但清理时报错，于是报告同时出现 passed 与 error。阶段统计不一定是一项测试只能贡献一个计数的互斥分类。Notebook 的辅助运行器保留这些阶段信息；它不是 pytest 官方报告格式。

## 32. 退出码、JUnit XML 与失败附件

pytest 常见退出码：0 表示测试成功，1 表示存在测试失败，2 表示执行被中断，3 表示内部错误，4 表示命令使用错误，5 表示没有收集到测试。常规收集错误可能经中断路径导致 2；先看报错阶段，不要只按数字猜根因。默认选到零项也不能当通过。

```text
uv run --project ../.. python -m pytest -q -ra --junitxml=reports/junit.xml
```

JUnit XML 是便于自动系统读取的结构化结果格式；不是所有日志、附件和阶段细节都会自动包含。`-ra` 显示额外结果摘要。报告应与本轮版本、选择范围和收集数量关联，不能只保留一个绿色百分比。

需要保存失败附件时，先定义内容、关联编号、输出目录与保留策略。临时结果要在清理前读取或复制；报告目录应单独安排，避免固定文件名被下一次执行覆盖。示例默认不保存真实环境信息，公开附件只用虚构数据。

## 33. 单独通过、整组失败的定位顺序

先固定失败节点、输入、版本和第一次失败证据，再分别运行目标节点、可能污染它的前置节点、最小组合。检查模块全局、session fixture、嵌套参数对象、环境变量、工作目录、缓存和文件名。

依赖“先执行 test_create，再执行 test_read”的用例，把数据准备混入了另一个测试。应让每项通过 fixture 或明确接口自行准备所需条件。把顺序锁死可能短暂隐藏问题，却没有建立独立运行能力。

也有测试目标本身是一段状态序列，此时将相关步骤组织在同一个明确场景中检查中间状态。不要机械地把所有步骤拆成互相依赖的 test 函数。

## 34. 不稳定用例、重试与证据

**不稳定用例 flaky test** 在预期相同条件下时过时不过，可能源于未受控时间、调度、共享状态、外部依赖或测试错误。先记录触发输入、环境条件和失败阶段，再用可控时钟、替身、同步条件或独立数据缩小问题。

重试可以作为受管理的缓解手段，但应声明次数、适用条件、首次失败和最终结果，不能覆盖第一次失败只报最后通过。重试不是 pytest 所有测试默认具备的能力，第三方插件须显式声明。

测试运行器重跑一项用例与业务函数内部重试是两个层次，后者可能已产生副作用。不要因为测试会重跑，就让创建数据、写文件等操作依赖“多试几次总会好”。

## 35. 并行执行中的资源隔离

pytest 默认按通常的串行会话执行，安装扩展也不会自动使任意共享资源安全。pytest-xdist 等公开插件可用多个 worker 进程分发测试；worker 是执行一部分测试的独立进程。

每个 worker 通常有自己的 Python 模块与 session fixture，因此 session 并不保证跨进程只创建一个实例。磁盘路径、固定端口、远端记录和报告目标却可能仍共享。进程内互斥锁不能协调另一进程或另一台机器。

本章不把并行插件列为运行前提。需要实际采用时先声明依赖，设计 worker 与运行标识、文件和数据分区、跨进程协调及清理，再验证串行与并行结果。顺序依赖未解决前，增加并行只会更容易暴露它。

## 36. 帮助函数、断言组件与测试基类

重复的数据转换适合普通帮助函数；重复的业务检查可提取命名明确的断言组件；需要生命周期的条件交给 fixture。组合让依赖通过形参可见，通常比层层继承一个万能测试基类更便于局部使用。

基类适合确有共同测试契约的场景，但应说明哪些方法提供用例、哪些负责准备，避免继承隐藏大量状态和顺序。pytest 的普通测试类不应通过自定义 __init__ 取得资源，应使用 fixture 等框架生命周期接口。

公共断言组件也可能写错。用一个正确对象和若干故意错误对象检查其区分能力；别只验证“组件能运行”。抽取的价值来自明确责任与可维护性，不来自文件或类的数量。

## 37. hook、命令行选项与配置错误

**hook** 是框架在特定阶段调用的扩展函数。pytest 按公开约定识别 `pytest_addoption`、`pytest_configure`、`pytest_collection_modifyitems` 等名字，将参数交给扩展；不要把任意同名函数都当普通用例。

示例工程用 pytest_addoption 注册 `--include-extra`，默认不运行 extra 标记测试，显式提供后才运行。布尔开关使用 `action="store_true"`；读取用 `config.getoption()`。范围型选项还要做语义校验，非法配置应尽早报 pytest.UsageError，避免每条用例重复报准备错误。

```text
uv run --project ../.. python -m pytest -m extra -q
uv run --project ../.. python -m pytest -m extra --include-extra -q
uv run --project ../.. python -m pytest --help
```

第一条选中了额外测试，但因未开启选项跳过；第二条才执行。默认值、覆盖来源、条件标记与帮助文本都要有文档。不要在收集 hook 中执行真实业务操作或吞掉配置错误。

## 38. conftest 扩展与可复用插件

小范围扩展先放相应 conftest；多个独立工程确实复用时，再提取为普通插件模块或可安装包。可用 `-p module_name` 显式加载插件，发行包也可通过约定的入口点发现；加载机制和版本兼容属于需要维护的接口。

插件自身要测试默认选项、有效覆盖、无效值、空收集、标记选择以及其他扩展共存等行为。最直接的方法是在临时目录创建小工程，用独立解释器运行 pytest，检查退出码、选中项与状态。这也是本章 Notebook 和检查器的做法。

pytest 还提供 pytester 等专用测试支持，需要显式启用，不能假定随处都有对应 fixture。复杂 hook wrapper、插件发现和分发机制留待后续独立主题，本章先把一个简单公开接口做清楚。

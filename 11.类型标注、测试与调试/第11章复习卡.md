# 第 11 章复习卡：类型标注、测试与调试

学完讲义与实验后使用。先独立复述，再对照；想不起原因时回讲义，不把短句当首次教学。

## 1. 类型检查、输入校验、测试与调试

| 方法 | 主要职责 | 仍需补充 |
|---|---|---|
| 类型标注与静态工具 | 声明、分析类型关系 | 实际输入内容、业务正确性 |
| 运行时校验 | 拒绝不符合本次接口的数据 | 需求范围与选择场景 |
| 测试 | 执行明确条件并核对预期 | 未覆盖需求、真实依赖边界 |
| 调试与性能诊断 | 观察执行、原因与成本 | 修复后的重复验证 |

标了整数不等于自动转换；字符串类型正确不代表端口合法；测试通过不代表所有需求都覆盖。

## 2. 类型写法与边界

- `value: int`、形参冒号与 `-> str` 记录预期，不修改对象绑定规则。
- `list[int]` 不保证非空；`tuple[str, int]` 固定位置，`tuple[int, ...]` 表达可变长度同类元组。
- `Optional[T]` 等价于 `T | None`；实参能否省略由默认值决定。
- `Literal` 表达有限值选择；外部数据仍需实际校验。
- `Any` 放宽静态约束，`object` 使用专属行为前要收窄。
- `cast` 表达信任，不转换、不检查实际对象。
- `Callable` 描述调用，`Iterable` 不保证下标或重复遍历，`Iterator` 保存消费状态。
- `Generator[Y, S, R]` 对应产出、接收与结束返回类型。
- 类型别名为表达式命名；TypeVar 保留输入输出等类型关联，不自动处理空输入。
- 可变容器不变性是类型替代约束，不等于对象不可变。
- Protocol 声明结构能力；运行时协议判断不完整核对签名与业务。

注解求值要标明版本。3.12 普通函数注解与 future annotations 有不同保存行为，3.14 默认延迟求值；解析还需要可用名字环境。mypy、Pyright 的版本、范围和配置影响诊断。

## 3. 测试预期与断言

准备条件 → 执行目标 → 检查结果、异常及必要副作用。预期来自约定或独立规则，不能复制被测实现求出 expected。

单元、集成、端到端按实际验证边界分类，不由 pytest 或 unittest 的工具名称决定。替换依赖的单元测试不能证明真实 SQL、网络和权限。

普通 assert 可被优化模式移除，不承担必要输入校验，也不放必要副作用。异常测试限制类型，范围尽量小，不能任意异常都算通过或没有异常也直接结束。

## 4. unittest 与 pytest

| 能力 | 回忆要点 |
|---|---|
| unittest | TestCase 写用例，套件组织，运行器执行，结果对象收集 |
| failure / error | 断言未成立与未预期异常，均需继续定位责任 |
| setUp / tearDown | 准备成功后才有对应退出前提，部分失败要单独安排 |
| addCleanup | 每次取得后登记，已登记清理可覆盖后续准备失败 |
| pytest 收集 | 先确认选中哪些测试，不能只看有没有失败 |
| 参数化 | 每组独立报告；数据中的共享对象不自动深拷贝 |
| fixture | 按名字请求，默认按测试函数；创建新对象才可能独立 |
| yield 清理 | 提供资源后的退出责任，不自动覆盖 yield 前的全部失败 |
| tmp_path / monkeypatch | 管理本地路径和受支持替换，不回滚任意远端系统 |

测试单独通过、整组失败，先查全局对象、嵌套引用、文件、环境与模块缓存。固定顺序、休眠和重试不能代替隔离。用本地 Random 实例和记录输入建立可复现数据，种子不固定调度或时间。

## 5. 替身与依赖查找

`return_value` 控制返回，`side_effect` 控制失败或逐次行为，调用记录核对交互；同时检查业务结果。spec、autospec 约束成员或签名，不证明真实返回和集成正确。

patch 作用于被测代码实际查找位置。`from time import monotonic` 在 service 中建立绑定，通常替换 `service.monotonic`；只改原模块属性不自动改已有绑定。with 退出恢复；依赖注入可让协作者由接口明确传入。

异步替身要区分已调用、已等待与已完成，不丢弃未接收结果的协程。普通失败、取消与资源收尾仍遵守第 10 章的责任。

## 6. 日志、调用链与断点

先看产生日志的 logger 门槛，再看 handler 级别与过滤；传播交给祖先 handler，不重新按祖先 logger 级别产生记录。多 handler 或重复配置可能重复输出，库不随意重置 root。

`exception()` 在异常现场附加 traceback；普通 `error()` 默认只有消息。选择负责处理或上报的边界记录，避免每层重复。日志输出不是自动断言结果。

traceback 给调用与失败位置，原因链补充转换来源，错误输入可能更早形成。pdb 的 where 看栈，step 进入、next 越过、continue 继续，up/down 切换查看现场。求值仍可能有副作用，不在变量窗口随意 pop。

先保留失败条件并缩小复现，修复后增加能暴露原错误的回归测试，不把偶然通过当完成。

## 7. 性能测量与工具分工

timeit 的 number 是组内次数，repeat 是组数，时长按组返回。setup 不一定每次操作都执行；输入被修改会改变后续工作量，复制放进函数就计入复制成本。默认临时关闭循环 GC，要确认与测量目标一致。

cProfile 看调用分布：ncalls 是次数，tottime 是自身时间，cumtime 包含下游。累计高可能源于下游热点，剖析也有开销。先确认正确结果与代表性工作，再定位并比较，不要求固定秒数。

格式化统一风格，lint 检查规则，类型工具分析关系，测试执行行为。它们互补，都不能单独证明全部正确；系统负载、吞吐与容量评估作为独立领域学习。

## 8. 一分钟自测

1. 为什么 Optional 不等于形参可省略？
2. cast 为什么可能掩盖类型错误，却不改变实际对象？
3. fixture 每次调用为什么仍可能返回共享列表？
4. patch 为什么找实际查找位置，而不是只找最初定义位置？
5. 只有调用记录的 mock 测试遗漏了哪项证据？
6. logger INFO、handler DEBUG 会输出 DEBUG 吗？
7. traceback 失败行与业务错误最早形成的位置有什么区别？
8. number=3、repeat=2 对应多少次执行和多少个时长？
9. cProfile 累计时间高为什么不必然重写外层函数？
10. 怎样证明新回归用例确实针对原缺陷？

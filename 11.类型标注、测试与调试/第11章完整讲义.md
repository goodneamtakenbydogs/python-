# 第 11 章完整讲义：类型标注、测试与调试

前十章已经能解释 Python 怎样执行。本章学习怎样表达预期、验证行为，以及在结果错误或运行过慢时找到证据。类型标注说明接口期望，测试核对具体行为，调试帮助检查执行过程；它们各自能发现的问题不同。

代码以当前项目 **CPython 3.12.13** 为验证基线，主线兼容 Python 3.11 及以上。`pytest` 是第三方测试工具，使用本项目开发环境中的版本；其他示例主要使用标准库。讲义中的 `python` 代码块均可保存为独立脚本运行，包含测试的脚本会明确运行入口。实验 Notebook 保留原始预测，实际观察与预测分开填写。

## 1. 接口预期、实际行为与失败证据

假设函数把成绩文本转换为整数。只看函数名，无法确定空字符串是否允许、失败时抛出什么异常、有没有修改输入。**接口约定**就是调用方可以依赖的输入、输出、异常和副作用规则。

可以先把要回答的问题分开：

| 方法 | 主要问题 | 一个例子 |
|---|---|---|
| 类型标注与静态检查 | 代码是否按照声明的类型关系使用对象 | 本应传文本，却传了列表 |
| 运行时校验 | 这一次实际输入是否符合要求 | 文本是 `"abc"`，不能表示成绩 |
| 自动化测试 | 给定条件下，实际行为是否符合预期 | `"0"` 应得到整数零 |
| 调试与诊断 | 这次错误在哪一层、哪一步形成 | 转换前输入已被错误截断 |

**静态检查**是在不执行目标业务路径的情况下分析源代码；**运行时**是代码真正执行的阶段。类型符合要求的字符串仍可能违反业务范围，几个测试通过也不代表需求全部覆盖。先理解每种证据的范围，才能正确使用工具。

## 2. 变量、形参与返回值的类型标注

类型标注记录“这里期望哪类对象”。变量写成 `name: Type`，函数形参写成 `name: Type`，返回值写在 `-> Type` 后。冒号和箭头描述预期，不执行转换。

```python
def format_score(name: str, score: int) -> str:
    return f"{name}: {score}"

count: int = 2
message: str = format_score("Ada", 90)
print(count, message)  # 2 Ada: 90
```

`name`、`score` 仍是本次调用的局部形参；调用时先计算实参对象，再按第 3 章的绑定规则传入。返回标注 `str` 表示调用方应得到文本，不会在函数返回时自动调用 `str()`。

如果函数仅产生副作用、不交还业务数据，通常标为 `-> None`。标注应解释实际接口，而不是为了消除工具提示随便写一个类型。

## 3. 标注不自动执行校验或转换

下面故意传入与标注不符的实参，观察普通运行时行为：

```python
def twice(value: int) -> int:
    return value * 2

print(twice("ha"))  # haha；静态检查器应指出调用类型不符
```

函数体执行的是字符串重复，所以普通 Python 没有仅因标注而拒绝调用。静态检查器可能在执行前报告问题，但它不是普通解释器默认执行的检查步骤。

真正需要拒绝外部输入时，应写运行时条件，或使用明确提供校验功能的库。例如业务要求只接受整数时，要考虑第 1 章的 `bool` 是 `int` 子类这一边界：`isinstance(True, int)` 为真。接口是否接受布尔值，应由需求决定，不能靠标注猜测。

**面试连接：** 回答“Python 已经动态类型，为什么还要标注”时，可以说明接口表达、编辑器提示和提前发现类型误用，再补充业务值域仍需要校验与测试。

## 4. 注解的保存与版本差异

**注解**是语法允许附着在变量或函数等位置的说明，类型标注是其主要用途。本章不根据 `__annotations__` 的打印形式推断运行时校验。

```python
from typing import get_type_hints

def length(text: "str") -> "int":
    return len(text)

print(get_type_hints(length) == {"text": str, "return": int})  # True
```

引号中的名称称为字符串形式的前向引用，适合类型还未定义等情况。`get_type_hints()` 结合命名空间解析类型提示，比直接假定保存内容永远是类型对象更可靠。

在 Python 3.12 中，普通函数注解表达式通常在执行函数定义时求值；使用 `from __future__ import annotations` 可改变保存方式。Python 3.14 默认引入延迟求值，不能把 3.12 的观察说成所有版本规则。本章不依赖这些表达式的副作用。

解析注解可能执行表达式，不应把来自不可信来源的注解当作普通安全数据随意求值；仅在 `TYPE_CHECKING` 分支导入的名称也未必在运行时解析现场存在。`TYPE_CHECKING` 是 `typing` 提供的标志，运行时为假、静态工具可以把对应分支视为需要分析。当前先记住静态工具看得到与运行时能解析是两回事。

## 5. 容器类型与元素约束

`list[int]` 表示元素按整数使用的列表，`dict[str, int]` 表示文本键到整数值的映射。方括号表达类型参数，不是在读取某个运行时元素。

```python
scores: list[int] = [80, 90]
count_by_name: dict[str, int] = {"Ada": 2}
pair: tuple[str, int] = ("Ada", 90)
numbers: tuple[int, ...] = (1, 2, 3)
print(scores[0], count_by_name["Ada"], pair[1], len(numbers))
```

`tuple[str, int]` 指定两个位置的类型；`tuple[int, ...]` 表示任意长度的同类元素元组。这里的省略号属于类型表达式的一部分，不表示代码遗漏。`list[int]` 不保证非空，也不会阻止运行时把其他类型放入列表。

参数如果只需要逐项读取数据，不应仅因为示例使用列表，就强制要求列表。第 8 节会用 `Iterable` 表达更合适的能力要求。

## 6. 联合类型、Optional 与 None 分支

**联合类型**表示允许的类型选择。`int | str` 表示整数或文本；`Optional[str]` 等价于 `str | None`，不是“调用时可以不提供这个实参”。是否可省略由默认值决定。

```python
from typing import Optional

def display_name(name: Optional[str]) -> str:
    if name is None:
        return "anonymous"
    return name.upper()

print(display_name(None))  # anonymous
print(display_name("Ada"))  # ADA
try:
    display_name()
except TypeError:
    print("仍需提供实参")
```

工具可以根据 `name is None` 的控制流，把后一个分支中的 `name` 缩小为 `str`，称为**类型收窄**。`Union[int, str]` 是兼容旧写法，与 `int | str` 表达同类选择。

对外部共享对象，不应把一次检查当作以后状态永远不变。第 10 章的并发修改仍需同步或取得稳定局部值；标注不会替你锁住对象。

## 7. Literal、Any、object 与 cast

`Literal` 表达有限的具体值选择，例如 `Literal["json", "text"]`。它帮助工具发现拼写或调用错误，不自动验证实际传入字符串。

```python
from typing import Literal

def mode_label(mode: Literal["json", "text"]) -> str:
    return mode.upper()

print(mode_label("json"))  # JSON
print(mode_label("xml"))  # XML；静态工具应报告此处不符合有限值约定
```

第二次调用没有由函数体执行允许值检查，所以运行时仍返回文本。这不是 Literal 已完成校验后放行，而是当前函数根本没有实施那项运行时检查。

`Any` 表示对这一位置放宽静态类型约束，许多操作会不再得到充分检查。`object` 表示可以接收任意 Python 对象，但只能直接使用所有对象都支持的行为；使用专有方法前需要收窄。二者不能互换理解。

```python
from typing import Any

def upper_any(value: Any) -> str:
    return value.upper()

def upper_object(value: object) -> str:
    if isinstance(value, str):
        return value.upper()
    raise TypeError("text required")

print(upper_any("Ada"), upper_object("Ada"))  # ADA ADA
for operation in (upper_any, upper_object):
    try:
        operation(7)
    except (AttributeError, TypeError) as error:
        print(type(error).__name__)  # 依次为 AttributeError、TypeError
```

Any 版本的 `upper()` 调用通常不会因缺少已知成员而被静态拒绝，但实际整数没有该方法；object 版本先缩小范围，再使用文本能力。如果直接删掉收窄而对 object 调用 upper，静态工具就有理由指出成员不明。

```python
from typing import cast

raw: object = "42"
claimed = cast(int, raw)
print(type(claimed).__name__)  # str
print(claimed is raw)  # True
```

`cast(int, raw)` 是告诉静态工具“在这里相信这个类型判断”，不会转换或校验对象。真正把 `"42"` 转为整数应调用 `int()`，并处理无效输入。若一个函数大量使用 `Any`、`cast` 或忽略提示来通过检查，应先追查接口是否描述错误。

## 8. Callable、Iterable、Iterator 与 Generator

`Callable[[int], str]` 描述接收一个整数并返回文本的可调用对象。`Iterable[int]` 需要能够开始逐项读取整数的过程，`Iterator[int]` 还表示自身保存遍历状态并支持 `next()`。它们接上第 5 章的行为协议。

```python
from collections.abc import Callable, Generator, Iterable

def render(values: Iterable[int], formatter: Callable[[int], str]) -> list[str]:
    return [formatter(value) for value in values]

def squares(stop: int) -> Generator[int, None, None]:
    for number in range(stop):
        yield number * number

print(render(squares(3), str))  # ['0', '1', '4']
```

`Generator[YieldType, SendType, ReturnType]` 分别描述产出的值、通过 `send()` 传入的值，以及生成器结束时的返回值。这里只产出整数，不接收业务数据，也不返回结束结果，因此后两项为 `None`。如果调用方只需普通迭代能力，返回 `Iterator[int]` 常更简洁。

选接口类型应按实际能力：只消费一遍就别隐含要求下标、长度或可重复遍历。标注也不改变第 5 章中迭代器会耗尽的状态规则。

## 9. 类型别名与新的运行时类型

**类型别名**是为重复出现的类型表达式取名，帮助读懂接口。它不会创建新的业务对象种类。

```python
from typing import TypeAlias

CaseId: TypeAlias = str
ResultRow: TypeAlias = tuple[CaseId, bool]

def passed_ids(rows: list[ResultRow]) -> list[CaseId]:
    return [case_id for case_id, passed in rows if passed]

print(passed_ids([("login", True), ("order", False)]))  # ['login']
```

这里的 `CaseId` 仍表示 `str`，不是独立于字符串的新运行时类型。Python 3.12 起还支持 `type CaseId = str` 等类型别名语法，涉及新的别名对象与求值规则；本章用兼容 Python 3.11 的写法，不混用来推断 `isinstance()`。

类型别名描述类型，默认值和普通常量描述值，不应因为它们都用赋值符号就混淆职责。

## 10. TypeVar、泛型与可变容器

**泛型**让一个结构表达随具体使用而变化、但需要保持关联的类型。`TypeVar` 声明类型变量；同一次类型关系中的 `T` 把输入元素与返回值联系起来，不是运行时业务变量。

```python
from collections.abc import Iterable
from typing import TypeVar

T = TypeVar("T")

def first(values: Iterable[T]) -> T:
    return next(iter(values))

print(first([10, 20]))  # 10
print(first(["Ada", "Lin"]))  # Ada
```

工具能从输入推断结果类型；若简单标为 `Any`，这种关联会丢失。空输入仍会抛出 `StopIteration`，类型变量不会自动添加边界处理。类也可通过 `Generic[T]` 保存类似关系，当前先掌握函数中的输入输出关联。

`list[str]` 不能直接被视为任意的 `list[object]`：如果接收者能向后者追加整数，原本按纯文本使用的列表就会被破坏。这称为可变容器的**不变性**，强调这种类型替代不被直接允许，不是指列表对象不可变。只读使用时可考虑 `Sequence` 或 `Iterable`；`Sequence` 表达长度、位置读取等序列能力，但它本身也不保证底层数据永久不变。

## 11. Protocol 与结构化类型关系

第 6 章的鸭子类型关注对象提供什么行为。`Protocol` 把所需行为写成静态工具可以核对的接口，常称为**结构化子类型**：对象不必显式继承协议，只要满足声明的能力。

```python
from typing import Protocol

class TextReader(Protocol):
    def read(self) -> str:
        ...

class MemoryReader:
    def read(self) -> str:
        return "report"

def load(reader: TextReader) -> str:
    return reader.read().upper()

print(load(MemoryReader()))  # REPORT
```

协议中的 `...` 表示这里描述所需方法，没有提供真实读取实现。抽象基类通常建立显式继承和实例化约束，Protocol 主要描述结构关系，不替代业务测试。

只有标为 `@runtime_checkable` 的适当协议才支持相应运行时检查；检查主要关注成员存在等结构，不完整验证形参、返回值和业务语义。一个 `read()` 实际返回整数的对象，也不能仅凭“运行时协议判断通过”就宣称读取契约正确。

## 12. mypy、Pyright 与静态检查流程

`mypy` 和 Pyright 是分析类型关系的工具。它们读取源代码与类型信息，在实际运行前报告可能的调用、返回和成员使用问题。工具版本、配置和第三方类型说明都会影响结果；通过某次检查不能证明业务正确。

先用明确范围的小文件建立流程。以下是命令示意，不是 Python 源码；路径和工具安装按实际环境选择：

```text
python -m mypy sample.py
pyright sample.py
```

若使用 `uv`，可通过隔离工具环境运行 `uvx mypy sample.py` 或 `uvx pyright sample.py`，不要求同时装入项目运行依赖。先确认检查的文件、Python 目标版本及严格程度，再读第一条诊断。类型缺失或 `Any` 太多可能让错误路径没有得到充分检查。

第 3 节的 `twice("ha")` 能运行，却应被静态检查指出。相反，`divide(1, 0)` 即使形参都是整数，也可能在运行时除零。修复类型诊断与设计输入边界测试是两项互补工作。

## 13. 从接口约定确定测试预期

**测试用例**说明在什么条件下执行什么操作，以及应该观察到什么。**断言**将实际结果与预期关系作比较，条件不成立时使测试失败。预期结果应来自接口、需求或独立可信规则，不能把当前实现复制一遍当答案。

假设接口约定“折扣按整数金额计算，数量为零时结果为零，负数量抛 `ValueError`”。正常数量、零和负数量对应不同路径。类型标注只能帮助描述输入和结果，不能替测试选择这些代表性条件。

本章先学会把已明确的约定写成可靠测试。怎样系统从复杂需求中设计测试点、边界与优先级，在第 13 章展开；不能因此在当前题目中省略预期来源。

## 14. 单元测试、集成测试与端到端测试

分类先看测试对象和边界。**单元测试**聚焦较小逻辑，例如一个金额计算函数；**集成测试**检查组件协作，例如程序通过实际数据库驱动读写临时测试库；**端到端测试**验证完整用户或业务链路，例如经页面提交订单后核对最终状态。

不是“一个函数等于单元、两个函数等于集成”，也不是按使用 `unittest` 还是 `pytest` 分类。一个函数也可能跨网络和数据库，一个纯逻辑模块也可能内部调用多个小函数。

越多真实依赖通常意味着更复杂的数据准备、环境和失败定位。用替身替换数据库的单元测试能快速验证分支，却不能证明真实 SQL、权限和事务兼容；需要对应集成证据。测试工具可以执行不同层次的测试，名称不决定层次。

## 15. 准备条件、执行操作与断言结果

把测试分为准备、执行、断言，便于看出输入和预期来源。通常也称 Arrange、Act、Assert，缩写 AAA。不要把复杂业务分支和参考算法都塞进测试，让错误实现与错误测试一起通过。

```python
def line_total(price: int, quantity: int) -> int:
    if quantity < 0:
        raise ValueError("quantity must be non-negative")
    return price * quantity

price, quantity = 12, 3
actual = line_total(price, quantity)
assert actual == 36
assert line_total(12, 0) == 0
try:
    line_total(12, -1)
except ValueError:
    pass
else:
    raise AssertionError("负数量没有被拒绝")
```

预期 `36` 来自这份明确接口的整数乘法约定，零和负数分别检查边界与异常路径。异常测试必须检查预期类型；捕获任意异常就算通过，可能把代码里的 `NameError` 当成正确拒绝输入。

还应检查相关副作用，例如输入没有被修改、失败前后资源状态符合约定。只断言函数没报错，容易漏掉错误结果。更系统的业务测试设计在第 13 章学习。

## 16. assert 的用途与优化模式

`assert condition, message` 在条件为假时抛出 `AssertionError`，适合表达测试中的预期关系和程序内部不变量。**不变量**是某个操作范围内必须保持的约束，例如转账前后总金额相同。

普通 Python 使用 `-O` 优化时可移除断言及其表达式求值，不能用它做必须执行的用户输入校验，也不要把保存文件等必要副作用放进断言。

```python
source = """
def positive(value):
    assert value > 0
    return value
result = positive(-1)
"""
namespace = {}
exec(compile(source, "<optimized>", "exec", optimize=1), namespace)
print(namespace["result"])  # -1，断言已被移除
```

业务校验应使用明确的 `if` 与 `raise`。pytest 对收集到的测试模块断言还提供重写和诊断机制，这是测试工具行为，不应据此让业务校验依赖 assert。在本章练习中保持普通运行模式，单独观察优化边界。

## 17. unittest 的测试对象与结果

`unittest` 是标准库测试框架。继承 `TestCase` 后，用 `test_` 开头的方法表达用例，使用 `assertEqual`、`assertRaises` 等接口检查。**测试运行器**负责执行用例并收集结果，不是被测业务函数。

```python
import io
import unittest

def quotient(total, count):
    return total / count

class QuotientTests(unittest.TestCase):
    def test_normal(self):
        self.assertEqual(quotient(8, 2), 4)

    def test_zero_count(self):
        with self.assertRaises(ZeroDivisionError):
            quotient(8, 0)

suite = unittest.defaultTestLoader.loadTestsFromTestCase(QuotientTests)
result = unittest.TextTestRunner(stream=io.StringIO()).run(suite)
print(result.testsRun, result.wasSuccessful())  # 2 True
```

`assertRaises` 只接受约定异常及其匹配子类，不是无条件吞错。测试失败表示断言未成立；运行中出现未预期异常则属于错误，二者都需要定位原因。

实际项目可以用 `python -m unittest discover` 发现用例，也可以明确选择模块或方法。本例显式构造测试套件，避免脚本直接解析 Notebook 或外层工具的命令行参数。

## 18. unittest 的准备与清理

`setUp()` 在每个测试方法前准备条件，`tearDown()` 在成功完成准备后负责测试后的清理。每个测试方法通常有自己的 TestCase 实例，但引用同一全局列表仍会共享对象。

如果 `setUp()` 执行到一半就失败，不能假定 `tearDown()` 一定负责已取得资源。`addCleanup()` 可在每次成功取得资源后登记对应清理，已登记的清理即使准备失败也会执行，且按登记的逆序运行。

```python
import io
import unittest

events = []

class ResourceTests(unittest.TestCase):
    def setUp(self):
        events.append("prepare")
        self.addCleanup(events.append, "cleanup")

    def test_work(self):
        events.append("test")
        self.assertTrue(True)

    def tearDown(self):
        events.append("tearDown")

suite = unittest.defaultTestLoader.loadTestsFromTestCase(ResourceTests)
result = unittest.TextTestRunner(stream=io.StringIO()).run(suite)
print(result.wasSuccessful())  # True
print(events)  # ['prepare', 'test', 'tearDown', 'cleanup']
```

这与第 7 章“谁取得资源，谁建立清理责任”一致。不能把清理留给某个碰巧最后运行的测试。

## 19. pytest 的发现、运行与退出结果

`pytest` 可用普通函数表达测试，并提供断言诊断、fixture 和参数化。**测试发现与收集**是从给定文件找到符合规则的测试项；有代码文件不等于有测试被执行。

把下面的完整代码保存为 `.py` 文件，直接运行会由入口调用 pytest；在测试工程中通常命名为 `test_*.py`，然后通过 `python -m pytest` 收集。

```python
import pytest

def double(number):
    return number * 2

def test_double():
    assert double(3) == 6

if __name__ == "__main__":
    raise SystemExit(pytest.main([__file__, "-q", "-p", "no:cacheprovider"]))
```

`-q` 减少输出；本例关闭磁盘缓存插件，避免教学脚本留下运行缓存。正常测试可使用默认设置。命令退出状态为零通常表示测试通过，但还要确认收集数量和预期范围；默认没有收集到测试时，pytest 使用专门的非零退出码。

不要在 Notebook 中反复 `pytest.main()`，以为每次都会重新导入所有已缓存模块。本章相关观察在独立子进程和临时目录里运行，避免污染内核的模块、插件和环境。

## 20. pytest 的断言与异常验证

pytest 对测试模块里的普通 assert 提供更清楚的失败信息。`pytest.raises()` 用上下文管理方式验证异常；`match` 匹配异常消息的正则表达式，不是简单的固定文本相等。**正则表达式**按模式匹配文本，完整语法在第 12 章学习，当前只用简短稳定片段。

```python
import pytest

def parse_count(text):
    number = int(text)
    if number < 0:
        raise ValueError("count must be non-negative")
    return number

def test_zero():
    assert parse_count("0") == 0

def test_negative():
    with pytest.raises(ValueError, match="non-negative"):
        parse_count("-1")

if __name__ == "__main__":
    raise SystemExit(pytest.main([__file__, "-q", "-p", "no:cacheprovider"]))
```

with 范围应尽可能只包预期抛错的操作。把许多无关准备动作一起包进去，可能让准备阶段的同类错误误满足断言。异常类型、必要的消息或业务字段都按真实接口检查，不机械绑定不稳定的完整内部文本。

## 21. 参数化让多组输入保留独立结果

**参数化测试**把同一项测试逻辑与多组输入、预期组合。`@pytest.mark.parametrize` 为每组数据建立独立测试项；它不同于在一个测试函数里循环，后者中间失败可能直接跳过后续输入。

```python
import pytest

def clamp(value, lower, upper):
    return min(upper, max(lower, value))

@pytest.mark.parametrize(
    "value, expected", [(0, 1), (1, 1), (3, 3), (5, 5), (6, 5)],
    ids=["below", "lower", "inside", "upper", "above"],
)
def test_clamp(value, expected):
    assert clamp(value, 1, 5) == expected

if __name__ == "__main__":
    raise SystemExit(pytest.main([__file__, "-q", "-p", "no:cacheprovider"]))
```

参数名按位置绑定每一行的数据；`ids` 为失败案例提供可读编号，不决定预期。这里按已声明的闭区间约定选择输入，不从被测函数动态计算 expected。

pytest 不会为每次使用自动深拷贝参数对象。若多组参数引用同一列表，测试修改后仍可能污染其他项。第 9 章的共享与复制规则仍然适用。

## 22. fixture 提供独立条件与清理范围

**fixture** 是测试运行时按依赖请求获得的准备条件或资源。pytest 通过测试函数的形参名称请求它，不是手动按约定顺序调用的普通帮助函数。默认作用域是每个测试函数。

```python
import pytest

@pytest.fixture
def records():
    values = []
    yield values
    values.clear()

def test_append(records):
    records.append("A")
    assert records == ["A"]

def test_starts_empty(records):
    assert records == []

if __name__ == "__main__":
    raise SystemExit(pytest.main([__file__, "-q", "-p", "no:cacheprovider"]))
```

这两项测试各自执行列表创建，所以无需依赖测试顺序。`yield` 前提供资源，`yield` 后负责该资源的退出动作；使用时测试失败，正常进入后的退出部分仍由工具安排。若 yield 之前就失败，那之后的退出段没有进入，需要按取得资源的时点建立其他清理责任。

本章只建立最小使用能力。作用域组合、依赖图、工厂、共享成本与框架组织在第 14 章深入。不要把所有资源都改为整个会话共享来追求速度，导致可变状态越过用例边界。

## 23. 测试隔离、临时目录与随机数

**测试隔离**表示一项测试不会通过遗留状态改变其他项的条件。文件、环境变量、模块缓存、全局配置和外部账号都可能是共享来源。pytest 的 `tmp_path` 提供测试专用临时目录，`monkeypatch` 可以在受管理范围替换环境或属性。

```python
import os
import pytest

def test_environment(monkeypatch, tmp_path):
    monkeypatch.setenv("CH11_REPORT_MODE", "brief")
    report = tmp_path / "report.txt"
    report.write_text("passed", encoding="utf-8")
    assert os.environ["CH11_REPORT_MODE"] == "brief"
    assert report.read_text(encoding="utf-8") == "passed"

if __name__ == "__main__":
    raise SystemExit(pytest.main([__file__, "-q", "-p", "no:cacheprovider"]))
```

`tmp_path` 是路径对象，`/` 在这里按路径协议拼接文件名；`write_text` 和 `read_text` 按指定编码写读文本。第 12 章会展开路径与编码。环境修改在 fixture 管理的范围退出后恢复，不应把真实用户目录当作临时测试空间。

随机数据也应可复现。优先使用本地 `random.Random(seed)` 实例，避免修改全局随机发生器。固定种子不固定时间、线程调度或远端系统状态；记录输入和种子，仍需合理设计边界与独立预期。

## 24. Mock、替身与可控依赖

**测试替身**是测试中替代真实协作者的对象或实现。固定返回值的简化实现可称桩，记录交互并据此检查的对象常称 mock；这些称谓描述测试中的职责，不是所有工具都严格互斥的类型分类。

`unittest.mock.Mock` 可控制返回值、抛出异常并记录调用。优先对接口边界做替换，保留真正需要验证的业务逻辑。

```python
from unittest.mock import Mock

def load_label(reader, case_id):
    return reader(case_id)["label"].upper()

reader = Mock(return_value={"label": "login"})
print(load_label(reader, "C-1"))  # LOGIN
reader.assert_called_once_with("C-1")
reader.side_effect = TimeoutError("dependency timeout")
try:
    load_label(reader, "C-2")
except TimeoutError:
    print("收到可控依赖失败")
```

`return_value` 是调用结果，`side_effect` 可表示异常或逐次行为；`assert_called_once_with` 检查交互约定。只检查“调用过”而不检查业务返回值，仍可能漏掉错误映射。mock 返回什么就断言什么，也可能只证明测试自身配置一致。

## 25. patch 要替换实际查找依赖的位置

第 8 章说明 `from module import name` 建立当前名字绑定。patch 应作用于被测代码实际查找的那个绑定，不能只因为依赖最初定义在某个库里就替换那个库的位置。

```python
import time
from time import monotonic
from unittest.mock import patch

with patch("time.monotonic", return_value=123):
    print(time.monotonic())  # 123
    print(monotonic is time.monotonic)  # False，已有导入绑定没有跟着替换

with patch(__name__ + ".monotonic", return_value=456):
    print(monotonic())  # 456
```

真实工程中，若 `service.py` 用 `from time import monotonic`，函数内部写 `monotonic()`，通常应 patch `service.monotonic`。`with patch(...)` 退出会恢复对应绑定；手动全局赋值后不恢复，可能污染后续测试。

如果函数直接接收 reader、clock 等可调用对象，测试也可以传入替身，称为**依赖注入**：协作者由外部提供，而不是函数内部固定寻找。这能减少替换隐含名字的需要，但不应为了测试任意拆散清楚的业务接口。

## 26. spec、autospec 与替身的局限

普通 Mock 很宽松，拼错属性也可能得到新的 mock 对象。`spec` 或 `spec_set` 约束可用成员，`autospec` 还能根据原对象检查调用签名，帮助更早发现测试替身与真实接口不一致。

```python
from unittest.mock import create_autospec

def fetch(case_id, *, timeout=1):
    return case_id

reader = create_autospec(fetch, return_value="ready")
print(reader("C-1", timeout=2))  # ready
try:
    reader("C-1", 2)
except TypeError:
    print("调用不符合关键字形参约定")
```

autospec 不保证返回值类型或业务效果，也不会证明真实网络、数据库和浏览器可用。类型标注、mock 签名约束与集成测试分别提供不同证据。异步协作者可用 `AsyncMock` 建立可等待替身；检查“已调用”与“已等待”不同，不能只创建协程后不消费。具体框架用法在第 14 章展开。

## 27. print、日志与断点的用途

`print()` 适合临时展示少量值；**日志**记录可分类、可筛选的运行事件，方便在不能重现现场时关联上下文；**断点**使程序在指定位置暂停，以检查当前局部状态和后续执行。

发现计算错了，先打印一个局部中间结果可能够用；生产环境中的偶发错误通常需要日志证据；可以稳定复现的局部问题则适合断点逐步检查。不要把所有中间对象、密码和令牌直接输出，也不要为了追踪而改变原来的业务状态。

第 10 章已经说明观测会影响并发调度。日志时间相近不能单独证明严格先后，固定随机种子也不能固定线程交错。保留输入、用例编号、任务关联和异常链，通常比大量无编号文本更有价值。

## 28. logging 的日志器、处理器与级别

标准库 `logging` 将产生事件的**日志器** logger 与接收事件的**处理器** handler 分开。**格式器** formatter 把事件组织成可读文本，**过滤器** filter 可按额外规则决定是否接收。

常见级别由低到高是 `DEBUG`、`INFO`、`WARNING`、`ERROR`、`CRITICAL`。级别表达事件的重要程度，不是“DEBUG 一定代表代码出错”。先由产生日志的 logger 有效级别决定是否产生记录，再由 handler 的级别和过滤规则决定是否输出。

下面为了独立观察，创建不加入全局命名注册表的局部日志器；业务模块通常使用 `logging.getLogger(__name__)`，由应用入口配置输出。

```python
import io
import logging

stream = io.StringIO()
logger = logging.Logger("chapter11.demo", level=logging.DEBUG)
handler = logging.StreamHandler(stream)
handler.setLevel(logging.WARNING)
handler.setFormatter(logging.Formatter("%(levelname)s:%(message)s"))
logger.addHandler(handler)
try:
    logger.info("case %s started", "C-1")
    logger.warning("case %s slow", "C-1")
    print(stream.getvalue().splitlines())  # ['WARNING:case C-1 slow']
finally:
    logger.removeHandler(handler)
    handler.close()
    stream.close()
```

`%(levelname)s` 等表示记录字段，不是未定义 Python 变量。日志调用的 `"case %s"` 与实参分开传入，可让工具推迟文本格式化，但函数实参表达式仍会先求值；不能据此认定昂贵函数调用不会执行。

## 29. 日志传播、重复输出与配置边界

`getLogger("app.worker")` 的命名体现层次，记录可通过 `propagate` 继续交给祖先 logger 的 handler。传播阶段不会重新按祖先 logger 的级别过滤同一记录，但祖先 handler 自身的级别与过滤器仍会生效。

如果子 logger 和 root 都有 handler，且继续传播，同一记录可能输出多次。重复运行 Notebook 配置单元格又反复添加 handler，也会制造重复；不应因此在每条业务日志后手动清空全局配置。

`basicConfig()` 面向简单应用入口，根日志器已有 handler 时通常不再添加默认配置；`force=True` 可以重配，但可能移除用户已有处理器。库代码通常只取得命名 logger，配置由拥有运行环境的应用负责。本章 Notebook 不重置 root 日志器，实验使用局部 logger 或独立子进程。

## 30. 异常日志与 traceback 的关联

`logger.error()` 默认只记录消息；在异常处理块中用 `logger.exception()` 或 `exc_info=True` 可以附加当前异常追踪。第 7 章的异常链继续决定记录里保留什么来源。

```python
import io
import logging

stream = io.StringIO()
logger = logging.Logger("chapter11.failure")
handler = logging.StreamHandler(stream)
logger.addHandler(handler)
try:
    try:
        int("invalid")
    except ValueError:
        logger.exception("case %s failed", "C-1")
    text = stream.getvalue()
    print("ValueError" in text, "C-1" in text)  # True True
finally:
    logger.removeHandler(handler)
    handler.close()
    stream.close()
```

优先在负责处理或统一上报的边界记录一次。每层捕获、打印再抛出，可能把同一个错误记录多次，却没有增加有效证据。异常日志也不是自动测试断言，输出 ERROR 不会天然让测试失败，测试结果仍需明确判断。

## 31. 从 traceback 定位调用与失败位置

**traceback** 记录异常相关的调用路径和源代码位置。普通显示通常从外层调用走向更内层失败，最后一行给出异常类型和消息。要同时看调用路径、最终失败行与异常链，不能只按最后一行文本猜原因。

```python
import traceback

def parse(text):
    return int(text)

def load():
    return parse("invalid")

try:
    load()
except ValueError as error:
    frames = traceback.extract_tb(error.__traceback__)
    print([frame.name for frame in frames][-2:])  # ['load', 'parse']
    print(type(error).__name__)  # ValueError
```

`extract_tb` 产生结构化帧摘要，包含文件、行号、函数名等。例子只比较稳定函数名，不把临时路径和具体行号当作答案。实际调试要检查 `parse` 收到了什么，再向上追查输入从哪里产生；异常发生的位置不一定是业务错误最早形成的位置。

`raise ... from ...` 的直接原因和隐式异常上下文可能同时影响显示。保存完整异常还可能持有 traceback 和局部对象，第 9 章的生命周期边界也应考虑。

## 32. pdb 与 IDE 断点调试

`pdb` 是标准库交互式调试器，IDE 也可用图形界面提供断点与变量查看。**单步进入**跟入被调用函数，**单步越过**让当前行中的调用整体完成后再停；它们不只是不同速度的运行按钮。

下面脚本默认正常运行。手动练习时取消 `breakpoint()` 的注释，或用 `python -m pdb script.py` 启动；不要让无人值守的检查停在交互提示上。

```python
def line_total(price, quantity):
    subtotal = price * quantity
    # breakpoint()  # 手动调试时启用
    return subtotal

print(line_total(12, 3))  # 36
```

调试命令示意如下，属于 pdb 交互输入，不是 Python 脚本：

```text
where       查看调用栈
list        查看附近源码
p price     求值并显示表达式
next        单步越过
step        单步进入
continue    继续到下一个断点或结束
up / down   切换查看上层或下层调用现场
quit        退出调试
```

也可使用条件断点只在特定输入时暂停。调试表达式仍可能产生副作用：在查看窗口执行 `items.pop()` 会改变列表，随后代码看到的状态已经不同。保留最小复现，先观察，避免无意修改现场。

## 33. 最小复现与回归测试

**最小复现**是在保留失败条件的前提下，移除无关环境、数据和代码。先记录输入、实际结果、预期、版本与操作步骤，再减少依赖。某次重跑通过不说明缺陷已经修复；应明确原来的错误路径为何不再出现。

修复后增加能暴露原错误的**回归测试**，让以后相同缺陷再次出现时得到反馈。例如原来把零误认为缺失，回归用例就应检查合法的零和真正的 `None`，而不是只测试一个普通正数。

调试时验证的是当前假设，回归测试则把明确约定转化为后续可重复的检查。第 13 章会深入缺陷报告和风险覆盖，第 14 章会处理测试工程中的不稳定因素。

## 34. timeit 测量小段代码

标准库 `timeit` 面向小段代码重复计时，帮助减少一次观察的偶然性。`number` 表示一组内执行次数，`repeat` 表示重复几组；返回的每个时长对应整组，不是自动计算好的单次平均。

```python
import timeit

calls = []

def operation():
    calls.append(None)
    return sum(range(10))

durations = timeit.repeat(operation, number=3, repeat=2)
print(len(durations), len(calls))  # 2 6
print(all(duration >= 0 for duration in durations))  # True
```

本例只训练测量接口，不以具体秒数或“两组一定谁快”作为答案。真实比较要保证相同工作量、相同正确结果和可比环境，合理选择重复次数与统计。测量输入太小，固定开销可能淹没差异；输入缺少代表性，也不能推断真实场景性能。

timeit 默认在计时范围临时关闭循环垃圾回收以减少干扰，结束后恢复相应状态；如果 GC 成本正是研究对象，要明确启用并说明。它不会停止 CPython 的全部引用管理，也不是自动控制所有系统噪声的工具。

## 35. 计时中的输入、准备和副作用

`setup` 通常在每组计时前执行，不是每次语句执行前都重建数据。若一组内重复 `pop()`，输入会越来越短，甚至耗尽；后面的次数不再测量同一条件。

```python
import timeit

base = [3, 1, 2]

def sorted_copy():
    return sorted(base)

durations = timeit.repeat(sorted_copy, number=10, repeat=3)
print(base)  # [3, 1, 2]
print(len(durations))  # 3
```

这里只读输入并返回新结果，每次条件一致。若目标操作必须修改输入，可以在每次调用内部建立副本，但这时复制成本也被计入；要明确想测“完整使用过程”还是“已准备好数据后的某一步”。

缓存预热、文件系统状态、解释器和硬件都可能影响计时。不要把一次 `print` 前后手写时间差当成严格基准，也不要用单个速度结果证明时间复杂度。第 2 章的复杂度分析与实际计时是相关但不同的证据。

## 36. cProfile 与调用成本分布

**性能剖析**观察程序把时间和调用次数分配到哪里。`cProfile` 是标准库调用级性能工具，`pstats` 帮助整理结果。先定位成本分布，再对明确热点做小实验，通常比先改代码风格有效。

```python
import cProfile
import io
import pstats

def convert(value):
    return value * 2

def pipeline():
    return [convert(value) for value in range(4)]

profiler = cProfile.Profile()
result = profiler.runcall(pipeline)
stream = io.StringIO()
pstats.Stats(profiler, stream=stream).sort_stats("cumulative").print_stats("convert")
print(result)  # [0, 2, 4, 6]
print("convert" in stream.getvalue())  # True
```

常见报告中的 `ncalls` 是调用计数，`tottime` 是函数自身耗时，`cumtime` 包含它继续调用其他函数的时间。外层函数累计时间大，可能是某个下游操作贵，不能只按名字把全部责任归给外层函数。递归时还要区分总调用与原始调用。

剖析自身有开销；异步等待、线程、原生扩展和外部系统也有各自的观测限制。它不是系统压测工具，不直接给出服务容量；系统性能测试在第 16 章学习。

## 37. 格式化、lint、类型检查与测试的分工

**格式化工具**统一空格、换行等风格；**lint** 静态规则检查可发现未使用导入、可疑写法等问题；**类型检查器**主要分析类型关系；**测试**执行所选条件下的行为。Ruff 可以承担格式化和多类 lint 规则，但启用哪些能力取决于命令与配置。

```text
python -m ruff format --check path
python -m ruff check path
python -m mypy path
python -m pytest path
```

以上是命令职责示意，工具需在相应环境可用。格式统一不能证明金额计算正确，类型检查通过不能证明字符串内容合法，测试通过也不能证明没有遗漏需求。自动修复后应检查差异，并运行与变化相关的验证，不把所有工具当作重复的一道检查。

## 38. 为一个测试工具组织验证与诊断

假设工具从 reader 取得记录、转换成绩并生成结果。先用类型表达 reader 的调用、记录和结果；用运行时校验拒绝不符合接口的数据；用测试覆盖明确的正常、边界、异常和状态变化。reader 可以在单元测试中替换，真实连接另用集成测试验证。

失败日志保留用例编号、操作阶段与异常链；稳定复现时使用断点检查首次错误状态；慢时先确定代表性输入和热点，再用 timeit 比较局部方案。只在需要的边界引入抽象，不为增加工具数量而增加复杂度。

第 14 章会把这些能力组织成可维护框架，第 15 章连接真实接口和页面，第 16 章提供流水线与系统性能证据。本章先完成独立、可解释的小测试，不要求先搭建平台。

# 第 11 章参考回答：类型标注、测试与调试

与面试题的 45 道题逐题对应。每题先给结论，再说明原因、例子与证据范围。常见误答和追问用于复盘，不要求逐字背诵；代码依赖与版本以主讲义为准。

## 一、类型标注与静态检查

### 第 1 题：类型标注的作用与局限

**首轮结论：** 标注表达接口预期，静态工具据此发现类型误用；运行时校验和测试仍负责实际输入与具体行为。

例如 str 标注可以帮助发现把列表传给解析函数，却不能说明文本 'abc' 是有效端口。几个用例通过也不代表没有遗漏需求。普通解释器不会仅因标注就自动拒绝调用，工具分析和实际运行是不同阶段。

**常见误答：** 标了 int 就会自动转换所有输入，或类型检查通过便不需要测试。

**继续追问：** 哪些边界应该运行时拒绝，哪些只是开发者内部约定？

**回答边界：** 说明三项证据，并给一个类型正确但值无效的例子。

### 第 2 题：变量、形参与返回标注

**首轮结论：** 这些语法记录预期类型，不改变名字绑定和调用规则；-> None 表示不交还业务结果，仍可以有副作用。

例如日志函数可打印或登记事件后返回 None。形参接收的仍是实参表达式取得的对象；函数体若修改共享列表，标注不会自动复制它。箭头也不是返回时的强制转换调用。

**常见误答：** 返回标注会自动调用目标类型，或 None 返回说明函数不能修改状态。

**继续追问：** 如果函数实际返回了不同类型，静态工具与解释器分别如何看待？

**回答边界：** 说清标注描述什么和没有执行什么。

### 第 3 题：Optional 与默认实参

**首轮结论：** Optional[str] 等价于 str | None，允许 None 与调用时可省略不是同一属性；省略取决于默认值。

定义 display(name: Optional[str]) 仍需提供一个实参。检查 name is None 后，静态工具可把另一个分支的类型收窄为 str；空字符串也是 str，不能把所有假值都当成缺失。

**常见误答：** Optional 就是可不传，或 if not name 总等价于 is None。

**继续追问：** 联合类型与 Union 旧写法怎样对应？

**回答边界：** 同时解释类型选择、默认值和条件分支。

### 第 4 题：容器类型与非空约束

**首轮结论：** 它们描述元素或位置类型，其中固定元组指定位置，带省略号的元组允许任意长度；普通列表标注不保证非空或业务值域。

list[int] 可以是空列表，也可以包含负数。需要首项的函数仍要决定空输入抛错、返回 None 还是其他约定。运行时列表也不会因标注自动拒绝错误元素。

**常见误答：** 泛型方括号就是读取第一个元素，或 list[int] 自动验证每个元素。

**继续追问：** 当只需消费一遍时，为什么不必要求 list？

**回答边界：** 说明类型信息与值域约定的分工。

### 第 5 题：Literal 与有限值选择

**首轮结论：** Literal 为静态分析表达有限具体值，帮助发现模式拼写和调用错误，但不会自动建立运行时拒绝逻辑。

若配置来自文件或接口，仍要显式检查允许值并决定无效值的错误行为。把外部文本标成 Literal 只是声明，不是验证证据。

**常见误答：** Literal 等同于自动执行的枚举输入校验。

**继续追问：** 外部文本通过校验后，怎样让后续接口表达更明确？

**回答边界：** 说明有限值信息和实际检查即可。

### 第 6 题：Any、object 与 cast

**首轮结论：** Any 放宽静态约束，object 接受任意对象但使用专属行为前需要收窄；cast 只向工具表达信任，不转换对象。

cast(int, '42') 在运行时仍得到原字符串，真正数值转换需 int。随意引入 Any 或 cast 可能抹掉原有类型关系，使静态检查不再覆盖错误路径，应先修正数据来源或接口表达。

**常见误答：** object 和 Any 都是随便调用任何方法，或 cast 会校验并转换值。

**继续追问：** 为什么 cast 不应替代外部输入校验？

**回答边界：** 分别解释限制强度、信任和转换。

### 第 7 题：Callable 与迭代类型

**首轮结论：** 它们分别描述调用签名、逐项读取入口、保存遍历状态的迭代器，以及生成器产出/接收/结束返回的类型关系。

一个消费函数若只用 for，Iterable 更贴合所需能力；它不承诺下标、长度或重复遍历。Generator 的三个位置依次是 yield、send、return 的类型，不能全当作产出类型。

**常见误答：** Iterable 一定可反复消费，或 Generator 的三个类型都是元素类型。

**继续追问：** 返回 Iterator 而不是具体 Generator 何时更简洁？

**回答边界：** 连接第 5 章协议和接口能力。

### 第 8 题：TypeVar 与泛型关联

**首轮结论：** TypeVar 表达输入元素和返回值的关联，不决定业务边界；可变列表的类型替代还要考虑写入安全。

文本列表传给 first 后，工具可以推断返回文本，空输入仍需约定。若允许把 list[str] 任意当 list[object] 交出，接收方可追加整数，破坏原文本约束。不变性描述类型替代，不是列表对象不可变。

**常见误答：** T 是运行时转换器，或不变性表示列表不能 append。

**继续追问：** 只读使用时 Sequence 或 Iterable 可以怎样表达需求？

**回答边界：** 给输入输出关联与非法写入两个例子。

### 第 9 题：Protocol 与抽象基类

**首轮结论：** Protocol 为静态工具声明结构能力，鸭子类型是按行为使用的思路，抽象基类通常通过显式继承和抽象方法约束实例化。

若接口只需 read() -> str，普通对象提供相应方法便可满足协议，无需声明继承。但方法业务结果正确、资源生命周期正常仍要测试，结构关系不代替行为证据。

**常见误答：** Protocol 必须继承才有效，或满足协议就证明业务完全正确。

**继续追问：** 何时显式继承约束比结构匹配更有价值？

**回答边界：** 说清结构、继承和行为三个层次。

### 第 10 题：运行时协议判断的边界

**首轮结论：** 它让适当协议支持运行时结构检查，但不完整验证方法签名、返回值或业务语义。

一个对象存在 read 方法却返回整数，仍可能通过成员存在层面的判断。静态工具可检查声明关系，实际调用和运行时校验再确认数据；不能只看到 isinstance 为真就安全调用任意后续字符串操作。

**常见误答：** 运行时协议检查会调用所有方法并核对返回类型。

**继续追问：** 为什么不能为了校验而随意执行可能有副作用的方法？

**回答边界：** 说明结构检查的限制，不背实现内部细节。

### 第 11 题：类型别名与注解求值

**首轮结论：** 别名主要为类型表达式取名，注解保存形式和求值时机随语法及版本变化，不能把观察到的字典形式当普遍保证。

CaseId: TypeAlias = str 仍表达文本。Python 3.12 的普通函数注解通常定义时求值，future annotations 改变保存方式；3.14 默认延迟求值。get_type_hints 可解析提示，但需要名称环境，也可能执行注解表达式。

**常见误答：** 别名自动生成新的字符串子类，或所有版本注解都立即得到类型对象。

**继续追问：** TYPE_CHECKING 导入的名称为何可能不在运行时现场？

**回答边界：** 区分别名语义、保存与解析，标明基线版本。

### 第 12 题：mypy、Pyright 与检查范围

**首轮结论：** 工具分析源码和类型说明，发现声明关系下的可疑使用，证据范围由版本、配置和可用类型信息决定。

twice('ha') 在运行时可能字符串重复，仍会被正确的函数标注暴露；divide(1, 0) 类型正确却会运行时报错。若大部分数据是 Any，许多操作没有得到充分检查。先明确目标文件、Python 版本和严格程度，再解读结果。

**常见误答：** 没有报错就是所有路径正确，或不同工具诊断必须逐字一致。

**继续追问：** 修复诊断时为什么不应先加忽略注释？

**回答边界：** 说明工具输入、盲区与运行时验证的互补。

## 二、基础测试与依赖控制

### 第 13 题：assert 与输入校验

**首轮结论：** assert 适合测试与内部约束，普通 Python 优化模式可以移除它及其表达式，必要校验应使用 if 和明确异常。

assert save_report() 可能让优化运行不再保存文件；assert port > 0 也不能代替稳定的输入拒绝契约。pytest 的断言诊断是测试工具行为，不改变业务接口的责任。

**常见误答：** assert 比 raise 简洁，所以所有输入校验都用它。

**继续追问：** 断言条件本身有副作用时为什么更难重复测试？

**回答边界：** 明确优化边界和替代方式。

### 第 14 题：单元、集成与端到端边界

**首轮结论：** 按被验证的对象与依赖边界分类，不按工具名或调用函数数量分类。

纯金额规则可单元测试；程序与实际数据库驱动、事务共同运行属于集成证据；经用户入口完成整条业务链是端到端。用替身替换数据库只验证本地协作约定，不能证明真实 SQL 和权限。pytest 或 unittest 都能组织不同层次测试。

**常见误答：** 一个函数一定是单元测试，两个函数就是集成，pytest 只执行单元测试。

**继续追问：** 各层在反馈速度、真实程度和诊断成本上怎样取舍？

**回答边界：** 给具体边界，不罗列工具代替解释。

### 第 15 题：预期结果与测试结构

**首轮结论：** 三段结构让前置条件、目标操作与预期关系分开，expected 应来自明确约定或独立可信规则。

若代码把数量乘错，测试又调用同一错误帮助函数求 expected，就可能一致地错。明确的小数据和不变量可以给独立预期，断言还应关注必要副作用，不只检查没有异常。复杂场景设计在第 13 章展开。

**常见误答：** 实际函数返回什么就把它作为 expected，或只 assert result。

**继续追问：** 零、空字符串等合法假值为什么值得单独断言？

**回答边界：** 说明独立依据及一项具体比较关系。

### 第 16 题：正常、边界与异常路径

**首轮结论：** 按约定选择有效普通值、临界与空值、格式错误和不支持类型，并明确期望结果或异常。

'0' 与 None 可能代表完全不同状态；负数、空白和大数是否允许要先确定。异常验证要限制类型和必要业务信息，意外 NameError 不能算正确拒绝。需要保持的输入和资源状态也属于断言范围。

**常见误答：** 每种异常都算通过，或只测一个普通正数。

**继续追问：** 如果需求没有说明空白处理，应如何记录和补齐约定？

**回答边界：** 先声明需求，再给代表性输入，不虚构唯一业务规则。

### 第 17 题：unittest 的断言与结果对象

**首轮结论：** TestCase 表达测试，套件组织集合，运行器执行并收集结果；断言未成立与未预期异常通常分别记录为 failure 和 error。

assertEqual(1, 2) 是预期关系失败，测试中 int('bad') 未被预期处理则是错误。两者都不通过，但仅凭分类不能确定责任属于业务、测试还是环境；还要读 traceback。

**常见误答：** error 不影响通过结果，或 failures 数量直接等于业务缺陷数量。

**继续追问：** assertRaises 为什么应尽量只包目标操作？

**回答边界：** 说明各对象职责及分类的诊断边界。

### 第 18 题：setUp、tearDown 与 addCleanup

**首轮结论：** tearDown 通常建立在 setUp 成功完成的前提下；每项成功取得资源后立即 addCleanup，可覆盖后续准备失败。

先打开临时资源、登记关闭，再执行可能失败的配置。已登记清理按逆序运行，不能只把关闭动作写进准备过程尚未到达的后半段。每个测试方法有自己的实例也不消除共享全局对象。

**常见误答：** 只要写了 tearDown 就覆盖任何初始化失败。

**继续追问：** 清理本身失败时，如何保留原始证据？

**回答边界：** 按取得和登记时点解释，不只背方法顺序。

### 第 19 题：pytest 的收集与退出码

**首轮结论：** 先确认发现规则与选择范围，再解读通过结果；未收集到预期测试不是成功覆盖的证据。

pytest 默认从 test_*.py 等规则收集，零用例有专门退出码。Notebook 反复调用可能复用模块和插件状态，不能假定每次都从全新源码和环境开始。本章将相关观察放入临时独立进程。

**常见误答：** 没有红色失败就表示所有测试运行过，或清空输出等同于重置模块。

**继续追问：** 命令参数和项目配置怎样影响实际选择范围？

**回答边界：** 说明收集、执行与报告三阶段。

### 第 20 题：参数化与测试内循环

**首轮结论：** 参数化为每组数据建立独立测试项，方便编号、选择与失败定位；普通循环中的首次断言失败通常结束当前测试。

把 value 与 expected 成对提供，并用可读 ids 标识场景。不要根据当前实现动态生成全部预期，也不要假定工具深拷贝每个可变参数对象。数量更多不自动代表选择更有理由。

**常见误答：** 所有参数化数据都自动隔离，或参数行数就是覆盖率。

**继续追问：** 同一列表出现在多行中，被一项修改后会怎样？

**回答边界：** 说明独立报告、预期和共享边界。

### 第 21 题：fixture 的请求与清理

**首轮结论：** 测试按形参名字请求 fixture，默认按测试函数建立；yield 前准备并提供资源，之后在已进入的生命周期中退出清理。

每次在 fixture 里新建列表能隔离状态，直接返回全局列表则仍共享。yield 前失败时没有进入后面的退出段，需要按资源实际取得时点安排清理。更多作用域和依赖组织在第 14 章学习。

**常见误答：** fixture 就是手工按顺序调用的 setUp，或默认作用域自动复制任何返回对象。

**继续追问：** 共享昂贵连接与隔离可变业务状态为什么要分别设计？

**回答边界：** 解释请求、创建对象与退出责任。

### 第 22 题：可变参数与测试顺序依赖

**首轮结论：** 查看同一对象是否跨测试继续被持有，明确谁创建、谁修改、谁恢复，再让各测试独立建立所需状态。

两个测试引用同一全局列表，第一个 append 后第二个期待空表便失败。调换顺序只隐藏一条交错；应使用独立数据或明确恢复责任，并单独、整组及合理的不同顺序验证。浅拷贝也未必隔离嵌套数据。

**常见误答：** 测试必须按固定顺序运行才能正确，或整个问题用重试就解决。

**继续追问：** 模块缓存和环境配置如何产生类似污染？

**回答边界：** 指出对象路径和可验证的恢复方式。

### 第 23 题：临时路径与环境恢复

**首轮结论：** tmp_path 提供专用文件空间，monkeypatch 管理受支持的环境或属性替换；它们的责任范围有限。

文件操作放在测试目录，环境替换退出后恢复原绑定。真实数据库的写入、队列消息或远端账号仍需要单独准备和清理，不会因删除临时文件而回滚。保持实际依赖边界可见，才能判断隔离证据。

**常见误答：** 用了 fixture 就自动隔离所有外部系统。

**继续追问：** 为什么测试不应写死用户真实目录或共享端口？

**回答边界：** 区分本地文件、进程状态和远端业务状态。

### 第 24 题：随机种子与可重复性

**首轮结论：** 种子能让特定发生器和调用序列下的数据可重复，不固定线程调度、时间、网络和任意版本实现细节。

使用 random.Random(11) 避免重置全局发生器影响其他测试。记录输入和种子，保留明确边界案例；不能用大量随机输入替代预期依据，也不能用种子宣称并发执行顺序固定。

**常见误答：** 固定 seed 就完全确定所有运行，或随机次数多便无需边界测试。

**继续追问：** 怎样保存偶发失败，缩小成稳定最小输入？

**回答边界：** 说明发生器状态与外部不确定性的边界。

### 第 25 题：测试替身与业务断言

**首轮结论：** 它们让依赖结果、失败与交互可控，但业务输出和副作用仍需独立断言。

reader 返回 label 后，业务本应去空白并大写；只检查 reader('C-1') 被调用，会漏掉未转换的结果。替身可以模拟超时，却不证明真实服务的权限、响应格式和网络可用。

**常见误答：** mock 返回了预期值就证明被测业务正确，或所有依赖都替换后仍是完整集成。

**继续追问：** 何时用固定桩比复杂交互 mock 更容易理解？

**回答边界：** 说明替代范围、结果与交互三层断言。

### 第 26 题：patch 的实际查找位置

**首轮结论：** 通常替换 service.monotonic，因为被测函数读取的是 service 的已有绑定，不是每次重新到 time 查找。

from 导入建立局部模块名字，之后替换 time.monotonic 不自动重绑已有名字。使用 with patch 让退出恢复，或在合适接口直接注入 clock。先检查实际查找方式，不能只按依赖最初定义位置猜目标。

**常见误答：** 永远 patch 原始库，或任意同名函数被替换都会联动。

**继续追问：** 若 service 使用 import time 后写 time.monotonic，目标关系怎样变化？

**回答边界：** 连接第 8 章绑定规则说明。

### 第 27 题：spec 与 autospec

**首轮结论：** spec 等限制成员，autospec 进一步利用原签名检查调用方式，但不执行完整业务或返回类型校验。

原函数 timeout 仅限关键字，错误地作为第二个位置实参可被 autospec 拒绝；配置返回整数仍不能因此证明 read() -> str 约定成立。还要对业务结果和真实集成分别验证。

**常见误答：** autospec 自动测试返回值和真实外部服务。

**继续追问：** 使用错误版本接口作为 spec 会留下什么问题？

**回答边界：** 说明约束来源与不能证明的部分。

### 第 28 题：异步替身的调用与等待

**首轮结论：** AsyncMock 用于可等待协作者，调用产生可等待过程；只创建它不等于过程已被等待并消费。

测试若调用后直接丢弃，可能没有验证返回值或失败。应按第 10 章的任务责任等待结果，核对必要的等待交互、业务状态与清理；不能把调用计数当作完整异步执行证据。具体框架组织在第 14 章深入。

**常见误答：** call_count 增加便证明协程执行完成，或测试无需等待后台任务。

**继续追问：** 被取消时替身及被测函数应如何保留取消语义？

**回答边界：** 区分调用、等待、完成与清理。

## 三、调试、日志与性能

### 第 29 题：print、日志与断点

**首轮结论：** 打印适合少量临时观察，日志保留可关联事件，断点适合可重现时检查执行现场。

偶发测试失败先留用例编号、阶段和异常链；稳定输入则可在首次错误形成前暂停。调试表达式可能有副作用，例如 pop 会修改列表，日志也可能影响并发时机。避免输出敏感数据和无必要的巨大对象。

**常见误答：** 调试窗口里的表达式只读，或打印越多越容易定位。

**继续追问：** 无法复现时，哪些上下文最值得先保留？

**回答边界：** 说明选择依据和观测副作用。

### 第 30 题：logger 与 handler 的级别

**首轮结论：** 两道门槛都要满足；未被 logger 产生的 DEBUG 不会因 handler 更低就出现，反向还会被 handler 过滤。

logger DEBUG、handler WARNING 时，INFO 已产生但不输出。message 和 %s 实参分开可延迟格式化，昂贵实参表达式仍遵守 Python 调用规则先求值。不要仅凭日志级别猜测必要函数是否运行。

**常见误答：** 只看 handler 或只看 logger，就认为所有记录都会输出。

**继续追问：** 如何避免调试日志中的昂贵计算？

**回答边界：** 区分事件产生、接收和表达式求值。

### 第 31 题：传播与重复日志

**首轮结论：** 记录可交给祖先 handler，其自身规则仍生效，但不是重新按每个祖先 logger 的级别生成一次记录。

子与 root 都安装 handler 且继续传播，可能对一条记录输出多份；反复添加 handler 也一样。库通常 getLogger(__name__)，应用拥有输出配置，不应随意 basicConfig(force=True) 重置用户环境。

**常见误答：** propagate 自动去重，或反复 basicConfig 总是重置一切。

**继续追问：** 已有 root handler 时 basicConfig 通常怎样工作？

**回答边界：** 指出处理器路径、重复来源与配置所有者。

### 第 32 题：异常日志与错误上报

**首轮结论：** exception 在异常处理现场附加 traceback，普通 error 默认只有消息；应在负责处理或统一上报的边界保留证据。

每层记录同一异常会制造重复，未必增加原因。日志级别不是测试判定接口，ERROR 不会自动变成失败；仍需断言、异常传播或明确结果状态。注意异常消息也可能包含敏感输入。

**常见误答：** 只打印 str(error) 就保留完整调用链，或测试框架会自动把所有 ERROR 判失败。

**继续追问：** 异常被转换后，怎样保留直接原因？

**回答边界：** 说明日志现场、异常链和判定的区别。

### 第 33 题：traceback 与原因链

**首轮结论：** 调用路径与异常类型帮助定位实际失败操作，输入错误可能在更早的调用层形成；还应检查直接原因和上下文。

load 调用 parse，parse 在 int(text) 报错，真正的截断错误也许在 load 之前。extract_tb 可提取结构化帧；raise NewError from old 保留直接原因。比较临时路径或整条报错文本往往比检查稳定字段更脆弱。

**常见误答：** 只改最后一行就完成根因修复，或 RuntimeError 自动保留同样清楚的业务上下文。

**继续追问：** 长期保存完整异常对对象生命周期有什么影响？

**回答边界：** 同时给执行链和数据来源链。

### 第 34 题：pdb 与断点命令

**首轮结论：** 命令分别控制进入调用、越过调用、继续运行、查看堆栈与切换查看现场；表达式求值仍可能有真实副作用。

在金额计算前停住，先看 price、quantity，再用 next 检查 subtotal。切到调用者可追查输入；p items.pop() 会移走元素，不能当作无影响的查看。无人值守测试应避免遗留交互断点。

**常见误答：** next 不执行当前行，或 up/down 改变程序真实调用关系。

**继续追问：** 条件断点何时比逐行单步更有效？

**回答边界：** 结合一个小调用过程说明。

### 第 35 题：最小复现与回归

**首轮结论：** 保留导致失败的必要输入、步骤和环境，删除无关依赖；修复后把明确失败约定转成可重复回归测试。

把零当缺失的缺陷应同时测试合法零和 None，不能只增加一个正数用例。一次偶然通过不证明已修复，需说明原错误路径被何种修改阻止。项目复述只引用真实输入和效果，不虚构收益。

**常见误答：** 重试成功就是修复，或截图替代可执行复现步骤。

**继续追问：** 怎样验证测试本身在修复前确实能暴露错误？

**回答边界：** 给复现、原因、修复与回归关系。

### 第 36 题：timeit 的执行次数

**首轮结论：** number 是每组执行次数，repeat 是组数，每个时长对应整组；机器和运行状态使实际秒数变化。

number=3、repeat=2 会调用目标六次，产生两个组时长。比较时确认同一工作、正确结果、代表性输入及环境，并明确是否除以执行次数换算单次量。timeit 不自动证明复杂度或服务容量。

**常见误答：** repeat 只重复取时而不重复操作，或两个样本必定后者更快。

**继续追问：** 默认临时关闭循环 GC 为什么可能改变研究对象？

**回答边界：** 说明计量单位与测量条件。

### 第 37 题：计时准备与可变输入

**首轮结论：** setup 通常按每组准备，不是每次重新建立输入；可变操作可能让后续迭代测不同状态。

列表 pop 会减少长度，原地排序后再排序面对已排序数据。若每次先复制再操作，条件更一致但复制也计时，应明确测完整使用过程还是纯操作。缓存、预热和外部 I/O 状态也需要说明。

**常见误答：** 任何重复计时自动有相同输入，或复制成本不在计时范围。

**继续追问：** 如何分别设计不修改输入和必须修改输入的对照？

**回答边界：** 明确准备频率、状态变化和成本范围。

### 第 38 题：cProfile 与热点判断

**首轮结论：** 调用数说明频率，自身时间排除继续调用的部分，累计时间包括下游；热点判断还要结合调用结构。

pipeline 累计高可能源自它调用的解析函数，改外层循环写法未必解决。剖析有自身开销，也不能完整替代线程、异步等待和外部系统指标。先定位，再对明确候选用代表性输入比较，并验证结果一致。

**常见误答：** 累计时间可以沿调用栈直接相加成总时间，或 profiler 就是压测工具。

**继续追问：** 本地代码慢与系统吞吐不够可能有什么不同原因？

**回答边界：** 解释成本归属和后续验证。

### 第 39 题：格式化、lint、类型检查与测试

**首轮结论：** 格式化统一风格，lint 检查配置规则，类型工具分析类型关系，测试执行选定行为；各自的输入和证据不同。

格式整齐的函数仍可能把加法写成减法；类型正确的文本仍可能非法；测试没覆盖的分支也可能出错。Ruff 能做格式化和多类静态规则，但具体职责由命令配置决定。自动修复后应读差异并跑相关验证。

**常见误答：** 所有检查都做同一件事，或绿灯就是完整正确性证明。

**继续追问：** 哪些诊断适合自动修复，哪些需要理解语义后判断？

**回答边界：** 按问题类型说明工具分工。

## 四、代码分析与应用

### 第 40 题：标注与 cast 的代码结果

**首轮结论：** 依次输出 44 和 str；cast 没有转换 raw，函数体仍执行字符串重复。

工具会信任 cast 所声明的关系，所以这种错误信任可能让本应暴露的调用问题不再明显。实际需要整数时应显式转换并验证内容，不能用 cast 让未知数据自动变合法。

**常见误答：** 输出整数 8，或认为 cast 本身会抛类型错误。

**继续追问：** 若完全去掉 cast，工具对直接传 raw 会给出什么信息？

**回答边界：** 从对象身份和实际操作推导。

### 第 41 题：导入绑定与 patch 的代码结果

**首轮结论：** 依次输出 1、True、2。原模块属性替换不自动改变已保存的导入绑定，第二个 patch 才替换当前代码读取的名字。

退出各自 with 后会恢复对应属性。真实项目中把 __name__ 换成实际被测模块名，先确认代码是直接读导入名还是通过模块属性访问，不根据函数同名猜测。

**常见误答：** 第一次 patch 会让所有曾引用原函数的名字都指向 Mock。

**继续追问：** 闭包或默认实参已保存该函数时，为什么还要重新确认查找关系？

**回答边界：** 画出绑定在两个阶段指向的对象。

### 第 42 题：修复共享 fixture 数据

**首轮结论：** fixture 每次返回同一全局列表，作用域不等于自动复制；应在 fixture 中创建每项测试需要的新状态。

下面是可独立运行的修复脚本：

```python
import pytest

@pytest.fixture
def records():
    return []

def test_first(records):
    records.append('A')
    assert records == ['A']

def test_second(records):
    assert records == []

if __name__ == '__main__':
    raise SystemExit(pytest.main([__file__, '-q', '-p', 'no:cacheprovider']))
```

若真实资源必须共享，则单独设计可变状态准备与清理，不机械复制不可复制的连接。

**常见误答：** 默认 function scope 已保证任何对象独立，或只把 test_second 放前面。

**继续追问：** 返回新外层字典但共享内部列表是否足够？

**回答边界：** 说明对象创建位置和需要隔离的层次。

### 第 43 题：修复无效的异常测试

**首轮结论：** 输入拒绝依赖可移除的 assert，测试又既不限制异常类型，也不在没有异常时失败；可能什么都没验证到。

独立修复脚本如下：

```python
import pytest

def positive(value):
    if value <= 0:
        raise ValueError('must be positive')
    return value

def test_positive():
    with pytest.raises(ValueError, match='positive'):
        positive(-1)

if __name__ == '__main__':
    raise SystemExit(pytest.main([__file__, '-q', '-p', 'no:cacheprovider']))
```

测试应另补有效与边界输入；本例只修复这项明确约定，不暗中承诺接受任意类型。

**常见误答：** 原测试捕获了所有错误所以更稳定，或只把 assert 的消息写详细。

**继续追问：** 若 with 范围包含很多准备动作，会不会产生新的误通过？

**回答边界：** 指出两个独立漏洞并给有失败出口的检查。

### 第 44 题：端口解析的校验与测试

**首轮结论：** 先声明文本到整数接口，再按类型、去空白后格式、范围顺序显式校验，测试各项约定及异常，而不是用标注替代验证。

覆盖合法端点、前导零、空白、零和越界、符号、小数、下划线、其他数字字符及非文本输入。预期来自接口；对读取配置的协作者可注入固定替身，分别核对读取实参、解析结果和失败传播，真实文件或服务留给相应集成测试。

**常见误答：** int 能解析就视为业务合法，或只测试一个 8080。

**继续追问：** 怎样避免测试把当前实现的错误规则当作 expected？

**回答边界：** 连接三种验证层次，不展开完整配置框架。

### 第 45 题：从失败证据到性能改进

**首轮结论：** 先固定正确性约定和代表性输入，保留编号、阶段、异常链与资源信息；稳定复现后找首次错误状态，再为修复建立回归证据。性能单独测量和定位。

错误结果检查共享状态与输入来源，异常用 traceback 和断点追查；变慢先用 cProfile 看分布，再用 timeit 比较明确局部方案，说明复制、I/O 和预热是否计入。类型检查与基础测试纳入反馈，但不把工具通过当全部质量证明。项目只描述实际做过的判断和可验证效果。

**常见误答：** 先到处重试和加日志，再凭一次速度提升宣布问题全部解决。

**继续追问：** 如果 Python 热点解释不了系统延迟，应补充哪层指标？

**回答边界：** 给正确性、诊断、测量、修改与复测的完整关系。

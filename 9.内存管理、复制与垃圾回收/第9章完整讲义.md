# 第 9 章完整讲义：内存管理、复制与垃圾回收

前八章已经反复用“名字指向对象”解释代码。本章继续追问：一个对象除了被当前名字引用，还被谁保存着？复制以后哪些对象真的独立？不用的对象为什么有时仍占用内存？

本章示例采用 Python 3.11 及以上语法。引用计数、立即释放、分代回收布局和具体内存数字属于实现相关内容；相关观察以当前学习环境 **CPython 3.12.13** 为基线。普通 Python 代码不能把 CPython 的释放时机当作跨实现资源管理协议。

## 1. 对象共享、对象复制与对象回收

观察同一份数据的三种用法：

```python
import copy

original = {"scores": [80, 90]}
alias = original
shallow = original.copy()
deep = copy.deepcopy(original)

original["scores"].append(100)
print(alias["scores"])    # [80, 90, 100]
print(shallow["scores"])  # [80, 90, 100]
print(deep["scores"])     # [80, 90]
```

`alias` 没有得到副本；`shallow` 得到了新的外层字典，但保存的列表引用仍相同；`deep` 的这份列表也经过了复制。这里改变的不是一个叫“变量”的盒子，而是对象图中的某个列表。

**对象图**是用节点表示对象、用箭头表示引用关系的模型。它能同时回答本章三个问题：

1. 共享：哪些位置指向同一个对象？
2. 复制：哪些节点新建了，哪些箭头仍指向原节点？
3. 生命周期：从正在使用的程序状态还能不能到达这个节点？

不要一看到互相影响就直接调用深拷贝，也不要一看到内存增长就直接调用 `gc.collect()`。先确定问题属于哪一条线。

## 2. 栈帧、名字和堆中的对象

### 2.1 栈帧保存一次调用的执行状态

第 3 章的栈帧可以理解为一次函数调用的工作现场：它需要记录局部名字、执行到哪里、正在等待什么结果等信息。**调用栈**按调用和返回顺序组织这些现场。

**堆**在本章指运行时用于存放对象的动态存储区域，与第 2 章用于维护极值的“堆数据结构”不是同一个概念。CPython 中的大多数普通 Python 对象由运行时在动态存储中管理。

```python
def build_record():
    scores = [80, 90]
    record = {"scores": scores}
    return record


result = build_record()
print(result["scores"])  # [80, 90]
```

可以用下面的概念图理解返回前的关系，它不是 C 内存布局图：

```text
build_record 的调用现场
├── 局部名字 scores ──────────→ 列表 L
└── 局部名字 record ──────────→ 字典 D ── scores 对应的值 ──→ L

返回后：调用处名字 result ────→ D ─────────────────────────→ L
```

调用结束，不意味着函数创建的全部对象都必须销毁。返回值把字典交给调用方，字典继续引用列表。对象的生命周期由引用和运行时规则决定，不与创建它的函数执行期简单绑定。

### 2.2 局部变量和对象的存储位置

在常见的 CPython 实现中，函数的局部变量由本次调用的栈帧管理，局部变量引用的列表、字典等普通对象存放在运行时管理的堆内存中。栈帧保存的是找到这些对象所需的引用，不是把整个列表或字典的内容放进局部变量的位置。

“局部变量在栈、对象在堆”可以帮助建立初步印象，但具体存储方式取决于解释器实现和版本。栈帧本身也可能作为 Python 对象被观察，闭包、生成器和异常追踪还可能继续保存相关状态。

面试首轮到“调用现场保存局部绑定，多个绑定可以指向同一对象，对象可以在调用结束后继续存活”已经足够。不要推导成“所有局部对象一返回就释放”。

## 3. 强引用与可达性：对象还被谁使用

### 3.1 引用不只来自变量名

本章把能够使目标继续存活的普通引用称为**强引用**。名字、容器槽位、实例属性、函数默认值、闭包和缓存都可能持有强引用。

```python
class Record:
    pass


record = Record()
record.label = "A"
saved = [record]
del record
print(saved[0].label)  # A
```

`del record` 后少了一个名字，但列表仍保存实例。即使你只数源码里的变量名，也看不见全部引用来源。

### 3.2 可达与不可达

**可达**表示从程序仍在使用的入口沿强引用走，能够找到某对象。例如模块全局、活动调用现场等可以作为入门模型中的起点；这里把这些起点概括为**根**。这是一种分析模型，不是要求背诵 CPython 内部固定的根表。

```text
仍在使用的模块状态 → 注册表 → 实例 → 内部列表
```

这条路径存在，内部列表就仍然可达。即使业务上早已不再需要该实例，垃圾回收器也不能替你猜出业务意图。

**不可达**表示从这些外部入口已无法沿强引用到达对象。不可达与“内部引用数为零”不同：两个对象可以只互相引用，整体却已经不可达。这正是循环回收要处理的问题。

## 4. CPython 的引用计数怎样帮助释放对象

### 4.1 强引用的增加与减少

**引用计数**是跟踪对象被持有引用情况的一种管理机制。在普通 CPython 构建中，增加、移走某些强引用会相应影响引用计数；计数下降到零的普通对象通常可以立即进入释放流程。

```python
class Payload:
    pass


payload = Payload()
alias = payload
holders = [payload]
del alias
holders.clear()
```

按入门模型看：

```text
payload = Payload() → payload 持有实例
alias = payload     → 多一个名字持有实例
holders = [payload] → 列表再持有实例
del alias           → 移走 alias 的绑定
holders.clear()     → 列表不再持有实例
最后 payload 仍在   → 实例仍有外部强引用
```

临时表达式、函数调用和解释器内部状态也会影响观察，因此这里只分析引用关系，不给每一步写一个绝对整数。

### 4.2 释放对象还会影响它引用的对象

当一个字典被释放，它不再持有其键和值；这些对象的引用也随之减少。如果其中某个列表还有别的使用者，列表继续存活；如果没有，则可能继续释放。

“计数到零”不是把一整片对象图无条件清空。每个节点是否继续存活，要分别看是否仍有其他引用。

### 4.3 对象回收与文件关闭的区别

Python 语言不承诺所有实现都使用引用计数或都立即回收。即使在 CPython 中，对象也可能因为循环、缓存或调试状态继续被引用。第 7 章的 `with` 和 `try/finally` 才是表达文件、锁和连接生命周期的机制。

引用计数解释常见实现，资源协议表达程序必须做到什么，两者不能互相替代。

## 5. `del` 的作用：删除名字、容器元素或属性

### 5.1 删除名字

```python
values = [1, 2]
alias = values
del values
print(alias)  # [1, 2]
```

`del values` 删除当前作用域中 `values` 的绑定。列表没有因为这条语句就必然销毁；`alias` 仍引用它。

### 5.2 删除容器位置或属性

```python
class Holder:
    pass


shared = [1, 2]
holder = Holder()
holder.value = shared
items = [shared]

del items[0]
del holder.value
print(shared)  # [1, 2]
```

三种 `del` 的目标不同：`del name` 移走名字，`del items[index]` 请求容器删除一个位置，`del obj.attr` 请求删除属性。后两者可以由相应类型协议参与处理，不能统称为“删除变量”。

只有当这些操作使某个对象不再被需要的引用持有，运行时才可能回收它。`del` 本身不保证立即触发 `__del__()`，也不保证进程占用立刻下降。

## 6. `sys.getrefcount()` 的用法与观察偏差

先用普通实例观察相对变化。下面的实验专用于普通 CPython 3.12 环境，不用于判断其他解释器的释放时机：

```python
import sys


class Payload:
    pass


payload = Payload()
before = sys.getrefcount(payload)
alias = payload
with_alias = sys.getrefcount(payload)
del alias
after = sys.getrefcount(payload)

print(with_alias - before)  # 1
print(after == before)     # True
```

调用 `getrefcount(payload)` 时，作为调用实参的临时引用通常也被计入。因此数字不是“我在源码中能数出的名字数量”。这里保持对象和观测方式一致，只检查增加别名后的变化。

还要注意三个边界：

- Notebook 输出历史、调试器、容器和局部名字都可能额外持有对象。
- CPython 3.12 引入的不朽对象会显示与普通持有引用数不对应的很大计数；“不朽”指实现让某些长期存在的对象不按普通计数归零释放。
- 新版本及自由线程构建会调整引用管理策略，不能把此实验扩展为任何构建的并发存活判据。自由线程构建是可不依赖传统全局解释器锁运行线程的一种 CPython 构建方式，完整并发模型在第 10 章学习。

不要用整数 `1`、`None` 等特殊复用对象作为入门引用计数实验对象，也不要根据某个数字手动修改内存。

## 7. 循环引用与引用计数的局限

### 7.1 两个对象相互引用的例子

```python
class Node:
    pass


first = Node()
second = Node()
first.peer = second
second.peer = first
del first
del second
```

删除两个外部名字后，对象图概念上是：

```text
外部强引用入口 ──×──→ 节点 A ── peer ──→ 节点 B
                        ↑                    │
                        └──────── peer ──────┘
```

A 仍被 B 引用，B 仍被 A 引用，单靠“每个对象引用计数何时到零”无法识别这组不可达对象。

### 7.2 可达与不可达的循环引用

如果外部列表仍持有 A，这个环整体仍可达，不能回收。环是一种引用形状，垃圾是对象已经不再可达的状态，不能把两者混为一谈。

数据结构可能需要反向链接，不能为了避免任何环就破坏合理设计；需要正确理解所有权和回收边界。

## 8. CPython 循环垃圾回收的基本过程

CPython 的**循环垃圾回收器**补充引用计数，主要检测可能构成环的一些被跟踪对象。**跟踪**表示对象被纳入这套循环检查的管理范围，不表示对象正发生泄漏，也不表示所有对象都在这个集合里。

理解回收可以先使用下面的概念过程，不把它当作解释器源码逐句翻译：

```text
选出一组待检查的受跟踪对象
→ 分辨其中的引用哪些来自组内、哪些说明还有外部使用者
→ 保留仍被外部引用及由它们继续能到达的对象
→ 对剩下不可达的部分进行必要的终结与回收
```

真正的 CPython 算法、终结顺序和版本优化比图复杂。当前关键结论是：循环回收要判断“整组对象是否仍可达”，而不是简单检查“对象是不是互相引用”。

`gc.collect()` 也不能清掉仍被模块列表、闭包或缓存强引用的对象。对这种对象，问题首先是持有者没有按业务生命周期释放引用。

## 9. CPython 的分代垃圾回收

### 9.1 分代回收的目的与对象晋升

很多临时对象很快不再使用，另一些对象会活得较久。**分代回收**按对象在回收检查中的存活经历分组，让新对象所在组更频繁地接受检查，较老对象较少被完整检查，以降低扫描成本。

代不是业务年龄，不等于对象创建了多少秒；晋升与回收轮次和具体实现有关。不是对象经过固定时间就必然进入下一代，也不是某一代对象永远不会被回收。

### 9.2 不同 CPython 版本的分代回收机制

在本项目的普通 CPython 3.12 基线中，受跟踪对象按第 0、1、2 代管理。不要据此写成“Python 永远恰好有三代”。官方 3.14 文档记载：3.14 初始行为移除了第 1 代，3.14.5 又恢复它，并恢复了与 3.13 对应的相关行为。自由线程构建还可能使用不同的触发条件。

因此面试可以先说“CPython 用分代思想降低循环扫描成本”，需要具体代数、阈值和 `collect(1)` 语义时，再明确目标解释器、完整版本及构建。这里依据的是文末链接的官方版本文档，不要求把补丁变迁背成新的口号。

本章示例主要使用不带代号的 `gc.collect()` 请求完整检查，不通过修改全局阈值训练“调参”。

## 10. `gc` 模块的常用接口

### 10.1 回收控制、对象跟踪与回收统计

| 接口 | 用途 | 不能据此断定什么 |
|---|---|---|
| `gc.collect()` | 主动请求循环回收检查 | 返回整数不是当前进程全部垃圾的大小 |
| `gc.isenabled()` | 自动循环回收是否启用 | 不表示引用计数是否工作 |
| `gc.disable()` / `gc.enable()` | 改变自动循环回收开关 | 关闭自动检查不等于关闭所有内存管理 |
| `gc.is_tracked(obj)` | 对象是否在循环回收跟踪中 | 被跟踪不等于已不可达 |
| `gc.get_count()` / `gc.get_stats()` | 查看触发相关计数、回收统计 | 不等于存活对象总数或已用字节数 |
| `gc.get_referrers(obj)` | 调试时寻找部分引用者 | 不是不干扰对象的完整引用审计 |

在本章 CPython 3.12 基线中，`gc.collect()` 返回本次发现的不可达对象数量，不是字节数，也不是整个进程的存活对象总数。精确值可能受运行现场其他垃圾影响。教学应观察目标对象是否仍可取得，而不是断言“这次一定收了两个对象”。

### 10.2 使用弱引用检查对象是否被回收

弱引用稍后会完整解释；当前只需知道 `weakref.ref(obj)` 产生一个观察句柄，它自身不会仅靠这条关系让目标存活。调用句柄时，目标仍存活则得到目标，已回收则得到 `None`。

```python
import gc
import weakref


class Node:
    pass


def make_cycle():
    node = Node()
    node.peer = node
    return weakref.ref(node)


reference = make_cycle()
gc.collect()
print(reference() is None)  # True，目标没有其他外部强引用
```

函数只返回弱引用，没有返回实例。相比把对象放入一个“用于观察”的列表，这种方式不会因为观察列表本身又使目标可达。实验中的类没有终结器，也不人为使用保存垃圾的调试模式。

### 10.3 自动循环回收与手动回收

`gc.disable()` 只关闭自动循环回收，普通 CPython 的引用计数不会因此停止；手动 `gc.collect()` 也仍可以运行。需要比较关停前后时，必须保存旧开关并在 `finally` 中恢复。

本章 Notebook 将这类实验放进由当前解释器启动的独立子进程。**子进程**是当前程序启动的另一份独立运行程序，它有自己的解释器状态；当前 Notebook 的回收开关不被修改。第 10 章会系统讲进程，本章只用它隔离一次观察。

### 10.4 `gc.garbage` 的用途与 `DEBUG_SAVEALL` 的影响

现代 Python 的多数普通 Python 对象，包括许多有 `__del__()` 的循环对象，都可以被回收。不能沿用很旧的结论，说“有析构方法的环一定永远进 `gc.garbage`”。

`gc.garbage` 与无法回收的情况及调试配置有关。尤其 `DEBUG_SAVEALL` 会把发现的不可达对象保留在这个列表里供检查，调试动作自己就会持有对象。普通学习和业务代码不要无目的开启它。

`gc.get_referrers()`、`gc.get_objects()` 返回的列表以及保存下来的结果，同样可能增加引用、占用内存。它们更适合临时调试；不要把返回对象存入全局变量后，又惊讶于对象为什么没有消失。

## 11. 赋值、浅拷贝与深拷贝的区别

下面以含列表的列表为对象图，三种操作并排比较：

```python
import copy

original = [[1], [2]]
alias = original
shallow = copy.copy(original)
deep = copy.deepcopy(original)

print(alias is original)          # True
print(shallow is original)        # False
print(shallow[0] is original[0])  # True
print(deep[0] is original[0])     # False
```

概念图如下：

```text
original、alias ──→ 外层 A ──→ 内层 X、Y
shallow         ──→ 外层 B ──→ 同一个 X、Y
deep            ──→ 外层 C ──→ 新内层 X'、Y'
```

赋值只增加绑定；浅拷贝对这类可变复合对象建立新外层并复用内部引用；深拷贝按类型的复制规则继续处理内部对象。**复合对象**就是持有其他对象的对象，例如容器或保存属性的实例。

“深”不等于所有节点的身份都必然改变，也不等于可以复制任意运行资源。后面两节会拆开说明。

## 12. 容器自己的复制方法与不可变对象复用

### 12.1 列表和字典的浅层复制

`values.copy()`、`values[:]`、`list(values)` 对普通列表可以建立新的外层列表；`mapping.copy()` 和 `dict(mapping)` 对普通字典可以建立新的外层字典。它们不递归隔离内部可变对象。

```python
original = {"scores": [80]}
copied = dict(original)
copied["new"] = True
copied["scores"].append(90)

print("new" in original)  # False
print(original["scores"])  # [80, 90]
```

新增键只改新字典；追加分数改共享列表。要表达“外层独立但内容共享”，浅拷贝恰好是正确行为，不必把它称为“不完整的错误复制”。

### 12.2 不可变对象的复制与复用

对于不可变对象，构造函数或复制工具可能直接返回原对象。例如 CPython 中 `tuple(existing_tuple)` 可能复用原元组，`copy.copy()` 也可能复用不可变对象。

```python
import copy

original = (1, 2)
constructed = tuple(original)
copied = copy.copy(original)

print(constructed == original)  # True
print(copied == original)       # True
print(constructed is original) # 观察当前实现，不作为业务判断
```

不能因此推出“复制接口失效”。如果对象不会原地改变，共享它常常已经满足使用者的隔离需要。业务应依赖内容与可变性约定，不用新旧 `id()` 是否不同来证明所有复制都正确。

### 12.3 普通实例的浅拷贝也会共享属性值

对没有定制复制行为的普通类，浅拷贝通常建立新实例，再把状态中的对象引用放过去。先观察实例身份，再观察列表属性：

```python
import copy


class Report:
    def __init__(self, scores):
        self.scores = scores


original = Report([80])
copied = copy.copy(original)
copied.scores.append(90)
print(copied is original)                # False
print(copied.scores is original.scores)  # True
print(original.scores)                  # [80, 90]
```

新实例不代表每个属性指向的对象也被重新创建。这个模型适用于这里的普通类；自定义复制、特殊状态和资源类需要看对应协议，不能把“逐项复制普通属性”说成任意类型的永久规则。

## 13. 深拷贝与 `memo` 备忘录

### 13.1 深拷贝如何处理重复引用

```python
import copy

shared = [1]
original = [shared, shared]
copied = copy.deepcopy(original)

print(copied is original)            # False
print(copied[0] is original[0])      # False
print(copied[0] is copied[1])        # True
copied[0].append(2)
print(original)                      # [[1], [1]]
print(copied)                        # [[1, 2], [1, 2]]
```

原图中两个位置指向同一个列表。一次深拷贝建立一个新的内部列表，并让结果的两个位置仍指向它；结果与原图分离，但保留原图内部的共享关系。

这依赖一次复制过程使用的 **`memo` 备忘录**：它记录已经处理过的原对象及其对应副本，遇到同一个原对象时复用对应副本，而不是重复复制。使用者通常直接调用 `copy.deepcopy(value)`，不需要依赖备忘录内部布局。

### 13.2 深拷贝如何处理循环引用

```python
import copy

original = []
original.append(original)
copied = copy.deepcopy(original)

print(copied is original)  # False
print(copied[0] is copied) # True
```

工具先为外层列表准备副本，并记录对应关系；处理元素时再次遇到原列表，就能使用已经登记的副本。结果中保留自引用，但它指向副本自己。

“深拷贝遇到环就一定无限递归”不成立；自己编写递归复制却没有记录已处理对象，才容易出问题。

## 14. 一次整体深拷贝与多次单独深拷贝

```python
import copy

shared = [1]
original = [shared, shared]
together = copy.deepcopy(original)
separately = [copy.deepcopy(item) for item in original]

print(together[0] is together[1])    # True
print(separately[0] is separately[1]) # False
```

第一次是对整个对象图的一次复制，内部共享关系可以通过同一份备忘录保留。第二次对两个位置分别发起独立复制，默认不共享备忘录，因此可以产生两个内部列表。

所以问题不只是“有没有用 `deepcopy`”，还包括“把哪一部分作为一次复制的边界”。需要保留关联的数据应作为一个整体处理；是否有意拆开共享关系，则由接口明确规定。

## 15. 深拷贝的适用对象与性能开销

### 15.1 深拷贝对不可变对象、函数和类的处理

字符串、整数、函数对象和类对象等，不需要像可变容器一样全部重建。官方 `copy` 文档明确说明，函数和类的浅拷贝及深拷贝会返回原对象。

```python
import copy


def transform(value):
    return value * 2


configuration = {"operation": transform, "values": [1, 2]}
copied = copy.deepcopy(configuration)
print(copied["operation"] is transform)  # True
print(copied["values"] is configuration["values"])  # False
```

目标是遵守对象的复制语义，不是制造所有对象的新身份。

### 15.2 文件、锁和连接的复制限制

打开的文件代表读取位置和系统资源，数据库连接代表外部会话，锁代表同步状态。不能因为它们保存在字典中，就认为深拷贝能复制出另一份独立而有效的外部资源。

```python
import copy
import threading

lock = threading.Lock()
try:
    copy.deepcopy(lock)
except TypeError:
    print("这个资源不能按普通深拷贝复制")
```

需要新连接就按库接口建立新连接；需要记录配置就只复制配置数据。第 7 章的所有权与本章的复制边界必须同时成立。

### 15.3 浅拷贝与深拷贝的时间和空间开销

浅拷贝含 `n` 个条目的普通列表或字典，通常需要 `O(n)` 时间与外层空间。深拷贝可能访问整个可复制对象图，还需保存副本和备忘录。在单个节点与引用处理成本可视为常数时，可用图的节点数与引用数估计量级；自定义复制、巨大数值或外部操作会改变成本。

不要把 `copy.deepcopy(value)` 只有一行当作 `O(1)`，也不要无条件把任何对象图都称为“线性”。图的规模、共享关系和自定义行为必须先说清楚。

## 16. 自定义 `__copy__()` 与 `__deepcopy__()`

自定义类可以定义 `__copy__()` 与 `__deepcopy__(self, memo)`，为复制给出明确语义。只有默认规则不符合需求时才需要写它们。

下面把可变记录复制出来，却有意共享一个只按身份使用的服务标记。先观察结果关系：

```python
import copy


class Report:
    def __init__(self, rows, service):
        self.rows = rows
        self.service = service

    def __deepcopy__(self, memo):
        result = type(self).__new__(type(self))
        memo[id(self)] = result
        result.rows = copy.deepcopy(self.rows, memo)
        result.service = self.service
        return result


service = object()
original = Report([[1]], service)
copied = copy.deepcopy(original)
print(copied.rows is original.rows)    # False
print(copied.rows[0] is original.rows[0])  # False
print(copied.service is service)       # True
```

`__new__()` 在这里只取得尚未填字段的实例；随后先登记副本，再递归复制字段，避免字段绕回自身时又从头创建。对内部对象调用 `deepcopy` 时继续传同一份 `memo`，才能维持整次复制的关联关系。`memo` 应作为复制协议提供的上下文使用，不把它当业务状态保存或随意改造。

这个简单类没有建立复杂继承契约。若子类改变创建方式或增加字段，这份实现未必自动适用。普通数据记录通常优先采用默认复制，或用明确的构造函数重建所需字段。

## 17. 按字段复制需要的数据

假设界面只需要姓名和成绩快照，内部配置还保存了日志器、连接和缓存。把完整配置深拷贝给界面，并不是需求本身。

```python
record = {"name": "Ada", "scores": [80, 90], "internal": {"debug": True}}
snapshot = {
    "name": record["name"],
    "scores": list(record["scores"]),
}
record["scores"].append(100)
print(snapshot)  # {'name': 'Ada', 'scores': [80, 90]}
```

这份接口只承诺复制成绩列表。若成绩元素以后从整数变成可变字典，需要重新审视复制深度；不要让输入结构变化后仍沿用旧承诺。

选择时先问：调用方需要整个对象图的副本，还是某一层记录，还是只需要不能修改的值视图？浅拷贝、深拷贝、重新构造分别服务不同需求。

## 18. `weakref.ref()` 的用法

### 18.1 普通引用和弱引用的区别

```python
import gc
import weakref


class Payload:
    pass


payload = Payload()
reference = weakref.ref(payload)
print(reference() is payload)  # True
del payload
gc.collect()
print(reference() is None)     # True
```

`reference` 指向弱引用句柄，句柄对目标的关系不会像普通容器槽位那样让目标仅因它而存活。目标不存在后，调用句柄得到 `None`。

弱引用适合“有其他所有者时可以找到对象，但我不负责延长它的生命周期”的关系。它不是自动缩小对象内存，也不是替代所有普通引用的优化开关。

### 18.2 弱引用返回的对象仍会被局部变量持有

```python
import gc
import weakref


class Payload:
    pass


payload = Payload()
reference = weakref.ref(payload)
borrowed = reference()
del payload
gc.collect()
print(reference() is borrowed)  # True
del borrowed
gc.collect()
print(reference() is None)      # True
```

`borrowed` 是普通名字，它取得目标后就会继续持有目标。不能只看 `reference` 是弱引用，而忽略新取得的强引用。

真实代码通常只取一次：`target = reference()`，再判断 `target is None`；不要先调用一次判断存在，又调用一次取得，假设两个时刻的存活情况必然一样。第 10 章会展开并发状态变化，这里先建立“取出一次，使用这份局部引用”的习惯。

### 18.3 支持弱引用的类型与 `__slots__` 声明

普通自定义类实例通常支持；普通 `list`、`dict` 实例不能直接传给 `weakref.ref()`。某些内置类型、子类以及使用 `__slots__` 的类有各自规则。若槽类需要弱引用支持，通常还需声明 `__weakref__` 槽或通过基类获得支持。

不要为了观察列表而偷偷写出运行必然失败的示例。本章用可弱引用的包装实例保存列表，再观察包装实例。

## 19. 弱引用容器与绑定方法

### 19.1 `WeakValueDictionary` 的弱值存储

```python
import gc
import weakref


class Image:
    pass


images = weakref.WeakValueDictionary()
image = Image()
images["logo"] = image
print("logo" in images)  # True
del image
gc.collect()
print("logo" in images)  # False
```

这个映射对值使用弱引用，其他强引用消失、值被回收后，条目也会移除。它的键仍按映射自身规则保存；不能说整个字典里所有关系都是弱的。

弱值表适合非拥有式索引，不保证某个键的值一直存在。需要固定容量、过期策略或确保计算结果可复用时，应设计真正的缓存，不能直接用弱值表代替第 4 章的全部缓存语义。

`WeakKeyDictionary` 对键使用弱引用，`WeakSet` 对元素使用弱引用；两者同样要求对应对象支持弱引用，并有各自的相等与哈希条件。

### 19.2 绑定方法对实例的强引用与 `WeakMethod`

```python
import gc
import weakref


class Listener:
    def notify(self):
        return "ready"


listener = Listener()
reference = weakref.ref(listener)
callbacks = [listener.notify]
del listener
gc.collect()
print(reference() is not None)  # True
callbacks.clear()
gc.collect()
print(reference() is None)      # True
```

第 6 章的绑定方法有 `__self__`，指向实例。注册表长期保存方法，也可能长期保存实例。需要非拥有式监听时，可考虑 `weakref.WeakMethod`，它能在目标仍存活时重新取得绑定方法；直接对一次临时生成的绑定方法使用普通 `weakref.ref()`，可能只观察到那个短命的方法对象。

## 20. `__del__()` 与终结回调的限制

### 20.1 `__del__()` 的调用时机与限制

`__del__()` 常被称为析构方法，更适合在这里理解为对象的终结钩子。它与 `del name` 没有“写下这条语句就直接调用一次”的对应关系。仍有强引用时对象不会仅因删除另一个名字就终结；循环、实现与运行结束阶段也会影响时机。

不要把需要确定完成的关闭动作放到 `__del__()` 里等待。它抛出的异常不能像普通业务调用一样可靠传播给调用者；运行结束时依赖的全局状态也可能已经变化。终结过程中重新把自身保存到全局容器，还可能发生**对象复活**，也就是重新获得外部可达路径。

面试知道“时机、异常传播、运行结束环境与复活”这几条限制即可，不把终结钩子设计成事务提交接口。

### 20.2 `weakref.finalize()` 的用法与引用关系

```python
import gc
import weakref


class Payload:
    pass


events = []
payload = Payload()
finalizer = weakref.finalize(payload, events.append, "released")
del payload
gc.collect()
print(events)            # ['released']
print(finalizer.alive)   # False
finalizer()
print(events)            # ['released']，同一个终结器不会再次运行
```

这里回调持有事件列表和字符串，没有持有 `payload`。若写成 `weakref.finalize(payload, payload.close)`，绑定方法自身可能强引用 `payload`，终结器就反过来把目标留住。回调闭包或实参间接保存目标也有同样问题。

`finalize` 可以让备用终结逻辑更易管理，但确定性的资源释放仍用第 7 章的上下文范围。这里的 `gc.collect()` 是为受控实验完成回收请求，不表示业务要在每次使用后手动收集。

## 21. 导致对象长期存活的常见引用

### 21.1 全局容器与模块缓存

`sys.modules`、全局注册表和全局列表可能长期存在。只要它们继续强引用业务对象，循环回收器就不能将这些对象当作垃圾。修复应是限定注册表生命周期、移除过期条目或明确注销，不是提高回收频率。

### 21.2 函数默认值和闭包

第 3 章的可变默认值由函数对象保存；第 4 章的闭包保存所需外层绑定。删除调用处名字，不会自动让函数保存的对象消失。

```python
import gc
import weakref


class Payload:
    pass


def make_reader(payload):
    def read():
        return payload
    return read


payload = Payload()
reference = weakref.ref(payload)
reader = make_reader(payload)
del payload
gc.collect()
print(reference() is not None)  # True
del reader
gc.collect()
print(reference() is None)      # True
```

这里不用 `reader()` 的返回值保存在另一个名字里，否则新名字也会成为持有者。

### 21.3 缓存保存键与结果

`lru_cache` 在缓存条目存在时持有实参和结果。缓存有界也不意味着单项对象很小；无限缓存更可能随输入种类持续增长。要按业务选择容量、清理与失效。清空外部名字不等于清空缓存。

### 21.4 暂停的生成器

生成器保存暂停位置与局部状态。若局部形参是一个很大对象，生成器停在 `yield` 时可能仍持有它。正常耗尽或明确关闭可以结束这次执行，但关闭后返回给调用方、被其他对象保存的值仍可能继续存活。

“关闭生成器释放其执行现场”和“删除它曾产出的全部数据”不是同一承诺。

### 21.5 异常、traceback 与调试工具

保存异常对象可能间接保留 traceback，traceback 又可能关联栈帧及局部对象。长时间保存完整异常来写历史记录，可能把本来短期的数据一同留住。

Notebook 的输出历史、调试器中的变量面板和你自己建立的观察列表，也都是可能的持有者。用小函数缩短局部状态范围，只输出身份关系和必要值，不在全局保存整个被分析对象图。

## 22. 对象滞留、内存泄漏与进程内存占用

**内存泄漏**在排查语境中通常指已经不再需要的内存持续无法释放，或程序持续保留无用对象。Python 程序里的逻辑性泄漏常表现为“对象技术上仍可达，但业务上早就不需要”。扩展模块也可能存在 Python 对象图之外的分配问题。

需要区分：

1. 合理保留：缓存按设计保存有上限的数据。
2. 意外滞留：忘记注销回调，实例一直被注册表持有。
3. 等待循环回收：对象已不可达，但需要循环检查处理。
4. Python 对象已释放，内存分配器仍保留空间待复用。
5. 原生库、设备内存等并不都由 Python 追踪工具完整覆盖。

**内存分配器**负责取得、分配与复用内存。CPython 为减少系统调用成本，可能把释放出的空间留作后续对象复用。任务管理器中的进程占用因此未必立刻下降；这不自动证明对象还活着，也不自动证明完全没有问题。

进程的 **RSS** 通常指当前驻留物理内存的进程页面量，是操作系统层面的指标；它不是 `sys.getsizeof()` 所报告的单对象浅层大小。不同工具在 Windows 等平台还可能显示工作集等不同口径，比较前先确认指标含义。

## 23. 使用 `sys.getsizeof()` 查看对象大小

```python
import sys

payload = bytearray(100_000)
outer = [payload, payload]
print(sys.getsizeof(outer))
print(sys.getsizeof(payload))
print(outer[0] is outer[1])  # True
```

第一项主要报告外层列表自身及其引用槽位，不递归加总 `payload` 的全部内容。第二项观察字节数组本身。具体字节数随解释器版本和构建变化，不作为固定答案。

如果自行递归统计，又按两个位置各算一次 `payload`，就会重复计入同一对象；遇到环还可能无限递归。需要先定义“图中独立对象总大小”还是“每条路径累计大小”，再考虑按身份去重。第三方扩展对象对浅层大小的报告也有自己的实现边界。

不要把“某个生成器对象只有几百字节”当成整条流水线只用几百字节。它仍可能引用非常大的上游输入。

## 24. 使用 `tracemalloc` 比较内存分配

**`tracemalloc`** 是标准库中的 Python 内存分配追踪工具，可以记录许多 Python 分配对应的位置，并比较两个时刻的快照。**快照**在这里是追踪记录的采样结果，不是给业务对象做一次深拷贝。

下面的完整示例在独立脚本进程中运行；若已有其他工具启动追踪，它不会擅自关闭别人的追踪状态：

```python
import tracemalloc

started_here = not tracemalloc.is_tracing()
if started_here:
    tracemalloc.start()

try:
    before = tracemalloc.take_snapshot()
    retained = [bytearray(1024) for _ in range(100)]
    after = tracemalloc.take_snapshot()
    differences = after.compare_to(before, "lineno")
    print(bool(differences))
    for statistic in differences[:3]:
        print(statistic)
    retained.clear()
finally:
    if started_here:
        tracemalloc.stop()
```

`after.compare_to(before, "lineno")` 按源代码行比较追踪到的存储变化，帮助找到增长发生在哪里。结果会包含正负变化、文件与行号；不应把某一次输出的具体数字写成面试标准答案。

它主要回答“哪些追踪到的分配位置在增长”，不是“谁现在持有每个对象”的完整证明。追踪启动前的分配，以及某些原生库或设备内存，未必被覆盖。定位到增长行后，还需要回到引用图寻找持有者。

## 25. 内存持续增长的排查步骤

先固定工作量：重复处理相同规模、可重现的输入，区分启动预热、短期峰值和持续增长。然后按以下顺序缩小问题：

1. 确认增长口径：对象数量、追踪到的字节，还是进程工作集？
2. 比较多个批次后的分配快照，寻找持续增长的位置，而不只看一次峰值。
3. 检查长寿命持有者：全局表、缓存、默认值、闭包、生成器、回调和异常历史。
4. 用受控实例和弱引用验证生命周期；必要时短暂查看引用者，避免调试结果再次长期持有对象。
5. 判断是不可达环等待回收，还是可达对象没有按业务退出；分别处理。
6. 若 Python 追踪解释不了进程增长，再检查原生扩展、内存分配器和外部资源。
7. 用相同工作量复测，确认状态能稳定或按上限收敛。

不要先改垃圾回收阈值，不要在每个循环后无条件 `gc.collect()`。这样可能增加停顿，却无法修复一个一直增长的强引用列表。

## 26. 综合案例：一份历史快照应该复制到哪一层

需求是“保存每次成绩变化前的记录”。先看错误写法：

```python
current = {"name": "Ada", "scores": [80]}
history = [current.copy()]
current["scores"].append(90)
print(history[0]["scores"])  # [80, 90]
```

历史保存了新字典，成绩列表却仍是共享对象。修复不应从“`copy` 不好”开始，而应声明快照边界：当前记录仅含字符串姓名和整数成绩，因此复制外层与成绩列表即可。

```python
def snapshot_record(record):
    return {"name": record["name"], "scores": list(record["scores"])}


current = {"name": "Ada", "scores": [80]}
history = [snapshot_record(current)]
current["scores"].append(90)
print(history[0]["scores"])  # [80]
print(current["scores"])     # [80, 90]
```

若记录以后成为含多个共享分支或循环的数据图，可能需要一次整体 `deepcopy()`；如果混入数据库连接，则应继续只选择可快照的业务数据。

还要问历史保留多少份。复制解决互相影响，历史无限增长是另一项生命周期问题。两者不能靠同一个“用深拷贝”结论解决。

## 27. 小整数缓存、字符串驻留与身份复用

**缓存**保留对象或结果以供复用；**字符串驻留**让某些相等字符串有机会复用同一对象。CPython 的相关优化能影响 `is` 和引用计数观察，但不是业务上比较值的规则。

```python
left = "".join(["py", "thon"])
right = "python"
print(left == right)  # True
print(left is right)  # 当前环境的观察结果，不作为正确性依据
```

同值对象可能相同也可能不同，不要背固定缓存范围来选择 `is`。对象结束生命后，其 `id()` 也可能被后来对象复用；唯一性只覆盖生命周期重叠的对象，不是永不重复的业务编号。

本章不会制造必须依赖某个缓存范围或具体地址才能答对的实验。当前要稳定掌握的是：内容相等用 `==`，目标身份才用 `is`，内存管理优化不能改变代码表达的意图。

## 28. 面试表达与章节边界

回答内存问题时先给结论，再指明引用路径。例如：“删除局部名字没有释放实例，因为全局回调列表中的绑定方法仍持有它。”这比“Python 有垃圾回收，所以会自动释放”更有因果关系。

回答复制问题时先画出原图与结果图，再分别说明外层身份、内部共享、一次复制的范围和成本。回答回收问题时则分开“可达性”“CPython 引用计数”“循环回收”和“操作系统看到的内存”。

前八章已经讲对象、参数绑定、闭包、迭代、数据模型和资源协议，本章用生命周期把它们接起来。第 10 章继续讨论并发中共享状态与自由线程构建；第 11 章扩展测试、调试和性能定位；第 12 章深入文件和序列化。**序列化**是把状态转成可保存或传输的表示，它与在当前进程里复制运行时对象不是同一任务。

## 29. 本章总结

1. 对象不只被变量名引用，容器、属性、函数、栈帧和工具都可能持有它。
2. `del` 移走指定绑定、位置或属性，不是强制销毁对象的命令。
3. 普通 CPython 用引用计数处理许多对象的生命周期，循环回收补充处理不可达环。
4. 有环不等于垃圾；仍有强引用路径时，手动回收也不能替业务丢弃对象。
5. 分代是减少检查成本的实现策略，具体行为要标明完整解释器版本。
6. 赋值、浅拷贝、深拷贝和选择性重建改变的对象层次不同。
7. 一次深拷贝通常通过备忘录保留内部共享并处理环，不保证所有节点都换身份。
8. 弱引用不拥有目标，但从它取出的对象又会被普通局部名字持有。
9. 终结器不能替代确定的资源管理，回调自身也可能意外保留目标。
10. 对象回收、Python 分配统计与进程内存指标是不同观察层次。

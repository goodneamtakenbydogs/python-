# 第 9 章复习卡：内存管理、复制与垃圾回收

学完后用本卡回忆；第一次学习回到完整讲义。

## 1. 引用、复制与内存测量的分析顺序

```text
引用：谁持有对象 → 从外部入口是否还能到达 → 哪条引用应该结束
复制：原图哪些节点共享 → 复制到哪层 → 结果内部是否仍共享
测量：哪种内存指标增长 → 分配发生在哪 → 谁长期持有
```

栈帧保存调用状态；对象可以由返回值、闭包或容器继续持有。“函数结束”不等于“它创建的对象全部销毁”。内存堆不是用于 Top K 的堆数据结构。

## 2. 易混概念对比

| 概念对 | 必须分开的内容 |
|---|---|
| 删除名字 / 销毁对象 | `del name` 移走绑定，其他持有者可能仍在 |
| 有环 / 垃圾 | 有环是引用形状，不可达才是待回收状态 |
| 引用计数 / 循环回收 | 前者处理许多普通对象，后者补充识别不可达环 |
| 关闭自动 GC / 关闭内存管理 | `gc.disable()` 不停止普通 CPython 引用计数，也不禁止手动收集 |
| 浅拷贝 / 深拷贝 | 前者通常建立新外层，后者按规则处理整个复制范围 |
| 对象释放 / 进程占用下降 | 分配器可能保留已释放空间供复用 |
| 弱引用 / 取得目标的局部名字 | 弱句柄不保活；取得的普通对象引用会保活 |

## 3. 复制关系速查

```text
original = [shared, shared]

alias = original
→ 原外层，原 shared

shallow = copy.copy(original)
→ 新外层，原 shared

deep = copy.deepcopy(original)
→ 新外层，新 shared'，结果两处仍共同引用 shared'
```

一次深拷贝的 `memo` 记录原对象与副本的对应，处理重复分支和环。分别发起多次 `deepcopy()` 默认不共享这一份备忘录，可能拆开原共享关系。

函数、类和不可变节点可能复用；“深”不表示每个 `id()` 都不同。文件、锁和连接要按资源接口创建和关闭，不是普通数据快照。

自定义 `__deepcopy__()` 需要先登记当前副本，再用同一个 `memo` 复制内部字段；普通需求优先用默认复制或按字段重建。

## 4. CPython 的引用计数与垃圾回收版本差异

- 普通 CPython 中，很多普通对象失去最后强引用后可以及时释放；这不是跨实现资源保证。
- `sys.getrefcount()` 通常计入调用带来的临时引用；看相对变化，不背绝对值。
- CPython 3.12 的不朽对象会干扰把计数当普通引用数的解释。
- 本章以 CPython 3.12.13 验证。3.12 的三代模型不能写成所有 Python 的永久规则；3.14 初始行为与 3.14.5 又有变化。
- 代按回收存活经历管理，不是按秒数到期。
- `gc.collect()` 返回值不是垃圾总字节数，精确数量也可能含现场其他对象。
- `gc.garbage` 不是所有垃圾的清单；`DEBUG_SAVEALL` 还会主动保留已发现对象。

## 5. 弱引用与终结

`weakref.ref(target)` 不独自延长目标生命周期；`reference()` 得到目标或 `None`。通常只调用一次并保存局部结果，再检查它，避免两次取得之间状态已变化。

`WeakValueDictionary` 对值弱引用，适合非拥有式索引，不等于固定容量或保证命中的缓存。普通列表、字典不能直接弱引用；类型支持和槽声明有条件。

绑定方法持有 `__self__`，回调表可能留住实例；需要非拥有式方法关系时了解 `WeakMethod`。

`__del__()` 时机、异常传播和运行结束环境都有限制，还可能复活对象。`finalize(target, target.close)` 可能通过绑定方法反过来保留目标。需要确定关闭时，使用 `with` 或明确的关闭责任。

## 6. 对象长期存活时的引用来源检查

- 模块全局、注册表、无限增长的列表。
- 可变默认值、闭包捕获。
- 缓存的实参与返回对象。
- 暂停生成器的形参与局部状态。
- 保存绑定方法的监听器列表。
- 异常历史、traceback 和栈帧。
- Notebook 输出历史、调试器及观察结果自身。

仍可达时，垃圾回收器不能替业务判断“不需要了”。解决的是生命周期与容量，未必是 GC 频率。

## 7. 内存工具

| 工具或指标 | 回答的问题 | 关键限制 |
|---|---|---|
| `getrefcount()` | 当前 CPython 引用计数观察 | 临时引用、不朽对象、调试状态 |
| `getsizeof()` | 对象自身浅层大小 | 不递归内部对象；重复引用不能重复累计 |
| `gc.get_referrers()` | 一些可见的引用者 | 调试不完整且有干扰，不长期保存结果 |
| `tracemalloc` | 追踪到的分配位置与前后变化 | 尽早启动；不覆盖所有原生或设备内存 |
| RSS / 工作集 | 操作系统口径下的进程内存 | 不直接等于 Python 存活对象大小 |

普通容器浅拷贝通常按条目数用线性时间与外层空间。深拷贝应按实际对象图规模与类型行为分析，不能因为调用只有一行就说 `O(1)`。

3. 环外仍有一个强引用时，`gc.collect()` 应不应该回收它？
4. 浅拷贝后，替换外层位置与修改内部列表分别影响谁？
5. 一次深拷贝为什么仍让两个结果位置共享同一副本？
6. 深拷贝遇到自引用为什么能结束？
7. 弱引用取出目标后，哪个新名字可能再次留住对象？
8. 绑定方法、闭包和缓存分别怎样持有对象？
9. 对象释放后任务管理器数字不降，能直接证明泄漏吗？
10. 为什么 `getsizeof()`、分配快照与引用者分析需要配合？

# 第 4 章参考回答：闭包、装饰器与函数式工具

本文件与 `第4章面试题.md` 的 40 道题逐题对应。参考回答用于学习组织方式，不要求逐字背诵。

## 一、基础概念题

### 第 1 题：函数是一等对象、高阶函数与回调

**简短结论：** 执行 `def` 会创建函数对象并绑定名字；函数对象能像普通数据一样被其他名字引用、存入容器、作为实参和返回值，因此函数是一等对象。接收或返回函数对象的函数称为高阶函数。

`double` 是当前指向函数对象的名字，`double(6)` 是调用表达式，其值是调用结果。不能把名字、对象和调用结果混成一件事。

回调是交给其他代码、由接收方在适当时机调用的函数。`sorted(values, key=some_function)` 中，`key` 是 `sorted()` 的形参名称，`sorted()` 是接收函数的高阶函数，`some_function` 是传入的函数对象并在本次排序中扮演回调。回调描述使用角色，不是另一种函数类型。

常见错误是把 `some_function()` 作为 `key`，从而提前调用并传入返回值。

### 第 2 题：嵌套函数、自由变量与闭包

**简短结论：** 嵌套只说明定义位置；闭包还要求函数使用并继续访问外层绑定。

```python
def make_multiplier(factor):
    def multiply(value):
        return value * factor
    return multiply
```

`value` 是 `multiply` 的局部形参，`factor` 是来自外层函数的自由变量。完全不使用外层局部名字的内层函数没有需要捕获的自由变量，不能只因缩进嵌套就把重点说成闭包。

### 第 3 题：闭包为什么能保留状态

**简短结论：** 返回函数会保留之后执行所需的外层绑定，因此外层栈帧结束不等于相关状态立即不可用。

“复制值”不准确。闭包保留访问绑定的能力，多个闭包可能共享同一绑定，绑定所指向的可变对象也可能继续变化。晚绑定正是反例：调用时可能读到后来更新的绑定。

具体单元格和生命周期细节不必在首轮展开，第 9 章会继续解释对象为何存活。

### 第 4 题：闭包中的 `nonlocal`

读取外层名字按 LEGB 完成，不需要 `nonlocal`。若内层函数要通过赋值改变已有外层绑定，需要 `nonlocal`；否则该名字通常会被判断为内层局部名字。

`values.append(x)` 修改外层名字指向的列表对象，没有重新绑定 `values`，通常不需要 `nonlocal`。应始终区分“修改对象”和“重新绑定名字”。

### 第 5 题：观察闭包

`function.__code__.co_freevars` 可观察自由变量名称，`function.__closure__` 可观察与闭包绑定相关的单元格；无闭包时后者通常为 `None`。

这些接口适合学习、检查和调试。直接依赖单元格排列或修改内部状态会把代码绑在实现细节上，难以维护。业务代码应通过清晰的形参、返回值或闭包公开操作访问状态。

### 第 6 题：晚绑定

**简短结论：** 自由变量通常在函数调用时读取当前绑定，而不是创建函数时复制当时的普通值。

循环创建的多个函数可能共享同一个循环变量绑定；循环结束后调用，全部看到最终值。普通 `def` 与 `lambda` 都遵守作用域和闭包规则，所以不是 `lambda` 独有缺陷。

### 第 7 题：修复晚绑定

形参默认值写法把当前循环对象在函数创建时计算为该函数形参的默认对象：

```text
lambda number=number: number
```

函数工厂则通过每次调用建立新的外层作用域和独立绑定。前者简短，后者在逻辑较复杂时更明确。两种方式都不是“改变闭包读取规则”，而是改变每个函数的数据来源。

### 第 8 题：装饰器的本质

**简短结论：** 装饰器接收被装饰对象并返回替代对象。

```text
@trace
def work():
    pass
```

核心展开为：

```text
work = trace(work)
```

`trace` 接收和返回函数，因此是高阶函数；返回的包装函数需要访问原函数时，原函数是其自由变量，因此包装函数形成闭包。但装饰器不被规定必须是普通函数或必须使用闭包。

### 第 9 题：装饰阶段与调用阶段

执行函数定义时先创建原函数，再立刻把它交给装饰器，装饰器返回值重新绑定原名字。包装函数体与原函数体通常到以后调用该名字时才执行。

所以“装饰器只在调用函数时执行”混淆了两个阶段：装饰器本身在定义阶段应用，包装器在调用阶段执行。

### 第 10 题：包装器的实参转发和返回值

`*args, **kwargs` 让包装器收集多种调用形式的实参，再展开给原函数，避免无意缩小原接口。原函数仍负责最终的实参与形参绑定。

如果包装器不返回原结果，装饰后的调用会得到 `None`，即使原函数已经算出结果。日志或计时装饰器通常应保持实参绑定、返回值和异常语义。

### 第 11 题：`functools.wraps`

没有 `wraps` 时，装饰后的 `__name__`、`__doc__`、注解等往往来自 `wrapper`。`wraps` 更新常见元数据，并设置 `__wrapped__` 指向原函数，方便检查、调试和部分框架解包。

它不会自动转发实参、返回结果、处理异常，也不能保证静态类型签名完全精确。常见误区是把 `wraps` 当作装饰器正确性的全部条件。

### 第 12 题：带配置的装饰器

三层分别对应：

```text
repeat(3)           → 接收配置，返回 decorator
decorator(function) → 接收原函数，返回 wrapper
wrapper(*args, **kwargs) → 接收实际调用并执行原函数
```

展开为：

```text
decorator = repeat(3)
work = decorator(work)
result = work()
```

配置值通常由外层闭包保存。判断时按阶段命名每一层，比背“三层模板”可靠。

### 第 13 题：多个装饰器

```text
@outer
@inner
def work():
    pass
```

定义阶段组合为 `work = outer(inner(work))`，最靠近函数的 `inner` 先包装。调用阶段通常先进入最外层 `outer` 包装，再进入 `inner`，执行原函数后反向退出。

“从下到上”只描述应用顺序，没有回答装饰器表达式求值或包装器调用顺序。

### 第 14 题：类装饰器

类定义完成后产生类对象。类装饰器接收该类对象，并返回原类或替代对象：

```text
Report = register(Report)
```

它与函数装饰器共享“接收对象、返回替代对象、重新绑定原名字”的模型。当前至少应能完成这一步展开；实例化、继承、描述符和元类留到第 6 章。

### 第 15 题：`lambda`

`lambda parameters: expression` 创建函数对象，表达式结果自动返回。它只能包含一个表达式，不适合多步骤逻辑、异常处理或需要清楚名称和文档的函数。

简短 `key` 和局部回调适合使用。`lambda` 与 `def` 函数一样遵守 LEGB、实参与形参绑定和晚绑定。

### 第 16 题：`map()`、`filter()` 与推导式

`map` 对元素应用函数，`filter` 根据谓词真值保留元素。Python 3 中它们按需产生结果，因此示例常把结果对象传给 `list()` 消费并建立列表。

简单转换和筛选时推导式通常直观；已有命名函数、需要组合或按需处理时，`map`/`filter` 也可能合适。不存在脱离场景的“永远更好”。完整迭代机制在第 5 章。

### 第 17 题：`reduce()`

`reduce` 维护累计值，把累计值和下一个元素交给二元函数，直至得到一个结果。初始值定义第一次累计输入，也能为输入为空时提供结果。

没有初始值的空输入会抛出 `TypeError`。普通求和使用 `sum()` 更直接；`reduce` 适合没有更清楚内置函数的自定义合并。

### 第 18 题：`partial()`

`partial` 预先固定调用原函数时的部分位置实参或关键字实参，返回新可调用对象；创建时不会执行原函数，调用返回对象时才合并实参并执行。

这个返回对象支持调用，但不一定是由 `def` 创建的普通函数对象。预设关键字可以在调用时被同名关键字覆盖，最终仍按原函数签名完成绑定。

闭包也能保存配置并返回函数，但可以加入任意逻辑；`partial` 更适合直接复用已有函数并固定部分实参。

### 第 19 题：`lru_cache()`

缓存用调用实参构成键，保存对应返回对象。LRU 是最近最少使用，容量满时优先淘汰最久未使用条目。

键需要哈希查找，因此参与缓存键的实参必须可哈希。`maxsize=None` 不按条目数淘汰，长期服务中可能持续占用内存。还应说明缓存保存的是返回对象，不只是复制出来的值。

LRU 只定义容量满时的淘汰顺序，`lru_cache` 不提供按时间自动过期。时间过期或数据变化后的主动失效需要额外设计。

### 第 20 题：哪些函数不适合直接缓存

依赖外部状态的函数可能在调用实参不变时结果已经变化，缓存会返回旧数据。副作用函数命中缓存后跳过函数体，消息发送、写入或扣款也会被跳过。

返回可变对象时，相同键可能得到同一个对象，一个调用者的修改污染后续调用。需要明确过期策略、容量、清理方式和结果是否应复制。

## 二、代码理解题

### 第 21 题：闭包基本输出

输出：

```text
16
64
```

`power` 的局部形参是 `base`，自由变量是每次外层调用各自的 `exponent`。`square` 和 `cube` 是不同函数对象，分别保留 `2` 和 `3` 的绑定。

### 第 22 题：同次外层调用共享状态

输出：

```text
['A']
['A', 'B']
```

`add` 和 `read` 来自同一次 `make_box()` 调用，共享外层 `values` 绑定和列表对象。`read()` 返回浅复制快照，但内部共享状态本身仍由 `add` 更新。

### 第 23 题：`nonlocal` 与可变对象

输出：

```text
1 2
['A'] ['A', 'B']
```

`count += 1` 需要读取并重新绑定外层整数名字，因此声明 `nonlocal count`。`values.append()` 修改外层名字已经指向的列表，不重新绑定 `values`，所以不需要 `nonlocal`。

### 第 24 题：循环晚绑定

输出：

```text
[2, 2, 2]
```

三个函数共享同一个外层循环变量单元格，调用发生在循环结束之后，此时绑定为 `2`。不是每次 `append` 自动复制一个数字。

### 第 25 题：形参默认值修复晚绑定

输出：

```text
[0, 1, 2]
```

等号右侧 `number` 在每轮创建函数时求值，保存为该函数的默认对象；等号左侧 `number` 是每个函数自己的形参，调用时从默认值获得对象。函数不再读取共享循环自由变量。

### 第 26 题：装饰发生在什么时候

输出：

```text
['decorate']
done
['decorate', 'before', 'work', 'after']
```

函数定义结束时 `trace` 已经执行并记录 `decorate`。调用 `work()` 实际进入 `wrapper`，依次记录前置、原函数和后置事件，然后返回 `done`。

### 第 27 题：包装器遗漏返回值

没有正常输出。`wrapper` 调用了原函数但没有 `return`，所以 `add(2, 3)` 得到 `None`；先计算 `None * 10` 时抛出 `TypeError`，外层 `print` 尚未真正执行。

修复是 `return function(*args, **kwargs)`，而不是额外打印结果。

### 第 28 题：`wraps` 与元数据

输出：

```text
wrapper
second
True
```

第一个名字绑定到普通包装函数，元数据未保留。`@wraps(function)` 让第二个包装函数呈现原函数的常用元数据，并通过 `__wrapped__` 指向原函数。

### 第 29 题：带配置的装饰器

输出顺序：

```text
factory A
decorate A
call A
done
```

`configured("A")` 在装饰器表达式求值阶段执行；返回的 `decorator` 随后接收原函数；最后 `print(work())` 才进入 `wrapper` 并显示返回值。

### 第 30 题：两个装饰器的调用顺序

输出：

```text
enter outer
enter inner
work
leave inner
leave outer
```

定义结果是 `work = layer("outer")(layer("inner")(work))`。调用先进入最外层包装，返回时反向退出。

### 第 31 题：`map()` 迭代器的耗尽

输出：

```text
[2, 4, 6]
[]
```

第一次 `list(mapped)` 遍历并消费全部 `map` 对象。它保存的是向前推进的按需迭代状态，不会在第二次自动回到开头。完整迭代器协议在第 5 章学习。

### 第 32 题：缓存命中与可变结果

输出：

```text
[1]
True
['changed']
```

函数体只在第一次未命中时执行一次。第二次使用相同实参时直接返回缓存中的同一个列表对象，因此 `first is second` 为真，并能看到之前的修改。

常见误区是认为缓存会深拷贝结果。解决方式取决于接口，可考虑返回不可变对象、复制结果或不缓存该函数。

## 三、找错与场景题

### 第 33 题：日志装饰器泄露敏感信息

完整打印实参可能把密码、令牌、证件号写入终端、日志平台、备份和监控系统，扩大泄露范围。

应采用允许字段列表、敏感字段脱敏、限制长度和结构化日志；凭证通常完全不记录。调试需求不能自动获得记录所有输入的权限，还要考虑日志访问控制和保存期限。

### 第 34 题：计时装饰器遇到异常

原函数抛出异常后，普通顺序控制不会继续执行后面的结束计时代码，因此缺少记录。当前至少应知道异常路径与正常返回路径不同。

完整修复通常使用第 7 章的 `try`/`finally` 保证结束记录，并决定是否捕获、记录后重新抛出。不能为了计时吞掉原异常。

### 第 35 题：重试非幂等操作

查询通常不改变业务状态，短暂网络失败后重试可能安全。扣款等操作可能已经成功但响应丢失，再次执行会重复产生效果。

幂等最低限度是同一操作重复执行，最终业务效果与执行一次一致。可通过幂等键、事务状态或去重设计实现。装饰器不能仅凭捕获异常就判断业务操作可安全重试。

### 第 36 题：错误缓存设计

- 正确性：数据库变化后缓存仍返回旧用户信息。
- 内存：无大小限制且无清理，键和结果可能持续累积。
- 共享修改：相同键返回同一字典，一个调用者修改后污染其他调用者。

应明确过期、失效、容量、更新一致性和返回值可变性。`lru_cache` 更适合进程内、输入决定结果的计算缓存，不是通用数据库缓存方案。

## 四、连续追问题

### 第 37 题：闭包连续追问

1. 嵌套函数只是定义位置；闭包还需要外层自由变量绑定。
2. 更准确说保存访问绑定的能力，不是机械复制值。
3. 同一次外层调用返回的函数可共享绑定；不同调用通常建立独立绑定。
4. `nonlocal` 让内层赋值针对已有外层函数名字。
5. 只要闭包仍被引用，它需要的外层对象也可能继续存活。
6. 状态和操作很多时，类能提供清楚属性、方法、表示和扩展边界。

回答到这里足以覆盖本章；单元格内存布局和垃圾回收留到第 9 章。

### 第 38 题：装饰器设计连续追问

1. 普通装饰器展开为 `f = decorator(f)`；带配置的装饰器展开为 `f = factory(config)(f)`。
2. 包装器通常收集并转发实参，返回原结果，不应意外改变异常语义。
3. `wraps` 保留常用元数据和 `__wrapped__`。
4. 是否转换异常取决于公开接口；默认应避免静默吞掉。
5. 多层包装增加栈深度和追踪难度，也可能让静态签名变宽。
6. 横切行为稳定且多个函数共用时适合装饰；只有一个函数、逻辑强依赖业务主体或包装层过多时，显式调用可能更清楚。

### 第 39 题：函数式工具选型

- 转换和筛选：简单时推导式通常清楚；已有命名函数或按需流水时考虑 `map`/`filter`。
- 累计：优先检查 `sum`、`min`、`max` 等专用工具，再考虑 `reduce`。
- 预先固定实参：已有函数可用 `partial`，需要额外逻辑可用闭包或普通函数。
- 重复纯计算：调用实参可哈希且结果稳定时考虑 `lru_cache`。

选择还受惰性、内存、可读性、调试、副作用和团队习惯影响，代码最短不是独立目标。

### 第 40 题：综合定义与调用顺序

`definition_events` 为：

```python
[
    ("factory", "outer"),
    ("factory", "inner"),
    ("decorate", "inner"),
    ("decorate", "outer"),
]
```

装饰器表达式从上到下求值，所以先执行两个工厂；得到装饰器后从下到上应用，因此先 `inner` 后 `outer`。

`result` 为 `12`。`factor` 是模块全局名字，原函数在实际调用时读取当前绑定 `3`，不是定义时复制 `2`。

`call_events` 为：

```python
[
    ("enter", "outer"),
    ("enter", "inner"),
    ("leave", "inner"),
    ("leave", "outer"),
]
```

调用从最外层包装进入，原函数返回后按相反方向退出。这里工厂形参 `name` 的绑定由各自闭包保存，而全局 `factor` 在调用时查找，两种名字来源必须分开分析。
